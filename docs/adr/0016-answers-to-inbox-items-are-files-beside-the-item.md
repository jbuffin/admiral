# 16. Answers to inbox items are files beside the item

Status: accepted

## Context

Ships ask the engineer things: a question, a pending review, finding cards ([#112](https://github.com/jbuffin/admiral/issues/112), [#116](https://github.com/jbuffin/admiral/issues/116)). A ship writes each as an item file, `$ADMIRAL_HOME/inbox/<session>/<id>.json`, and a skill that resumes later has to find the engineer's answer. [ADR 0007](0007-needs-you-comes-from-harness-hooks.md) keeps ships and Admiral apart: ships write files and Admiral watches them.

## Decision

**The answer is a file next to the item, `<id>.answer.json`, and Admiral never edits the item.** An item with an answer file is answered, whoever wrote the file, and leaves the inbox. So does an item whose ship directory is deleted (ADR 0015's cleanup, which keeps the directory while an item is unanswered, below).

- **Written through a temp file and a link** in the ship's directory (`.<id>.answer.json.tmp-<random>`, which no reader takes for an item or an answer). Admiral holds one lock, re-reads the item and checks that no answer exists, then publishes the file with `os.Root.Link` and removes the temp file. A link fails when the answer exists, so an answer written by a ship, by hand or by another Admiral is never replaced, and the second writer gets a 409. A ship directory that vanishes mid-answer is a 404, never a 500.
- **Items are read defensively.** Ships are untrusted. Admiral reads through an `os.Root` on `$ADMIRAL_HOME`, never follows a link, opens with `O_NONBLOCK`, reads at most 1 MiB, and skips a file whose name is not `<id>.json` with `<id>` matching `^[A-Za-z0-9][A-Za-z0-9_-]{0,63}$`, whose `id` differs from its name, or that is not valid against #112's item format. A skipped file never hides another item. A ship that has ended but still has its files still shows its items.
- **Three answer shapes, one file.** Every file has `version` (1), `id`, `kind` and `answered` (RFC 3339, UTC).
  - `question`: `answers` maps each question id to `{"choice": "<label>" or ["<label>", ...], "other": "free text"}`, and an optional `note`. Every question needs an answer. A `choice` is an option label, a list only on a `multi` question, and `other` can stand alone.
  - `review`: `action` is `submitted`, `discarded` or `gone`. `event` (`COMMENT`, `APPROVE` or `REQUEST_CHANGES`) is there only for `submitted`. `gone` means GitHub no longer had a pending review to act on.
  - `findings`: `cards` maps each card id to `{"decision": "approved"|"edited"|"rejected", "proposal": {"kind", "content"}}`; `proposal` is present only for `edited`. Send only writes this file; the skill posts to GitHub.
  - Admiral writes all three with the same code. It refuses a findings answer that misses a card, names an unknown one, names one twice, gives a decision that is not one of the three, gives a proposal to a card that is not `edited`, or gives an `edited` card a proposal whose `kind` is not `diff` or `reply` or whose content is empty.
- **The outcome log gets a record per answer.** This extends [ADR 0015](0015-outcomes-are-an-append-only-history-beside-tmux.md)'s events, each with `item` and `kind`: `answered` for a question; `review_submitted` with `review_event` and `edited` (true when the engineer opened Edit on GitHub first; a line's own `event` is the record name); `review_discarded`, with `external: true` for `gone` and `invalid_target: true` for a review that had no valid target to delete; and `card_approved`, `card_edited` or `card_rejected` with the `card` id, one per card. A review or findings answer writes no `answered`.
- **Submit and Discard run `gh` as the engineer.** Admiral is not the engineer's hand until the engineer presses the button, so it never acts on a review without that request. It reads the pending review (`GET /repos/{owner}/{repo}/pulls/{n}/reviews/{id}`) and submits it with its current body (`POST .../events`), because the engineer may have edited the body on GitHub; an empty body becomes the item's `summary`. Discard is `DELETE` of the review. The owner, repo and number come only from the item's `pr_url`, which must be `https://<host>/<owner>/<repo>/pull/<n>` and nothing more (a GitHub Enterprise host is allowed), and `review_id` must be a positive integer. Item text reaches `gh` only inside the JSON on stdin, never as an argument. `gh` is found on Admiral's `PATH`, always gets `--hostname <host>` (so a `GH_HOST` in the environment cannot redirect the call), runs with a 30 s timeout and is never retried.
- **`gh` runs in the ship's dock environment.** The env is Admiral's own overlaid with the env of the dock the ship was launched from (`fleets[].harnesses.<name>.env`), so the engineer's token for that fleet is the one used. Admiral reads the current config when the engineer acts, not when the ship launched, so an edited token takes effect at once. It never reads or logs the token. A ship whose dock is unknown runs `gh` in Admiral's own environment, and an error says so.
- **A failed `gh` changes nothing.** The engineer gets the error with gh's message (cut at 4 KiB), no answer is written, nothing is recorded, and the item stays. The one exception is a review that is no longer there: a 404 on a pull request that is still there, a 422 whose `message` or `errors` name `pending` (GitHub's `documentation_url` does not count), or, on Submit, a review whose `state` is not `PENDING`, is the answer `{"action":"gone"}` with `review_discarded` marked `external: true`, and the item leaves. GitHub answers 404 for a repository the token cannot see as well, so on a 404 Admiral also reads the pull request (`GET /repos/{owner}/{repo}/pulls/{n}`, same host and environment); if that fails too, it is an access error with gh's message and the environment note, and nothing is answered or recorded. Any other 422, such as "Can not approve your own pull request", is an error. Every item has a way out from the UI: Discard on a review whose `pr_url` or `review_id` is invalid writes `{"action":"discarded"}` without running `gh` (the response also says `"invalid_target": true`, so the UI can say that nothing changed on GitHub), and a findings item with no cards takes an empty list.
- **A ship that sailed off keeps its inbox while an item is unanswered.** This amends [ADR 0015](0015-outcomes-are-an-append-only-history-beside-tmux.md)'s cleanup, which removed an exit-0 ship's report and inbox once `ended` was written. Now Admiral keeps both while the inbox holds an item with no answer file, so the engineer can still answer it. The answer that clears the last item removes the files with it, so a ship that has already sailed off never reads that answer; a skill that resumes a live ship does. Dismiss still removes everything. Before it kills the ship, Admiral copies the session's `name`, `fleet` (key, name and color) and `harness` into `$ADMIRAL_HOME/state.json` (`kept_inboxes`), never into `inbox/<session>/`, which the ship writes. The record serves the item's ship name and harness, gives `gh` the ship's dock, and keeps `launcher.pickName` from drawing the name, since a launch clears the inbox of the name it takes. When the last answer is written, Admiral removes the ship's report and inbox and drops the record. At start-up it does so for records whose items were all answered meanwhile. A directory with no record and no session is left alone, as ADR 0015 accepts.
- **Remove from inbox.** A kept review can fail forever (a deleted repository, lost access, a revoked token, a host that is gone), and neither Submit nor Discard then clears it. `POST .../discard` with `{"forget": true}` writes `{"action":"discarded"}` without running `gh`, records `review_discarded` with `unreachable: true`, and answers 200 with `"forgotten": true`: nothing changed on GitHub. It is allowed on any review item. Submit stays strict.
- **A report can resume its ship through an order.** When every item id a ship's report lists in `inbox` has an item file and an answer file, Admiral adds the report's `resume` text as an order to the panel `autopilot.resume_source` names (`{"source", "panel"}`, checked for shape at parse time and for existence when the order is added), using the same add the orders route uses. It waits for the report's ids, while the kept-inbox release waits for every unanswered item file in the directory, so an item the report does not list holds the files after the order is added, and an id listed with no item file never adds one while the files still go. The text is copied into `state.json` (`resume_orders`, keyed by session and a hash of the report, so a reused ship name starts clean) before the report can be deleted, by the answer, the scan, the start-up sweep and the `ended` cleanup alike, and it stays there until an add succeeds, so a source that is restarting or a target that does not exist yet is retried, and a restart does not lose it. A text the source refuses is logged and dropped. The add never runs under the answer lock. Success records `resumed` against the ship, and a report adds at most one order. Dismissing an anchored ship before its items are answered adds none. With no `resume_source`, nothing is added and the log says so once. The order runs like any other: under autopilot if the panel is on, and only if its text names a repository.
- **Admiral watches the directories** with fsnotify (`$ADMIRAL_HOME`, `inbox/` and each ship's directory), so a new item, an answer or a removed directory changes what is served within about a second.
- **ADR 0007 still holds.** Items aren't ship state, and skills write them, not hooks. No hook calls the server.

## Considered options

- **An answer file beside the item** (chosen). The skill that resumes already reads that directory, and a crash leaves no half state.
- **Edit the item in place.** It races the ship that wrote it and loses the original question.
- **Keep answers in the outcome log or `state.json`.** The log is never read back (ADR 0015), and a skill would need Admiral's server to read its answer. [ADR 0012](0012-ships-live-in-tmux-and-the-rest-in-admiral-home.md) keeps a live ship in tmux, not in a second table.

## Consequences

- A skill reads `<id>.answer.json` to resume, and a missing file means unanswered.
- An answer file written by hand hides its item, and a wrong one is not checked.
- The answer is the record. If the `answered` outcome write fails, the item is still answered and the log misses one line.
- Two Admirals on one home that answer the same item at once write one answer: the link fails for the second, which gets a 409. Both could still run `gh` first, and the second then finds the review gone.
- Submitting runs `gh` before the answer is written. If the write then fails, the review is posted on GitHub and the item stays, and a second Submit finds the review gone.
- A kept record is lost if `state.json` is lost, and a launch can then draw the name and clear the inbox. The record is written at once, not on the state's usual delay, to make that rare.
