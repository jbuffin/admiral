# 20. AdmiralBot reaches Admiral only through the admiral CLI

Status: accepted

## Context

[ADR 0018](0018-the-chat-is-one-long-lived-session.md) says AdmiralBot reads ships, outcomes and the inbox, that its only write is adding an order, and that it asks with a question card that never becomes an inbox item. [ADR 0019](0019-the-chat-is-carried-by-its-transcript-and-tmux.md) gives it a Claude Code session, a transcript and a paste. This ADR says how that session talks to Admiral, and what stops it from doing more ([#119](https://github.com/jbuffin/admiral/issues/119)).

The chat's Claude is a model that runs shell commands from a phone. Nobody watches each one, so a prompt would only stall the chat.

## Decision

**AdmiralBot runs `admiral` commands, and nothing else.** The commands are `admiral ships`, `admiral outcomes`, `admiral inbox`, `admiral orders`, `admiral orders add` and `admiral chat ask`. The last three of those are new (see `docs/cli.md`). The three that need the server find it as `admiral ships` does: `127.0.0.1:<port>`, and the server's `home` must match `$ADMIRAL_HOME`. The port comes from `ADMIRAL_PORT`, which Admiral sets in the chat's environment next to `ADMIRAL_HOME`. Loopback needs no token (`internal/auth`).

- **The skill.** The chat loads a Claude Code project skill, `admiralbot`. Admiral writes `$ADMIRAL_HOME/chat/.claude/skills/admiralbot/SKILL.md` every time it starts the chat session, before the session's process starts, from a file embedded in the binary. It writes through an `os.Root` on `$ADMIRAL_HOME`, a temp file and a rename, never following a link, so a link planted at that path is replaced and never followed. The chat's command line also carries `--append-system-prompt` with one short paragraph, its own argv element, that says who AdmiralBot is and to use the skill. This is a different sense of "skill" from the glossary's **Skill**, which is what a ship starts on.
- **The fence.** The chat's Claude runs these commands without a prompt and nothing else.
  - `--permission-mode dontAsk` denies every call that would prompt and still runs `permissions.allow` rules.
  - `--setting-sources project` leaves out the engineer's user and local settings, so their allow rules, hooks and mods don't apply. The `--settings` bundle is its own tier and still loads, and project skills come from the `project` source. The login is not in settings (it is in `~/.claude.json` and the keychain), so it is untouched.
  - `--tools Bash,Skill,Read` leaves out `Agent`, `SendMessage`, `RemoteTrigger`, `CronCreate`, `PushNotification`, `Edit`, `Write` and the rest, which need no permission at all or would write. `Read` stays so Claude can read a command's output.
  - The chat bundle (`chat-claude-settings.json`) allows exactly `Bash(admiral ships *)`, `Bash(admiral outcomes *)`, `Bash(admiral inbox *)`, `Bash(admiral orders *)`, `Bash(admiral chat ask *)` and `Skill(admiralbot)`. It denies `Edit`, `Write` and `NotebookEdit` as a second fence, and sets `permissions.blockReadsOutsideWorkingDirectories`. Deny beats allow in every scope.
  - These are the chat's own args, placed after the dock's args and before `--settings`, each flag and value its own argv element. Admiral refuses to start the chat when the chat dock's `args` hold a flag that skips or changes permissions (`--dangerously-skip-permissions`, `--allow-dangerously-skip-permissions`, `--permission-mode`, `--setting-sources`, `--tools`): `POST /api/chat/start` answers 409 and the session's `error` names the flag. Ships' bundles and command lines don't change.
- **What the fence can't stop.** Two things. A file written by hand into `chat/questions/` is read as a chat question, defensively like any other, and shows in the chat; the same is true of any process of the engineer's. And Claude Code runs read-only shell commands (`cat`, `grep` and the like) in every mode, so the chat can read anything in its directory with them; `blockReadsOutsideWorkingDirectories` confines the `Read` tool, not those commands. A `Bash(admiral orders *)` rule also matches any text after `orders`, so the commands are safe because of what the CLI does with its arguments, not because of the rule.
- **Text goes on stdin.** Order text and question JSON go on stdin in one exact form (`admiral orders add --source <key> --panel <id> <<'EOF'` … `EOF`, and the same for `admiral chat ask`), never as `-- <text>`: a command over 10,000 characters is refused under `dontAsk`. The allow rules match a command by its text, so the skill tells the model to run plain `admiral …` with no path, no `VAR=…` prefix and no `cd`.
- **Chat questions are files in their own directory.** `admiral chat ask` writes `$ADMIRAL_HOME/chat/questions/<id>.json` through a temp file and a rename, then waits for `<id>.answer.json` in the same directory, in ADR 0016's answer shape. The server reads the directory as ADR 0016 reads a ship's inbox directory (an `os.Root`, no links, `O_NONBLOCK`, at most 1 MiB, the name and id rules, #112's validation with kind `question` only) and serves the questions with the chat. The answer route writes the answer file with the code the inbox uses. `chat ask` needs no server, so a question can be asked while Admiral restarts. It returns within 100 seconds by default so it ends before the Bash tool's 2-minute default (a foreground Bash command that reaches its timeout is moved to the background, not killed); it then exits 3 and `admiral chat ask --wait <id>` resumes. New chat removes every question file, so a waiting command exits 4.
- **A chat started before an Admiral restart on another port keeps the old `ADMIRAL_PORT`.** Its commands then fail cleanly on the home check (another Admiral, or none, answers on that port) until New chat starts a fresh session. The chat survives an Admiral restart (ADR 0012), so this is possible.
- **`--append-system-prompt` is snapshotted once per conversation.** Claude Code records the prompt when the conversation's first request is made. That is harmless: Admiral never resumes (ADR 0012, 0019), and `/clear` starts a new conversation that takes the prompt of the running process, which is the one it started with.
- **ADR 0007 still holds.** No hook calls the server. The CLI is run by the model, not by a hook; the hooks only set pane options.
- **ADR 0016 still holds.** Chat questions reuse its answer shape and its write path (a temp file and `os.Root.Link`, one lock, a re-read before the write), and never its `inbox/` directory, its outcome records or its resume orders. A chat question never appears in `GET /api/inbox` or the `inbox` message, because the chat is not a ship.

## Considered options

- **The `admiral` CLI with allow rules** (chosen). Every call is a command a person can run too, Claude Code enforces the list, and the ship-facing commands (`ships`, `outcomes`) already exist.
- **An MCP server.** It could carry a typed question call, but it is a second process to start and keep in step with the chat's config, and a `--setting-sources project` chat would need `--mcp-config` as well.
- **`curl` against the API from the skill.** It needs a rule for `curl`, which allows any URL, and the model would have to build JSON in shell quoting. A fixed command with stdin is narrower.
- **Questions as inbox items under a pseudo-ship.** It reuses the inbox's code, but ADR 0018 says they stay in the chat, the inbox would need a ship that is not one (ADR 0019 refuses `_chat` as a ship), and a restart of the chat would leave them as inbox items with nobody waiting.
- **Enforcing "only write" by instruction alone.** The skill says it, but a prompt doesn't stop a model, and `dontAsk` with allow rules does.

## Consequences

- **Unverified:** that `--setting-sources project --tools Bash,Skill,Read --permission-mode dontAsk`, with the bundle's rules, lets the skill load and `admiral orders add <<'EOF'` run without a prompt, and refuses everything else; that `Skill(admiralbot)` is what the Skill tool needs under `dontAsk` (the docs disagree on whether it prompts); and that the heredoc form matches the allow rules. A real session settles them. Tests use a fake harness, which checks the argv, not Claude Code's behaviour.
- If Claude Code renames a flag or a tool, the chat fails to start or loses the fence's edges. The deny rules and `blockReadsOutsideWorkingDirectories` stay as the second fence.
- The skill text is part of the binary. Changing how AdmiralBot behaves means a new release, and an old chat session keeps the text it started with.
