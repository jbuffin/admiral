# 33. Pushes are Web Push from the Mac, with no hosted relay

Status: accepted, amended by [ADR 0042](0042-a-ships-result-comes-back-as-a-card-and-a-report-turn.md) (AdmiralBot's report on a finished ship pushes, outside the attention count); amended 2026-11-27 (a paired client can follow push events on `/ws/v1`)

## Context

Today Admiral only chimes in an open browser. Away from the Mac, the engineer has to know when a ship or AdmiralBot is waiting on them. The research in [#217](https://github.com/jbuffin/admiral/issues/217) ([note](../research/windows-and-native-apps.md)) weighed Web Push from an installed web app against native push through an APNs relay, which would have to be hosted. [ADR 0031](0031-remote-access-goes-through-tailscale-serve.md) gives HTTPS through the tailnet URL, and [ADR 0032](0032-devices-pair-for-their-own-tokens-and-the-api-is-versioned.md) gives each device its own token. [#236](https://github.com/jbuffin/admiral/issues/236) decided how pushes travel and what pushes.

## Decision

**Pushes travel as standard Web Push (VAPID) from the Mac to each subscribed device, with no hosted relay. Admiral pushes only what the engineer must act on, skips the push while the engineer is watching, and shows an attention count everywhere else.**

- **Transport.** Web Push only; the APNs relay goes out with the native apps, so nothing is hosted outside the Mac and [ADR 0001](0001-local-web-app-served-from-the-mac.md) holds. The payload is encrypted end to end (RFC 8291) and carries the fleet, the ship or source name and one line of text, never code, diffs or secrets, since it may show on a lock screen. One VAPID key pair serves all of Admiral, made on first use and kept in `$ADMIRAL_HOME`.
- **Subscriptions.** A subscription is stored with its paired device, and its registration endpoint lives under `/api/v1` with bearer or cookie auth. A 404 or 410 from the push service drops it, and that device shows notifications off. Revoking or expiring a device drops its subscriptions.
- **What pushes.** AdmiralBot's waiting chat question, a ship's question or permission prompt, approvals (a T3 wake proposal, approval before code pushes), a feedback round's findings item, **Ready to merge**, an anchored ship that ended with an error, and a routine with **Notify me** on, and AdmiralBot's reply to a ship's report turn ([ADR 0042](0042-a-ships-result-comes-back-as-a-card-and-a-report-turn.md)), which pushes though nothing waits on the engineer and is not an Inbox item, so the attention count never moves. Finished-turn stops, FYI items and quarantined triggers go to the Inbox and the attention count only.
- **Not while watching.** If any signed-in window is visible and was used in the last ~2 minutes, that window gets the chime and a toast, and no device gets a push. Otherwise every subscribed device gets it. A push is tagged with its item, so an update replaces it instead of stacking. Answering an item sends no push to clear it, because iOS revokes subscriptions that get pushes it doesn't show; the app closes stale notifications when it opens.
- **Controls.** Notifications are turned on per device, on that device, which subscribes its service worker. Each fleet has a **Notify** switch, on by default. There are no quiet hours; the OS's Focus modes cover that. A loopback browser on the Mac can turn notifications on without pairing; it registers as a device called This Mac, shows in the device list and can be revoked. A device on plain HTTP can't subscribe: its switch is disabled, says it needs Tailscale mode and links to Remote access. An iPhone or iPad not running Admiral from the Home Screen sees "Add to Home Screen first".
- **Tapping a push.** An Inbox item, AdmiralBot's waiting question included, opens the Inbox with Peek on that item, or the Inbox alone if the item is already answered. A Notify-me routine opens its result: AdmiralBot's chat at that message, or the launched ship. There are no action buttons on any platform, since iOS Web Push has none.
- **Attention count.** What waits on the engineer across every fleet: needs-you stops plus items that aren't FYI. It shows as "(3) Admiral" in the tab title, as a dot on the favicon, and as the app icon badge in an installed app (Badging API). It drops only when an item is answered or removed; viewing an item doesn't change it.
- **Chime and toasts.** The chime and its mute stay. Only the visible window plays it, and only for the events that push. Toasts follow the same events, at most two on screen, a third replacing the oldest; tapping one opens Peek.
- **Service worker.** It handles `push`, `notificationclick`, the app icon badge and closing stale notifications. It also caches the app shell for an installed app and nothing else, no API data ([#243](https://github.com/jbuffin/admiral/issues/243)).

## Considered options

- **Web Push from the Mac** (chosen). Nothing hosted, and the payload is encrypted to the device. On iOS it needs the Home Screen install, and it has no action buttons.
- **Native push through an APNs relay.** Needs native apps and a hosted relay, against [ADR 0001](0001-local-web-app-served-from-the-mac.md). Out of scope with the native apps.

## Consequences

- Devices subscribe against Admiral's VAPID key, so the key can't change without every device subscribing again.
- A device on plain HTTP, with no Tailscale mode, never gets pushes. It still gets the tab-title badge, the chime and toasts.

Amended 2026-11-12 (Web Push build, [#278](https://github.com/jbuffin/admiral/issues/278)): the app icon badge and closing stale notifications run in the page, not the worker. The page sets the badge from the shared Inbox queue and closes each shown notification whose entry is gone when it opens and when its lists change, so the worker only handles `push` and `notificationclick` (and the shell cache).

Amended 2026-11-24: a ship or crew boat that has not started (`needs_you` reason `not_started`) pushes as a question, but only once it is 30 seconds past launch; the Inbox shows it at 10 seconds. The in-app alert waits the same 30 seconds.

Amended 2026-11-27 ([Push events on /ws/v1](https://github.com/jbuffin/admiral/issues/946)): a paired client can follow pushes on `/ws/v1` and forward them to its own push service, so a native app gets Admiral's decision instead of copying its rules. Admiral learns nothing about the other channel.

- **Following.** A socket sends `{"type":"push_follow","after":<seq or null>,"boot":"<id>"}`, where `boot` is the boot id the follower last saw. Only a device paired with a bearer token may follow; a cookie-only window and an unpaired loopback browser may not, and a socket that may not follow gets `{"type":"push_refused","reason":"bearer_required"}` and stays open. Following adds no Web Push target. The fleet's **Notify** switch applies to it as it does to Web Push. The device is recorded as forwarding pushes on its first follow, and the Devices list shows it as "Notifications on · forwarded" with when it last connected. Revoking the device stops it; there is no separate switch on the Mac.
- **The push event.** `{"type":"push","boot":"<id>","seq":N,"kind":"…","attention":N,"choices":[{"id","label"}], …}` with the Web Push payload's fields (fleet, name, line, tag, target and ids), built from the same payload so the two can't drift. It goes out only for a push, after the not-while-watching rule, never for an alert or a fleet with Notify off. `kind` is the event's kind (`ship_question`, `wake_proposal`, `report_reply` and the rest). `choices` are the need card's buttons as the card shows them ([ADR 0051](0051-what-a-ship-needs-posts-a-need-card-in-its-fleets-chat.md)), cleaned like the name, and empty when the need has no fixed choices. The event names the card, and a choice is answered through the card's own answer route with its id, so the card's binding check and first answer wins hold. Admiral sends every choice; the client decides how many become buttons.
- **The clearing event.** `{"type":"push_clear","boot":"<id>","seq":N,"tag":"…","attention":N}` when an Inbox item or needs-you stop that pushed is answered, removed or moved on. Push-only events (report and digest replies, Notify-me routines) wait on nothing and never clear. Web Push still sends no clear.
- **The attention count** is computed by the server, as defined above, and served in the `/ws/v1` snapshot; the web app reads it instead of working it out. It rides on every `push` and `push_clear`, and `{"type":"attention","count":N}` goes to followers whenever it changes with no push, such as a finished-turn stop.
- **Catching up.** Admiral keeps the last day of `push` and `push_clear` events in memory, at most 500, numbered by `seq`, which starts at 1 each boot, and stamped with a boot id. A follower that comes back with `after` gets what it missed in order, then the current count. After a restart of Admiral, an `after` with an unknown or missing `boot`, or a gap older than the ring, it gets `push_reset`, which carries the new `boot`, and the count instead, since opening the app shows the Inbox. Nothing of the ring is written to disk.
- **Watching.** A native app in the foreground sends the existing `presence` message on its own socket, as a window does, so it counts as watching and gets `alert` messages. A socket that only follows never sends presence.
- **When forwarding stops** ([How Admiral's Devices list shows a forwarding device that stopped following](https://github.com/jbuffin/admiral/issues/950)). Admiral records `lastFollowed` in the devices file when a device's last follower socket closes. The hourly `lastSeen` can't show a gap of minutes, and it counts any request. Once a device that follows has had no follower socket open for 5 minutes, counted from the later of that close and Admiral's start, the Devices list shows "Forwarding stopped · last followed {when}" in the warning tone in place of "forwarded". `admiral devices` gets a last column, `FORWARDING`, after `ID` so scripts that read by position keep working: empty, `on`, or `stopped <RFC 3339>`. `--json` carries `forwarding` (`"on"`, `"stopped"` or `null`) and `lastFollowed`. A deliberate stop sends `{"type":"push_unfollow"}`, which clears the record so the row is a plain device again. Nothing else in Admiral shows it: the engineer who would need to know is away, maybe with only the native app, and the forwarding device reports its own health to that app.
