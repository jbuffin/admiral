# The command line

`admiral` with no command starts the server. On a terminal with no fleets it first asks whether to run setup (not under launchd, where stdin is not a terminal). The other commands work on `$ADMIRAL_HOME`. Exit codes: 0 ok, 1 error, 2 usage (unknown command, bad flags, `setup --yes` without `--answers`); `admiral crew` adds 4 and 5; `admiral orders add` adds 5 and `admiral chat ask` adds 3 and 4 (below); `admiral lock` adds 75 and 127 and passes on its command's own status.

| command | what it does |
| --- | --- |
| `admiral setup [--answers <file> --yes] [--dry-run]` | Finds your harnesses, wrappers (`claude-work`...), the names of `~/.claude*`, `~/.codex*` and `~/.copilot*` (never what is inside them) and folders under `~` that hold git checkouts, asks for each fleet, shows the change as a diff and asks before writing. It only adds or updates: fleets it isn't told about and top-level keys it doesn't know stay as they are. Interactively, a re-run lists the fleets already in the file, takes each default from the fleet you name, offers a wrapper named `<harness>-<key>` as the executable, and ends on an empty key. If `config.json` changes while setup waits to write, it plans again on the new file and asks again. It refuses a fleet that shares an identity directory with another fleet for the same harness. After it saves, and also when it finds "No changes.", it probes every harness of every fleet in the file (dry run and a declined write probe nothing): it prints a `Probing` heading for the harness and fleet, the detected version and one line per capability that reads `passed`, `failed` with the reason, or `not checked` (the advisor is printed once per fleet, after all its harnesses, as the API and the gate compute it), and stores the results in `capabilities.json`. A failed probe is a result and setup still exits 0. Claude Code gets one probe for its pre-tool guard hook, which runs it headless on haiku (one short model call); a Claude Code older than 2.1.295 reads `not checked`. Setup also runs the judge probes (no tools, no network, JSON schema, per-call cap) on every docked claude, codex and copilot, each on that harness's small model. That costs money: up to 3 short claude calls capped at $0.05 each plus one capped at $0.0001 (it is meant to stop), up to 3 short codex calls and 2 short copilot calls. Three probes are fixed fails that make no call: codex's per-call cap, and copilot's JSON schema and per-call cap. |
| `admiral fleet list \| add \| edit \| check [<key>]` | `add <key> --name N` and `edit <key>` take `--color`, `--harness`, `--executable <harness>=<path>`, `--arg <harness>=<arg>`, `--env <harness>=<NAME>=<value>`, `--unset-env <harness>=<NAME>`, `--search-root` and `--remove-search-root`; every flag may repeat, and the key comes first. On `edit`, the `--arg` values for a harness replace its arguments. `~` is stored as typed. `check` resolves each executable without running it and exits 1 when one is missing; with a key it checks only that fleet. |
| `admiral config show \| validate \| edit` | `edit` opens a copy in `$EDITOR` (`vi` without one) and saves it only if it loads, so it also fixes a file that is invalid now. |
| `admiral ships [--port N] [--names]` | Lists ships (`NAME SESSION FLEET HARNESS STATUS REPO`, tab-separated) as the running server on `--port` sees them, if it serves this `ADMIRAL_HOME`. Otherwise it reads tmux and says so on the first line. Under each ship's line goes one line per crew boat (teammates; subagents are not listed), sorted by name, in the same six columns: the name indented by two spaces, then empty SESSION and FLEET, the crew boat's HARNESS, its own STATUS (`anchored (exit N)` once it has exited, `anchored (KILL)` for a signal) and REPO (the basename of its directory). With the server up, STATUS is the server's wire status, so an underway ship with a crew boat that needs you lists as `needs_you`; read from tmux it is the ship's own, so a ship line can differ between the two. The crew lines are the same either way. `--names` prints ship display names only. Control characters in any field are printed as spaces. |
| `admiral inbox [--port N] [--json]` | Lists everything waiting on you, as the dashboard's inbox does (needs the running server for this `ADMIRAL_HOME`, found as `ships` does). One tab-separated line each, `SHIP KIND TITLE AGE`: the items `GET /api/inbox` serves (`KIND` is `question`, `review`, `findings`, `notice`, `wake_proposal`, `crew_notes` or `crew_member`), then the ships that need you, with `KIND` `needs-you` and the reason as the title. Control characters print as spaces. `--json` prints `{"items": <GET /api/inbox's items>, "needs_you": [<the needs-you ships as GET /api/ships serves them>]}`. No server for this home exits 1. |
| `admiral orders [--port N] [--json]` | Lists the order sources' panels from `GET /api/sources`: one line per panel, even an empty one, `SOURCE PANEL TITLE`, and under it one indented line per order, `ID TITLE`. Orders that already have a ship are not listed. `--json` prints the server's body unchanged. No server for this home exits 1. |
| `admiral orders add --source <key> --panel <id> [--port N] [-- <text>]` | Adds an order to a panel (`POST /api/sources/{key}/orders`) and prints its id. Without `-- <text>` it reads the text from stdin. Text that is empty after trimming exits 2 without calling the server. A 502 or 504, an answer with no id, a 2xx whose body can't be read, and any transport error (a refused or dropped connection, or its own 40 s client timeout) may mean the order was added: it prints that, says to check with `admiral orders` and exits 5, and never sends the order again (ADR 0016). Any other error (an unknown source or panel, a read-only source, a refusal) prints the server's message and exits 1. |
| `admiral hold on\|off --fleet <key>` or `--all` `[--port N]` | Turns Hold fire on or off for a fleet (`POST /api/fleets/{key}/hold-fire/on` or `off`) or for all fleets (`POST /api/hold-fire/on` or `off`) and prints the new state. While it is on, a routine set to Act asks first. Turning a fleet off leaves the all-fleets switch on. No `--fleet` or `--all`, both, or any other word exits 2. |
| `admiral hold status [--fleet <key>] [--port N]` | Prints whether Hold fire is on, and who turned it on. With `--fleet` it also says when the all-fleets switch holds the fleet; without it, it reads the all-fleets switch. An unknown fleet exits 1 with the server's message. |
| `admiral chat ask [--timeout <dur>] [--wait <id>]` | Asks the engineer a question in the chat (AdmiralBot's, ADR 0020) and waits for the answer; it needs no server. It reads the question on stdin, as lines (`title: <title>`, then for each question `question: <id> \| <text>`, an optional `multi: true` and one `option: <label> \| <description>` for each option; blank lines are ignored) or as JSON `{"title": ..., "questions": [{"id", "text", "multi", "options": [{"label", "description"?}]}]}` when the body starts with `{`. The lines are turned into that JSON. The line form is for people typing it; AdmiralBot's chat has no shell and asks through the `ask_question` tool instead. It checks the result as the inbox checks a question item, writes `$ADMIRAL_HOME/chat/<fleet>/questions/<id>.json` and waits for `<id>.answer.json`, which it prints (ADR 0016's answer shape) before exiting 0. After `--timeout` (default 100 s) it prints that it is still waiting, with the id and `admiral chat ask --wait <id>`, and exits 3. `--wait <id>` waits on an existing question, and exits 4 at once if it is gone. A question that disappears while waiting (New chat) exits 4 with "withdrawn". The fleet comes from `ADMIRAL_CHAT_FLEET`, which only a fleet's chat session has; a bad question, `ADMIRAL_SHIP` set (ships don't ask in the chat) or no valid `ADMIRAL_CHAT_FLEET` exits 2 and writes nothing. |
| `admiral attach <ship> [<crew>]` | Attaches this terminal to the ship's tmux session (`Ctrl-b d` detaches), by display name or session name. `attach <ship>` always opens the ship's own window, never the session's current one. `attach <ship> <crew>` opens that crew boat's window, read-only exactly when the crew boat is anchored (the ship's status doesn't decide). The whole argument list is tried as a ship first (`admiral attach Saltpaw II` works unquoted); otherwise the last argument is the crew name, which holds no spaces, and the rest is the ship. An unknown ship or crew boat exits 1 and names it. `attach <ship>` is read-only for an anchored ship. `_admiral`, `_setup`, every `_chat-<fleet>` and the old `_chat` are refused. |
| `admiral mcp` | AdmiralBot's tool server: the Model Context Protocol over stdio (JSON-RPC 2.0, one message a line; nothing but JSON-RPC goes to stdout). Each tool calls the local Admiral server on loopback with the `X-Admiral-Actor` token from `ADMIRAL_ACTOR_TOKEN`, so the server's guard fences it to the token's fleet and stamps its writes `"via":"admiralbot"`. Without the token it exits 2 and prints nothing on stdout. It finds the server as the other commands do (`ADMIRAL_PORT`, else the default port) and sends the token only after the server on that port proved to be this `ADMIRAL_HOME`'s; `ADMIRAL_CHAT_FLEET` is the fleet it puts in a launch. The token is never logged. Tools: `list_ships`, `read_conversation {session}`, `read_outcomes {ship?, limit?}`, `list_inbox`, `list_sources`, `list_campaigns`, `launch_ship {harness, dir?, clone?, clone_repo?, skill?, text?, source?, order_id?, crew?, issues?, anyway?, with_me?}` (no message id: the server keys the launch on the chat's latest prompt), `add_order {source, panel, text}`, `answer_item {session, id, answers}`, `next_prompt {session, text}`, `wake_ship {session, text?}`, `stop_ship {session}`, `dismiss_ship {session}` and `ask_question {title, questions, wait_id?, wait_seconds?}`. `skill` is `commodore`, `none` or a skill's name. A Commodore launch runs in autopilot unless `with_me` is true; the result is JSON with `mode` (`autopilot` or `interactive`) and the launched ship. When autopilot is at its cap (409), the launch is sent again as interactive and the result gives the reason. `ask_question` waits up to 100 s, then says it is still waiting and names the id, and `wait_id` keeps waiting on it. A server refusal comes back as a tool result with `isError`. There are no tools for harness approvals, typing into a turn that is running, config, sources, settings or Preferences. |
| `admiral mcp-probe` | The fence probe's MCP server over stdio, with one tool `ping`; it writes `called-<nonce>` under `$ADMIRAL_PROBE_DIR` when the tool is called. The probe starts it, not people. |
| `admiral advise` | The advisor of an autopilot ship: it asks the fleet's judge harness whether a decision is low or high stakes. It reads one JSON object on stdin, `{"question": string, "options": [string, …], "recommendation": string}` (at most 1 MiB; `options` holds at least two distinct, non-empty strings and `recommendation` is one of them; trailing data after the object and unknown fields are refused), and prints exactly one JSON line, `{"stakes": "low" or "high", "reason": string, "cost": number or null}`, exit 0. `cost` is what the harness reported in USD, else `null`. Every failure answers `high` with a fixed reason: no ship (`ADMIRAL_SHIP` unset, which includes every crew boat), no home, no fleet, no judge harness, a failed, timed-out, over-budget or unusable call, or a `stakes` that is not `low` or `high`. Text from a failed call never reaches the output. Bad stdin exits 2 and makes no call. It runs one Strong-model call under a $0.15 cap (where the harness has a proven cap) and a one-minute timeout, and logs one `advised` outcomes line with `stakes`, `fleet`, `harness`, `failure` and `cost`, never the question. `fleet` is the ship's fleet key, left out when the fleet could not be found. |
| `admiral outcomes [--since <date>] [--ship <name>]` | Prints the outcome log (ADR 0015) as JSON lines, each as stored, in file order with the months ascending. It reads `$ADMIRAL_HOME/outcomes/` directly, so it works whether or not the server runs. `--since` takes `YYYY-MM-DD` (UTC midnight) or an RFC 3339 time, and keeps records at or after it. `--ship` takes a session name or a display name (mapped to its session name the way a launch does it); a name with a space needs quotes. A name is reused once it is free, so `--ship` matches every past ship that had it. An `underway` record means a needs-you stop cleared, not the ship's status. A `usage` record holds a harness exit's `fleet`, `harness`, `round` (a moored round), `tokens` and `money` (`null` when unknown) and `crew` boats, one per exit and one for a fleet's chat (`_chat-<fleet>`) at each reset; see ADR 0015. A line is skipped unless it is a JSON object with a time and either a ship or one of autopilot's ship-less events, `skipped`, `launch_failed`, `resource_wait` and `retro_queued` (a crash can leave one cut short), and so is a line over 7 MiB. `--ship` drops `skipped`, `launch_failed`, `resource_wait` and `retro_queued`, which have no ship. No match prints nothing and exits 0; a bad `--since` or a positional argument exits 2. |
| `admiral lock [--port N] [--wait] <resource> -- <command…>` | Holds one unit of a locked resource (`resources` in the config, #118) while the command runs, so a launch that names it is refused (409) until the command ends. Flags may come before or after the resource; everything after `--` is the command, run with no shell and your terminal's input and output, so `admiral lock r -- tool --help` runs `tool --help`. It needs the running server for this `ADMIRAL_HOME` on `--port` (default 7420), finds it by the `home` field of `GET /api/ships`, which the CLI compares with its own `ADMIRAL_HOME`, and starts the command only once the unit is taken. A lock doesn't need the resource's check to pass. Without `--wait` a busy resource exits 75 at once with a message; with `--wait` it waits for a free unit. The holder shows in the dashboard and `GET /api/resources` as `admiral lock (pid N): <command name>`. `kill` (SIGTERM) sent to `admiral lock` goes on to the command; Ctrl-C and other terminal signals reach the command from the terminal, so `kill -INT <lock pid>` doesn't reach it (use SIGTERM). Exit status: the command's own (128 plus the signal number if a signal ended it), 127 if it can't be started, 75 busy, 2 usage, 1 for an unknown resource or no running server. The lock ends when the command ends. It also ends when the server stops or restarts: `admiral lock` then prints `admiral: lost the lock on <resource> (the server went away); <command> is still running without it` and leaves the command running, and its exit status is still the command's. `admiral lock` ignores SIGINT, SIGHUP and SIGQUIT. If it is killed with SIGKILL, the server notices the dropped connection and frees the unit at once, but the command keeps running without the lock. The server takes locks from this Mac only. |
| `admiral pair [--port N] [--json]` | Mints a pairing code from the running server for this `ADMIRAL_HOME` (`POST /api/pairing-codes`) and prints the pairing URL, the code (`XXXX-XXXX`) and the clock time it expires (5 minutes from now). The code is single-use, and minting another voids it. A missing or extra argument exits 2. The CLI is local, so it needs no token and never sees the paired device's token. `--json` prints the server's body unchanged. No server for this home exits 1. |
| `admiral devices [--port N] [--json]` | Lists paired devices, one tab-separated line each, `NAME LOGIN PAIRED LAST-SEEN ID`; `LOGIN` is empty for a device paired over the LAN. An extra argument exits 2. No paired devices prints nothing and exits 0. Control characters print as spaces. `--json` prints the server's `{"devices": [...]}` unchanged. No server for this home exits 1. |
| `admiral devices rename <name-or-id> <new-name> [--port N]` | Renames a paired device. A name must match exactly. A missing or extra argument exits 2. An unknown name or id exits 1 and says `no paired device "x"`; a key that matches more than one device (two devices with one name, or an id that is also another device's name) exits 1, changes nothing and lists the ids. |
| `admiral devices revoke <name-or-id> \| --all [--port N]` | Revokes one paired device, or every one with `--all`: its token stops working and its open connections close. It finds the device as `rename` does. A missing or extra argument, or a name together with `--all`, exits 2. |
| `admiral codex-pane --socket <path> -- <codex> [args…]` | Internal: the command a Codex ship's pane runs, written by the launcher, not typed. It makes `/tmp/admiral-<uid>/` (mode 0700; refused when it is a symlink, another user's or wider than 0700) and starts `<codex> app-server --listen unix://<path>` plus the ship's `-c`/`--config`, `--enable` and `--disable` flags (the dock's, Admiral's `model_reasoning_effort` and `hooks.*`; not `tui.*` ones) as its own process group, with stdin and output on `/dev/null`. Once the socket accepts a connection (up to 5 s) it runs `<codex> --remote unix://<path> <args…>` in the foreground. If the server does not come up, exits early or the directory is unsafe, it prints one line to stderr naming the reason and runs `<codex> --no-daemon <args…>` instead, with `--no-daemon` only when `<codex> --help` lists it (older Codex has no app-server and rejects it; `--no-daemon` keeps a plain Codex off a shared background server whose hooks would lack the pane's `TMUX_PANE` and `ADMIRAL_SHIP`; Codex refuses it together with `--remote`). `<codex>` is the dock's resolved executable, never one found on `PATH`. SIGINT and SIGQUIT are ignored while the TUI runs; when it exits, or on SIGHUP or SIGTERM, the server's process group is killed (unless the server had already exited) and the socket removed, along with Codex's real socket and `.lock` behind it when they sit in Codex's private daemon directory, and the command exits with the TUI's status. A SIGKILL leaves a stale socket and an orphan server. |
| `admiral crew launch --dir <dir> [--name <name>] [--member <member>] [--harness <h>] [--ship <ship>] [--role <role>] [--arg <value>]... -- <prompt>` | Starts a teammate (a crew boat, #152) in a new window of the ship's tmux session; the ship stays window 0 and the current window. `--member <member>` launches the boat as that crew member, resolved over the built-in, fleet, repo and the ship's run layers (and the fleet's memory): the member's `harness` is a lock (a `--harness` that differs is refused, and the fleet needs a dock for it), its `model` goes in as `--model` (`-m` on Codex), after the `--arg` values and before the prompt, unless it breaks the model name rule (then a warning on stderr and the dock's default stands) or the dock or an `--arg` already sets a model (refused), and the prompt is the member's instructions, its notes block, then the text after `--`, each part skipped when empty. A fix checker keeps the launch's harness and model, with a warning, and gets no instructions or notes. A member's `skills` are ignored with a warning. With `--member`, `--name` defaults to the member's name and `--role` to its role; an unknown member exits 1, and an ad hoc member is unknown too, since ad hoc is not a layer `--member` reads. `--name` is lowercase letters, digits and `-`, unique in the ship. `--dir` is any existing directory (it need not be in a search root). `--harness` defaults to the ship's and must be one the ship's fleet has a dock for (else exit 1). `--ship` is a session or display name; without it the command uses `ADMIRAL_SHIP`, and with neither it exits 2 with `not inside an Admiral ship`. Everything after `--` is the prompt, on the harness's command line. Admiral's hooks are on its command line like a ship's. `--arg <value>` is repeatable: each value is one argument for the harness, kept in order and placed after the dock's `args` and Admiral's hook flags, right before the prompt (`exe, dock args, hook flags, --arg values, prompt`). A value that overrides or disables Admiral's hooks, runs a subcommand or moves the session off this machine is refused with exit 1, whether or not `ADMIRAL_AUTOPILOT` is set, and nothing is launched. Refused on every harness: a bare `--` (write it `--arg=--`; `--arg --` is a usage error, exit 2), a value with an ASCII control character, and a value that equals one of the harness's subcommand names (such as `mcp`, `doctor`, `exec`, `e`, `login` or `help`), wherever it appears. A flag value that equals a subcommand name has to use the joined `--flag=value` form, such as `--setting-sources=project`. Claude also refuses `--settings` (also `--settings=<x>`), `--bare` and `--safe-mode`. Codex refuses `-c`/`--config` (`-c <kv>`, `-c<kv>`, `-c=<kv>`, `--config <kv>`, `--config=<kv>`) whose key, taken before the first `=` with spaces and quotes removed, is `hooks`, starts with `hooks.`, is `features`, `features.hooks`, `features.codex_hooks`, `profile`, `profiles` or starts with `profiles.`; `--disable hooks` and `--disable codex_hooks` (also `--disable=<x>`); `-p`/`--profile` in any spelling; and `--remote` (also `--remote=<x>`). Copilot refuses `--plugin-dir`, `--connect` and `--acp`, also in their `=` forms. A trailing flag that takes a value (`--arg --model`) is the caller's to pair with its value. A caller with `ADMIRAL_AUTOPILOT=1` also meets the autopilot args allowlist, and a refusal exits 1 with nothing launched. The launch is refused for a harness whose guard probe has not passed in the ship's fleet (exit 1, naming the harness; it also posts one Inbox notice, as a refused hand launch does), and never falls back to launching without autopilot. Every `--arg` must then be one of claude's `--model`, `--advisor`, `--effort`, `--disallowedTools` and `--permission-mode`, each as the next `--arg` or joined as `--flag=value`. `--model`, `--advisor` and `--effort` take exactly one value, which may not start with `-`; `--disallowedTools` (or its alias `--disallowed-tools`) takes one or more `--arg`s up to the next that starts with `-`, and is refused when the dock's `args` already set it, under either spelling, since a repeat may replace the dock's list. `--permission-mode` passes only when its mode is no looser than the dock's last `--permission-mode` in `args` (strictest first: `plan`, `dontAsk`, `default` = `manual`, `acceptEdits`, `auto`, `bypassPermissions`), or `default` when the dock has none; `default` itself is refused as a value, since claude 2.1.310 doesn't accept it, and so is an unknown mode. Any other flag, a bare value and a flag without its value are refused, and the error names the first one. The hook refusal above runs first. Known gaps: the signal is the caller's own environment, which an agent can unset or change (`env -u ADMIRAL_AUTOPILOT admiral crew launch …`); a dock with no `--permission-mode` whose `CLAUDE_CONFIG_DIR` settings set `permissions.defaultMode` can be stricter than the baseline `default`, so the check can loosen it; and a crew boat gets the dock's `args`, not the stricter `args` an autopilot panel gives its ships, so the comparison is with the dock. `--role <role>` names the teammate's part, such as `test-writer`; it is lowercase letters, digits and `-` (else exit 2) and is kept as the window option `@admiral-role`. Its environment is the ship's session environment with the chosen dock's `env` over it and Admiral's `PATH` (`$ADMIRAL_HOME/bin` first); the caller's own environment never goes in. `ADMIRAL_SHIP`, `ADMIRAL_REPORT` and `ADMIRAL_INBOX` are cleared, and so is any key the ship's dock sets that the chosen dock doesn't. `ADMIRAL_CREW_DIR` and `ADMIRAL_RUN_CREW` are kept: the boat resolves the same fleet crew directory and run layer as its ship. A caller with `ADMIRAL_AUTOPILOT=1` may not name another ship with `--ship` (exit 1), and with no `ADMIRAL_SHIP` it may not use `--ship` at all, as any `crew` command. A name already in use exits 5. |
| `admiral crew send <name> [text] [--ship <ship>]` | Types the text into the crew boat and submits it: a bracketed paste, then Enter (after a 0.3 s pause for Codex, which drops an Enter that arrives with the paste). Without `text` it reads stdin, with a trailing `\r\n` trimmed. Text with a control character other than newline or tab exits 1. An unknown name exits 1; an anchored crew boat exits 4. |
| `admiral crew list [--json] [--ship <ship>]` | Lists the ship's crew boats. `--json` prints `[{name, harness, dir, state, launched, last_activity, role, transcript}]`. `state` is `anchored` whenever the process has ended (any exit code: a crew boat never sails off), `needs_you` when it waits on the engineer, `idle` when its turn ended and it waits for its lead, else `underway`; it is never `working`. `launched` and `last_activity` are RFC 3339, and `last_activity` is `null` until the crew boat's first hook. `role` is the `--role` it was launched with, `null` without one or if the stored option is not a valid role. `transcript` is the crew boat's transcript path (ADR 0021), `null` until a hook has recorded one or if the stored option fails the check on read (`ValidTranscriptPath`: absolute, ends in `.jsonl`; plus valid UTF-8, no control (C0/C1), bidi or line/paragraph separator character, and none of `'`, `"`, `\`, `` ` ``, `$`, `#`, `;`, `{`, `}`). Admiral never opens the file. |
| `admiral crew close <name> [--ship <ship>]` | Closes the crew boat's window, live or anchored. The boat's token figures stay with the ship and count in its `usage` record. An unknown name exits 1. |
| `admiral completion zsh \| bash` | Completes ship names for `attach`. It does not complete crew names (that would take a second `admiral` call per shell). |
| `admiral service install \| uninstall \| status` | `install` writes the LaunchAgent `~/Library/LaunchAgents/dev.jasonbuffin.admiral.plist`, points it at the stable path (`$(brew --prefix)/bin/admiral` under Homebrew, never the versioned Cellar path), gives ships the `PATH` of your login shell as it is when you run `install` (run it again after changing `PATH`), logs to `$ADMIRAL_HOME/logs/admiral.log`, loads it and prints the "On other devices" URL (no token in it; pair a device with `admiral pair`); `uninstall` unloads it and removes the plist; `status` says `Service: not installed`, `installed, not loaded` or `installed, loaded` (from the exit code of `launchctl print`) and prints the URL. |
| `admiral --version` | Prints `admiral <version> (<commit>)`. |

Every command that takes `--port` (`ships`, `lock`, `inbox`, `orders`, `orders add`, `hold`, `pair`, `devices`, `devices rename`, `devices revoke`) takes its default from `ADMIRAL_PORT` when that is set, else 7420. A port is a decimal number from 1 to 65535: a bad `--port` exits 2, and a bad `ADMIRAL_PORT` is ignored. `admiral` itself (the server) also reads `ADMIRAL_PORT` as the port of its default listen address, which the Tailscale mode derives (`127.0.0.1` with the mode on, `0.0.0.0` off); an explicit `--listen` wins and sets the whole address. A bad value (not 1 to 65535) is ignored with one log line, as for the commands. This is a test and advanced setting. With the mode changed while running, Admiral moves its listener live unless `--listen` was given. Admiral sets `ADMIRAL_PORT` (the port it listens on) in the chat session's environment, so AdmiralBot's MCP server finds the server without `--port`; ships never have it.

`admiral hook <event>` and `admiral guard pretooluse` are internal: the hook bundles run them, and the usage text doesn't list them. `hook` also handles `SessionStart`, which only the chat's bundle registers (ADR 0019): it sets the pane option `@admiral-transcript` on `$TMUX_PANE` to `<unix nanoseconds> <source> <transcript_path>` and writes no state. It records nothing for a path that isn't absolute, doesn't end in `.jsonl` or holds a control character. On a crew boat's pane, any event's `transcript_path` (Claude Code, Codex; Codex may send `null`) or a Copilot lead `agentStop`'s `transcriptPath` is recorded in the pane option `@admiral-crew-transcript` (ADR 0021), through a tmux `if` that checks the window's `@admiral-crew-name` is non-empty (`#{!=:#{@admiral-crew-name},}`), so a ship or the chat never gets it, and only for a `%N` pane id. A path that fails the same check as the read (`ValidTranscriptPath`; plus valid UTF-8, no control (C0/C1), bidi or line/paragraph separator character, and none of `'`, `"`, `\`, `` ` ``, `$`, `#`, `;`, `{`, `}`) is not recorded.

`admiral statusline [--chat]` is internal too: Admiral's Claude settings run it as the `statusLine`. It reads Claude's status JSON on stdin and keeps a compact subset (the time, `session_id`, `transcript_path`, `cost.total_cost_usd`, the `context_window` token totals and `current_usage`, and `rate_limits` with `five_hour`, `seven_day` and `spend_limit`, a missing one left missing; one wrong-typed field drops only itself) in the pane option `@admiral-statusline` on `$TMUX_PANE`, in one write and before anything else, since Claude cancels a running status line on its next update. It never keeps `session_name`, `prompt_id`, `cwd` or the model, and it keeps nothing for input that isn't a JSON object, for no `$TMUX_PANE`, or for a value over 4 KB. It then runs the engineer's own `statusLine` with `sh -c`, the same JSON on stdin and a 10 s limit (Claude documents none; Claude's own cancel on the next update ends most runs sooner) that kills the command's process group, and passes its stdout through unchanged. A non-zero exit or a timeout prints nothing, as Claude blanks the line then. On SIGTERM, SIGINT or SIGHUP (Claude cancelling the wrapper) it kills the command's group before it exits, and it sets `ADMIRAL_STATUSLINE=1` on the command, so an `admiral statusline` reached by any route does nothing. The command's stderr goes to the wrapper's stderr, and its stdout is passed through even when a background child still holds the pipe after it exits 0, and that child is left running (the group is killed only on the timeout or a signal to the wrapper, never after a normal exit). It always exits 0. The engineer's line is the first `statusLine` in the managed settings (`/Library/Application Support/ClaudeCode/managed-settings.json` on macOS; unconfirmed in Claude Code's docs), then `$CLAUDE_CONFIG_DIR/settings.json` (or `~/.claude/settings.json` when that is unset; a relative directory reads nothing), skipping a user file with `disableAllHooks`. Project and local settings are never read: a ship's checkout is untrusted and the wrapper can't apply Claude's workspace-trust check. A line that is itself `admiral statusline` isn't run. `--chat` (AdmiralBot, which loads project settings only) keeps the JSON and prints nothing. Admiral's `statusLine` replaces the engineer's whole key, so their `padding` and `refreshInterval` are lost. The `statusLine` is always set, so Claude hides most footer hints (`esc to interrupt`, `? for shortcuts`) in every Claude ship, even for an engineer with no status line. The wrapper reads the engineer's user settings even when a dock passes `--setting-sources` without `user`. The tmux write has a 2 s deadline, so a hung tmux can't hold the line back.

The answers file for `setup --answers` is JSON holding the same `fleets` object as `config.json`, in the order the fleets should have:

```json
{"fleets": {"work": {"name": "Work", "search_roots": ["~/code"],
                     "claude": {"env": {"CLAUDE_CONFIG_DIR": "~/.claude-work"}},
                     "codex": {}}}}
```

An `executable` left out is looked up on `PATH` (and `/opt/homebrew/bin`, `/usr/local/bin`, `~/.local/bin`) and written as the absolute path found, without following symlinks. The identity variable (`CLAUDE_CONFIG_DIR`, `CODEX_HOME`, `COPILOT_HOME`) is always written, with the harness's default directory when the file leaves it out; two fleets that leave it out share that default and are refused.

The file may also carry a top-level `remote`, `{"tailscale": true, "allowedLogins": ["bob@example.com"]}`, and then `fleets` is optional (a file with neither is refused). `tailscale: true` turns on Tailscale mode; interactively, setup asks after the fleets (default no). Setup then prints one line per check, `[passed]` or `[failed]` with the reason: tailscaled running and logged in; HTTPS certificates and MagicDNS on for the tailnet (if either is off it says what to turn on in the admin console); Funnel off for Admiral's port. A failed check stops setup with exit 1 and writes nothing. Next it warns that the HTTPS certificate publishes the Mac's ts.net name in public Certificate Transparency logs, and, unless `--yes` or `--dry-run`, asks to go on. Then it runs `tailscale serve --bg --https=443 http://127.0.0.1:7420` (found through `PATH`, 60 s timeout, `ADMIRAL_TAILSCALE_SERVE_TIMEOUT` shortens it for tests) after the write is confirmed. A serve that already proxies to Admiral's port is left as it is. Port 443 held by anything else is never replaced: setup stops and prints the command for another HTTPS port. A failed or hung serve prints the CLI's message and writes nothing. The one diff and write then cover `fleets` and `remote` together: `remote.tailscale` becomes true and the Mac's own login (from `tailscale status --json`) and the file's `allowedLogins` join the logins already allowed. `--dry-run` prints the checks, the serve command and the diff, and runs no serve.

A fleet may also carry `owners` (a list of GitHub organizations and users), `wake_reviewers` (a list of GitHub logins, each 1 to 39 letters, digits and single hyphens, with an optional `[bot]` suffix, whose feedback wakes a moored ship), `clone_root` (a path) and `env` (an object of names and values). The fleet's `env` is added to the environment of that fleet's order-source plugins and of the `gh` calls of its GitHub source, over Admiral's own environment. Changing it restarts that fleet's sources. A command that reads a `config.json` from an older Admiral, one with a source that names no fleet or a freeform source, refuses with ``config.json is from an older Admiral: start Admiral once (`admiral`) to migrate it``. Only starting Admiral migrates the file.
