# The command line

`admiral` with no command starts the server. On a terminal with no fleets it first asks whether to run setup (not under launchd, where stdin is not a terminal). The other commands work on `$ADMIRAL_HOME`. Exit codes: 0 ok, 1 error, 2 usage (unknown command, bad flags, `setup --yes` without `--answers`); `admiral crew` adds 4 and 5; `admiral orders add` adds 5 and `admiral chat ask` adds 3 and 4 (below); `admiral lock` adds 75 and 127 and passes on its command's own status.

| command | what it does |
| --- | --- |
| `admiral setup [--answers <file> --yes] [--dry-run]` | Finds your harnesses, wrappers (`claude-work`...), the names of `~/.claude*`, `~/.codex*` and `~/.copilot*` (never what is inside them) and folders under `~` that hold git checkouts, asks for each fleet, shows the change as a diff and asks before writing. It only adds or updates: fleets it isn't told about and top-level keys it doesn't know stay as they are. Interactively, a re-run lists the fleets already in the file, takes each default from the fleet you name, offers a wrapper named `<harness>-<key>` as the executable, and ends on an empty key. If `config.json` changes while setup waits to write, it plans again on the new file and asks again. It refuses a fleet that shares an identity directory with another fleet for the same harness. |
| `admiral fleet list \| add \| edit \| check [<key>]` | `add <key> --name N` and `edit <key>` take `--color`, `--harness`, `--executable <harness>=<path>`, `--arg <harness>=<arg>`, `--env <harness>=<NAME>=<value>`, `--unset-env <harness>=<NAME>`, `--search-root` and `--remove-search-root`; every flag may repeat, and the key comes first. On `edit`, the `--arg` values for a harness replace its arguments. `~` is stored as typed. `check` resolves each executable without running it and exits 1 when one is missing; with a key it checks only that fleet. |
| `admiral config show \| validate \| edit` | `edit` opens a copy in `$EDITOR` (`vi` without one) and saves it only if it loads, so it also fixes a file that is invalid now. |
| `admiral token rotate [--port N]` | Writes a new token and prints the new "On other devices" URL. A running server notices and signs out every device that isn't on this Mac, dashboard and bridge alike. `--port` (default `ADMIRAL_PORT`, else 7420) is the port of the URL and of the server it looks for (`GET /api/ships` carries a `home` field, a hash of `ADMIRAL_HOME`, which the CLI compares); a server on that port that serves another `ADMIRAL_HOME` doesn't count, and the command says there is no running server for this home. |
| `admiral ships [--port N] [--names]` | Lists ships (`NAME SESSION FLEET HARNESS STATUS REPO`, tab-separated) as the running server on `--port` sees them, if it serves this `ADMIRAL_HOME`. Otherwise it reads tmux and says so on the first line. Under each ship's line goes one line per crew boat (teammates; subagents are not listed), sorted by name, in the same six columns: the name indented by two spaces, then empty SESSION and FLEET, the crew boat's HARNESS, its own STATUS (`anchored (exit N)` once it has exited, `anchored (KILL)` for a signal) and REPO (the basename of its directory). With the server up, STATUS is the server's wire status, so an underway ship with a crew boat that needs you lists as `needs_you`; read from tmux it is the ship's own, so a ship line can differ between the two. The crew lines are the same either way. `--names` prints ship display names only. Control characters in any field are printed as spaces. |
| `admiral inbox [--port N] [--json]` | Lists everything waiting on you, as the dashboard's inbox does (needs the running server for this `ADMIRAL_HOME`, found as `ships` does). One tab-separated line each, `SHIP KIND TITLE AGE`: the items `GET /api/inbox` serves (`KIND` is `question`, `review` or `findings`), then the ships that need you, with `KIND` `needs-you` and the reason as the title. Control characters print as spaces. `--json` prints `{"items": <GET /api/inbox's items>, "needs_you": [<the needs-you ships as GET /api/ships serves them>]}`. No server for this home exits 1. |
| `admiral orders [--port N] [--json]` | Lists the order sources' panels from `GET /api/sources`: one line per panel, even an empty one, `SOURCE PANEL TITLE`, and under it one indented line per order, `ID TITLE`. Orders that already have a ship are not listed. `--json` prints the server's body unchanged. No server for this home exits 1. |
| `admiral orders add --source <key> --panel <id> [--port N] [-- <text>]` | Adds an order to a panel (`POST /api/sources/{key}/orders`) and prints its id. Without `-- <text>` it reads the text from stdin. Text that is empty after trimming exits 2 without calling the server. A 502 or 504, an answer with no id, a 2xx whose body can't be read, and any transport error (a refused or dropped connection, or its own 40 s client timeout) may mean the order was added: it prints that, says to check with `admiral orders` and exits 5, and never sends the order again (ADR 0016). Any other error (an unknown source or panel, a read-only source, a refusal) prints the server's message and exits 1. |
| `admiral chat ask [--timeout <dur>] [--wait <id>]` | Asks the engineer a question in the chat (AdmiralBot's, ADR 0020) and waits for the answer; it needs no server. It reads the question on stdin, as lines (`title: <title>`, then for each question `question: <id> \| <text>`, an optional `multi: true` and one `option: <label> \| <description>` for each option; blank lines are ignored) or as JSON `{"title": ..., "questions": [{"id", "text", "multi", "options": [{"label", "description"?}]}]}` when the body starts with `{`. The lines are turned into that JSON. AdmiralBot uses them because Claude Code refuses a heredoc whose body has both `{` and `"` under `dontAsk`, so a JSON body never matches the allow rule. It checks the result as the inbox checks a question item, writes `$ADMIRAL_HOME/chat/questions/<id>.json` and waits for `<id>.answer.json`, which it prints (ADR 0016's answer shape) before exiting 0. After `--timeout` (default 100 s) it prints that it is still waiting, with the id and `admiral chat ask --wait <id>`, and exits 3. `--wait <id>` waits on an existing question, and exits 4 at once if it is gone. A question that disappears while waiting (New chat) exits 4 with "withdrawn". A bad question, or `ADMIRAL_SHIP` set (ships don't ask in the chat), exits 2 and writes nothing. |
| `admiral attach <ship> [<crew>]` | Attaches this terminal to the ship's tmux session (`Ctrl-b d` detaches), by display name or session name. `attach <ship>` always opens the ship's own window, never the session's current one. `attach <ship> <crew>` opens that crew boat's window, read-only exactly when the crew boat is anchored (the ship's status doesn't decide). The whole argument list is tried as a ship first (`admiral attach Saltpaw II` works unquoted); otherwise the last argument is the crew name, which holds no spaces, and the rest is the ship. An unknown ship or crew boat exits 1 and names it. `attach <ship>` is read-only for an anchored ship. `_admiral`, `_setup` and `_chat` are refused. |
| `admiral outcomes [--since <date>] [--ship <name>]` | Prints the outcome log (ADR 0015) as JSON lines, each as stored, in file order with the months ascending. It reads `$ADMIRAL_HOME/outcomes/` directly, so it works whether or not the server runs. `--since` takes `YYYY-MM-DD` (UTC midnight) or an RFC 3339 time, and keeps records at or after it. `--ship` takes a session name or a display name (mapped to its session name the way a launch does it); a name with a space needs quotes. A name is reused once it is free, so `--ship` matches every past ship that had it. An `underway` record means a needs-you stop cleared, not the ship's status. A line is skipped unless it is a JSON object with a time and either a ship or one of autopilot's ship-less events, `skipped`, `launch_failed`, `resource_wait` and `retro_queued` (a crash can leave one cut short), and so is a line over 7 MiB. `--ship` drops `skipped`, `launch_failed`, `resource_wait` and `retro_queued`, which have no ship. No match prints nothing and exits 0; a bad `--since` or a positional argument exits 2. |
| `admiral lock [--port N] [--wait] <resource> -- <command…>` | Holds one unit of a locked resource (`resources` in the config, #118) while the command runs, so autopilot launches that need it wait. Flags may come before or after the resource; everything after `--` is the command, run with no shell and your terminal's input and output, so `admiral lock r -- tool --help` runs `tool --help`. It needs the running server for this `ADMIRAL_HOME` on `--port` (default 7420), finds it as `token rotate` does, and starts the command only once the unit is taken. A lock doesn't need the resource's check to pass. Without `--wait` a busy resource exits 75 at once with a message; with `--wait` it waits for a free unit. The holder shows in the dashboard and `GET /api/resources` as `admiral lock (pid N): <command name>`. `kill` (SIGTERM) sent to `admiral lock` goes on to the command; Ctrl-C and other terminal signals reach the command from the terminal, so `kill -INT <lock pid>` doesn't reach it (use SIGTERM). Exit status: the command's own (128 plus the signal number if a signal ended it), 127 if it can't be started, 75 busy, 2 usage, 1 for an unknown resource or no running server. The lock ends when the command ends. It also ends when the server stops or restarts: `admiral lock` then prints `admiral: lost the lock on <resource> (the server went away); <command> is still running without it` and leaves the command running, and its exit status is still the command's. `admiral lock` ignores SIGINT, SIGHUP and SIGQUIT. If it is killed with SIGKILL, the server notices the dropped connection and frees the unit at once, but the command keeps running without the lock. The server takes locks from this Mac only. |
| `admiral crew launch --name <name> --dir <dir> [--harness <h>] [--ship <ship>] [--role <role>] [--arg <value>]... -- <prompt>` | Starts a teammate (a crew boat, #152) in a new window of the ship's tmux session; the ship stays window 0 and the current window. `--name` is lowercase letters, digits and `-`, unique in the ship. `--dir` is any existing directory (it need not be in a search root). `--harness` defaults to the ship's and must be one the ship's fleet has a dock for (else exit 1). `--ship` is a session or display name; without it the command uses `ADMIRAL_SHIP`, and with neither it exits 2 with `not inside an Admiral ship`. Everything after `--` is the prompt, on the harness's command line. Admiral's hooks are on its command line like a ship's. `--arg <value>` is repeatable: each value is one argument for the harness, kept in order and placed after the dock's `args` and Admiral's hook flags, right before the prompt (`exe, dock args, hook flags, --arg values, prompt`). A value that overrides or disables Admiral's hooks is refused with exit 1, whether or not `ADMIRAL_AUTOPILOT` is set, and nothing is launched: claude `--settings`, `--bare` and `--safe-mode`; codex `-c`/`--config` for the key `hooks`, `hooks.*` or `features.hooks` (any spelling), `--disable hooks` and `-p`/`--profile`; copilot `--plugin-dir`; and a bare `--` on any harness (write it `--arg=--` to reach the check; `--arg --` is a usage error, exit 2). A trailing flag that takes a value (`--arg --model`) is the caller's to pair with its value. `--role <role>` names the teammate's part, such as `test-writer`; it is lowercase letters, digits and `-` (else exit 2) and is kept as the window option `@admiral-role`. Its environment is the ship's session environment with the chosen dock's `env` over it and Admiral's `PATH` (`$ADMIRAL_HOME/bin` first); the caller's own environment never goes in. `ADMIRAL_SHIP`, `ADMIRAL_REPORT` and `ADMIRAL_INBOX` are cleared, and so is any key the ship's dock sets that the chosen dock doesn't. A caller with `ADMIRAL_AUTOPILOT=1` may not name another ship with `--ship` (exit 1), and with no `ADMIRAL_SHIP` it may not use `--ship` at all, as any `crew` command. A name already in use exits 5. |
| `admiral crew send <name> [text] [--ship <ship>]` | Types the text into the crew boat and submits it: a bracketed paste, then Enter (after a 0.3 s pause for Codex, which drops an Enter that arrives with the paste). Without `text` it reads stdin, with a trailing `\r\n` trimmed. Text with a control character other than newline or tab exits 1. An unknown name exits 1; an anchored crew boat exits 4. |
| `admiral crew list [--json] [--ship <ship>]` | Lists the ship's crew boats. `--json` prints `[{name, harness, dir, state, launched, last_activity, role}]`. `state` is `anchored` whenever the process has ended (any exit code: a crew boat never sails off), `needs_you` when its pane says so, else `underway`; it is never `working`. `launched` and `last_activity` are RFC 3339, and `last_activity` is `null` until the crew boat's first hook. `role` is the `--role` it was launched with, `null` without one or if the stored option is not a valid role. |
| `admiral crew close <name> [--ship <ship>]` | Closes the crew boat's window, live or anchored. An unknown name exits 1. |
| `admiral completion zsh \| bash` | Completes ship names for `attach`. It does not complete crew names (that would take a second `admiral` call per shell). |
| `admiral service install \| uninstall \| status` | `install` writes the LaunchAgent `~/Library/LaunchAgents/dev.jasonbuffin.admiral.plist`, points it at the stable path (`$(brew --prefix)/bin/admiral` under Homebrew, never the versioned Cellar path), gives ships the `PATH` of your login shell as it is when you run `install` (run it again after changing `PATH`), logs to `$ADMIRAL_HOME/logs/admiral.log`, loads it and prints the "On other devices" URL; `uninstall` unloads it and removes the plist; `status` says `Service: not installed`, `installed, not loaded` or `installed, loaded` (from the exit code of `launchctl print`) and prints the URL (`No token yet; Admiral creates it the first time it starts.` when there is no token). |
| `admiral --version` | Prints `admiral <version> (<commit>)`. |

Every command that takes `--port` (`ships`, `token rotate`, `lock`, `inbox`, `orders`, `orders add`) takes its default from `ADMIRAL_PORT` when that is set, else 7420. A port is a decimal number from 1 to 65535: a bad `--port` exits 2, and a bad `ADMIRAL_PORT` is ignored. Admiral sets `ADMIRAL_PORT` (the port it listens on) in the chat session's environment, so AdmiralBot's commands find the server without `--port`; ships never have it.

`admiral hook <event>` and `admiral guard pretooluse` are internal: the hook bundles run them, and the usage text doesn't list them. `hook` also handles `SessionStart`, which only the chat's bundle registers (ADR 0019): it sets the pane option `@admiral-transcript` on `$TMUX_PANE` to `<unix nanoseconds> <source> <transcript_path>` and writes no state. It records nothing for a path that isn't absolute, doesn't end in `.jsonl` or holds a control character.

The answers file for `setup --answers` is JSON holding the same `fleets` object as `config.json`, in the order the fleets should have:

```json
{"fleets": {"work": {"name": "Work", "search_roots": ["~/code"],
                     "claude": {"env": {"CLAUDE_CONFIG_DIR": "~/.claude-work"}},
                     "codex": {}}}}
```

An `executable` left out is looked up on `PATH` (and `/opt/homebrew/bin`, `/usr/local/bin`, `~/.local/bin`) and written as the absolute path found, without following symlinks. The identity variable (`CLAUDE_CONFIG_DIR`, `CODEX_HOME`, `COPILOT_HOME`) is always written, with the harness's default directory when the file leaves it out; two fleets that leave it out share that default and are refused.
