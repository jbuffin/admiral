# API

The HTTP and WebSocket shapes a client reads. Every route is also served under `/api/v1/...` and `/ws/v1/...` (see `docs/agents/codebase/api-versions.md`). The bridge sockets are in `docs/bridge-protocol.md`.

## Ships

### `GET /api/ships` (alias `GET /api/v1/ships`)

`{"ships": [...], "home": "..."}`: the ships, and the id of the home they belong to. Each ship is also in the WebSocket `{"type":"ships","ships":[...]}` message, which is sent on connect and again whenever any ship's fields change, its `tail` included.

A ship carries `worktree`, the absolute path of its own worktree under `$ADMIRAL_HOME/worktrees/<session>`, while that directory exists, on a live and on a moored ship alike; it is omitted when the ship works in `dir` itself (a skill ship, or one whose worktree is gone). A quick or drafting ship's `dir` stays the engineer's checkout, so a client that opens the folder a ship works in prefers `worktree` over `dir`.

A ship also carries `origin_repo`, the `owner/repo` of the `origin` remote of the checkout it works in (its `worktree` when it has one, else its `dir`), on a live and on a moored ship alike. Only github.com remotes count; the field is omitted when the ship has no `dir`, the checkout has no `origin`, or the origin is not on github.com. `repo` is unchanged: the folder's name. The server reads each directory's origin with `git` once and keeps the answer for five minutes, so a remote added later shows up within that time. A client groups ships by the repo they work in from this, the repos of their `prs` and their order `url`.

A ship AdmiralBot launched also carries `via` (`"admiralbot"`); the engineer's ships omit it. A request that carries an actor token sees only its fleet's ships (see "AdmiralBot's requests").

A ship carries `launched` (RFC 3339), the stamp of its latest launch, which a wake or a Hand to Commodore relaunch resets, and `first_launched`, the stamp of its first launch, which they never move. A ship or moored record from before `first_launched` was kept serves its `launched` there; `first_launched` is absent only when both stamps are empty. The chat links a ship's name in an AdmiralBot reply when AdmiralBot launched the ship (`via`), it is in the chat's fleet and its `first_launched` is at or before the reply.

A ship's `url` is its issue, or the pull request or GitHub stack it was launched to review (see `reviewing` below). A ship launched without an order gets its `title` and `link` once its first prompt is known, whether it came with the launch or was typed later: `link` is the main link of the prompt (the only one, or the one the titler picked), and `title` is, in order, the GitHub title of `url` or `link` when it is a pull request or issue on one of the fleet's GitHub hosts, Claude Code's own title for the session, the titler's, or the prompt's first line without its links. `titling` is true while that is worked out and omitted otherwise. Unlike `url`, `link` claims nothing. The title and link are set once: an order's ship and a later round keep the ones they launched with. A ship that holds several issues (a slice) also carries `issues`, every issue URL in order with `url` the first; a single-issue ship omits `issues`. The moored record keeps the list, so a moored slice ship carries it too.

A live ship also carries `open_prs`: the PRs it carries that the last poll saw `OPEN` (see `carries_prs` below), then the PRs in its report that GitHub confirms open on the fleet's host and routed to its fleet, each URL once; omitted when there are none. The report half is checked as below; the carried half is read from the poll's state, so it adds no GitHub call here. The server checks GitHub only when the report file's modification time or size changes, never while serving this request, so a ship that just wrote its report shows `open_prs` a moment later. A check GitHub does not answer is retried later with a growing wait (30 s, doubling to 4 min), the report unchanged. When the ship's turn ends (needs you, reason `stop`) and its report's `result` is `done` with at least one open PR, and it is not returning, the server moors it without a request (only a `done` report triggers this, whatever the ship carries): it appears as `moored` with its `prs`, and the outcome log gets `moored`, then `ended` (signal `KILL`).

A moored ship has `status` `moored` and no tmux session: it is listed from its record in `$ADMIRAL_HOME/moored/`, with `prs`, `moored_at` (RFC 3339), `polled_at`, `stale`, `no_resume` and `waiting`, which no other ship carries. `waiting` is a string, present while a feedback round is due and has not started: `Waiting for room under the cap`, `Waiting for <resource> (busy|missing|pending)`, `Waiting for the current wake to finish`, `Waiting for Admiral's terminal host`, or `Can't wake: <the refusal>` for one that a later poll won't clear. It clears when a poll answers and does not decide to wake, on a successful wake and when the mooring ends; a poll that fails to reach GitHub keeps it. `prs` is a list of `{url, state, review, checks, mergeable, conflicts, ready}`, plus `author` and `reviewing`, and `behind` and `failing_checks` on an `OPEN` PR with that merge problem, and `merge_reasons`, and `feedback` and `answer` on a PR that has new feedback (below): `state` is `OPEN`, `MERGED` or `CLOSED` (a PR GitHub answers NOT_FOUND for counts as `CLOSED`; a NOT_FOUND on its repository says nothing about it, so its ship stays moored and `stale`); `review` is GitHub's `reviewDecision` (`APPROVED`, `CHANGES_REQUESTED`, `REVIEW_REQUIRED`, or `""` for none); `checks` is the status check rollup (`SUCCESS`, `FAILURE`, `ERROR`, `PENDING`, `EXPECTED`, or `""`); `mergeable` is `MERGEABLE`, `CONFLICTING` or `UNKNOWN`; `conflicts` is true only for an `OPEN` PR that is `CONFLICTING`; `behind` is true only for an `OPEN` PR whose merge state is `BEHIND` under a base that requires up-to-date branches, and `failing_checks` lists the names of the failing checks of the repo's own (an Actions workflow's check run, or any check or status the base requires) on an `OPEN` PR, both omitted when false or empty; `merge_reasons` lists why GitHub won't merge an `OPEN` PR that is not `ready`, as codes in this order (omitted when ready or not open): `draft`, `behind` (merge state `BEHIND`, whether or not Admiral read a strict base, so it can hold when `behind` is absent), `conflicts`, `checks_failing`, `checks_pending` (a pending check while the merge state is `BLOCKED`), `changes_requested`, `review_required`, `unknown` (GitHub is still working it out) and `held` (`BLOCKED` with none of the rest to explain it, so another rule of the base). It is everything GitHub would refuse a merge for, not only the merge problems a ship can fix; `conflicts_with_base` is the base branch (`main`) the stack as a whole conflicts with, on the top PR of a stacked or chained ship only when Admiral's whole-stack check found it, served whether or not a Fix offer exists (the same answer as `fix.problems[].conflicts_with_base`); `author` is the PR author's login, present once a poll has answered for it, and `reviewing` is true for a PR the ship reviews, both omitted otherwise; `ready` is true when the PR is `OPEN`, `APPROVED`, its checks are `SUCCESS`, it is `MERGEABLE` and its merge state is not `BLOCKED`, `BEHIND`, `DIRTY` or `DRAFT`, so a repository with no required review or no checks never reads ready. `feedback` is the number of waking events the last poll found for an `OPEN` PR that are newer than the PR's cursor, or newer than the mooring when it has none: a review that requests changes or comments with a body, a comment, or a CI failure, conflict or behind-base condition, as the automatic feedback round would hand them, and without waiting for its debounce. A stranger's events and the viewer's own replies do not count, and nor does thread resolution. `answer` is, when `feedback` is above 0 and the ship has a valid resume text, the exact prompt Answer review sends: `<resume> feedback round <round+1> on <PR url>`. Both are left out when 0 or empty, on a merged or closed PR, before the first poll answers, and on a ship that is not moored. Every other key is always served: before the first poll answers a PR has its `url`, `state` `OPEN`, empty chips and `conflicts` false. `polled_at` (RFC 3339) is the last poll that answered, absent before one has. A ship that moors from a live ship keeps that ship's last poll when it was not stale and answered every one of its PRs, so its chips, authors and `polled_at` show before the first moored poll. `stale` is omitted while false and true when the latest poll failed to reach GitHub: the chips are the last known ones, and a failed poll never ends mooring. `no_resume` is omitted while false and true when the record has no valid resume text (`moor.ValidResume`): a hand wake then starts the ship bare, and no feedback round can start it. A moored ship also carries `fix` while a merge problem stands on an `OPEN` PR it authored (a PR it only reviews never counts) and it has a valid resume text: `{pr, stack?, command, problems: [{pr, conflicts?, behind?, failing_checks?, conflicts_with_base?}]}`, where `pr` is the lowest such PR, the one the round is on, `stack` is true when the round covers more than one PR (every answered `OPEN` PR the ship authored, whether or not it has a problem; omitted otherwise, and the client's Fix PR or Fix stack follows it), `command` is the exact prompt `POST /api/ships/<session>/fix` sends (`<resume> feedback round <round+1> on <pr>`) and `problems` lists each PR with a merge problem, lowest first; `conflicts_with_base` is the name of the stack's base branch, on the stack's top PR only, when every layer is `MERGEABLE` but the top does not merge cleanly into that base as a whole (Admiral checks this itself, for a stacked or chained ship, in its own bare clone, since GitHub only answers per layer; a check that cannot run says nothing); it is omitted otherwise, and refreshes with `feedback`. A moored ship also carries `stack_ready` (the ship has at least one `OPEN` PR, every `OPEN` PR is `ready`, and the stack does not conflict with its base as a whole (`fix.problems` `conflicts_with_base`); `MERGED` and `CLOSED` PRs are skipped; omitted while false), `ready_up_to` (the URL of the last `ready` `OPEN` PR, in the order of `prs`, before the first `OPEN` PR that is not `ready`; omitted when the lowest open PR is not) and `merge_method` (the repository's default, `merge`, `squash` or `rebase`, asked of GitHub once per repository and fleet; omitted until a poll has it). Its `session` is its slug, `dir` its checkout, `crew`, `subagents` and `agents` empty and `launched` the stamp of its last launch or wake (empty for a record written before the stamp was kept) and `first_launched` the stamp of its first launch (`launched` for a record from before that stamp, so absent when that is empty too).

A ship whose `url` is a pull request URL, or a stack URL (`https://<host>/<owner>/<repo>/stack/<N>`), on the fleet's GitHub host and routed to its fleet *reviews* the open PRs there whose author is not the fleet's `gh` user: it carries each of them in `prs` with `reviewing` true, whatever their creation time, and a stack's open layers join bottom first. A free-text launch (no source) names its PRs in its launch text, the note and the text: every PR URL there on the fleet's GitHub host, routed to its fleet, is judged the same way at launch, so a ship launched on a PR shows it in `prs` at once, whether the text is only the URL (a Commodore launch included), the URL among other words, or in the note; a `/files` tail is dropped. A source order's text is not read for PRs. A launch PR or PR order URL the fleet's user opened, and a stack's open layers the fleet's user opened, are carried without `reviewing`, and one that is closed or merged is not carried. GitHub is asked about the order URL again until every PR answers, up to three failed asks, and once more after a restart; a woken ship keeps the role of the record it was moored with; a stack GitHub does not have, or a PR that is not open, ends the check at once. The role is kept on the session (`@admiral-reviewing`) and the moored record (`reviewing`, a subset of `prs`). A ship moors when its turn ends with a `done` report even if the report lists no PRs, as long as a PR of its launch order (a launch or order PR, or a stack's layer) is open, whether it reviews it or opened it, carried PRs first in their `prs` order; a PR the ship only printed does not moor it; a moored ship never wakes or proposes a wake for a reviewed PR, so its review activity raises nothing (see `responded` and Re-review below) and its reviewed PRs carry no `feedback` or `answer`, and Merge and Don't follow reviews answer `409` for a ship that reviews any PR, as Answer review does for a reviewed PR.

A reviewed PR in `prs` also carries `responded` (true or omitted) when its author answered the fleet user's review. The rule: the PR's head commit is no longer the commit of the fleet user's latest submitted review (a `PENDING` or `DISMISSED` review doesn't count, and a review GitHub names no commit for never reads as pushed past; GitHub doesn't say who pushed, so any new head counts), or the author commented in a review thread the fleet user commented in, after both the fleet user's last comment there and the fleet user's latest submitted review (the same `PENDING` and `DISMISSED` filter), so a new review by the fleet user clears both. A top-level PR comment never counts and logins compare case-insensitively. The poll reads the last 20 reviews and the last 20 review threads with their last 10 comments, so the fleet user's comment in a long or old thread can fall outside it, and the author's reply there reads as not responded; on a busy PR the fleet user's own review can fall out of the last 20 reviews as well, and then the push rule reads as not responded. A stack has no field of its own: it responded when any of its reviewed layers did. `responded` raises no wake and no proposal. A live ship keeps it until a poll shows its new review.

### `POST /api/ships/<session>/rereview`

Re-reviews a moored reviewing ship: the same ship, under the same name, is woken by hand (counted toward `max_ships` like `POST .../wake`, never blocked by it) with the prompt `<mark><skill> <url>`, where the skill is the Commodore the wake finds for the ship's harness and checkout, as for a fresh launch (`/commodore <url>`; `/jasonbuffin:commodore <url>` for a plugin install; `$commodore <url>` on Codex). Body: `{"url": "<url>"}`. The `url` must equal, byte for byte, one of the ship's reviewed PRs, or its order URL when that is a stack URL and the ship reviews at least one PR; the launch text is that string. Anything else is `400`. A ship not launched as Commodore, a live ship, or one already waking is `409`; an unknown ship is `404`. It needs no resume text and does not require `responded`. The round keeps the ship's role and the order URL. The `woken` outcome has `by` `"hand"` and `pr` set to the `url`. Answers `201 {"ship": {...}}`. Engineer only: AdmiralBot gets `403`. Also served under `/api/v1/`.

A running ship (any live ship, not only a woken one) carries the PRs it or its crew boats opened: `prs` (the moored shape above), `polled_at` and `stale` appear once it carries one, and `carries_prs` is true while at least one of them is `OPEN`. The poll that serves moored ships asks GitHub about each PR URL that appears in a tool result of the ship's or its crew boats' transcript, and the ship carries it when the fleet's `gh` user opened it at or after the ship's launch. A candidate counts only on the fleet's own GitHub host and for a repository the fleet routes to, with a number that has no leading zero and fits in 31 bits; at most 20 fresh ones are asked per ship per poll. The fleet's poll is one query for the moored and carried PRs and, when a ship has fresh candidates, a second for those alone, so a candidate GitHub cannot answer never makes a ship or the fleet `stale`. A candidate GitHub does not find, or whose query fails three times, is dropped for that launch. Each PR a ship confirms is also kept on its session, so an Admiral restart keeps it. A PR the ship names in its report is not judged this way. A merged or closed PR stays in `prs` with its state but no longer counts for `carries_prs`. `stale` is set only when a PR the ship already carries goes unanswered. A ship woken from its mooring carries its record's PRs at once, before any poll, and keeps them beside the new ones. When the ship exits cleanly, the PRs it carries that are open are checked against GitHub again, with the report's, and the ones still open on the fleet's host are moored with it; if GitHub cannot be reached, the last poll's open PRs stand.

### `GET /api/ships/<session>/pr?url=<PR URL>`

Reads one PR the ship carries, fresh from GitHub through the ship's fleet, with one query and a 15 second limit. It serves running and moored ships; the PR must be one of the ship's `prs`. Response `200` with `{number, url, title, author, reviewing, body, state, draft, head, base, default_branch, review, checks, mergeable, merge_state, failing_checks: [{name, url}], reviews: [{author, state}] (the review history in order, as GitHub recorded it, not folded to one per author), requested: [{login, bot}], threads: [{path, line, resolved, comments}], comments: [{author, body, url, created_at}], stack, answer_all}`, where an author is `{login, bot}`, `reviewing` is true when the ship reviews the PR and `stack` is `{number, size, base, url, entries: [{position, number, url, state, head}]}` or `null`. `default_branch` is the repository's default branch (`""` when GitHub gives none), which is not the PR's `base`. `body` and comment bodies come whole; the lists are capped: 20 reviews, threads, comments and requests, 10 comments per thread, and only the first 50 check contexts are read for `failing_checks`, and `stack.entries` holds at most 50. `answer_all` is the exact command Answer all reviews would send, and is left out unless the ship is moored, its `resume` starts with the Commodore skill (`/commodore`, `$commodore` or `/plugin:commodore`), the `stack` holds exactly the ship's PRs, more than one of them is `OPEN` and every `OPEN` one has `feedback`; the poll's stored answers decide, so no PR's detail reads GitHub twice, and every PR of the stack carries the same one. `404`: no such ship, a session that is not a ship, an anchored, sailing-off or exited ship, or a PR the ship does not carry. `502`: the fleet has no GitHub access, GitHub failed or did not answer in time. AdmiralBot may not call it.

### `POST /api/ships/<session>/pr/rerequest`

Asks GitHub to request another review from someone who already reviewed a PR the ship carries (the PR tab's Re-request review). Body: `{"pr": "<PR URL>", "login": "<GitHub reviewer's login>"}`. The server reads the PR fresh from GitHub and offers the request only where GitHub's PR page does: the login has a submitted review (approved, changes requested, commented or dismissed; an unsubmitted `PENDING` draft does not count), is not in the PR's `requested` now, and is not the PR's author. The request keeps the requests already there. Answers `200 {"requested": "<login>"}`. `404`: no such ship, a ship that carries nothing, or a PR the ship does not carry. `400`: the body is not JSON. `409`: the rule above does not offer it (an empty login included); GitHub is not called. `502`: the fleet has no GitHub access, the fresh read failed, or GitHub refused the request; `error` is GitHub's own message. The whole request (the fresh read, the lookup of the node ids and the mutation) has a 45 second budget, and the web client waits 60 seconds; a request that outlives the budget answers `502` with a message that says the result is unknown, so look at the PR on GitHub before asking again. A refusal found while looking up the ids (a reviewer GitHub's API cannot request, which is neither a User nor a Bot, or a login whose review is outside the last 20 the lookup reads) also answers `502`, with a message that names the login. A login of `ghost`, the placeholder for a deleted user, is refused with `409` like an empty one. Engineer only: AdmiralBot gets `403`.

Each boat in a ship's `crew` also carries `role` and `conversation` (see "A crew boat's conversation").

`subagents` and `agents` are always present (`[]` when empty) and come from the harness's hooks, kept on the ship's pane. `subagents` lists only the running subagents and agent-team teammates, which is what the classic view shows as deck crew. `agents` lists every stored entry, running or finished, for the new shell's Agents tab: `{id, type, start, kind, end}`.

- `kind` is `subagent`, `teammate`, `shell` (a background Bash) or `monitor` (Claude Code's Monitor). An entry stored before kinds existed has no `kind` and reads as `subagent`.
- `start` and `end` are RFC 3339. `end` is absent while the entry runs. Claude Code reports background shells only at a `Stop`, so a shell's `start` means "first seen by Admiral".
- A `shell` or `monitor` entry carries only its id, kind and times: `type` is `""` and no command, description or output is stored.
- Running and finished entries together stay within 64. A new entry on a full list drops the finished entry that ended first; when all 64 are running the new entry is refused.
- A finished entry stays until the lead session starts anew (Claude Code `startup` or `clear`, Copilot `new`; `resume` and `compact` keep it) or the pane goes. A moored or dead ship serves `agents: []`.

`tail` is always present, a string of one line and at most 200 characters, `""` when nothing is readable. It comes from the ship's conversation, never from the terminal. Of the conversation's pending questions, tool calls and assistant items, the latest one decides:

- a pending question: its text;
- a tool call: its summary line, or its name when it has none;
- assistant text: its first non-empty line.

A pending question wins only while it is the latest of these, so a question an interrupted turn left pending does not pin the tail. Answered questions and every other item (user, turn end, compaction, notice) are skipped. Only Claude Code, Codex and Copilot ships have a conversation adapter: a ship with no transcript yet and one whose transcript cannot be read have `tail: ""`.

### `POST /api/moored/refresh` (alias `POST /api/v1/moored/refresh`)

Asks the poller to poll every moored ship's PRs now and answers `202` at once. A kick during a poll joins the next one, so polls never overlap. Admiral also polls every 2 minutes (`ADMIRAL_MOOR_POLL`).

### `POST /api/ships/<session>/dismiss` and `/unfollow`

Dismiss ends an anchored ship or a moored one. A moored ship's record goes, its name is free and one `unmoored` outcome with reason `dismissed` is written; the answer is `200 {"dismissed": "<session>"}`. `unfollow` (Don't follow reviews) ends a moored ship the same way with reason `unfollowed` and answers `200 {"unfollowed": "<session>"}`. An unknown ship, or one already ended, is `404`; a live ship that is not moored gets the `409` Dismiss gives a ship that is not anchored. `unfollow` is also `409` for a ship that reviews a PR, which has no reviews to stop following.

### `GET /api/ships/<session>/stack`

The ship's PR shape for the stack bar, read fresh from GitHub through the ship's fleet with one detail read per PR and a 15 second limit. It serves running and moored ships (the ships `GET /api/ships/<session>/pr` serves). Response `200 {"shape": "stacked|chained|independent|mixed|none", "stack_number": n, "prs": ["<url>", …]}`. `prs` is bottom to top for `stacked` and `chained`, and in the ship's own order otherwise; `stack_number` is present only for `stacked`. The shapes are those of Merge below. `none` (with `"prs": []`) means the ship carries no PR. A single PR is `independent` when it is based on the default branch and `mixed` otherwise, and `stacked` when it is the only entry of a GitHub stack. Errors: `404` no such ship (or an exited, anchored or sailing-off one); `502` the fleet has no GitHub access, or GitHub failed. It needs no merge token.

### `POST /api/ships/<session>/update-branch`

Update branch: the engineer brings a moored ship's PR up to date with its base. The body is `{"pr": "<url>"}`, one of the ship's PRs. It takes the same `X-Admiral-Merge-Token` and origin check as Merge (a missing or wrong token answers `403` and runs no `gh`), AdmiralBot may not call it, and it holds Merge's per-ship slots, so an update, a merge, a stack link and a wake of one ship never overlap. It works whether or not the ship can resume.

Admiral reads the PR fresh and runs `gh pr update-branch <url>` once through the fleet's token: GitHub's merge-method update, never `--rebase`, so the head keeps its commits. It writes no outcome and asks for a poll. `202` with `{"updated": true}`. Errors: `400` the PR is not the ship's; `403` as above; `404` no such ship; `409` the ship is not moored, is waking, has a merge or update under way, reviews a PR, its fleet has no GitHub source, or the PR is not open and behind its base or is a layer of a GitHub stack (a stack is fixed as a stack); `422` the PR is not on the fleet's GitHub host; `502` gh's own message; `504` the update ran past gh's limit and its result is unknown (a poll is asked for).

### `POST /api/ships/<session>/ready-for-review`

Mark ready for review: the engineer takes a ship's draft PRs out of draft, one PR or a whole stack. The body is `{"prs": ["<url>", …]}`, one or more of the ship's own PRs, bottom to top. It takes the same `X-Admiral-Merge-Token` and origin check as Merge (a missing or wrong token answers `403` and runs no `gh`), AdmiralBot may not call it, and it holds Merge's per-ship slots, so a mark, an update, a merge, a stack link and a wake of one ship never overlap. It works on a moored ship and on a live one, and whether or not the ship can resume. It merges nothing and changes no branch.

Admiral first checks the whole request and, if any check fails, runs no `gh` at all. It reads each PR fresh, so a PR that is already ready for review is skipped. Then for each PR in the order given it runs `gh pr ready <url>` once through the fleet's token for a draft, and keeps going after one fails. It asks for a poll. `200` with `{"results": [{"url", "outcome", "error"?}, …]}`, one per PR in request order. `outcome` is `marked_ready`, `already_ready_for_review` (no `gh` call) or `failed`; a failed result's `error` is gh's own message, or, when the call ran past gh's limit, a line saying the result is unknown until the next refresh. Errors, all before any write: `400` the body is not JSON, names no PR, names one twice or names one that is not the ship's; `403` as above; `404` no such ship; `409` the ship is waking, has a merge, update or mark under way, reviews a PR, its fleet has no GitHub source, or a PR is not open; `422` a PR is not on the fleet's GitHub host; `502` GitHub could not be read.

### `POST /api/ships/<session>/stack`

Stack on GitHub: the engineer makes a moored ship's chained PRs one stack on GitHub. It takes the same `X-Admiral-Merge-Token` and origin check as Merge (a missing or wrong token answers `403` and runs no `gh`), and AdmiralBot may not call it. It holds the same per-ship slots as Merge, so a link, a merge and a wake of one ship never overlap. The body is ignored.

Admiral reads the shape fresh and links only a `chained` one. It runs `gh stack link --base <branch> <n> <n> …` once through the fleet's token, with the numbers of the ship's PRs as GitHub answered them, bottom to top. `--base` is the bottom PR's base, the repository's default branch: without it gh-stack asks git for the default branch, which the empty folder has none of, and a different base would retarget the bottom PR. No other flag: `--open` would take drafts out of draft, and a branch name would be pushed. Every PR must be in the one repository `GH_REPO` names: PRs in more than one repository never read `chained`, so they are refused. Like Merge it runs in an empty folder of its own with `GH_HOST` and `GH_REPO` pinned, and reads no checkout: the ship's directory may be gone.

`200` with the shape read again after the link, the answer of the `GET` above, so a client can show `Stacked on GitHub · stack #n` with no further call (Merge answers `202` because its result is a poll away; the link is done when this answers). If GitHub's stack has not caught up the answer is still `chained`. Errors: `403` as above; `404` no such ship; `409` the ship is not moored yet (a running ship, or any ship that still has a session: stack after it moors), is waking, has a merge or link under way, its fleet has no GitHub source, it has fewer than two PRs, or its PRs are already a stack, independent or mixed; `422` a PR whose URL is not on the fleet's GitHub host, refused before GitHub is read; `502` GitHub or `gh` failed, with the message, and nothing else changes; `504` `gh` ran past 2 minutes, so the result is unknown, and a poll is asked for.

### `POST /api/ships/<session>/merge`

On top of the usual access control, on every path (local, LAN, tailnet), the request needs the header `X-Admiral-Merge-Token`, a random secret made when the server starts and served only as `<meta name="admiral-merge-token" content="…">` in the `/app/` page; a missing or wrong token, one from an earlier server process, or an `Origin` that is not the host answers `403` and runs no `gh`. This raises the bar from curling one URL to deliberately scraping the page; it is not a boundary against a local process that impersonates a browser.

The Merge act: the engineer merges a moored ship's ready PR. A ship that reviews any PR answers `409` before anything else: a review ship does not merge it. It runs only on this request, never from the poller, an order or an agent. The body is `{}` or holds `upTo` and `pr`, each one of the ship's PR URLs. Before it runs `gh`, Admiral reads the PRs to merge from GitHub again and refuses unless they are `ready` now. The merge method is the repository's default. It runs through the fleet's token, with no `--admin` or `--auto`, and reads no checkout: the ship's directory may be gone.

A ship with one PR runs `gh pr merge <url> --merge|--squash|--rebase` and needs no `pr`. A ship with more than one PR reads each PR fresh from GitHub, one detail call per PR, and sorts the ship into one of four shapes:

- **stacked**: every PR sits in the same GitHub stack and the stack's entries are exactly the ship's PRs (matched by number within the ship's repository). It merges whole: `gh stack merge <stack number> --yes --merge-method <method>` once. The stack number is the integer GitHub reported. `gh` runs in an empty folder of its own, removed afterwards, with `GH_HOST` and `GH_REPO` pinned to the fleet's host and the ship's repository. Every open PR must be ready; a layer that already merged or closed is skipped, so the rest of the stack merges (what GitHub keeps in a stack after a layer merges is not checked: if it drops the merged PR, the ship reads mixed and is refused). A stack with no open PR answers `409`. `upTo`, when given, must be the top of GitHub's stack (the highest `position`). Naming a `pr` is refused.
- **independent**: no stack, and every PR is based on its own repository's default branch. The PRs may be in different repositories. The body must name one with `pr`; only that PR must be ready, and it runs `gh pr merge <url>` as for a single PR. The ship stays moored until its last PR merges or closes.
- **chained**: no stack, but the PRs are in one repository and form one chain by base and head branch. Nothing merges: stack it on GitHub first.
- **mixed**: anything else, including PRs in more than one repository that are not all on their default branches, part chained and part independent, a PR based on another branch, or a stack that is not exactly the ship's PRs. Nothing merges.

`202 {"merged": ["<url>", …], "method": "squash"}` lists the PRs this request merged, all of a stack's or the one `pr`, and means `gh` exited 0. A `merged` outcome is written and a poll is asked for; the ship stays moored until the poll sees every PR `MERGED` or closed (a merge queue behaves the same way). When all of them merged, the mooring ends with `unmoored` reason `merged` and the ship wakes to return to port; when all closed, reason `closed`; with some merged and some closed, reason `prs_done`. Errors: `403` the merge token is missing or wrong; `404` no such ship; `409` the ship is live, is waking, has a merge under way, its fleet has no GitHub source, a PR to merge is not ready on GitHub now, the PRs are chained but not stacked, mixed, independent with no `pr` named, or stacked with a `pr` named; `400` `upTo` or `pr` is not one of the ship's PRs, `upTo` is not the top of the stack, or the body is not JSON; `422` a PR whose URL is not on the fleet's GitHub host, refused before GitHub is read (the argv URL is rebuilt from the parsed parts on that host); `502` GitHub or `gh` failed, including a failed read of a PR's detail, the message being the failure (for a failed merge everything `gh` printed on stdout and stderr, with the token redacted, escapes stripped and at most 4000 bytes, or `gh could not merge the pull request` when it printed nothing; a failed merge also writes one `admiral: ship <session>: merging stack <n>|pull request <n> failed: …` line to Admiral's log), and the ship stays moored; `504` `gh` ran past 2 minutes, so the merge's result is unknown, and a poll is asked for since it may have happened.

### `GET /api/editors` (alias `GET /api/v1/editors`)

`{"local": <bool>, "vscode": {"installed": <bool>}}`. `local` is true when this request comes from the Mac Admiral runs on (a loopback peer, no proxy headers, a Host of this Mac; the same test as the remote-access setting). `vscode.installed` says VS Code is on this Mac, found read-only by bundle id with Spotlight and then in `/Applications` and `~/Applications`, within two seconds; nothing is launched. It is always `false` for a request that is not local. The shell turns the answer into a `vscode://file/<path>/` link the browser follows, so Admiral opens nothing itself. A test build (`-tags e2e`) never looks at the machine: it answers `installed` only when `ADMIRAL_VSCODE_TEST=installed`, and `missing` otherwise.

### `POST /api/ships/<session>/wake` (alias `POST /api/v1/ships/<session>/wake`)

Wakes a moored ship by hand: the same ship, under the same name, starts a feedback round. Body: `{"text": "<optional>"}`. The prompt is the report's `resume` text as it is, then a space and `text` when there is any; no skill is prefixed again. A moored ship whose report gave no valid `resume` text (`no_resume`) wakes bare: `text` alone is the prompt, with no skill invocation, and with no `text` the harness starts with no prompt and waits for a message. The wake is a hand launch: it is not autopilot, counts toward `max_ships` and is never blocked by it, and it writes no feedback file (`answer-review` is the one hand launch that runs a feedback round and writes one). The round number is the record's `round` plus one. The ship keeps its fleet, harness, model, skill, checkout and resources; crew pins do not carry over. Answers `201 {"ship": {...}}`, the shape `POST /api/ships` answers. Errors: `400` for a body that is not valid JSON; `404` for an unknown or ended ship; `409` for a live ship, for a wake of the same ship already in progress, for a ship ended (Dismiss, Don't follow reviews, a merged PR) while its wake waited, and for a resource the ship holds that is busy; `503` while Admiral has not yet read its tmux sessions. A Dismiss that arrives once the wake is making the session is the one that loses: it answers `404`.

### `POST /api/ships/<session>/commodore` (no `/api/v1` alias)

Hand to Commodore on a live Claude ship (a scout is refused: `400`, `a scout cannot be handed on`): the same conversation continues as Commodore under the same name, fleet, harness and checkout. Body: `{"kind": "issue"}` or `{"kind": "other", "text": "<what to do>"}`; `text` is trimmed, at most 4 KiB and holds no control character but newline. Admiral keeps the hand in memory, as it was when the engineer asked (fleet, harness, checkout, conversation, launch fields and the ask), and marks the ship with the session option `@admiral-handing`: `queued` until its own turn ends (needs you, reason `stop`), when Admiral types the ask (file the design as an issue, or follow `text`, then write the issue URL or a file path to a ref file Admiral names) and sets `sent`. When the turn that ask started ends the same way, Admiral checks the ship still matches that entry (a changed harness, skill, fleet, checkout or conversation fails the hand, naming the field) and reads the ref. A ref is an issue URL in the checkout's `origin` repo, or an absolute path to a non-empty file under the checkout or the ship's folder in `$ADMIRAL_HOME/ships/`, symlinks resolved, and not the ref file itself; the resolved path is what Commodore is given. A good ref stops the ship (`stopped` with `"handed": true`, `ref` and `conversation`) and relaunches the conversation as Commodore with the ref as its order, a hand launch (`woken` with `"by": "hand"`, the round plus one) that counts toward `max_ships` and is never blocked by it. Effort is not kept on the relaunch. A bad or missing ref, a ship that changed, exited or was stopped before the hand finished, a failed relaunch, or a restart of Admiral during the hand (the mark is cleared) logs `handing_failed` with a `reason` and Admiral never asks again by itself. A ship being handed is not moored at its turn end, and `POST /api/ships/<session>/return` answers `409` for it. The outcome log gets `handing` (with `kind`) and then `handed` (`ref`, `conversation`) or `handing_failed`. Response `202 {"handing": true}`. `400`: a body that is not valid, a `kind` other than `issue` or `other`, or `text` that is empty, too long or holds a control character. `404`: unknown ship. `409`, each with its own message: the ship is moored or has exited; a hand to Commodore or Return to port is already under way; the harness is not Claude; the ship already runs Commodore; the ship is restricted or an outside event launched it, or Admiral could not read the trigger log to tell; its conversation is not bound to a transcript yet.

`GET /api/ships` shows a hand on the ship. `handing` is `true` while its pane carries the handing mark, from the request until the ship is relaunched or the hand fails; it is omitted otherwise. `hand_refusal` is the route's `409` message for a ship whose own options rule the hand out (`ship <session> runs on <harness>: only a Claude ship can be handed to Commodore`); it is omitted on a Claude ship. A restricted ship, one an outside event launched and one with no bound conversation are refused only by the route, as they cost the list a trigger-log read or two tmux calls per ship. `hand_failed` is the `reason` of a `handing_failed` record written for a ship that stayed live, and holds until the next hand starts; a failure after the ship was stopped leaves no live ship to carry it. It is kept in the session option `@admiral-hand-failed`. `drafting` is `true` on a ship launched as a drafting ship until Admiral follows a campaign from its ref, and omitted otherwise; a Hand to Commodore ends it. `drafting_notice` is the one line about the last campaign the ship named that Admiral did not follow, either the follow's own refusal (`No fleet owns acme/widgets, so Admiral can't read it`, `That campaign belongs to fleet <owner>, not <fleet>`) or `Ignored acme/widgets#21: this ship already follows acme/widgets#20.` for a later ref to another issue; it is omitted while there is none, and a later ref to the issue already followed adds none. The ship keeps running either way. Admiral reads the ship's `campaign-ref` file once at each turn end, when the ship anchors and when it sails off, never on every pass, and deletes the file after reading. Both fields live in Admiral's memory, so an Admiral restart drops them and the ship is no longer followed or reported. `skill_kind` is `commodore` on a Commodore ship, `skill` on a ship running a named skill and `none` on one with no skill; a moored ship carries the kind its moor record kept. It is omitted when the ship has no skill kind.

### `POST /api/ships/<session>/answer-review` (alias `POST /api/v1/ships/<session>/answer-review`)

Answers the new feedback on a moored ship by hand, started attended: on one PR, or on every PR of its GitHub stack. Body: `{"pr": "<PR url>"}`, which must be exactly one of the ship's `prs`, or `{"stack": "<stack URL>"}` (see below). The round is the one the automatic poll would start for the PR, without waiting for its debounce: Admiral writes the PR's waking events to `.admiral/untrusted/feedback-<round>.md` in the checkout, advances the PR's cursor and sets the round to the record's `round` plus one. The prompt is the `answer` the ships list shows for the PR: the report's `resume` text, `feedback round <round>` and the record's PR URL; nothing of the request's text reaches it. Unlike an automatic round it is a hand launch: it is not autopilot or unattended, counts toward `max_ships` and is never blocked by it, and its `woken` outcome line carries `by: hand` and `pr`. Answers `201 {"ship": {...}}`, the shape `POST /api/ships` answers. Errors: `404` for an unknown or ended ship; `409` for a live ship, a moored ship with no valid `resume` text, a PR with no new feedback now (the page was stale), and a wake of the same ship already in progress or one whose wake state changed meanwhile; `400` for a body that is not valid JSON, one with both `pr` and `stack` or neither, or a `pr` the ship does not carry, whatever its spelling; `503` while Admiral has not yet read its tmux sessions. A launch that fails answers the launcher's status and puts the wake state back; the feedback file stays and the next round of that number overwrites it. AdmiralBot gets `403`: only the engineer answers a review by hand.

### `POST /api/ships/<session>/fix` (alias `POST /api/v1/ships/<session>/fix`)

Fix PR and Fix stack: wakes a moored ship by hand, attended, for one feedback round on the whole ship. The body has no fields; nothing the page sends reaches the prompt or the feedback. Admiral decides from the stored poll answers and the wake state: the round covers every `OPEN` PR the ship authored, and it is on the lowest one with a merge problem. It writes every covered PR's merge problems (conflict, behind its base, a stack that conflicts with its base, each failing check by name) and the feedback waiting on any of them to `.admiral/untrusted/feedback-<round>.md` in the checkout, opens the round on every covered PR (cursors past the folded feedback, snapshots of the problems the round carries, so the automatic wake does not fire again for them) and sets the round to the record's `round` plus one. The prompt is the `fix.command` the ships list shows: `<resume> feedback round <round> on <PR url>`. It is a hand launch like `answer-review`: counted toward `max_ships` and never blocked by it, its `woken` line carries `by: hand` and `pr`. Answers `201 {"ship": {...}}`. Errors: `404` for an unknown or ended ship; `409` for a live ship, a moored ship with no valid `resume` text, a ship with no merge problem on its open PRs (including one that only reviews), a ship whose merge problems changed between the decision and the launch, and a wake of the same ship already in progress; `503` while Admiral has not yet read its tmux sessions. AdmiralBot gets `403`.

**The stack form, Answer all reviews.** With `{"stack": "<stack URL>"}` the ship starts one new Commodore run on the whole stack: the prompt is the `answer_all` the detail shows, the resume's skill token as the ship was launched with it, a space and the stack URL Admiral read from GitHub; nothing of the request reaches it. It is a hand launch like the PR form (attended, counted toward `max_ships`, never blocked by it) and its `woken` line carries `by: hand` and no `pr`. The round is the record's `round` plus one, once, and every `OPEN` PR's cursor advances past its feedback. It writes no feedback file, because the new run reads GitHub itself; a `feedback-<round>.md` left by an earlier failed PR launch stays in the checkout, and nothing names it. Errors, in the order they are reached: `404` and `409` for the ship, as above; `400` for a bad body; `409` when the resume's skill is not Commodore; `502` when the fleet has no GitHub access or GitHub fails (the stack is read fresh from the ship's PRs); `409` when GitHub reports no stack or its layers are not exactly the ship's PRs; `400` when `stack` is not exactly that stack's URL; then the wake's own `409` (a wake in progress) and `503`; and `409` when, from the stored answers, fewer than two PRs are `OPEN` or one of them has no feedback.

### A stranger's proposal: `GET /api/inbox`, `POST /api/inbox/_admiral/<id>/launch` and `/dismiss` (also under `/api/v1`)

A stranger's feedback on a moored ship's PR is an Inbox item with `kind: "wake_proposal"`, `session: "_admiral"`, `name: "Admiral"` and a title `Wake <ship> for @<login>'s review?`. Its `wake_proposal` object is `{"ship": "<name>", "ship_title": "<the moored ship's title, left off when it has none>", "session": "<session>", "pr": "<url>", "login": "<login or ghost>", "events": [{"id", "kind", "url", "at", "body"}]}`. Each `body` is the event's text as GitHub gave it, cut to 4096 bytes; show it as plain text. A proposal holds one batch and is never rewritten; a later comment makes a new one.

`launch` takes `{}` or `{"events": ["<id>", …]}`, the event IDs the engineer was shown: a list that differs from the item's is `409`. It starts a feedback round for the PR, as autopilot, handing the ship the proposal's events in `.admiral/untrusted/feedback-<N>.md`. It is never blocked by `max_ships`. Answers `201 {"ship": {...}}` and writes the answer `{"launched": true, "ship": "<name>"}`. Errors: `404` for an unknown item, a ship no longer moored or an item that does not match the moored ship and what the poll proposed; `409` for an item already answered, a live ship, a wake in progress or a ship with no valid `resume` (the item stays); the rest as `POST /api/ships/<session>/wake`. `dismiss` takes `{}`, writes `{"dismissed": true}` and answers `204`; a second press is `409`. Remove from inbox on a proposal dismisses it. Neither brings the comment back.

### `POST /api/launch-orders/dirs` (alias `POST /api/v1/launch-orders/dirs`)

Body: `fleet`, `harness`, and either `source` and `order_id` (the server reads the order) or the `repo` and `text` the order would have. Answers `{"entries": [...], "selected": ..., "reason": ..., "clone": ...}`. The entries are the checkouts and search roots of the fleet, which include its `clone_root`. Each entry carries `remotes`, the identity (`host/owner/repo`, lower case) of each of its git remotes, empty when it has none.

`clone` is always present. It is `{"repo": "<host/owner/repo>", "path": "<target>"}` when the order's repo (else the first URL in its text) has no checkout in the fleet and gh can clone it, and `null` otherwise. `path` is `<clone_root>/<repo name>`, where `clone_root` defaults to the fleet's first search root. The folder name is the repo's name in lower case (`Acme/MyWidget` clones into `mywidget`). When `clone` is set, `selected` is `null` and `reason` is `"clone"`: launching clones the repo. When a file or folder already exists at `path`, `clone` carries `"exists": true`, nothing is preselected as a clone (`selected` and `reason` are as without a hint) and a launch there would be refused with 409, so a client can warn. Otherwise `selected` and `reason` are as before.

### `GET /api/launch-orders/skills?fleet=<key>&harness=<dock>&dir=<checkout>` (alias `GET /api/v1/launch-orders/skills`)

The skills a launch on that dock and checkout offers. Answers `{"mark": "/", "skills": [{"name": "tdd", "description": "...", "favorite": false}], "commodore": {"found": true, "name": "...", "state": "ok"}}`. `mark` is what the dock's harness types before a skill (`$` for Codex, `/` otherwise), `description` is `""` when the `SKILL.md` has none, and `skills` is `[]` when none is installed. `favorite` marks the engineer's favourite skills. `commodore` says whether the Commodore skill is installed there and under what name. `state` is what the dock's own identity (never the checkout) holds, compared with the minimum version Admiral knows (3.5.0, compared number by number, so 3.10.0 is above 3.9.1): `missing` (no Commodore plugin or loose skill in the identity; a project copy sets `found` but leaves `state` at `missing`), `ok` (at or above the minimum, or newer than Admiral knows), `outdated` (adds `installed` and `minimum`) or `unknown-version` (a loose skill, or a plugin whose manifest has no `version`). One example each: `{"state": "missing"}`, `{"state": "ok"}`, `{"state": "outdated", "installed": "3.1.0", "minimum": "3.5.0"}`, `{"state": "unknown-version"}`. `404`: unknown fleet. `400`: the fleet has no such dock, or `dir` is not a checkout or search root of the fleet. `409`: the fleet has no search roots.

### `POST /api/launch-orders/commodore` (alias `POST /api/v1/launch-orders/commodore`)

Engineer only: AdmiralBot's token is refused, and there is no MCP tool or CLI command for it. Installs or updates the Commodore plugin (`jasonbuffin@jbuffinskills`) in a dock's own identity by running the harness's plugin commands. Body: `{"fleet": "<key>", "harness": "<dock>", "action": "install" | "update"}`. The commands run with the dock's executable and environment and `$ADMIRAL_HOME/bin` first on `PATH`; `install` adds the `jbuffin/skills` marketplace unless the identity already has it, then installs the plugin, and `update` runs only the update command. After an `install` on Claude or Copilot that added the marketplace itself, with no Commodore plugin detected beforehand (a loose skill does not count), Admiral sets `extraKnownMarketplaces.jbuffinskills.autoUpdate: true` in the identity's `settings.json` and keeps every other key. An `update` never sets it, and Codex gets nothing.

Answers `200` with the dock's new state alone, as in the skills route without `found` and `name`: `{"state": "ok"}`. When the install worked but Admiral could not turn on auto-update (`settings.json` unreadable or not JSON), the answer is still `200` and carries a `warning` string beside the state, and the server logs it; the plugin is installed and only the `autoUpdate` key is missing. Or `{"error": "..."}` with:

- `502`: a command exited non-zero, timed out or its binary is missing. The body is `{"error": "...", "output": "<last 20 lines of the commands' output>", "commands": ["claude plugin marketplace add jbuffin/skills", "claude plugin install jasonbuffin@jbuffinskills"], "state": {...}}`. `commands` are the exact commands to run by hand, in order (`codex plugin add` replaces `install` on Codex, and an update is the one update command), and `state` is unchanged: `missing` after a failed install, `outdated` after a failed update;
- `404`: unknown fleet; `400`: the fleet has no such dock, a body that is not JSON, or an `action` other than `install` and `update`;
- `409`: `update` when the state is not `outdated`, or another request for the same harness and configuration directory is still running (two fleets sharing one directory take turns).

### `POST /api/ships` (alias `POST /api/v1/ships`)

Launches a ship. Body: `fleet`, `harness`, `skill` (`{"kind": "commodore" | "skill" | "none", "name": ...}`), `text`, `model`, `effort`, `autopilot`, `scout`, `resources`, `source` and `order_id` (a launch from an order; the server reads the order's text), and either `dir` (a checkout or search root of the fleet) or `clone: true` with no `dir`, and optionally `clone_repo`, the `host/owner/repo` the form showed. `crew` is a list of member names to pin, only on a Commodore launch (see below). A launch with `clone: true` derives the repo like the dirs route does, runs `gh repo clone <host/owner/repo> <temporary folder>` in the fleet's environment, moves the result to `<clone_root>/<repo name>` (lower case) and starts the ship there. The client never sends the target path. Only github.com and the host of a GitHub source the fleet has are cloned. `issues` (a list of GitHub issue URLs) goes only on a launch with no `source` (`400` otherwise; an order has its own issue): each must be an `https` issue URL on github.com or the host of a GitHub source the fleet has, and the ship keeps the normalised form. One issue claims that URL, two or more make a slice, one ship holding every claim with `url` the first. `stack: true` with `source` and an `order_id` naming one layer's order launches on that layer's GitHub stack: the ship's `url` and text are the GitHub stack URL the source served on the layer (never a client string), its `title` is `Stack #<N>`, and its `order_id` is the GitHub stack URL, so a second launch from any layer of the GitHub stack is refused unless `anyway` is sent. The order is not marked launched. `400` when the layer is in no GitHub stack. The ship then reviews the open layers whose author is not the fleet's `gh` user (see Re-review). The server sets `url` and `title`, never the client. `chat_message` (a chat message id, from the engineer's CLI or UI only) gives the launch the key `chat:<fleet>:<id>`, so one fleet's ids never meet another's. AdmiralBot never sends one: the server drops any it does send, and gives an actor's freeform launch (no order, no issue) the key `chat:<fleet>:<session>-<stamp>`, where `<session>` is the chat session's nonce and `<stamp>` the time of the chat's latest prompt, which the chat's `UserPromptSubmit` hook records, so a message typed in the terminal counts too. One message is one key; the next message, or a new chat session, is a new key. `anyway: true` gives the launch a fresh key instead, so one message can launch twice. An order's key is `<source>:<order id>` and an issues launch's key is its set of issues (`this issue already has a ship` for any overlap, in any order or spelling). A key is held by any listed ship of any status (a moored one included), a pending launch or a launch in flight, and the ship keeps it across an Admiral restart and mooring; it frees when the ship is dismissed or sails off. A woken ship never collides with its own key. On the engineer's own launch from an order or an issue, `anyway: true` also skips the order key and the issue claim, so a second ship can start on an order or issue another ship holds (Launch another ship sends it); the launch is still refused with `409` while another launch is in flight on the same order or issue. The server ignores `anyway` on AdmiralBot's order or issue launch, which never gets past a key or claim another ship holds. The second ship records the same `source` and `order_id`. A launch with no order is freeform: `text` is its prompt and `skill` may name a skill, which the harness runs with the text as its argument (`/skill text`, `$skill text` on Codex). `model` and `effort` are empty for the harness's own default. Every harness takes any plain `model` name (letters, digits, `.`, `-`, `_`, `:`, never dash-led, with an optional `[1m]`-style suffix), whether or not the dock's model list holds it. Claude's `effort` is one of `low`, `medium`, `high` and `max`; Codex's `low`, `medium` or `high`; Copilot takes no effort, since it picks its own.

Answers `201 {"ship": ...}`, or `{"error": "..."}` with:

- `400`: a `crew` that pins on a launch whose skill is not Commodore, a name that is not a lowercase slug of at most 64 characters or is given twice (checked before any clone), a name no layer resolves, or a resolver error in any file of the layers, even an unpinned one (the message lists them); a `model` that is not a plain name or an `effort` the harness does not offer (the message names which), `autopilot` on a dock whose harness `admiral guard` does not cover (only Claude today) or whose guard probe has not passed in the fleet (the Inbox gets a notice, and a Check again in Preferences runs the probe), a `resources` name the config does not define, an `issues` entry that is not a GitHub issue URL (the message names it), `dir` and `clone` were both sent ("send dir or clone, not both"), no repo can be derived, or the repo is not one gh can clone (a host that is not GitHub, a name that starts with `-`, a dot name), or `source` is `campaign`, whose launches go through `POST /api/campaigns/<id>/launch`;
- `400` for `scout: true` (a scout is an autopilot ship that changes nothing, in the fleet's existing checkout): without `autopilot`, or with a skill other than `none`, `member`, `crew`, `issues`, `source`, `order_id` or `clone` (`a scout takes no <what>`); on a harness whose scout guard is not proven in the fleet (`autopilotgate.CheckScout`, which also needs the autopilot guard; only Claude has one), or in a fleet with no advisor (the autopilot check, with no Inbox notice), refused before any cap check, and the cap never applies to a scout. The ship's JSON carries `"scout": true` (omitted otherwise); its own end (needs you, reason `stop`) stops it with a `stopped` outcome marked `scout: true`, which reads as sailed, and it is never moored. A scout whose harness errors anchors as usual; a clean end sails off. A scout's session carries `ADMIRAL_SCOUT`, the resolved checkout path.
- `400` for `drafting: true` (a drafting ship drafts a campaign with the fleet's drafting skill): without `skill` of kind `skill`; with `clone` (it needs a `dir`); in a `dir` that is not a git checkout (it gets its own worktree); when no installed skill on the harness for the `dir` carries the name (the name itself, or its part after `plugin:`); or when more than one does, the reason then listing the names so a client can send the one it picked. A drafting ship runs With you whatever `autopilot` says, so the autopilot gate and cap never apply to it, and it runs in a worktree of the `dir`. Its launch text is the skill and `text`, then a line asking it to write the URL of the parent issue it files to `$ADMIRAL_HOME/ships/<session>/campaign-ref`. Admiral keeps which ships are drafting ships in memory, by session and the ship's first launch (`first_launched`), so a woken ship stays one, a successful Hand to Commodore ends it, and a later ship reusing the name is not one, clears any `campaign-ref` left in the ship's folder at launch, and sets the pane option `@admiral-drafting` for display only, since a ship can rewrite its own options. The invocation name that matched is the one typed, so a bare `wayfinder` held by one plugin runs as `plugin:wayfinder`.
- `409`: a resource in `resources` is held by another ship (`resource "db" is ...`), `autopilot` when the underway and needs-you ships are already at `max_ships` (`autopilot is at its cap of N ships`) unless AdmiralBot made the launch on the engineer's instruction, the repo already has a checkout in the fleet, a search root that is itself a checkout included (the message names it: launch there with `dir`), a folder already exists at the target, which is never touched, or `clone_repo` is set and differs from the repo the server derives ("the order's repo changed to X; reopen the form");
- `404`: the fleet is not found; `400`: the fleet has no such dock or no search roots, `dir` is missing, not a directory or not a checkout or search root of the fleet, a skill kind is unknown or a skill name is empty or holds whitespace, Commodore or the dock's executable is not found, or the command line is too long for tmux; `409`: the order already has a ship (`this order already has a ship (<name>)`; AdmiralBot's request, when the holder is in another fleet, gets `a ship in fleet <fleet>` in place of the name, for the order, the chat message and an issue alike; issue claims are machine-wide), the chat message already has one (`this chat message already has a ship (<name>)`), or its URL or any of its `issues` names a GitHub issue that any ship holds, listed in any status or still launching (`this issue already has a ship (<name>)`; the ship leaves the claim when it is dismissed or sails off); `503`: tmux is not on PATH;
- `502`: gh failed, the message holds its stderr on one line with the credentials of any URL in it replaced by `***`, and nothing is left behind;

### Launching as a crew member on `POST /api/ships`

`member` (a crew member name) launches the ship as that member, and only with `skill` `{"kind": "none"}` (Just launch); with any other skill, or sent next to `crew`, it is a `400`, as is a name that is not a lowercase slug of at most 64 characters (checked before any clone). Admiral resolves it over the same layers as pins plus the fleet's memory layer. The member's `harness` is a lock: a `harness` in the body that differs is a `400`, and the fleet needs a dock for the final harness. Its `model` goes after the dock's `args` and Admiral's own model flags, before any extra args, as `--model <m>` (`-m` on Codex), unless it breaks the model name rule (dropped, and the reason goes to the server log) or the dock's `args` already set a model (`400`); a `model` in the body next to a member's model is a `400`. The prompt is the member's instructions, its notes block (`### Every repo` and `### This repo (<owner/repo>)`, the repo read from the launch directory's `origin`), then `text`, joined by a blank line, empty parts skipped. A fix checker takes the body's harness and model and gets no instructions or notes; a member's `skills` are ignored. Warnings go to the server log, not the answer. A member no layer resolves (an ad hoc member is one: ad hoc is not a layer `member` reads), or a resolver error in any layer file, is a `400`.

### Pinned crew members on `POST /api/ships`

`crew` (a list of member names; empty or absent pins nothing) is the only way a launch pins members: the launch text is never read for them. Admiral resolves the names itself over the installed Commodore's `crew/` directory (beside its `SKILL.md`, empty when it has none), the fleet's crew directory `$ADMIRAL_HOME/fleets/<fleet key>/crew/` and the launch directory's `.commodore/crew/`, a later layer replacing an earlier member of the same name. It then writes a byte-exact copy of each pinned member's file as `<name>.md` into the ship's run layer, `$ADMIRAL_HOME/run-crew/<session>/` (0700), and gives the ship `ADMIRAL_RUN_CREW` with its absolute path. A launch with no pins has no `ADMIRAL_RUN_CREW`, whatever a fleet's `env` says, and a crew boat keeps its ship's value. The run layer is removed with the ship's report and inbox, and cleared when a ship name is reused.

A refusal for pins is a `400` before any session exists. One that comes after a `clone` launch has cloned (a name no layer resolves, a resolver error) leaves the clone in place, like any checkout.

### `GET /api/launch-orders/crew` (alias `GET /api/v1/launch-orders/crew`)

Query: `fleet`, `harness` and optionally `dir` (a checkout or search root of the fleet, checked as `POST /api/ships` checks it; without it the repo layer is left out, as for a launch that has not cloned yet). Answers `{"members": [...], "warnings": [...], "errors": [...]}`: each member is `{"name", "role", "pick-me-when", "layer", "harness"}` (`layer` is `built-in`, `fleet` or `repo`; `harness` is the lock, or `null`), `warnings` and `errors` are the resolver's diagnostics. When `errors` is not empty, `members` is empty and a launch that pins would be refused. A harness with no installed Commodore has an empty built-in layer, not an error. `404`: the fleet is not found; `400`: no such dock or `dir` is not in the fleet; `409`: the fleet has no search roots.

### `GET /api/ships/<session>/findings[?first_launched=<RFC 3339>]` (alias `GET /api/v1/ships/<session>/findings`)

A ship's kept findings, as the ship wrote them to `$ADMIRAL_FINDINGS`. Answers `200 {"ship": "<session>", "first_launched": "...", "fleet": "<fleet key>", "findings": "<markdown>"}`. `first_launched` (the ship card carries it) picks the voyage; without it the voyage with the newest first launch answers. A malformed `first_launched` is `400`; a ship with no kept findings, and a live ship that has not ended, is `404`. Both answers are JSON `{"error": "..."}`. Admiral keeps the findings when it writes the ship's `ended` record, so the route answers after that and survives the sail-off and a restart. A woken ship's later round that writes findings again replaces its voyage's copy; one that writes none leaves it. A file over 1 MiB, a link, a pipe or an empty one is not kept. A `lost` ship never writes `ended`, so its findings are not kept. A ship whose kept inbox is answered before its `ended` is written (about one observe pass after an auto-moor) has its findings file removed with its other files, so nothing is kept. First launch has one-second resolution, so a name reused within the same second of an earlier voyage's first launch shares its findings.

AdmiralBot (the actor token) may read this route, fenced to its fleet: only a voyage whose fleet is the token's answers, and a voyage of another fleet, an unknown ship, a ship with no kept findings and a voyage with no fleet all give the same `404` "no findings are kept for this ship". Without `first_launched` it reads its own fleet's newest voyage of that name, so a name reused across fleets never shows the other fleet's findings. The web reads every fleet's. `read_findings` returns this route cut at 8,000 characters.

The `ended` outcome carries `findings` on every ship: it is per round, true only when this round's findings were kept. "Has findings" means the store: a caller asks the route or the store, not the latest `ended`. A scout whose voyage holds no kept findings, from this round or an earlier one, also carries `"result": "failed"`; `report` is as the ship left it, and a scout with findings has no `result` field. A store error leaves `result` off and is logged. `GET /api/outcomes` and `read_outcomes` show both.

### `POST /api/ships/<session>/next` (alias `POST /api/v1/ships/<session>/next`)

Types the next prompt into a ship whose turn has ended, as AdmiralBot's tool `next_prompt` does. Body: `{"text": "..."}`. Answers `200 {"typed": true}` and records a `resumed` outcome with `"live": true`, and `"via":"admiralbot"` for an actor. Errors: `400` for text with a control character, an empty text, one over 16 KiB, and, for an actor, text whose first non-space character is `/` or `!` (AdmiralBot may give a ship a prompt, never a harness command; the engineer's text is unchanged); `404` for an unknown ship; `409` for a ship that is not underway or needing you, one that is mid-turn, and a moored ship (wake it instead).

## Sending to a ship

`GET /api/version` lists the `ship-input` capability when the server has these routes. They are unversioned in the code; `/api/v1/...` reaches them too.

- `POST /api/ships/<session>/messages` with `{"text": "..."}` pastes the text into the ship's pane as one bracketed paste and presses Enter, then clears needs you as `input-seen` does. The text is cleaned first: CRLF and lone CR become LF, control characters other than LF and tab are removed, and the edges are trimmed. Response `{"sent": true}`.
- `POST /api/ships/<session>/crew/<name>/messages`: the same for a crew boat, which clears the boat's needs you.
- `GET /api/ships/<session>/skills` and `.../crew/<name>/skills` list the skills the message box offers: those the ship's or boat's own harness has installed, read in its own checkout (a worktree too) with its dock's identity variables. Response `{"mark": "/", "skills": [{"name": "tdd", "description": "..."}]}`, sorted by name; `mark` is what the harness types before a skill (`$` for Codex, `/` otherwise) and `description` is `""` when the `SKILL.md` has none. `404`: unknown ship or boat.
- `POST /api/ships/<session>/seen` with `{"stop_since": "..."}` marks the ship's stop that began at that `stop_since` as looked at. The pane still needs you, so its question can be answered and its ended turn resumed, but the ship carries `"seen": true` and the new shell leaves it out of the inbox and the Needs you group until a new stop begins. A body for a stop that is over, or a ship that does not need you, changes nothing. Response `{"ship": {...}}`. `404`: unknown ship.
- `POST /api/ships/<session>/interrupt` and `.../crew/<name>/interrupt` press Escape in the pane. They don't clear needs you. Response `{"interrupted": true}`.
- `POST /api/ships/<session>/stop` ends a ship, live, anchored or moored, and its crew boats with it. A moored ship ends as Dismiss ends it, with one `unmoored` outcome of reason `stopped`; its PRs stay open on GitHub. A live ship's tmux session is killed and the outcome log gets `ended` (signal `KILL`, no exit code) then `stopped`; an anchored ship gets the `ended` it already has, then `stopped`. The ship leaves the list. Response `{"stopped": "<session>"}`. An optional body `{"moor": true}` moors a live ship instead: Admiral checks GitHub at once for the PRs it has open (its carried PRs and its report's, each once; if GitHub does not answer, the carried PRs the last poll saw open stand), writes the moored record, then ends the session as above (`moored`, then `ended`; no `stopped`, `via` stamped on `moored` for AdmiralBot). Response `{"moored": "<session>"}`. `409`: the ship has no open PR (none carried and open, none listed by the report; GitHub failing past the retry window also gives 409 unless carried PRs stand, because then Moor goes ahead with the ones the last poll saw open); the ship is untouched. `500`: the record cannot be written (the ship stays live), or the session would not end (the record stays, and a retried Moor ends it). `400`: the body is not valid JSON. On an anchored ship the body is ignored.
- `POST /api/ships/<session>/return` starts Return to port (ADR 0036) on a live ship and marks it with the session option `@admiral-returning`: `queued` until its own turn ends (needs you, reason `stop`), when Admiral types the clean-up prompt (`ReturnPrompt` in `internal/ships/return.go`) and sets `sent`; when the turn that prompt started ends the same way, the ship is stopped as by `stop`, with `stopped` carrying `"returned": true`. A turn that stops for anything else waits on the engineer. The outcome log gets `returning` (with `via` for AdmiralBot), the ship carries `"returning": true` in `GET /api/ships`, and a second call answers the same. Response `{"returning": true}`. With the body `{"moor": true}` a live ship with an open PR moors instead, exactly as `stop` does: no clean-up prompt is typed, no `returning` is logged, and the response is `{"moored": "<session>"}`; its `400`, `409` and `500` are `stop`'s, and it works on a woken ship that carries a PR. `404`: unknown ship. `409`: the ship is moored, has exited, is being handed to Commodore, or carries a PR (`"carries_prs": true`, a live ship that carries at least one `OPEN` PR). A moored ship whose PRs are all done with at least one merged is woken by the poll with its resume text and the clean-up prompt, already `sent` (`woken` has `"by": "return"`, then `unmoored` and `returning`); a woken ship's round then ends `sailed`.
- `POST /api/ships/<session>/answer` and `.../crew/<name>/answer` answer the permission or question menu the pane shows, by sending the harness's keys (`internal/keymap`: Allow once is `1`, Deny is Esc, a question's option is its digit; Copilot's keys are `1`, Esc, and Down then Enter, since its question form ignores digits). The body is `{"card":"permission","reason":"permission:<Tool>","choice":"allow"|"deny"}` or `{"card":"question","reason":"<the pane's reason>","item":"<question item id>","option":<1-based number>}` for one single-choice question, or `{"card":"question","reason":"<the pane's reason>","item":"<first question item id>","answers":[{"options":[<1-based numbers, ascending>],"other":"<free text>"}]}` for a Claude call, one entry per question in order (a single-choice entry has one option or an `other`, a multi-select one at least one option or an `other`; at most 4 questions). Answers go one at a time per pane, and the gate reads the pane's own `@admiral-state` and `@admiral-reason`, not the poll cache: keys are sent only while the pane needs you and its reason equals the body's `reason`. Claude Code also fires PermissionRequest for AskUserQuestion, so a question's pane reason is `question` or `permission:AskUserQuestion`, and the question card accepts either. The permission card refuses `permission:AskUserQuestion` and `permission:ExitPlanMode`, whose menus are not yes or no, and a Codex tool other than `Bash` and `apply_patch`, whose menus are unrecorded. A question also needs `item` to be the newest pending call's first question, with every question of the call pending. Claude's call of any shape (up to 4 questions, multi-select, an Other answer) is answered in place with `answers`, from keys recorded in `internal/keymap/testdata/claude/`. The server sends them one step at a time, reading the pane (`capture-pane`, at most 3 s per step) before each. Claude draws only the bottom of a menu taller than its pane, so for the answer the server grows a window smaller than 120x60 (a phone's or iPad's terminal leaves it so) and then puts back its size and its own `window-size` option: it refuses with `409` and leaves the pane needing you unless the menu is fresh (first tab, cursor on row 1, nothing toggled), each step lands, and the review screen shows the intended answers before the final `1`; Copilot and Codex are answered only for a single single-choice question with `option`. A question item carries the call's `header` chip when it has one. An optional `"stop_id"` binds the answer to one stop: it must be the pane's live `@admiral-stop-id` and not yet answered, or the route answers `409` `already answered` and sends no keys (checked before the pane's state, under the same pane lock, so the first of two answers wins). A body without it behaves as before for the engineer; the crew boat route ignores it, and a request under AdmiralBot's token without it is `400` with nothing sent. An exited pane answers `409` `has exited` before the stop is checked. Every answer to a stop (permission or question menu) is marked `@admiral-stop-answered` as `<id>`, or `<id> admiralbot` under AdmiralBot's token; the `answered` outcome and the need card read it. Allow and a question answer clear needs you as `messages` does; Deny leaves the pane needing you with reason `stop`, because the harness sits at its prompt: no hook says so for Claude or Copilot, and Codex's `Interrupt` hook writes the same `stop` after the route does. A Copilot pane is answered in place too: its permission card takes `notification:permission_prompt` and its question card takes `question` or `notification:elicitation_dialog`, each for a pending single-choice `ask_user` of 1-9 options (a several-field form, and a crew boat before its first `agentStop`, go to the terminal). Response `{"answered": true}`. `400`: invalid JSON, an unknown card or choice, or a missing field, whatever the pane shows. `404`: unknown ship or boat. `409` and no keys sent: the pane is not on that card now, has exited, or runs a harness with no key map, or the question is not answerable as above. `502`: tmux refused the keys.
- `400`: the message is invalid JSON, empty after cleaning, or over 16 KiB; the body is capped at 1 MiB. `404`: unknown ship or boat. `409`: the ship or boat is anchored or sailing off (send and interrupt). `502`: tmux refused the keys. Stop answers `500` when the session cannot be killed.

## A ship's conversation

The conversation of a Claude Code, Codex or Copilot ship, read from the harness's own record (Claude Code's transcript, Codex's rollout, Copilot's `events.jsonl`). `GET /api/version` lists the `conversation` capability when the server has it.

### How the file is found

The launcher starts a Claude Code ship with `--session-id <uuid>` and sets the pane option `@admiral-transcript` to `<unix ns> launch <path>` before the harness runs. `<path>` is `<config dir>/projects/<project slug>/<uuid>.jsonl`, where the config dir is the one Claude Code uses for the fleet's Claude dock (`CLAUDE_CONFIG_DIR`, else `~/.claude`). Claude Code may store the file under another project directory name (it shortens long ones), so when the computed path is missing the server looks for `<config dir>/projects/*/<uuid>.jsonl`.

A dock whose args, or an order whose extra args, already choose a session (`--session-id`, `--resume`, `-r`, `--continue`, `-c`) launches as before with no `--session-id` of ours and no option. That ship's state is `none`.

The option's text is untrusted: anything running in the ship can write it. The session id in the option must equal the `--session-id` in the command the pane was started with (tmux keeps that, and `set-option` from the ship cannot change it; only a respawn of the pane, which replaces the harness too, can); on a mismatch, or when the start command has no `--session-id`, the state is `none`. The server takes the file from the option's path, else from the `projects/*/<uuid>.jsonl` lookup above, and reads it only if it is a regular file under the harness's own `<config dir>/projects/` with no symlink on the way (ADR 0019). A file or directory that is a symlink is `unreadable`, never `ok`.

A Copilot ship launches with `--session-id <uuid>` and records `<copilot home>/session-state/<uuid>/events.jsonl`; the server checks the id against the start command the same way, and the file's layout is fixed by the id, so a missing file is not searched for. When Copilot accepts `--ui-server` the launch also passes `--ui-server --port <n>` on a free loopback port. The server reads `<n>` back from the start command (never from a pane option) and follows that Copilot's live events while a client has the ship open; see "Live text" below. A ship whose command has no `--ui-server` is served from the file alone. When the order or the dock already carries `--server`, `--headless`, `--stdio`, `--connect`, `--host` or `--port`, the launcher adds nothing; but if a dock passes `--ui-server --port N` itself, Admiral still observes N, subject to the ownership check (the listener must be the pane's process or one of its descendants).

A Codex ship has no `--session-id` to launch with. Its `SessionStart` hook writes `@admiral-transcript` as `<unix ns> <source> <path>` from the payload's `transcript_path`: the rollout, `<Codex home>/sessions/YYYY/MM/DD/rollout-<timestamp>-<uuid>.jsonl`, where the Codex home is the fleet's `CODEX_HOME`, else Admiral's, else `~/.codex`. A null `transcript_path` records nothing, so the state is `none`. The server takes any source word, since a pane can write the option and nothing binds a Codex ship's path to its launch, and reads the file only if it is a regular file under `<Codex home>/sessions/` with no symlink below it (a symlinked home or `sessions/` is fine). A pane can therefore point the option at another rollout under the same `sessions/`. `SessionStart` fires again on resume, `/new`, fork and compact and records the new path: the server reads the option again about once a second and switches to the new file. A rollout has no pending question. The adapter reads a `compacted` record as a compaction marker, a shape no real rollout has confirmed.

### Live from the app-server (Codex)

A running Codex ship's server (`codex app-server`, see `docs/agents/codebase/codex.md`) also tells its conversation, and Admiral keeps one observer per running ship, shared by every view. While the observer is connected it is the only source: `GET` and the WebSocket `conversation` messages carry the server's items, and the rollout is not read. A ship with no rollout yet still has a conversation then.

The observer connects to the pane's `@admiral-codex-socket` only when the pane's start command names the same `--socket`, and only if the socket resolves (symlinks followed) to a socket of this user in `/tmp/codex-daemon-<uid>`. It sends `initialize` (with `experimentalApi`), `initialized`, `thread/loaded/list`, `thread/resume {threadId}` and, when several threads are loaded and none matches the rollout, `thread/list {limit: 50}`, nothing else, and never answers a request of the server: the TUI answers, and the observer would be deciding for the engineer. Frames are read with no timeout; a connect or a handshake that takes longer than the bound fails.

The thread is the one the server last announced with a non-ephemeral `thread/started` that is not a sub-agent's (the TUI's `/new`, `/resume` or a fork), else the one whose id is in the `@admiral-transcript` rollout's file name when the server has it loaded, else the only one loaded, else the most recently updated of those loaded. The history on attach is the `thread/resume` answer. Items: a user message, a finished agent message, a command as `Bash` with the full command in `input`, a file change as `apply_patch` with its paths one per line in `input`, a compaction, and a turn end. Reasoning and hooks are not shown.

The observer follows the TUI: a `thread/started` for another thread, or a new `@admiral-transcript` rollout, makes it attach to that thread at once, and each open view gets `reset: true` with that thread's history. A running ship's pane options and rollout are read when its panes change and otherwise every few seconds, so a change of rollout shows within that time; `thread/started` does not wait for it.

A live view holds the last 200 items of the thread and `GET`'s `more` and `before` page inside them; the rollout view has the rest. The observer does not page older items from the rollout, so that a view has one source between resets.

A tool call from the server carries `live: true`. A command or file change the server asks to approve carries `approving: true`, with `input` and `summary` from the request's own command and cwd. Only one plain approval waiting (a `command` kind with no `approvalId`, or a file change with no `grantRoot`) is marked; any other approval, or more than one, is marked on nothing and the card sends the engineer to the terminal. An approval clears on `serverRequest/resolved` for its request and at turn end. A question key for a ship with an approval waiting is refused with `409`.

A Codex question is answered the same way, with `reason` `bell` and Codex's keys, while the observer holds a pending single-choice question that is the newest one, alone in its call, with no approval waiting. Codex's TUI rings no bell for `request_user_input` in a pane it takes as focused, and no hook fires for one, so the observer's pending question is the signal: it sets the pane to `needs_you` with reason `bell` when a question starts waiting (unless a hook already has the pane at `needs_you` for something else), and back to `working` when the request resolves or the thread changes, clearing only its own `bell` mark. A real bell sets the same state. The observer sends nothing over the protocol.

A question already pending when the observer attaches is not shown as a card: the server's `thread/resume` answer holds the history, and the request itself is not replayed to the observer, so the engineer answers it in the terminal. (Not verified against a 0.167.1 server beyond the recorded probe, where the observer received requests only after it had attached.)

A view that opens while the observer is connected gets no `reset`. When the connection drops, each open view gets `reset: true` with the rollout's items (when the ship has one), with `reset: true` and no items when there is no rollout either, and when the observer reconnects, `reset: true` with the server's history. The observer retries with a growing pause. A pane whose option and start command disagree is never dialled and its conversation is the rollout's.

A pending question is a `question` item whose `id` is `<item id>#<index>`. Only a request with one question, with options and not secret, is answerable from the card; Codex rings the bell for it, so the pane's reason is `bell` and the answer route takes `{"card":"question","reason":"bell",...}` only while the observer holds a pending question whose id is the request's `item`. Any other state is a 409.

### `GET /api/v1/ships/<ship>/conversation[?before=<id>]`

```json
{"state": "ok", "items": [ ... ], "more": true}
```

- `state`:
  - `ok`: the file was read. `items` may be empty (a new session has only metadata lines).
  - `none`: the ship has no conversation Admiral can read: not a Claude Code, Codex or Copilot ship, no `@admiral-transcript` of ours, or the file has not been written yet.
  - `unreadable`: the path is refused (a symlink, not a regular file) or nothing in the file parses.
  - `gone`: the file was read before and is not there now. This is kept in memory, so after an Admiral restart a missing file is `none` until it is seen again.
- `items`: at most 200, oldest first, the newest 200 without `before`. An item is the model in `internal/conversation` (`id`, `kind`, `text`, and the tool call or question it holds; a tool call carries `name`, `summary`, `output`, `error`, `done` and `input`, what allowing it approves: a Bash call's full `command`, or the path of a Write, Edit, MultiEdit, NotebookEdit or Read call (on Copilot, the `command` of `bash` or the path of `edit`, `create` or `view`), cut at 4 KiB with a marker and omitted for any other tool, while `summary` stays the one-line label, which may be the model's own description; a question carries `text`, `header` (the call's chip for that question, when it has one), `options`, `answer`, `pending` and `multiSelect`, present and true for a question that takes several answers). A `kind` of `interrupted` (text `Interrupted`) marks where the engineer's Escape ended a turn: Claude Code's `[Request interrupted by user…]` user line, or a Codex rollout's `turn_aborted` event with reason `interrupted`; it ends the turn like a user item, and no other `turn_aborted` reason makes one). Ids contain characters that need URL escaping in `before`.
- `before`: the id of an item; the page is the up to 200 items before it. An empty `before`, one that is not an item's id, or one older than the window the server reads is `400`.
- `more`: there are items older than the first one returned, within the window the server reads. It is `false` at the file's first item.
- An unknown ship is `404`. A dismissed ship is unknown. A ship anchored after its harness exited stays readable until it is dismissed.

### A ship's rounds

A moored ship is relaunched under the same name for each feedback round, and each round is a fresh session. Admiral records each round when the ship moors: its session id, fleet, transcript path, launch time and the time it moored, in `$ADMIRAL_HOME/moored/rounds/<ship name>.json` (paths only, never content; the history keeps the latest 50 rounds, and an older round's divider and items drop off). A round's path is recorded only when it passes the same check as above (the option's session id equals the `--session-id` of the start command); any other round, a non-Claude one included, is recorded with no path. The history ends with the mooring (Dismiss, Don't follow reviews, merged or closed), and a wake keeps it.

When a ship has rounds, the endpoint stitches them oldest first:

- **A moored ship** is served from its history, with state `ok`, where it has no live session and would otherwise be `404`. A moored ship whose page would have no items (no history, a history that cannot be read, or only an undivided round 0) answers `none`.
- **A live ship in round N of 1 or more** serves the recorded rounds, then its live round.
- **A `round` item opens each round of 1 or more**: `{"id": "r<N>", "kind": "round", "round": N, "at": "<the round's launch time>"}`. It carries `state` when the round cannot be shown: `none` (no transcript recorded, for example a non-Claude round), `gone` (the file is no longer there) or `unreadable` (the file cannot be read or parsed). Such a round shows only its divider, and never fails the page. A live round's divider has no `state` while its transcript is not bound yet (right after a wake) or its file is not there yet. Round 0 has no divider, so a missing round-0 file shows nothing.
- **Ids:** an item of round N of 1 or more has the id `r<N>:<id>`, on the page and on pushes alike. Round 0 keeps its own ids.
- **`before`:** an id of the form `r<N>:<id>` for a round N of 1 or more in the history is read in that round, and `r<N>` (the divider) pages from the round before. Any other id is round 0's.
- **Paging** reads the newest round first and opens an older file only while the page has room, at most 8 files a page; `more` is true while anything older exists, so a page may hold fewer than 200 items.
- `tail` comes from the live round.

Paging reaches back as far as a first read does: the last 8 MB of the file, at most 16 MB read per request. An older item is not reachable and `more` is `false` at the start of that window.

### WebSocket

A client sends:

```json
{"type": "conversation_open", "ship": "<ship>"}
{"type": "conversation_close", "ship": "<ship>"}
```

The server answers an open with `{"type": "conversation_opened", "ship": "<ship>"}` once the subscription is in effect. A client sends `conversation_open`, waits for `conversation_opened`, then reads the page over HTTP, so no append falls between the page and the pushes. From then on, items that are new or changed in the file go to the clients that opened the ship, and to no other:

```json
{"type": "conversation", "ship": "<ship>", "items": [ ... ]}
```

- `reset: true` is added when the transcript was truncated or replaced, or when a Codex ship's recorded rollout changed to another file: `items` are what the file now holds, and the client drops what it holds.

- A changed item is sent again under the same `id` (a tool call whose output came later); the client replaces its copy.
- A message holds at most 200 items.
- An open for an unknown ship, or one with no conversation, is ignored, with no reply. An open for a moored ship is answered with `conversation_opened` and watches nothing: its rounds are recorded, and its file no longer grows.
- A live round's pushes carry the same `r<N>:` ids as its page.
- A client holds at most 16 ships open. A 17th open closes the oldest.
- A subscription ends on `conversation_close`, when the connection closes, or when the ship is dismissed.
- The server follows the file by offset, about four times a second while any client has the ship open.
- Live text (Copilot ships with a `--ui-server`): while a client has the ship open, the server also attaches to the ship's server as a read-only second client and pushes the assistant text of a turn as it is written, before the file has it. A live reply has the id of Copilot's message (`messageId`), which is also the id the file's item gets, so the finished item replaces the live one and the text never shows twice. Every other live item has the id of its event, which is the id of its line in the file. The HTTP page and the ship's `tail` read the file only. An interrupted reply (Esc, an error) keeps the partial text it already showed in every open tab until the conversation is reopened, because there is no message that removes an item; the file page never has it. Subagent text is not shown live, as in the file. When the server cannot be reached, is not the ship's own, or goes away, the conversation comes from the file alone, with no error; the server retries slowly.

## The default fleet

`GET /api/config` carries `default_fleet` (a fleet key) and `default_fleet_fallback`. `default_fleet` is the fleet the config names, which new sources, unclaimed GitHub items and migrated sources go to. When the config names none, or names a fleet that is gone, it is the first fleet and `default_fleet_fallback` is `true`. With no fleets it is `""` and the fallback is `true`.

`PUT /api/default-fleet` with `{"fleet":"<key>"}` sets it, keeping every other key of `config.json`, and answers `200` with the same body as `GET /api/config`. Picking the first fleet still writes the key. It answers `422` for a key that is not a fleet (nothing is written), `400` for a body that is not JSON, or a `fleet` that is missing, not a string or empty, `409` when `config.json` is invalid or changed under the write, and `500` for any other failure. Any authenticated client may call it, a paired device's Bearer included (`/api/v1/default-fleet`); AdmiralBot's actor token is refused at the guard.

## A fleet's Limits

Each fleet in `GET /api/config` carries `preset` (`"work"` or `"home"`, `"work"` when the file has none), `limits`, `sentences` and `overridden`. `limits` is the full effective set: the preset's values with the fleet's own saved Limits layered over them leaf by leaf. Levels are `"A0"`, `"A1"`, `"A3"`, `"A4"` and `"A5"` (there is no A2). `overridden` lists the Limits the fleet stores itself, as the `field` paths of the sentences (`ceilings.t1`, `rates.concurrent`, `wall_clock_minutes`), so a client can mark them and reset them. `sentences` is one `{field, sentence}` per Limit in catalog order (a skip scoped to a routine reads `<value> (<routine name> only)`, or `<value> (a deleted routine only)` once the routine is gone), then two fixed sentences with an empty `field` (a restricted ship never pushes; its network reaches package registries only).

`PUT /api/fleets/<fleet>` takes `preset` and a `limits` object, each optional. Switching `preset` clears the saved Limits except `quiet_hours`. `ceilings`, `rates`, `spend` and `skip` merge per key, and a ceiling merges per leaf too: `{"ceilings":{"t1":{"level":"A5"}}}` leaves `asks_first` as it was, and a T4 save with only `level` and `restricted` keeps its `threshold`. A level that leaves A3 drops the stored `restricted`; one that enters A3 without it takes the preset's, else `investigate`. A threshold is replaced whole, must not lower its ceiling (a level below it, or `investigate` under a `draft_fix` base), and `"threshold": null` removes it. Every other key, lists included, replaces. A `null` for any other key inside `limits` deletes the stored value, so that Limit reads as the preset's again. A refused value is a `400` whose `error` names `fleets.<fleet>.limits.<path>`, and nothing is written. Rules: T3 is at most A1; an A3 ceiling needs `restricted` (`investigate` or `draft_fix`) and no other level has one; `asks_first` is T1 only and `threshold` T4 only. Entries sent in `repo_allowlist` that the fleet does not already store (compared case-insensitively) must be repos under the fleet's search roots, so a checkout that moved never blocks a save that keeps its entry; an unknown fleet is a `404` before that check. A `write_deny` entry has no leading or trailing whitespace, control characters, `(`, `)` or `,`. Bounds: lists at most 5000 entries, quiet-hour windows at most 100, launches per hour and per sender per day 1 to 1000, concurrent 1 to 100, wall clock 1 to 1440 minutes, quota hold 1 to 100, spend 0 to 10000 dollars in whole cents, threshold events 1 to 100000 and days 1 to 365.

## A fleet's allow rules

`GET /api/fleets/<fleet>/allow-rules` (also under `/api/v1`) is the fleet's allow rules and the allow rule proposals the engineer skipped, each list in the order they were added: `{"rules":[<rule>...],"skipped":[<rule>...]}`. A rule is `{harness, repo, rule, pattern, added}`. A Claude or Copilot rule has its harness's rule text in `rule` (`Bash(gh pr view:*)`, `shell(gh pr)`) and a `repo`, the remote's `owner/repo` or else the checkout's path. A Codex rule has a `prefix_rule` pattern in `pattern` (`["make","check"]`) and no `repo`, because it covers every repo of the fleet. `added` is an RFC 3339 time.

`POST /api/fleets/<fleet>/allow-rules/remove` deletes a rule, so it is no longer added at launch, and `POST /api/fleets/<fleet>/allow-rules/skipped/remove` deletes a skip, so the rule can be proposed again. Each takes `{"rule": <rule>}` as the list gave it. A rule is matched on `harness`, `repo`, `rule` and `pattern`; `added` is ignored. Removing one that is already gone is not an error. Each answers with the fleet's list after the change. An unknown fleet is a `404`, a body without a rule of the right shape for its harness is a `400`, and a store that can't be read or written (a corrupt `allow-rules.json`) is a `500`. Rules are added only from the Inbox, so there is no add or edit route. AdmiralBot can't reach these routes.

## A fleet's chat

Each fleet whose chat is on (`chat.on` in `GET /api/config`) has its own AdmiralBot: a session of the fleet's chat harness (Claude Code or Codex; Copilot is not launchable yet) named `_chat-<fleet>` that runs in `$ADMIRAL_HOME/chat/<fleet>/`. Every route is also served under `/api/v1/...`. A fleet that doesn't exist is a 404, and one whose chat is off is a 409 whose `error` is the reason (no dock, a key that differs from an earlier fleet's only in case, and so on). The notes and instructions routes below are the exception: they only read and write files, so they stay served while the chat is off, and refuse only the case clash, since both keys would share one directory. The old global `/api/chat/*` routes are gone and answer 404.

Each dock in `GET /api/config` (`fleets[].docks[]`) also carries `models` and `models_source`. `models` is the names the dock's harness offers for a launch or the chat, in the order the harness lists them (the built-in list has the chat's default first); `models_source` is `listed` when Admiral got them from the harness, and `built_in` when it has not (or never could) and serves its built-in list. Admiral asks each dock's harness at startup and on `POST /api/harness-capabilities/check`, in the background, so a config read never waits for it. A listing that fails, times out, or leaves no valid name keeps the last good list (or the built-in). A name must match `^[A-Za-z0-9][A-Za-z0-9._:-]*(\[[A-Za-z0-9]+\])?$` to be offered. The `config` WebSocket message is sent again when a dock's served list changes, and only then.

In `GET /api/config`, each fleet's `chat` object carries the AdmiralBot settings and what the fleet may choose:

- `harness`, `model`, `effort` and `context_threshold` are the fleet's settings; `on` and `off_reason` say whether the chat runs.
- `harness_options` has one entry for each of `claude`, `codex` and `copilot` the fleet has a dock for, in that order: `harness`, `offered`, and when it isn't offered `reason` (one line naming the harness and the missing capability, with the probe's detail when it failed) and `capability` (`bot.mcp_fence` or `bot.config_home`); both are `""` when offered. `models` and `efforts` are the lists that harness's chat accepts (`""` is the harness default effort; `efforts` has the default first). A harness is offered when its probes say so for this fleet (ADR 0035): Claude unless `bot.mcp_fence` failed, Codex and Copilot only with `bot.mcp_fence` and `bot.config_home` both passed.
- `harnesses` is the offered subset of `harness_options`, by name.
- `models` and `efforts` are those of the fleet's own `harness`. `models` is that dock's model list (from the dock's harness; see the dock fields above); with none listed it is the built-in: Claude `sonnet`, `opus`, `haiku`, `fable` and efforts `low`, `medium`, `high`; Codex `gpt-6.1-sol` and `gpt-6-luna` with the same efforts; Copilot `gpt-5.6-sol` and `gpt-5.6-luna` with no effort. Each `harness_options` entry's `models` is that dock's list too.

`PUT /api/fleets/<fleet>` with a `chat` object checks what it sends. Naming a `harness` that isn't offered is a `400` with its reason, and so is a model or effort outside the harness's lists, checked against the harness the save leaves the fleet on and, for a model, against that dock's model list. A save that names no harness is not checked against the offered list, so a fleet whose harness lapsed can still change its threshold. Switching harness checks the model and effort the fleet keeps against the new harness, and refuses the save when either isn't one it takes (Codex `high` to Copilot with no `effort` sent is a `400`).

### `GET /api/fleets/<fleet>/drafting`

The fleet's drafting skill and where it is installed: `{"skill": "<name or empty>", "harnesses": [{"harness": "claude", "names": ["wayfinder"]}]}`. `harnesses` lists, in the fleet's dock order, each dock where an installed skill carries the saved name, with the installed invocation names that carry it (the name itself, or its part after `plugin:`). Two or more names on one dock mean the name is ambiguous there. With no skill saved, or a skill installed nowhere, `harnesses` is `[]`. `?dir=<checkout>` must be a checkout or search root of the fleet (`400` otherwise) and adds that checkout's own skills; without it only the user's skills are read. `404`: unknown fleet. An actor token may read it for its own fleet; AdmiralBot's `get_drafting_skill` calls it, with the repo's `dir`.

### `PUT /api/fleets/<fleet>/drafting`

Body `{"skill": "<name>"}` saves `drafting.skill` on the fleet; `""` clears it (no skill). A namespaced `plugin:skill` is accepted. A name that is not a safe invocation (empty parts, whitespace, control characters or more than one colon) is a `400` and nothing is written. Answers the config like `PUT /api/fleets/<fleet>`. `404`: unknown fleet; `409`: config.json cannot be edited now.

### `GET /api/chat/<fleet>/session`

```json
{
  "fleet": "harbor",
  "running": true,
  "state": "idle",
  "messages": [
    {"id": "u-1", "kind": "message", "role": "user", "text": "...", "at": "2026-11-11T10:00:00Z"},
    {"id": "q-7c1", "kind": "question", "text": "Which repo?", "at": "...", "card": {}},
    {"id": "reset-1794455969929283000", "kind": "reset", "text": "New chat", "at": "..."}
  ],
  "questions": [],
  "error": "...",
  "needsTerminal": true
}
```

- `state` is `idle`, `working` or `waiting`, and `""` while the chat isn't running. `error` is present when something needs saying: why the last start was refused, or that the transcript can't be read. `needsTerminal` is `true` (omitted otherwise) when `error` asks the engineer to finish starting the chat in the terminal (any harness's startup prompt), so the panel offers Open terminal beside it.
- `messages` is the newest 200 entries of the fleet's history (`HistoryWindow` in `internal/chat`), oldest first, served from Admiral's log whether or not the chat is running. `kind` is always set: `message` (with `role` `user` or `assistant`), `question` (a chat question as a card: `text` is its title and `card` is the question item as asked, without its answer) `reset` (a marker: `text` is `New chat` or `Context refreshed`), `interrupted` (a marker, with `text` `Interrupted`, where an Interrupt ended a turn; see `POST /api/chat/<fleet>/interrupt`) or `commitment` (a card the server posts when a commitment settles, with no chat turn: `id` is `commitment-<commitment id>-<outcome>`, `text` is the commitment's text and `card` is `{"commitment", "outcome", "ship", "reason"}`; `outcome` is `launched` (`ship` is the session), `reminded`, `cant_run` (`reason` says why) or `dropped` (`reason` says why) or `aged` (a commitment with no trigger turned 14 days old; it stays open and its card comes once)). or `ship_card` (see below) or `need_card` (see Need cards) or `answer` (what the engineer chose on a proposal the runner then removed: `id` is `a-<question id>`, `text` the chosen labels, no `card`; the thread folds it into that question's card). Each `id` appears once. A message may carry `thread`, the id of the ship card whose report turn it is (the user entry Admiral typed) or whose reply it is (the assistant entries from the turn's own user line until the next user line after the turn has ended; before it ends, only the engineer's message closes the thread). A user line of any kind closes it once the turn has ended, a notice included, and a reply logged after the end but before that line is still marked. The mark is set when the entry is first logged and never changes; a notice inside the turn is not marked and does not close it. The turn's own user line is the one whose `card:` line names the ship card, logged after the paste. A report turn for scouts launched together names several ships but one `card:` line, the card of the scout whose end completed the group, so the reply threads under that card. Only the turn Admiral pasted is marked: an engineer's own message that starts with `[Report:` never is.
- `questions` are the fleet's chat questions, each the inbox's question item with `session` `_chat-<fleet>` and `answer`: the engineer's answer or `null`. While one waits it is also an Inbox item (see Inbox below), except a proposal (id `campaign-…`), which only the chat shows.

### Ship cards

A ship card is a chat entry with `kind: "ship_card"` that the server posts in the chat of the ship's own fleet when the ship's result comes in. It starts no turn, sends no push and is never shown to AdmiralBot. It reaches clients the way every entry does, through the `chat` WebSocket message.

`id` is `ship-<ship>-<first_launched>-<result>`, so a result posts once per voyage and a reused ship name posts its own cards. `text` is the ship's session name and `card` is:

```json
{"ship": "calm-otter", "name": "Calm Otter", "title": "Fix the login", "first_launched": "2026-11-17T10:00:00Z", "fleet": "harbor", "skill": "tdd", "skill_kind": "skill", "result": "moored",
 "prs": [{"url": "https://github.com/acme/api/pull/7", "number": 7}]}
```

- `ship` is the session name and `name` the ship's display name. `title` is what the ship is about, once settled (a title from an order, or the Titler's); it is left off until then, so a ship that moors before the Titler names it shows its name alone, and when the ship has none. A voyage first seen before this field existed stays without one. Show it beside the name, never instead of it. `first_launched` is the voyage's stamp, as written in the `id`; `GET /api/ships` lists the same stamp as `first_launched`, falling back to `launched` when a ship has none. `skill` is the skill's name, empty when none, and `skill_kind` is `commodore`, `skill`, `none`, `scout` or `quick`. `scout` is a scout, whatever its skill. `quick` is a ship AdmiralBot launched with no skill that is neither a scout nor a Commodore ship; nothing records a quick ship at launch, so every such ship reads it. The server decides the kind, and an empty one reads `skill` when the ship names a skill, else `none`.
- `findings: true` is added when the chat is served, and only when the voyage has kept findings; it is left off otherwise. The log keeps the card as posted, so a moored ship's earlier card gains it when a later round keeps findings. A client shows a Findings link that opens `GET /api/v1/ships/<ship>/findings?first_launched=<first_launched>`.
- The ship's conversation, `GET /api/v1/ships/<ship>/conversation`, is reachable only while the voyage is live, moored or anchored; it is `404` for a ship that sailed off or returned, and a reused name opens the new voyage. A client links the card to the conversation only while a ship in `GET /api/ships` has this `ship` and `first_launched`.
- `result` is `sailed_off` (the ship ended clean with no PR to moor on and has left the ship list, a scout ran to its own end and has left it, or its moored PRs all closed; each waits 15 s for a moor or a return to port to follow), `anchored` (it ended with an error), `moored` (it first moored with an open PR; a later re-moor posts nothing), `ready_to_merge` (a moored ship's stack became ready to merge; once per voyage), `returned` (it returned to port), `failed` (a scout ended with no findings, so its `ended` record says `result: "failed"`; posted where `sailed_off` would be, instead of it) or `lost` (accepted, but nothing posts it yet).
- Every ship posts `ready_to_merge`, whoever launched it, along with the other results. A scout's own end posts `sailed_off` once, told from an engineer's Stop ship by the `scout` mark on its `stopped` record. Stop ship, Dismiss and a Hand to Commodore relaunch post no card.
- `prs` are the ship's PRs as last seen, in order; `number` is read from the URL.
- Ships already moored or anchored when the server first runs this feature post nothing, and a moored one's `ready_to_merge` waits out its first answered poll: if that poll shows the stack ready, no card. Admiral records them as seen in `$ADMIRAL_HOME/ship-cards.json`, which also keeps each voyage's posted results across restarts.

### Following cards

A Following card is a chat entry with `kind: "following_card"` that the server posts in the fleet's chat when Admiral follows the campaign a drafting ship filed, for a drafting ship AdmiralBot launched from the chat (the ships that post a launch line). A drafting ship launched from the Add campaign modal posts none. It posts once per ship, when the first ref is followed, from the turn-end read or the end-of-ship read; a later ref the follow ignores adds nothing. It starts no turn and sends no push, so AdmiralBot never reads it. Drafting state is in memory, so a ship that outlives an Admiral restart posts none.

`id` is `following:<ship>:<first launch>:<campaign id>`, so a later ship reusing the name still posts, and `text` is the plain card line. The server strips bidi, zero-width and control characters from the title and text. `card` is `{"ship": "<session>", "campaign_id": "<id>", "title": "<campaign title>"}`; the title is the one Admiral read from the issue on GitHub, never the ship's own words, and is data, never markup. The campaign may be one the fleet already followed.

### Need cards

A need card is a chat entry with `kind: "need_card"` that the server posts in the chat of a ship's own fleet for each open question, pending review and findings item of that ship, and in the chat of its own fleet for each routine proposal, allow rule proposal and campaign draft, and for each stop of a ship that needs the engineer (see Stop cards), whether or not the fleet's chat is on. It starts no turn, sends no push, marks nothing seen and is never shown to AdmiralBot. Items of the chat (`_chat-<fleet>`), other `_admiral` items, items of a ship with no fleet, and a fleet item whose fleet the config does not hold, post none. A fleet item lives under `_admiral` and names its fleet: `fleet` in a routine proposal and a campaign draft, the object's `fleet` in an allow rule proposal. Every such item open when Admiral starts gets its card, once: the card is posted once per item.

`id` is `need-` and a hash of the ship's session, the item id and the item's `created` stamp, so a reused session name or item id gets its own card; it is one URL path segment of `[A-Za-z0-9_-]`. `text` is the item's title. `card` is `{"ship", "item", "item_kind", "state", "answered_in"}` and the fields of its kind:

- `ship` is the session, `item` the item id and `item_kind` is `question`, `review`, `findings`, `routine_proposal`, `allow_rules` or `campaign_draft`, or a stop kind (see Stop cards). A fleet card has no `ship`.
- A `question` card has `questions`: the item's `question.questions` as `GET /api/inbox` serves it (`id`, `text`, `multi`, `options` of `{label, description}`, `recommended`).
- A `review` card has `events` (`["COMMENT","APPROVE","REQUEST_CHANGES"]`), `discard` (`true`: the card offers Discard) and `pr_url`, the pull request's link.
- A `findings` card has `cards`: one `{"id", "proposal"}` per finding card of the item, `proposal` being `{"kind", "content"}` or `null`. A client offers Edit where `proposal.kind` is `diff` or `reply`. The finding's own text is read from the item.
- A `routine_proposal` card has `action`, `reason`, `routine_name` and `expires_at` (RFC 3339), and offers Launch and Dismiss.
- An `allow_rules` card has `cards`: every proposed rule as `GET /api/inbox` serves it (`id`, `harness`, `repo`, `rule`, `pattern`, `every_repo`, `count`, `reason`, `prompts`), and offers Add or Skip for each. The item grows in place while rounds add rules, keeping its id and `created`, so its one card serves the item's current rules and is never posted twice.
- A `campaign_draft` card has `repo`, `title` and `body`, the seed for Create (which may send them edited), and offers Dismiss.
- `state` is `open` while the item is listed and unanswered. It is `answered` once the item is answered, with `answered_in` `chat` when the card's own route answered it and `inbox` for any other way (the Inbox, the ship's own answer file); and `removed` once the item is removed, or left with no answer file; and `moved_on` for a routine proposal that closed without the engineer: it expired, or the routine's next run replaced it. The state is worked out when the entry is served and is recorded the first time it settles, in `$ADMIRAL_HOME/need-cards.json`, so releasing a kept ship's files never changes it. `answered_in` is absent unless `state` is `answered`.

`POST /api/chat/<fleet>/need-cards/<card>/answer` (also under `/api/v1`) answers the item through its kind's Inbox path, with that path's body, and answers what that path does: for a `question` card the body of `POST /api/inbox/<session>/<id>/answer` (`{"answers":{"<qid>":{"choice","other"}},"note"}`) and `{"answered": "<item id>"}`; for a `review` card `{"event","edited"}` as `POST /api/inbox/<session>/<id>/submit` takes it, or `{"discard":true}` as its `/discard` does, answered `{"answered", "action"}` (and `invalid_target` as the Inbox says); for a `findings` card the body of `POST /api/inbox/<session>/<id>/findings` (`{"cards":[{"id","decision","proposal"}]}`); for a `routine_proposal` card `{"launch":true}`, answered `{"ship": …}` as `/launch` does, or `{"dismiss":true}`; for an `allow_rules` card the body of `/allow-rules` (`{"cards":{"<id>":{"decision":"add"|"skip"}}}`), which must decide every rule the item holds now; for a `campaign_draft` card `{"repo","title","body"}` as `/create` takes it, answered `{"campaign":{"id","url"}}`, or `{"dismiss":true}`. A refusal from a routine launch or a campaign create comes back with the Inbox route's status and body: `501` when it is not wired, `410` `the proposal expired`, `422` for a repo the fleet does not hold, the hook's own status, and a create that failed after its parent issue was filed answers `{"error","parent","answered"}` with the item answered. Every card that offers choices also takes `{"choice":"<id>"}`, the ids a `push` lists in `choices`: for a permission stop `allow` or `deny`; for a `question` card with exactly one single-select question the option's index as a string (answered as `{"answers":{"<qid>":{"choice":"<option label>"}}}`, the label read from the item as it is now); for a `review` card `COMMENT`, `APPROVE`, `REQUEST_CHANGES` (as `{"event"}`) or `discard`; for a `routine_proposal` card `launch` or `dismiss`; for a `campaign_draft` card `create` (the item's own repo, title and body, so it is refused as an empty body is) or `dismiss`. The choice takes the kind's own path and answers what it answers. A body with no top-level `choice` is read as before. The refusals come in this order: `404` for an unknown fleet or card; `409` for a card that is not open or whose item changed, before the choice is judged; then `400` for an id the card does not offer, and for a `choice` on a card with none (findings, allow rules, several questions, a multi-select question). A stop card judges its `choice` as Stop cards say. The server tells the kinds apart by the card's item, not the body. It is served whether or not the fleet's chat is on. Until the Inbox's first scan after a start, a card keeps the state it had: nothing settles from an item's absence before then. `404` for an unknown fleet, an unknown card or a card of another fleet; `400` for an invalid answer, with nothing written; `409` `item <id> is already answered` when the card or the item was answered or removed first, when the item has since left the Inbox, or when the item now in that place is not the one the card was posted for (a different `created` stamp, or questions, review, findings, routine proposal or campaign draft that changed since the card posted; an allow rule proposal is bound on id and `created` only); `409` with the Inbox's message when another action on the item is still running. A review's gh failure answers as the Inbox's submit route does (`502`, or `503` when gh is missing) and the card stays open; a stale card runs no gh. A review removed in the Inbox settles its card as `removed`. The AdmiralBot actor token gets `403`: a tap is the engineer's own answer, and AdmiralBot answers through `answer_item`.

### Stop cards

A stop card is a need card for a ship that needs you for a permission prompt, a finished turn or a launch that never started. `item_kind` is `permission`, `stop` or `not_started`; other reasons (a plan to approve, a question tool, a bare notification) post none. It posts once per stop: `id` is `need-` and a hash of the session and the stop's identity, and a restart posts nothing twice.

- `item` is the stop's identity: the id the ship's pane minted when it began needing you (`@admiral-stop-id`, new for each stop and cleared when the ship works). A ship that was never started has had no hook write, so its `item` is its launch stamp.
- `tool` is the tool a permission prompt asks about. `answerable` is `false` when the card has no buttons: a prompt the keys can't answer (a question tool, a plan, a tool the harness's menu has no card for), and always for `not_started`. Show those with no buttons and say to answer in the terminal; `not_started` points to the Terminal tab.
- `state` is `open` while the ship still needs you for that stop, even once a route has answered it (a second answer to the same stop gets `409`: the first wins). It is `answered` with `answered_in` `chat` (the card's own route), `inbox` (the ship's messages, next-prompt, interrupt or answer routes with the engineer's token) or `admiralbot` (the same routes with AdmiralBot's token; an item card answered through the Inbox answer route with it settles as `admiralbot` too). It is `settled_terminal` when the stop ended with no Admiral route answering it (the engineer typed in the terminal), and `moved_on` when the ship left (moored, anchored, sailed off or gone). It is recorded the first time it settles.

The card route takes `{"choice": "allow"}` or `{"choice": "deny"}` on a permission card and `{"text": "<next prompt>"}` on a stop card, and answers `{"answered": "<item>"}`. It re-reads the pane under the pane's answer lock, so a tap sends nothing when the ship has moved past the stop. `409` `item <item> is already answered` when the card is settled or the pane no longer shows that stop; `400` for a body that doesn't fit the card (a choice on a stop card, text on a permission card, an unknown choice, empty text, a card with no buttons, text over 16 KiB or a control character) and for a refusal by the ships layer; `403` for the AdmiralBot token; any other pane error is `500`.

### Launch lines

A launch line is a chat entry with `kind: "launch_line"` that the server posts in the chat of the ship's fleet when AdmiralBot launches a ship the engineer asked for in the chat. It starts no turn, sends no push and is never shown to AdmiralBot. Commitment and campaign launches, launches from the UI and event launches (which post a launch card) post none. It reaches clients through the `chat` WebSocket message.

`id` is `launch-line-<ship>-<stamp>`, and `text` is the ship's session name. `card` is:

```json
{"ship": "calm-otter", "name": "Calm Otter", "title": "Fix the login", "first_launched": "2026-11-17T10:00:00Z", "fleet": "harbor", "kind": "quick_ship", "reason": "to read the AWS logs", "text": "Read the logs and fix the 500."}
```

- `ship` is the session name and `first_launched` the voyage's stamp, the same as on a ship card. `title` is the ship's title, left off until the title is settled (a launch from an order has it at once; a freeform launch is still titled by the Titler, and its provisional title would be the launch text's first line) and when the ship has none. A client links the line to the ship only while a ship in `GET /api/ships` has this `ship` and `first_launched`, since a session name can be reused.
- `kind` is `scout`, `quick_ship`, `commodore`, or the name of the skill the ship runs (a drafting ship shows its skill's name).
- `reason` is the one line AdmiralBot gave `launch_ship`, which requires it.
- `text` is the launch text as AdmiralBot wrote it, without the closing steps Admiral adds to a quick ship's prompt. It is empty for a launch from an order (`source` and `order_id`), which has no launch text.

### The log

Admiral appends the history to `$ADMIRAL_HOME/chat/<fleet>/conversation.jsonl`, one JSON entry a line: `id`, `kind`, `role`, `text`, `at`, `card`, and `logged`, when Admiral wrote it. An entry whose `id` is already in the log is skipped, so reading the transcript again, after a restart too, adds nothing. On the first append of a new month (UTC) the file is renamed `conversation-YYYY-MM.jsonl`; old months are kept. The log is Admiral's: nothing in it is fed back to the model, though the chat can read its own file in its working directory.

### `POST /api/chat/<fleet>/start`

Starts the fleet's chat session or leaves a running one alone, and answers `{"running":true}`. Admiral doesn't start one at server start. `501` naming the harness when the fleet's chat harness is Copilot, which launches no chat yet.

### `POST /api/chat/<fleet>/messages`

`{"text"}` pastes the text into the chat and presses Enter. 400 for empty text or over 16 KiB. 409 when the chat isn't running, no transcript has been recorded yet, or Admiral is refreshing the context (`Refreshing`).

### `POST /api/chat/<fleet>/interrupt` (also `/api/v1/chat/<fleet>/interrupt`)

Ends the chat's turn in progress and leaves its session and context as they are: it presses one Escape in the chat's pane, then withdraws the fleet's unanswered chat questions, as a New chat does (a `GET /api/chat/questions/<id>/answer` for one says `withdrawn`; an unanswered campaign proposal stays). It pastes nothing, resets nothing, starts no session and does not render the brief again. Any turn counts, whoever started it: the engineer's message, a report turn or a routine's prompt. The engineer and paired clients call it; AdmiralBot's token gets `403`. The `chat-interrupt` capability in `GET /api/version` says the server has the route.

- `state` `working` or `waiting`: `200 {"interrupted": true}`.
- `state` `idle`: nothing is pressed or withdrawn, `200 {"interrupted": false}`.
- `409` for every reason a message send would be refused: the chat isn't running, is refreshing (`Refreshing`), or has not started (no transcript recorded yet, `Open the terminal to finish starting the chat`; for a Codex chat also when its hooks need trusting, it needs an update, or it isn't trusted, each with its own message). Nothing is pressed. These come before the state check, since a chat that has not started reads `idle`.
- `502` `could not read the chat's state: ...` when the chat's pane can't be read, and `could not interrupt: ...` when tmux refuses the key; the questions stay open.

The Claude Code or Codex turn then ends and the harness writes its own record of it, which the conversation reads as an `interrupted` entry (once, in the history too; the raw `[Request interrupted by user]` line never shows as the engineer's message). Claude Code does not run its `Stop` hook on an interrupt, so `state` can still read `working` until the next turn. A message already sent stays with the harness: Admiral neither withdraws nor resends it, and what the harness does with it after the Escape is its own (not confirmed here for either harness). A Copilot chat gets the same Escape, with no claim about its transcript.

### `POST /api/chat/<fleet>/new`

Clears the model's context and appends a `reset` entry to the log; the earlier history is still served. An idle chat first gets the hidden flush turn (the held answer takes up to `ADMIRAL_CHAT_FLUSH_WAIT`, 3 minutes); the flush and its reply are not served or logged. It sends `/clear` when the running session's model, effort and fleet match the fleet's chat settings, else it ends the session and starts a new one. It withdraws the fleet's chat questions. 409 when the chat isn't running.

While a queued turn (a message Admiral types into the chat by itself) is waiting or running, the clear is deferred: the answer is `200 {"running":true,"deferred":true}` at once, nothing is cleared yet, and the clear runs once the queue is empty and the chat is idle. Queued turns are kept. The clear is dropped if the chat is stopped or restarted, or the engineer sends a chat message, before it runs.

### `POST /api/chat/<fleet>/questions/<id>/answer`

Takes the inbox's question answer body and writes the answer file. 404 for an unknown id, 409 when it is already answered, 400 for an invalid answer. A question in one fleet's chat can't be answered through another fleet's route.

### WebSocket

`{"type":"chat","fleet":"<fleet>", ...}` carries the fields of the session beside `type`. It is sent on connect, one per fleet whose chat is on, and again within about a second of a change. Messages are coalesced per fleet, so one fleet's update never replaces another's.

### `POST /api/chat/questions` and `GET /api/chat/questions/<id>/answer` (AdmiralBot only)

These two serve AdmiralBot's `ask_question` tool and need an actor token: any other caller is `403`, and nothing is written. The fleet is the token's. `POST` takes `{"title", "questions"}`, checked as the inbox checks a question item, writes the question file and answers `201 {"id"}`; `400` for a bad question. `GET` holds the request for up to `wait` seconds (a non-negative integer, at most 110) and answers `200` with `{"state": "answered", "answer": {...}}`, `{"state": "withdrawn"}` once the question is gone (a New chat), or `{"state": "waiting"}` at the deadline. A bad id or `wait` is `400`. A question of another fleet is never answered.

While a queued turn runs in a fleet's chat, every AdmiralBot write for that fleet (every route that isn't a GET, this `POST` included) is refused with `403 {"error": ...}` telling AdmiralBot the turn can only read and talk and to offer the action to the engineer in plain text. Reads still pass, and the engineer's own requests are never gated.

### `POST /api/chat/notes` (AdmiralBot only)

Serves the `save_note` tool and needs an actor token: any other caller is `403`, and nothing is written. The fleet is the token's. The body is `{"text"}`; the text is trimmed, and must hold 1 to 500 characters. `201` answers the note `{"id", "text", "ts", "via": "admiralbot"}`. A refused note is `400` for a body that isn't that shape and `422` with an `{"error"}` AdmiralBot can act on for an empty or over-long text, a text holding a character that shows nothing (a control other than newline and tab, a zero-width, bidi-override or tag character, a private-use or unassigned code point), or a full ledger (30 open notes; the message says the engineer can remove notes on Preferences).

### `GET /api/chat/<fleet>/notes`

The fleet's open notes, oldest first: `{"notes": [{"id", "kind", "text", "ts", "via"}]}`, empty for a fleet with no ledger. `kind` is `note` (commitments are listed apart, below). `ts` is RFC 3339 to the second. `via` is absent on a note the engineer wrote. Served while the fleet's chat is off; `404` for a fleet that isn't configured, `409` for a key that clashes in case with an earlier fleet's (`POST /api/chat/notes` too). An actor token can't call it.

### `POST /api/chat/commitments` (AdmiralBot only)

Serves the `make_commitment` tool and needs an actor token: any other caller is `403`, and nothing is written. The fleet is the token's; a `fleet` in the body is ignored. The body is `{"text", "trigger": {"kind", "subject"}, "action", "launch"}`, one JSON value of at most 64 KiB. `text` is trimmed and holds 1 to 500 characters. `trigger.kind` is `ship_sailed` or `ship_anchored` (`subject` is a ship of the fleet), `pr_merged` or `pr_closed` (an https pull request URL on a GitHub host the fleet uses), `issue_closed` (an https issue URL on such a host), `time` (a future RFC 3339 time) or `none` (no subject). `action` is `remind` (no `launch`) or `launch`, whose `launch` is a `POST /api/ships` body: it is stored with the fleet set, `autopilot` true and no `anyway` or chat message, and a launch of its own fleet only, from an existing checkout (`dir`) or a clone (`clone: true`, with no `dir`). It is judged at record time by the rules `POST /api/ships` applies that need no free capacity (`launcher.CheckSpec`: dock and its executable, a codex dock's args, skill, member, pins, model, checkout inside the fleet's roots, Commodore found), for a clone also `launcher.CheckClone` (the fleet can launch and has a place to clone into, the order's repo or the first repository URL in the text names a host the fleet uses, `clone_repo` matches it, and no checkout of it exists yet; nothing is cloned and the checkout's own checks wait for the launch), plus: the source belongs to the fleet and lists the order, no issues beside a source, issue URLs on the fleet's hosts, known resources, no control characters in the prompt, a spec of at most 16 KiB, and autopilot proven for the harness with its advisor (without the Inbox notice a live launch posts). The stored trigger is canonical: a PR or issue subject is the URL rebuilt from its parsed parts (host lowercased) and a time is UTC; a ship trigger also carries `launched`, the matched ship's launch stamp, so a later ship that reuses the session name is not taken for it; a ship with no stamp is refused, since a trigger on it could never fire. A refusal is `4xx` with an `{"error"}` and stores nothing; `422` when the ledger is full (30 open or waiting). `201` answers `{"id", "text", "trigger", "action", "launch", "ts", "via"}`. The same text and trigger may be recorded twice.

### `POST /api/chat/campaign-commitments` (AdmiralBot only)

Serves the `work_on_campaign` tool and needs an actor token: any other caller is `403`. The fleet is the token's. The body is `{"reference", "harness"}`: the campaign's parent issue as a URL or `owner/repo#n` (a bare `#n` is refused), and the harness its children run on (`claude` when absent). The route follows the campaign as `POST /api/campaigns` does, so its `400` and `422` pass through; a campaign that belongs to another fleet is `403`, and `422` when autopilot is not proven for the harness with its advisor (answered in the chat, with no Inbox notice). It records one commitment: trigger `campaign` (the subject is the campaign's id), action `work`, `harness`. `201` for a new one, `200` with the open one when the campaign already has it. Admiral never edits the issue tree, and AdmiralBot cannot create one. The generic `POST /api/chat/commitments` refuses trigger `campaign`, and a launch from source `campaign` is refused there too.

A campaign commitment stays open across its children and closes only when the campaign ends (every issue closed, or unfollowed: `ended` card) or the engineer cancels. On each tick it launches the campaign's ready Without-you children in autopilot with `Decide`'s rules (autopilot mode: ADR 0034), one launch key `commitment:<id>:<child url>` each, and records a child event per child: `child_launched`, `child_waiting`, `child_declined` or `child_failed`, with `url`, plus `ship` on `child_launched` and `reason` on `child_failed` (the commitment's `harness` is on its first event). A commitment lists as `{..., "harness", "children": [{"url","state","ship","reason"}], "launched", "waiting_children"}`, one entry per child URL with its last state. At most 200 child events are kept for a commitment; a launch can record two, so it launches no more once fewer than two remain, and posts one `too_large` card. A campaign missing from the follow store ends the commitment ("stopped following").

A campaign commitment also proposes the ready With-you children, one at a time per fleet, when the fleet has chat on (with chat off it proposes nothing and holds the fleet). A proposal is a chat question with id `campaign-<commitment id>-<4 hex of the child URL hash>-<n>`, title `Start <child> with you? (<campaign>)`, and one single-choice question `start` with options `Yes, start it with you` and `No, skip it`; its card reads "Admiral asks". It is not an Inbox item and never counts as a waiting question, so a reset (new chat) keeps an open one and the brief lists it apart as "Admiral is asking", naming the child as `owner/repo#n` (the card keeps the title). A Yes launches the child as a With-you ship (no autopilot, no cap or gate; a claim, resource or launcher error refuses it); No, or an answer of text alone, declines it. Once the runner has acted on an answer (launched, refused or declined) it removes the question and its answer file; the thread's card keeps what the engineer answered (a log entry `a-<question id>`, kind `answer`) and reads "You answered: …", not Withdrawn. A New chat or reset also clears an answered proposal that was left over, and `questions` lists at most 20 proposals apart from at most 20 of AdmiralBot's own questions. The runner withdraws a proposal when the child is no longer ready, when the campaign ends, and when the commitment is cancelled. A fleet is held, and proposes nothing more, while a proposal is open or a With-you child the commitment launched has a ship that is underway or needs you; a ship started by hand or a Without-you child never holds. More child events: `child_proposed` (`url`, `question`) and `child_withdrawn` (`url`, `reason`: `not ready`, `ended`, `cancelled` or `question removed`); `child_launched` carries `mode` (`with_you` or `without_you`). A commitment lists `proposal: {"url","question"}` while one is open, `children[].state` also reads `proposed` or `withdrawn`, and each proposal and its answer takes two of the 200 child events.

Cards: a launched or can't-run card for a child carries `child` (the child's URL) and has the id `commitment-<id>-<outcome>-<4 hex of sha256 of the URL>`; `ended` and `too_large` cards are `commitment-<id>-<outcome>`.

### `POST /api/fleets/<fleet>/campaign-drafts` (AdmiralBot only)

Serves the `draft_campaign` tool and needs an actor token for `<fleet>`: an engineer's request, or another fleet's token, is `403`. The body is `{"repo": "owner/name", "title": "…", "body": "…"}`. It writes one Admiral-owned Inbox item (see "A campaign draft") and answers `201 {"id": "<item id>"}`; the tool turns the id into the link `/app/inbox/_admiral/item/<id>`. Every call makes a new item. It writes nothing to GitHub and makes no model call. `400`: a blank repo, title or body, a title over 100 characters or a body over 64 KiB. `422`: the repo is not one of the fleet's repos, meaning a project of the fleet that GitHub routing sends to it, and the message names the repo and lists the fleet's. This is not `POST …/campaigns/draft`, the model drafter, which AdmiralBot may not call.

### `GET /api/chat/<fleet>/commitments`

The fleet's open and waiting commitments, oldest first: `{"commitments": [{"id", "text", "trigger", "action", "launch", "ts", "via", "waiting", "wait_reason", "shown"}]}`. `shown` is true once the engineer was asked "still want this?" (the mark stays on an open commitment). `waiting` is true once a launch commitment fired and is held for cap room, a resource or quota, and `wait_reason` (left out when empty) is the refusal's wait text; closed ones (done, dropped, cancelled) are not listed. Served while the chat is off. An actor token can't call it.

### `DELETE /api/chat/<fleet>/commitments/<id>`

Cancels the commitment as the engineer and answers `204`. `404` naming a commitment for an id that is unknown, closed, another fleet's, or a note's. An actor token can't call it.

### `GET` and `PUT /api/chat/<fleet>/instructions`

The fleet's instructions, which only the engineer writes: `{"text", "max": 2000}`, `text` empty when there are none. `PUT` takes `{"text"}`, stores it trimmed (whitespace and a byte order mark) and answers the same shape; empty text clears them. The cap is 2,000 Unicode code points after trimming: more is `422` with an `{"error"}` saying by how many characters. `400` for a body that isn't `{"text": string}`. They live in `chat/<fleet>/instructions.md`. Same fleet rules as the notes route; an actor token can't call either method.

### `DELETE /api/chat/<fleet>/notes/<id>`

Cancels the note as the engineer (the event has no `via`) and answers `204`. `404` for an id that is unknown or already cancelled. An actor token can't call it.

### `POST /api/chat/<fleet>/notes/<id>/promote`

Moves the note into the instructions: its text is appended after the existing instructions and a blank line (the note alone when there are none), and the note is cancelled, under one lock. Answers `200` with the new `{"text", "max"}`. `404` as for delete; `409` with an `{"error"}` when the note holds a character that shows nothing (as `POST /api/chat/notes` refuses; a note saved before that check can't be promoted), or saying by how many characters the result would pass the 2,000 cap (the blank line counts), with the instructions and the note unchanged. An actor token can't call it.

The ledger lives in `$ADMIRAL_HOME/chat/<fleet>/ledger.jsonl`, an append-only log with one event a line: `{"v": 1, "ts", "event", "id", "kind", "text", "via"}`. `event` is `added` or `cancelled` for a note; `kind` is `note` or `commitment`, `text` comes on `added`, and `via` is `admiralbot` when AdmiralBot wrote the event and absent for the engineer. A commitment's `added` also carries `trigger` (`{"kind", "subject"}`), `action` and, for a launch, `launch`; its later events are `fired` (a launch commitment now waiting, with the wait text as its `reason`), `shown` (the "still want this?" mark, set when its `aged` card is posted; it stays open), `done` and `dropped` (each with a `reason`) and `cancelled`. A closed commitment never changes again. The caps count per kind: 30 open notes and 30 open or waiting commitments. Reading folds the events; a line that doesn't parse is skipped.

## Inbox

The items ships leave for you: a question, a review, findings, and Admiral's own notices, wake proposals, campaign drafts and crew items. Every route is also served under `/api/v1/`.

### `GET /api/inbox` (alias `GET /api/v1/inbox`)

```json
{"items": [{"version": 1, "id": "q-1", "kind": "question", "title": "Which port?", "created": "2026-10-22T10:00:00Z",
  "session": "s1", "name": "Dory", "ship_title": "Fix the login redirect", "harness": "claude", "fleet": "work", "fleet_name": "Work", "fleet_color": "#38bdf8",
  "question": {"questions": []}}]}
```

Oldest `created` first. An item is its file's fields plus `session`, and `name`, `ship_title`, `harness`, `fleet`, `fleet_name` and `fleet_color` when the ship is known, live or from the record Admiral kept after it sailed off. Admiral sets those last, so a file cannot name another ship or fleet; `ship_title` is what the ship is about, beside its `title`, which is the item's own heading; it is omitted when the ship has no title, and for a ship that sailed off, whose kept record holds none. They are omitted for an unknown ship and on a notice (session `_admiral`, name `Admiral`). A fleet's waiting chat question is listed too, with session `_chat-<fleet>`, `name` `AdmiralBot` and the fleet from its directory (never from the file); it is not a ship, so Ships never counts it. It leaves the list when answered or withdrawn. The two crew kinds, `mission` and `allow_rules` are the exception: session `_admiral`, name `Admiral`, and `fleet`, `fleet_name` and `fleet_color` from the object's `fleet` while that fleet is configured (left off otherwise). `kind` is `question`, `review`, `findings`, `notice`, `wake_proposal`, `crew_notes`, `crew_member`, `mission`, `drafting_ended` or `allow_rules`, and the item holds only that kind's own object (`question`, `review`, `findings`, `notice`, `wake_proposal`, `crew_notes`, `crew_member`, `mission`, `drafting_ended` or `allow_rules`). The WebSocket `inbox` message, `{"type": "inbox", "items": [...]}`, carries the same list and is sent to each new connection and on every change.

The WebSocket (`/ws`, `/ws/v1`) also sends `{"type": "attention", "count": N}`: how many things wait on the engineer across every fleet (see ADR 0033). It is sent to each new connection and again whenever the count changes; a ships or inbox change that leaves it the same sends nothing. It counts five parts:

- inbox items of any kind except `notice`
- ships with status `needs_you` and a reason other than `crew`, seen or not
- crew boats with status `needs_you`, on ships that aren't `sailing_off`
- moored ships with `stack_ready` and no PR with `reviewing` set, whatever its state
- moored ships with a PR that is `reviewing`, `responded` and `OPEN` (a re-review)

Viewing a stop (`seen`) never changes the count; it drops only when what it counts goes away (an item answered or removed, a stop ended, a stack merged, a re-review done). Until the first inbox scan has finished and the ship list is known, no `attention` message is sent, since empty lists would read as zero; the first one follows as soon as both are known. A socket that follows push events (see "Following push events") gets its count from those messages instead of from this broadcast.

A `crew_notes` item holds `crew_notes: {"fleet", "ship", "run_date", "notes": [{"id", "member", "role", "scope", "repo", "note", "replaces"}]}`. A `crew_member` item holds `crew_member: {"fleet", "ship", "run_date", "member", "role", "ad_hoc_run", "definition", "notes": [...]}`, where `definition` is the ad hoc file's text and the notes are that member's. `fleet` is the fleet key the ship was launched in. The answer files are `{"version": 1, "id", "kind", "answered", "notes": {"<note id>": {"decision", "note", "scope", "repo"}}}` for `crew_notes` and `{..., "decision", "file_removed"}` for `crew_member`.

A `mission` item holds `mission: {"fleet", "ship", "run_date", "name", "scope", "repo", "text"}`: a mission the ship's report proposed (`missions` in the report, validated upstream by Commodore's report schema), `text` being the whole mission file. `repo` is the proposing repo for `scope` `repo` and `null` for `fleet`. Admiral writes the item only when `name` is a valid crew name and not a built-in mission (`build`, `pr-feedback`, `review`), `scope` is `fleet` or `repo` (with a valid `owner/repo`), and `text` is non-empty and at most 65536 bytes; a proposal that fails gets no item. A stored item that isn't that shape is not listed and answers `404`. Its answer file is `{"version": 1, "id", "kind", "answered", "decision", "file_written"}`.

A migration notice also carries `notice.entries`: `[{"key", "name", "panel", "fleet"}]`, one for each order source panel the old config held (`key` is the source key, `panel` its view id, `fleet` the fleet the source fed: its own, else the default fleet). The shell shows the notice as plain text with no link; a note already on disk has no `entries` and stays plain text.

An `allow_rules` item is an allow rule proposal: `allow_rules: {"fleet", "cards": [<card>...]}`, one item per fleet while it waits, in session `_admiral` only. A card is `{"id", "harness", "repo", "rule", "pattern", "every_repo", "count", "reason", "prompts"}`. A Claude or Copilot card has its harness's rule text in `rule` and a `repo`: the origin's `owner/repo` for a GitHub origin (after `insteadOf`), else the real path of the checkout (a linked worktree names its main checkout). The permission log and launch compute it with the same function, so an added rule reaches the next ship launched in that repo. A Codex card has the `prefix_rule` words in `pattern`, no `repo` and `every_repo: true`: its rule applies to every repo in the fleet, so a client says that instead of naming one repo. `prompts` is the logged prompts the rule would have answered, `[{"ship", "id", "crew", "at", "tool", "command"}]` (`crew` only for a crew boat's), and `count` is their number. `reason` is the ship's own line for the rule, left off when the report gave none.

Admiral writes and refreshes the item when a ship's round ends (the first build, or a feedback round; a crew boat's prompts count under its ship). Only the prompts of the ship's newest launch count, so an earlier round's, and an earlier ship's of the same name, are never counted again. Each rule that passes the checks in `internal/allowrules` gets one card; a rule already waiting on a card gets the new prompts added and its `count` raised. An item with an answer file, whether answered or removed, is never rewritten: the next round's candidates, the same rule included, go on a new item. A ship launched restricted, or by an event of tier T2 to T4, proposes nothing, and neither does one whose trigger or tier Admiral can't read. The answer file is `{"version": 1, "id", "kind", "answered", "cards": {"<card id>": {"decision"}}}`.

### A v2 report's `allow_rules`

A v2 Admiral report may carry a top-level `allow_rules: [{"rule", "reason"}]`. `reason` is plain text on one line, cut to 200 characters, and shown on the card whose rule matches `rule` exactly: a Claude or Copilot rule's text, or a Codex pattern's words joined by single spaces (`make check`). An entry that matches no card is ignored: it never adds a candidate, because the permission log, not the report, says what was allowed. A ship with no report or a non-v2 one still gets its cards, without reasons.

### A campaign draft

A drafting ship that ended without Admiral following a campaign from it is an Inbox item with `kind: "drafting_ended"`, `session: "_admiral"`, `name: "Admiral"`, the title `<ship name> ended without filing a campaign`, and `fleet`, `fleet_name` and `fleet_color` of the ship's fleet. Its `drafting_ended` object is `{"ship": "<session>", "name": "<ship name>", "fleet", "harness"}`; the name is data, never markup. It posts when the engineer or AdmiralBot stops the ship through the stop route, when the ship sails off cleanly and when an anchored ship is dismissed, once, after a last read of the ship's `campaign-ref`; a ref written just before the end is followed and posts nothing. A Hand to Commodore, Return to port, a scout's end, a routine worker and a mooring that ends by merge or close post none. A ship that moors keeps drafting and posts nothing until it ends; stopping it then posts the item, from the binding read when it moored. It does not push: an ended draft is information, not a decision. The list refreshes on a poll, so the item shows on the next Inbox refresh, not when the stop route answers. The item's fleet and harness are the ones the ship launched with, which Admiral keeps in memory; a pane option the ship rewrites changes neither. The item holds the ship's conversation binding as it was when the ship ended and never sends it, and the route reads the config dir from the fleet's config, never from the item; `GET /api/inbox/_admiral/<id>/conversation` (also under `/api/v1`) answers with the same shape as `GET /api/ships/<session>/conversation`, with the same `before` query, read through that binding with the checks a live ship's gets, so a binding the launch does not back is the `none` page, and `404` once the item is gone. Remove from inbox deletes the item.

A campaign AdmiralBot drafted is an Inbox item with `kind: "campaign_draft"`, `session: "_admiral"`, `name: "Admiral"`, the title `AdmiralBot drafted a campaign`, and `fleet`, `fleet_name` and `fleet_color` of the draft's fleet. Its `campaign_draft` object is `{"fleet", "repo", "title", "body", "via": "admiralbot"}`: `via` says AdmiralBot wrote it. `title` and `body` are model-written, so render the body as markdown only through the shared renderer. The item never expires; it leaves the list when the engineer creates or dismisses it, and an answered item keeps its answer file.

- `create`: `POST /api/v1/inbox/_admiral/<id>/create`, `{"repo", "title", "body"}`, the draft as the engineer edited it. It files the parent issue and follows it, as `POST /api/campaigns/create` does with no issues, in the draft's fleet, and answers `201 {"campaign": {"id", "url"}}`. The answer file is `{"created": true, "url": "<parent>"}`, and a card naming the campaign goes into the fleet's chat with no model turn. A refusal before any GitHub write leaves the item for another try: `400` for a blank or over-long title or body or a blank repo, `422` for a repo that is not one of the fleet's repos, and the create route's own refusals. Once the parent exists the item is answered even if linking or following failed: the answer is `502 {"error", "parent", "answered"}`, the card says what failed, and a second press is `409` or `404`, so no second parent is ever filed. An action already running on the item is `409`.
- `dismiss`: `POST /api/v1/inbox/_admiral/<id>/dismiss`, `{}`, writes `{"dismissed": true}`, posts a "thrown away" card to the chat with no model turn, and answers `204`. Remove from inbox on a draft does the same.

Both are the engineer's alone: an actor token is `403`. AdmiralBot is not told the outcome: it never reads cards. A `campaign_draft_card` entry in the chat's history (`kind: "campaign_draft_card"`, `text` the plain card line, `card` `{"title", "url", "created", "failed"}`) is the card.

### Acting on an item

Each route is `POST /api/v1/inbox/<session>/<id>/<action>` and answers `404` for an unknown item. An item already answered is `409` and final. A `409` is also returned while another action on the item is running (`another action on this item is still running`); that one can be retried.

- `answer`: a question's answers, `{"answers": {"<question id>": {"choice", "other"}}, "note"}`; `400` for an invalid answer. For a chat question (`<session>` is `_chat-<fleet>`) it writes the answer file in that fleet's `chat/<fleet>/questions/`, the same as the chat's own answer route; `404` once the question is withdrawn or the fleet is unknown.
- `submit`: a review, `{"event": "COMMENT"|"APPROVE"|"REQUEST_CHANGES", "edited": bool}`, posted to GitHub through `gh`.
- `discard`: a review, `{}`; deletes the pending review on GitHub. `{"forget": true}` runs no `gh`.
- `findings`: `{"cards": [{"id", "decision": "approved"|"edited"|"rejected", "proposal": {"kind": "diff"|"reply", "content"}}]}`; every card needs one decision and only an edited card takes a proposal. Nothing is posted to GitHub.
- `crew-notes`: a `crew_notes` item (`POST /api/v1/inbox/_admiral/<id>/crew-notes`), `{"notes": {"<note id>": {"decision": "keep"|"edit"|"drop", "note", "scope", "repo", "replaces"}}}`. Every note needs exactly one decision and an unknown note id is `400`. Only an edit takes `note`, `scope` (`fleet`|`repo`), `repo` and `replaces` (a note line without its dash, or `null` for none); a field left out keeps the proposal's value. A kept or edited note is written to the fleet's crew as `- <run_date> (<ship>): <note>`, and a fact the scope already holds is not written twice. A note that doesn't fit (the scope holds 30 and no `replaces`, or `replaces` matches no line) answers `409` `{"error", "note": "<note id>"}` with nothing written; so does a fleet that is no longer configured. A drop writes nothing.
- `crew-member`: a `crew_member` item (`POST /api/v1/inbox/_admiral/<id>/crew-member`), `{"decision": "keep"|"drop"}`, answering `{"answered", "file_removed"}`. Keep writes the ad hoc member into the fleet's crew without its `ad-hoc` lines, then its notes, then removes the ad hoc file; it answers `409` with nothing written when the fleet already has that member, the name is a built-in member of one of the fleet's docks (an ad hoc member never replaces a standing one), the ad hoc file is gone or no longer matches the item's `definition`, a note doesn't fit, or the fleet is no longer configured. Drop removes the ad hoc file only if it still matches `definition`.
- `mission`: a `mission` item (`POST /api/v1/inbox/_admiral/<id>/mission`), `{"decision": "keep"|"drop"}`, answering `{"answered", "file_written"}`. Keep writes `text` byte for byte to `$ADMIRAL_HOME/fleets/<fleet key>/missions/<name>.md`, the one place Commodore's resolver reads, for either scope. It never replaces a file: the same text already there counts as kept with `file_written` false, other text answers `409`. It also answers `409` with nothing written when the fleet is no longer configured, the name is a built-in mission, or a link or non-directory is on the path. Drop writes nothing, and is allowed when the fleet is gone.
- `allow-rules`: an `allow_rules` item (`POST /api/v1/inbox/_admiral/<id>/allow-rules`), `{"cards": {"<card id>": {"decision": "add"|"skip"}}}`. Every card needs exactly one decision, and an unknown card id or any other decision (there is no edit) is `400` with nothing written. A card set that doesn't match the item (a round refreshed it after the client read it) is `400` `card <id> has no decision`, or `the item has no card <id>`; the client reloads the item and asks again. A card keeps its newest 20 `prompts`, while `count` counts all of them. Add puts the card's rule in the fleet's allow rules, so the fleet's next launch gets it (a Codex rule also rewrites the fleet's Codex rules file); Skip records it as skipped, so a later round does not propose it again. Answers `{"answered"}`. AdmiralBot can't answer it: the route is not on its allow-list.
- `remove`: Remove from inbox, any item; changes nothing on GitHub and never resumes the ship. Answers `200` with `"forgotten": true`. A notice's file is deleted. On a crew item or a `mission` item it counts as Drop: nothing is written to the crew or the missions directory. On an `allow_rules` item it only hides the item: its rules are not skipped, so a later round can propose them again. On a `crew_member` item it also answers `"file_removed"`, whether the ad hoc file went (`false` when the fleet is no longer configured or the file changed or was gone), so a client can tell.

## Crew

A fleet's Crew page: its built-in and fleet members, their notes, and the edits the page makes. Every route is also served under `/api/v1/`, and `{key}` is a fleet key (an unknown fleet is 404). Only the **built-in** and **fleet** layers are listed; repo-layer and ad hoc members are not. Error bodies are `{"error": "<message>"}`. A 400 that names a member field also carries `"field": "<key>"` (`name`, `role`, `based-on`, `skills`, `model`, `harness`, `pick-me-when` or `instructions`). A refusal changes nothing on disk, and no write follows a link: a link anywhere from the crew directory down to the file is refused with 409.

### `GET /api/fleets/{key}/crew[?harness=<dock>]`

`{harness, members, unclaimed, warnings, errors}`. The built-in layer is the Commodore installed for the dock `harness`, which defaults to the fleet's first dock (`""` when it has none, and then the built-in layer is empty); an unknown dock is 400. A missing crew directory reads as empty and a GET never creates it.

A member is `{name, role, based-on, skills, model, harness, pick-me-when, instructions, layer, customized, notes}`. `layer` is `built-in` or `fleet`, the winning layer; `customized` is true for a fleet member with a built-in member of the same name. `notes` is `{fleet: [...], repos: {"<owner>/<repo>": [...]}}`: strings without the leading dash and space, only scopes holding a note, the fix checker's always empty. Only the first 30 notes of a scope show, so lines past 30 in an over-full file can't be reached from the page. A link, a non-directory or an `<owner>` or `<repo>.md` name that is no path segment is skipped with a warning.

`unclaimed` is `[{member, notes}]` sorted by name: every `memory/<name>/` holding a note whose name no built-in or fleet member uses. A repo-layer member's notes show here too, and the set can differ by `?harness=` when the docks' Commodore installs differ. A directory name that is not a member name is skipped with a warning. When the resolver reports `errors`, `members` and `unclaimed` are empty.

### `GET /api/fleets/{key}/crew/skills[?harness=<dock>]`

The skills a member can list, for the Crew page's picker: `{"skills": [{"name", "description", "harnesses", "aliases"}]}`, sorted by `name`, with `harnesses` and `aliases` sorted. `aliases` is every name the skill is installed under on any dock, `name` included, so a member saved with `plugin:name` still matches the entry `name`. With `harness`, only that dock's skills; without it, every dock's. An unknown fleet is 404 and a `harness` the fleet has no dock for is 400; a fleet with no docks answers `{"skills": []}`. It reads each dock's user and plugin skills with the dock's identity variables, never a checkout's skills. One skill is one entry: within a dock a plugin skill `plugin:name` is listed as `name` unless another skill of that dock has the bare name `name`, and then both keep their full names; the same resulting name on several docks is one entry whose `harnesses` lists them and whose `description` is the first non-empty one in dock order (`""` when none has one). A name a saved member would refuse (one that does not start with a letter or digit, or holds a character outside letters, digits and `.` `_` `:` `-`) is left out. AdmiralBot reads it for its own fleet through `list_skills`; another fleet's key is 403.

### `GET /api/fleets/{key}/repos`

`{"repos": [{path, name, kind, remotes}]}`: the git checkouts up to two levels below the fleet's search roots and its clone root, then the roots themselves, as a launch's `dir` accepts them. `kind` is `checkout` or `search_root`; `remotes` are normalised `host/owner/repo` ids. It reads the disk and runs no git. An unknown fleet is 404.

### `GET /api/fleets/{key}/cloneable`

`{"hosts": [...], "clone_root": "...", "owners": [...]}`: the rule for what Admiral clones, not a list, and no network call. A `host/owner/repo` on one of `hosts` (github.com and the host of each of the fleet's GitHub sources) with no checkout in the fleet clones into `clone_root` (the fleet's `clone_root`, else its first search root, `""` when neither is absolute) under its lower-case repo name. `owners` are the fleet's configured owners, a hint of where its repos live. An unknown fleet is 404.

### `GET /api/fleets/{key}/docks`

`{"docks": [{harness, version, detected_at, features}]}` in the config's order: each dock's probed version and capabilities as `GET /api/harness-capabilities` lists them for one fleet, `features` being `[{id, label, capabilities: [{id, label, status, checked_at, detail}]}]`. It reads the store and runs no probe. An unknown fleet is 404.

### Fleet members

Edits touch only `$ADMIRAL_HOME/fleets/<key>/crew/`. A member route keys on whether `<name>.md` exists there, so a PUT can repair a broken file. A name with no fleet file but a built-in member is 409 (customize it first); with neither it is 404; a name that is no member name is 400. Each success is 200 `{"name": "<name>"}`. The built-in layer is the `?harness=` dock's, as in GET.

- `PUT /api/fleets/{key}/crew/members/{name}` with `{role, based-on, skills, model, harness, pick-me-when, instructions}` rewrites the file (Go writes the frontmatter and the instructions as the body). It is 400 with `field` when the resolver would refuse the bytes (a parse or field error, a custom role without a valid `based-on`, a built-in role with `based-on`), when `role` or `based-on` differs from the same-named built-in, when a value is not one line, or when a value would read back differently (a skill name that is not valid, the fix checker's skills and instructions). Blank lines around `instructions` are trimmed before the write, as the resolver trims them on read. A file over 65536 bytes is 400 with `field` `instructions`.
- `POST .../members/{name}/customize` copies the built-in member's file into the fleet layer: 404 with no built-in of that name, 409 when the fleet already has it. Its notes stay with the name.
- `POST .../members/{name}/rename` with `{to, carry_notes}` renames a fleet member: `to` is a member name that differs from `name` (400) and names no listed member (409). With `carry_notes: true` its `memory/<name>/` moves to `memory/<to>/`, and the whole rename is 409 if `<to>` already has a note. A `memory/<to>/` that holds no note (what a deleted last note leaves) is replaced; the source having no notes still makes a `<to>` with notes 409. Otherwise the notes stay under the old name, and show in `unclaimed` unless a built-in member of that name claims them.
- `DELETE .../members/{name}` removes the fleet file. Its notes stay; a customized built-in falls back to the built-in member.

### Adding a member

- `POST /api/fleets/{key}/crew/draft` with `{description}` runs one headless judge call (a strong model, 0.30 USD, 2 minutes) with Admiral's bundled crew-writer prompt, and writes nothing, not even the crew directory. The description is the engineer's own text, at most 4000 characters, and goes to the writer as fenced data. It is 400 when empty, blank or longer. It is 409 in two cases, and no call is made in either: `{error, reason}` when no harness is proven to run the judge call, and `{error}` with no `reason` when the fleet's crew path holds a link or a non-directory. A failed call is 502 `{error, kind}` with `kind` `timeout`, `budget spent`, `bad reply` or `error`. A cancelled request cancels the call. A 200 is `{draft, problems}`: `draft` is `{name, role, based-on, skills, model, harness, pick-me-when, instructions}` as the model wrote it (an empty field stays `""`; `harness` is always `""`), and `problems` is `[{field, message}]`, `[]` when the draft would be accepted. A problem's `field` is one of:
  - `name`: not a member name, taken by a fleet member or a built-in of any of the fleet's docks, or `crew/<name>.md` is a link or not a regular file;
  - `role`, `based-on`, `skills`, `model`, `pick-me-when` or `instructions`: the resolver would refuse the file (a custom role with no `based-on`, a skill it would drop, a file over 65536 bytes), a single-line field holds a line break, or the file would be read back differently from what was sent;
  - `skills`: more than 20 skills;
  - any of the above except `name`, for a hidden character; the message names its `U+XXXX`. Hidden means a control, format, private-use or unassigned code point, a line or paragraph separator, a blank filler (U+3164, U+115F, U+1160, U+FFA0, U+2800) or a variation selector, except U+FE0E or U+FE0F directly after an emoji or text-presentation character. `instructions` may hold line breaks and tabs.

  The reply is untrusted model output: show it, and don't act on it.
- `POST /api/fleets/{key}/crew/members` with the PUT body plus `name` creates the fleet file. 201 `{name}`. It is 400 with `field` for a failed check, as the draft's problems; 409 with `field: "name"` when a fleet member or a built-in of any dock has the name, and 409 for a link in the crew directory or at the member file. A create never overwrites.

### `POST /api/fleets/{key}/crew/notes`

`{op, member, scope, repo, note, text, to}`: `op` is `edit`, `move` or `delete`; `scope` is `fleet` or `repo` (with `repo` as `<owner>/<repo>`); `note` is the note exactly as GET returned it. `member` need not resolve, so an unclaimed name works. A `member` or `repo` that is not a valid path part is 400. The note is the first line equal to `- <note>` (a trailing `\r` ignored); none is 409, and the page reloads. Every other line of the file is kept byte for byte.

- `edit` replaces the fact and keeps the date and run. `text` is one line of visible text, at most 500 bytes, and the line must pass the resolver's note check (400).
- `move` takes `to: {scope, repo}`, removes the line and appends it unchanged to the destination, making `memory/<member>/repos/<owner>/` as needed. A destination equal to the source is 400; one that already holds 30 notes is 409.
- `delete` removes the line, and the file when no note is left (also after a `move` out of it). An empty scope is not listed.

The response is 200 with the member's notes after the change, in GET's `notes` shape.

## Campaigns

A campaign is a GitHub issue with sub-issues, followed. Admiral reads the tree through the fleet's GitHub source and never edits it; the one write is creating a campaign's parent on the engineer's confirm (ADR 0027). All routes are also served under `/api/v1/`. Errors are `{"error": "..."}`.

A campaign is:

```json
{"id":"3f9c0a41b7d2e8a5","url":"https://github.com/acme/widgets/issues/20","fleet":"work",
 "work_repo":"","ended":false,"last_read":"2026-11-11T09:00:00Z","read_error":"",
 "progress":{"closed":1,"total":4},"counts":{"ready":2,"blocked":1,"done":1},
 "root":{"number":20,"title":"...","url":"...","repo":"acme/widgets","closed":false,"parent":true,
  "status":"","blockers":[],"ship":"","mode":"","skill":{"kind":"","name":"","args":""},
  "children":[{"number":21,"status":"ready","mode":"with-you","skill":{"kind":"none","name":"","args":""},"...":"..."}]}}
```

`status` of a child is `ready`, `blocked` (`blockers` lists `{"url","title"}` of the open ones), `underway` (`ship` names the ship holding the issue), `claimed-no-ship` (assigned, no ship) or `done`. A nested parent has `"parent": true` and no status. The root, the campaign's own issue, is `"parent": true` too but carries `status`, `mode`, `skill`, `default_mode`, `default_skill` and `blockers` (its own open ones) like a child, so it can be launched by hand; it is never in the ready set, `progress` or `counts`, and a mode override never applies to it. `mode` is `with-you` or `without-you`; `skill` is what the child's ship starts on (`commodore`, `skill` with a `name`, or `none`), `args` the text after the skill name. `unreadable` appears on a node GitHub counts more sub-issues for than were read. `last_read` is when the last good read finished, and `read_error` the last failed read's message, empty after a good one: a failed read keeps the last tree. The list route leaves `root` out.

A campaign also carries:

- `title`, `number` and `repo` (`https://host/owner/repo`) of the root issue, so the list can name it without the tree;
- `followed_at`, and `ended_at` once it has ended (absent while followed);
- `end_reason`, once it has ended (absent while followed): `unfollowed` when the engineer stopped following it, `ended` when its tree closed. Only an `unfollowed` campaign can be followed again;
- `ready_with_you` and `ready_without_you`: the launchable `ready` children by their resolved mode;
- `commitment`, while the campaign's fleet has an open work commitment on it (AdmiralBot is working it), absent when Admiral only follows it: `{"id","ts","launched","waiting_children"}`, the last two left out at zero. Every route that returns a campaign carries it. A ledger that can't be read counts as no commitment;
- `reading`: `true` while a reread of this campaign is in flight, and `last_tried`, the time of the last attempt, good or bad, kept across restarts (absent before any). A failed attempt moves `last_tried` and not `last_read`, so a poller tells a read still under way from one that failed again.

Each node carries `labels` (names, `[]` when none; a parent's too, so the root's kind shows). A child also carries `default_mode` and `default_skill`, what ADR 0027's table gives it with no override, and `overridden: true` (absent otherwise) when the campaign has a mode override (even to the default), so a client can offer Use labels. A blocker is `{"url","title","capped"}`; `capped: true` marks the stand-in for the `Blocked by` lines past the cap (its `url` is the issue that carries them, not a blocker; a blocker GitHub could not be read for, past the lookup cap, is not marked), and is absent on a real blocker.

### `GET /api/campaigns[?ended=true|false]`

`{"campaigns": [...]}`, active and ended in the order they were followed; `ended` filters.

### `POST /api/campaigns`

Body `{"reference": "<issue URL or owner/repo#n>", "fleet": "<fleet key>"}`. `owner/repo#n` means github.com. `fleet` is optional: the fleet the engineer follows from. Reads the tree, stores the campaign and launches nothing. `201` with the campaign; `200` with the campaign already followed for that issue. Following a campaign the engineer unfollowed follows it again (Follow again): the tree is read first, then the end is cleared and rereads resume, and the answer is `200` with the same `id`; the campaign ends as `ended` at once if its whole tree is closed by then, and a failed read is `422` with the campaign still ended. A campaign whose tree closed is returned as it is, still ended. The campaign commitment the unfollow ended does not come back, and AdmiralBot's `work_on_campaign` does not follow an unfollowed campaign again. `400` for a reference that is not an issue (the message says what to paste); `422` when no fleet owns the repo, the fleet has no GitHub source for the issue's host (a host is compared ignoring case and must be the source's own), or the read failed.

With `fleet`, the reference must belong to that fleet: the one that follows it already, else the one that routes its repo. Another fleet's is `422` with a message naming the owning fleet, and nothing is followed. This is the engineer's own request, so it is a `422`, where `POST /api/chat/campaign-commitments` answers the same check with an actor fence's `403`. A request without `fleet` follows into whichever fleet owns the repo.

### `GET /api/fleets/<key>/campaigns/search?q=<text>`

Finds issues to follow in one fleet, for the Add campaign modal. `404` for an unknown fleet. `{"results": [...]}`, at most 20 issues from each of two GitHub searches. Both are scoped to the repos and owners the fleet's GitHub source claims (`is:issue (repo:a/b OR user:o) <text>`), and a hit in a repo that routes to another fleet is dropped, which an owner scope can reach. One search asks for parents only (`has:sub-issue`), the other for all issues. Parents come first and an issue both found shows once. Closed issues are in the list when `q` has text.

- Empty `q` lists only the fleet's open parents.
- `owner/repo#n` or an issue URL runs as a search too. When it has no hit, one read resolves it and its row comes first. A pull request, a missing issue and a repo of another fleet get no row.
- A bare `#n` searches the number and keeps only issues numbered `n`, across all the fleet's repos. (`POST /api/campaigns` still refuses a bare `#n`.) Digits alone search as plain text.
- A fleet with no repos and no owners answers `[]` without calling GitHub.

A row is `{"title", "reference": "owner/repo#n", "url", "state": "open"|"closed", "parent": bool, "progress": {"closed", "total"}, "status"}`. `progress` counts the sub-issues a parent has, `0` and `0` for a leaf. `status` is `followed`, `unfollowed` (the engineer stopped following it), `ended` (its tree closed), or `""` for a campaign not followed. A campaign stored without a reason reads `ended` when its whole tree is closed, else `unfollowed`.

`422` with `{"error"}` when gh is signed out, GitHub refuses the search or it times out (8 seconds). Not an AdmiralBot route: the guard refuses it.

### `POST /api/campaigns/create`

The engineer's confirm to make a campaign, from issues or with none. Needs a browser or CLI token: an actor token is `403`. An Inbox campaign draft is created through `POST /api/inbox/_admiral/<id>/create`, which runs the same core. Body `{"repo": "owner/name", "title": "…", "body": "…", "issues": ["<issue URL or owner/repo#n>", …], "host": "…", "fleet": "…"}`: 0 to 50 distinct issues in the order to link them, all on one host (`owner/repo#n` means github.com), the title not blank. `issues` may be empty or missing: the parent is then filed alone. `host` is optional: empty means the issues' host, or `github.com` with no issues; a value must equal the issues' host. `fleet` is optional: when given, the fleet that owns `repo` on that host must be it. Using the fleet that owns `repo`, it reads every issue first, creates the parent in `repo`, links each issue under it with one call each in the given order (none with no issues), then follows the parent as `POST /api/campaigns` does. Nothing launches. `201` with the campaign.

- `400`: the body is not JSON, `repo` is not a plain `owner/name`, the title is blank, there are more than 50 issues, a ref is repeated or can't be read. Nothing is written.
- `422`: the hosts differ (an issue's, or `host` against the issues'), no fleet owns `repo`, `fleet` is not the fleet that owns `repo`, an issue routes to another fleet or is owned by someone other than `repo`'s owner, or the fleet has no GitHub source for the host. Nothing is written.
- `409`: an issue already has a parent; the error names it. Admiral never moves an issue. Nothing is written.
- `422` too: an issue is a pull request (named in the error).
- `502` before the parent exists: an issue could not be read, or the parent could not be created. Nothing is written.
- `502` after it: `{"error": "…", "parent": "<parent URL>", "linked": ["<issue URL>", …]}`, when a link or the follow fails. `linked` holds the issues linked so far in order. Admiral deletes, retries and edits nothing, so the engineer can finish the links on GitHub.

### `GET /api/campaigns/<id>`

The campaign with its tree. Opening it rereads in the background when the last attempt is 30 seconds old or more (never for an ended campaign). `404` for an unknown id.

AdmiralBot reads it through `read_campaign {id}`; for AdmiralBot an unknown id or another fleet's campaign is the guard's `403`.

### `POST /api/campaigns/<id>/unfollow`

Ends the campaign at once; it stays readable and is listed with `ended: true` and `end_reason: "unfollowed"`. `POST /api/campaigns` follows it again. Answers the campaign.

### `PUT /api/campaigns/<id>/override`

Body `{"child_url", "mode"}`; an empty `mode` clears the override. An override sets only the mode: a body with a `skill` field is `400` whatever it holds (an object, `{}` or `null`), and nothing is stored. A skill is chosen when a child is launched. `404` when the issue is not in the campaign, `400` for a nested parent, the root or a mode that does not exist. An ended campaign's mode can still be changed. An override stored with a skill by an earlier version loads with the skill ignored and is dropped on the next write. Answers the campaign.

### `PUT /api/campaigns/<id>/work-repo`

Body `{"repo": "host/owner/repo"}` or its URL; `""` clears it. It is stored and answered as `https://host/owner/repo`, with any userinfo or query dropped. The work repo is the checkout a launch preselects, or the repo it clones, for children filed in the campaign's own repo; a child in another repo keeps its own. `400` for a value that is not a repo. Answers the campaign.

### `POST /api/campaigns/<id>/launch`

Body `{"child_url", "harness", "dir" | "clone": true, "clone_repo", "start_anyway", "model", "effort", "skill"}`; `skill` is optional and only with `child_url` (see below); `clone_repo` is the `host/owner/repo` the form showed, as for `POST /api/ships`, and when it is omitted the server uses the work repo (or the child's own repo) it would show. It launches through the same path as `POST /api/ships`, so its refusals are the same, with the source `campaign` and `<campaign id>/<child issue URL>` as `order_id`, so a child in two followed campaigns is two orders, each answered with its own campaign's skill, text, repo and panel (the campaign id). The claim is still by the child's issue URL alone: one ship holds the child in every campaign. The server sets the ship's title, `url`, text and skill; the skill is the child's resolved one unless the body sends `skill`, `autopilot` is always off, and any other such field in the body is ignored. A launch rereads the tree first when the last read is over a minute old. Answers `201 {"ship": ...}`, or:

- `404`: the issue is not in the campaign;
- `400`: it is a nested parent (the root launches like a child, its order id `<campaign id>/<root URL>`);
- `409`: the child is done, a ship holds it (the message names the ship), it is blocked (the message lists the blockers' URLs), it is assigned with no ship and `start_anyway` is not true, the campaign has ended, or any `POST /api/ships` conflict;
- the launcher's own statuses otherwise.

What the launcher puts in the prompt: the `skill` runs with the text as its argument (`/skill text`, `$skill text` on Codex). The text is the child's `skill.args` when set (`<map URL> <ticket URL>` for `/wayfinder`), else the ticket URL; a child with no skill gets its title and URL. A slice's text is its children's URLs, one per line.

A picked skill: `skill: {"kind": "commodore" | "skill" | "none", "name": ...}` with `child_url` runs that launch with that skill instead of the child's resolved one. It is for this launch only: the child's override is not changed. Another kind is `400`. A `skill` kind with an empty name or one containing whitespace (after dropping one leading `/` or `$`) is `400` with the launcher's own message (`skill name is empty`, `skill name "<x>" contains whitespace`). The server does not check that the skill is installed. When the picked skill is the child's resolved one (the same kind, and for `skill` the same name), the text is as above, with the child's saved `skill.args`; names are not compared for `commodore` and `none`. When it differs, the saved args belong to the other skill and are dropped: the text is the ticket URL, or the title and URL for `none`. Without `skill`, nothing changes. `skill` with `issues` is `400` ("a slice runs on the Commodore skill; send skill only with child_url").

A slice: `issues: ["<issue URL>", ...]` in place of `child_url` (never both, `400`) launches two or more children as one Commodore ship. `start_anyway` is not read. Every child must be ready, resolved to Without you (a mode override counts) and to the `commodore` skill kind (its label default), and all in one repo. Refusals, naming the child where one is at fault: `400` for fewer than two issues, a URL that is not an issue URL, a URL containing a comma, an issue listed twice (once normalised by the claim key), a nested parent, the root or children in two repos; `404` for an issue not in the campaign; `409` for a child that is done, blocked (listing its blockers), underway or assigned with no ship, With you, on another skill or not ready, and for any child a live ship already holds, which includes the same set launched again in any order (the message names the ship; while two such launches race it says "a launch in flight"). The ship has `autopilot` off, `issues` in the order given and a title of the first child's title and `+N`. Its `order_id` is `<campaign id>/<first issue URL>,<next>,...`, the children in launch order, where a child in the first one's repo is written as its issue number alone (`c0ffee/https://github.com/acme/widgets/issues/31,32`); that id answers `/api/launch-orders/dirs` and the clone, and the issue URLs are recovered from it. A single child's `order_id` is unchanged. The text is the child URLs, one per line, built from the URLs alone.

A campaign ends when the parent and every issue under it, nested parents included, are closed, and none has sub-issues that could not be read; or when it is unfollowed. It is reread when a child's ship anchors or sails off, when its page is opened, and every five minutes.

## A crew boat's conversation

Each boat in a ship's `crew` list carries `role` (the `--role` it was launched with, left out when none) and `conversation` (always present: `true` only for a Claude Code, Codex or Copilot boat with a recorded transcript). The recorded transcript path itself is not on the API.

### `GET /api/v1/ships/<ship>/crew/<name>/conversation[?before=<id>]`

The same body, states and paging as a ship's conversation. The file is the transcript path the boat's hooks recorded (ADR 0021), read fresh from its pane on each request. A Claude Code, Codex or Copilot boat with no path recorded yet (a Copilot boat's is recorded at its first `agentStop`) reads `none`. An anchored (exited) boat stays readable until it is closed. An unknown ship or boat is `404`, and so is a boat that was closed.

A boat has no `--session-id` of ours to check the path against, and a boat writes the path itself, so the only limit is the one every transcript read has (ADR 0019): the file must be a regular file under the boat's fleet's `<config dir>/projects/` (Copilot: `<copilot home>/session-state/<id>/events.jsonl`; Codex: `<Codex home>/sessions/`) with no symlink on the way, else `unreadable`. A boat may therefore show any transcript in its fleet's `projects/` or `session-state/`, including another session's. Binding a boat to its own session is follow-up issue #357.

### WebSocket

The ship's messages take an optional `crew` field naming the boat: `{"type": "conversation_open", "ship": "<ship>", "crew": "<name>"}` and `conversation_close` the same way. The server echoes `crew` on `conversation_opened` and on every `conversation` push for that boat; the ship's own messages have no `crew`. A boat counts toward the 16 open conversations, and its subscription ends with `conversation_close`, when the connection closes, or when the boat's window closes or the ship is dismissed.

## Usage

`GET /api/version` lists the `usage` capability when the server has these routes. Both are also served under `/api/v1/`. Figures come from the outcome log's `usage` and `advised` records (ADR 0015), read on each request, plus the live figures of ships still running. Nothing is written. Money is never added across harnesses, and there is no total across harnesses or fleets.

### `GET /api/usage[?fleet=<key>]` (alias `GET /api/v1/usage`)

With `fleet`, one fleet object; `404` `{"error":...}` when the fleet is not found. Without it, `{"fleets":[<fleet object>, ...]}` in the config's order.

```json
{"key":"work","name":"Work",
 "periods":{
  "today":{"from":"2026-11-12T00:00:00-05:00","harnesses":[
   {"harness":"claude",
    "tokens":{"input":1200,"output":300,"reasoning":0,"cache_read":9000,"cache_write":400},
    "money":{"amount":1.32,"basis":"estimate","incomplete":false},
    "spenders":{"ships":{"tokens":{...},"money":{...}},
                "chat":{"tokens":{...},"money":{...}},
                "workers":{"tokens":null,"money":{"amount":0.12,"basis":"estimate","incomplete":false}}}}]},
  "7d":{...},"30d":{...},"month":{...}},
 "quota":[{"harness":"claude","label":"claude","has_data":true,"age_seconds":90,
   "windows":[{"id":"primary","used_percent":40,"window_minutes":300,"resets_at":"2026-11-12T17:00:00Z"},
              {"id":"secondary","used_percent":10,"window_minutes":10080,"resets_at":"2026-11-13T15:00:00Z"},
              {"id":"spend","used_percent":30,"used_usd":6,"limit_usd":20,"period":"monthly","resets_at":"2026-12-01T00:00:00Z"}]},
  {"harness":"codex","label":"codex","has_data":false,"windows":[]}],
 "quota_hold":{"held":true,"harness":"claude","window":"primary","window_minutes":300,"used_percent":93,"line_percent":90,"resets_at":"2026-11-12T17:00:00Z"}}
```

- `periods`: `today` starts at local midnight, `7d` is today and the 6 days before it, `30d` is today and the 29 before it, and `month` starts on the local 1st. `from` is that start in the server's local zone. A record counts in a period when its `ts` is not before `from`.
- `harnesses` is sorted by name, `[]` when the fleet used nothing, and holds a harness only when something was recorded for it. Each entry's `tokens` and `money` are the sum of its `spenders`. A spender is `ships` (ship records, plus the live figures of the fleet's running ships), `chat` (AdmiralBot, ship `_chat`) or `workers` (the `cost` of the fleet's `advised` records, USD `estimate`, no tokens); one with nothing is left out.
- Only a record's top-level `tokens` and `money` are summed: its crew boats are already inside. `tokens` has the five disjoint classes, or is `null` when nothing reported any.
- `money` is `{"amount","basis","incomplete"}` plus `premium_requests` when the harness gave one, or `null`. `basis` is `estimate` (US dollars, Claude) or `credits` (Copilot); Codex has no money. A harness's money is `incomplete` when the harness itself said so, or when some record or live reading it sums had none. `premium_requests` sums the values that are present, and the money is also `incomplete` when some part of the sum had none (and at least one had).
- A running ship's live figures count in every period, whenever it launched; the records of ended ships count in the period of their `ts`. AdmiralBot's live spend is not counted, only its records, so `chat` lags until its next record.
- `advised` records written before they carried a `fleet` belong to no fleet and are left out.
- `quota` has one entry per login of the fleet's docks that has a plan quota (Claude and Codex, in dock order), whether or not a ship is running. `label` is the harness; the login's directory is never sent. `has_data` is `false` after a restart until a figure arrives, and the entry then has no `age_seconds` and no windows. `windows` are `primary` and `secondary` (rate-limit windows, with `window_minutes`) and, on Claude, `spend` (the monthly spend limit). `age_seconds` is how old the last reading is. A window past its `resets_at` reads `used_percent: 0`. Live figures and quota are in memory only.
- `quota_hold` is present only while unattended launches (routine runs, commitments, review-wake rounds) are held for quota: some `primary` or `secondary` window of the first Claude or Codex login that has one is at or above the fleet's `quota_hold_percent` (`line_percent`). `window` says which, `window_minutes` and `resets_at` are as in `quota`, and the hold lifts when the window resets. Spend never counts, and a login with no window figure is never held. Hand launches, AdmiralBot launching on an instruction and accepted proposals are never held. The refusal's `Wait` text, which a commitment keeps as `wait_reason` and a moored ship shows as its waiting text, reads `Held for quota: Claude's 5-hour window is at 93% (line 90%), resets 14:00`.

### `GET /api/ships/<session>/usage` (alias `GET /api/v1/ships/<session>/usage`)

```json
{"session":"saltpaw-ii","harness":"claude","source":"live",
 "tokens":{"input":43,"output":2,"reasoning":0,"cache_read":0,"cache_write":0},
 "money":{"amount":0.3,"basis":"estimate","incomplete":false},
 "age_seconds":7,"at":"2026-11-12T08:00:00Z"}
```

The sum of the ship's `usage` records from its first launch on (one for each round of a moored ship) plus its live figures while it runs. The first launch is the newest fresh `launched` record for the name, so an earlier ship that had the name adds nothing, and month files that end before it are not read; a ship with no `launched` record counts from the start of the log. `source` is `live` when live figures are included (`age_seconds` is theirs), `record` when only records are, and `none` with `tokens` and `money` `null` when there are neither. `at` is the latest record's time, left out when there is none. `404` for a ship not in the ships list.

## Routines and Hold fire

A fleet's routines, their trigger log and Hold fire. A save is checked before it is stored; every route is also served under `/api/v1/`. Every error is `{"error": "…"}`: 404 for an unknown fleet or routine, 400 for a body that isn't a routine or fails a check, 403 for AdmiralBot turning Hold fire off. AdmiralBot's actor may read routines, read Hold fire, draft a routine, turn a routine off and turn its own fleet's Hold fire on (see "AdmiralBot's requests"); every other route here is 403 for it.

A routine:

```json
{"id": "9f2c…", "name": "Nightly sweep", "enabled": true, "when": "30 8 * * 1-5",
 "do": {"launch": {"harness": "claude", "dir": "/path/repo", "text": "sweep the board", "model": "sonnet", "effort": "high", "args": ["--effort", "high"]}},
 "before_acting": "ask_first", "notify": true, "created_at": "2026-11-12T08:00:00Z", "updated_at": "2026-11-12T08:00:00Z"}
```

- `name` is at most 80 characters, with no control characters and no `[` or `]` (400 otherwise, on create and update).
- `off_by` is set by the server when a routine is turned off: `"admiralbot"` when AdmiralBot turned it off. Turning it on clears it, an update keeps it, and a routine the engineer turned off has none.
- `when` is a standard 5-field cron expression (`*`, lists, ranges, steps, month and weekday names) in the server's local time zone, and it must fire at some time in the next five years (`0 0 30 2 *` is refused). A fixed hour runs once on the day clocks go back, not in the repeated hour, and a fixed time the spring-forward gap skips (`30 2 * * *`) runs once at the first instant after the gap, as Vixie cron does; a wildcard hour (`30 * * * *`) runs in every hour that exists.
- `on` replaces `when` for a routine that runs on a source event: `{"source": "<source key>", "kind": "review_requested", "panel": "mine"}`. `panel` is left out unless the source's catalog gives the kind a panel (then it is required). A routine has exactly one of `when` and `on`; an `on` routine is saved with `when` empty, is refused unless the fleet has that source and the source lists the kind, and cannot use a prompt `do`. It never fires on a schedule. An event routine on the built-in GitHub source fires only for events on a repository among its Checkout's remotes, any remote and not only `origin`, matched by lower-case owner/name with the host ignored and read when the event arrives; an out-of-scope event is treated as one of another kind: nothing is decided, recorded or proposed. A plugin source's events aren't scoped. An event runs it at Report only, Ask first or Act: with Act it launches a ship at the level the sender's trust tier and the fleet's Limits allow (A3 restricted, A4, or A5 for a Commodore spec), and any budget, a busy routine, the cap, a quota hold, a resource in use, an unknown ship host (`host_unknown`) or a failed Lookout drops it to a proposal.
- `do` is exactly one of `launch` (the launch form's fields, plus `args`, extra harness args the form has no field for), `prompt` (an AdmiralBot prompt) and `digest` (`{"extra": "lead with PRs"}`, the extra words optional and at most 1,000 characters; `{}` is a digest with none). A digest runs on a schedule only: with an `on` the save is `400`. It never acts: at each run Admiral gathers what changed in the routine's fleet since the last digest run that queued a turn or found nothing new (the routine's creation for the first), and queues one `[Digest: <name>]` turn for AdmiralBot on the fleet's report-turn queue, where it waits for an idle chat and every AdmiralBot write is refused during it. The record in Recent runs is `queued`, or `skipped` with the reason `nothing new` when no section has a fact (ships that sailed off or anchored, ships moored with a PR, the Inbox when an item other than a routine or event proposal arrived (those are in the routine runs), campaign children that closed or became ready since this routine's last such run, other routines' runs), or `failed` when the fleet's chat is off or the facts can't be read; only the first two move the next window. Before acting and Hold fire work as for a prompt: Report only records `reported`, Ask first and a held Act make a proposal whose accept queues the digest. A `queued` run sends no routine push, since AdmiralBot's reply does. A launch needs a `harness` (the form's Dock) and a `dir` (Checkout), and `text` unless the routine has an `on`; each missing one is its own `400` that starts with its label (`invalid routine: Dock …`, `Checkout …`, `Text …`), checked in that order. An event routine on the built-in GitHub source (plugin `github`) also needs a Checkout with a git remote, or the save is `400` (`Checkout has no remote, so a GitHub event routine on it never fires`); a schedule routine and a plugin-source event routine need none. An event routine's ship, from an Act launch or an accepted proposal, starts from the event's pull request or issue URL when the event's `ref` is one on github.com or a GitHub host the fleet has a source for: the prompt is the skill (when the routine has one) and the URL, a blank line, then `text` when it has any, and the ship's `url` is that URL (an issue URL claims the issue like any ship with that URL). Any other `ref` gives no URL and the ship starts from `text` alone; an event with no such URL and a routine with no `text` fails, with a record in Recent runs saying so, and starts no ship. A launch is refused unless the fleet has the dock, the harness's autopilot guard and the fleet's advisor are proven, and `args` pass the autopilot args allowlist. `resources` names resources the config has (refused otherwise) that the ship holds while it is underway or needs you, and `skill` is the launch form's `{"kind", "name"}` (empty means just launch); both are checked on save and again when the run fires.
- `before_acting` is `report_only`, `ask_first` or `act`. While Hold fire is on, `act` runs as `ask_first`; the stored value doesn't change.

### `GET /api/fleets/<key>/routines`

`{"routines": [<routine>, …]}`, `[]` when there are none. The body always carries `zone`, the name of the time zone the scheduler runs in (the server's, such as `America/Denver`), which the Routines screen shows beside each schedule's description. Each routine also carries `last_run: {"at", "outcome"}`, the newest record of its trigger log (see `…/runs`), and none while it has never run. The other routes return the routine without it. The body also carries `spend: {"today_usd", "cap_usd", "reached"}`: the fleet's worker spend today (the sum of every trigger record's `costs` since local midnight, the sum an event is checked against), its `spend.daily_worker_usd` Limit, and whether the first has reached the second. Once `reached` is true, events from this fleet stop at a proposal until the day turns, and the Routines screen says so. When today's trigger log can't be read, `spend` is `{"today_usd": 0, "cap_usd", "reached": true, "unreadable": true}`: events are held at a proposal, as the event path does, and the screen says the spend could not be read. `unreadable` is left out when the read works.

### `GET /api/sources`

Every source, each `{"key", "name", "plugin", "fleet", "icon_url", "capabilities", "has_schema", "state", "read_only", "error", "auth", "viewer", "refreshing", "warnings", "views"}`, and a GitHub source also carries `connection`. `viewer` is the signed-in login a built-in GitHub source's searches ran as, such as `alice`; a plugin source and a GitHub source before its first answer omit it. A client reads a layer as the fleet user's own when its order `author` equals `viewer`. A source that raises events also carries `events: [{"kind", "title", "panel"?}]`, its event catalog: one entry for each kind and panel a routine's `on` may name, with `title` the words to show ("Review requested of you", "Assigned to you"). `events` is left out until the source has listed them, so a client that needs it waits and asks again.

A GitHub source also carries `tabs: [{"id", "title"}]`, its visible views in list order with their effective titles, `for-you` included (hidden ones are left out; `[]` when every view is hidden). Orders draws its tabs from it, and `for-you`'s tab keeps that id when renamed. A source that isn't GitHub has no `tabs`.

`refreshing` is a boolean, true while the source pulls orders: from a refresh request or the start of a timed cycle until a cycle ends with no further refresh queued, whether it succeeded or failed. A refresh asked for mid-cycle queues one more cycle and `refreshing` stays true through it. The WebSocket `sources` push sends each change at once. A plugin source is always `false`, since the plugin protocol has no such signal. The pulled orders and `refreshed_at` may land a moment after it turns false.

`views` is `[{"id", "title", "orders", "error"?, "refreshed_at"?}]`, one for each panel the source lists. `error` is Admiral's message when the view's last answer failed; the orders beside it are the last good ones. `refreshed_at` (RFC 3339) is when the view last answered successfully: for the built-in GitHub source, the time its search finished, so a search that finds the same orders still moves it; for a plugin, the time of the last good `orders.list`. It is left out until the first success, a failure leaves it as it was, and it survives a panels re-list and a settings Restart. A GitHub view also keeps its orders across a Restart until the new search answers. A plugin can't set it.

Each order is `{"id", "title", "text", "url", "hot", "repo", "labels"?, "sub_issues"?, "parent"?, "stack"?, "pr"?, "author"?, "opened_at"?, "excerpt"?, "review_requested_at"?, "reviewed_since_push"?}`. The fields after `hot` are left out when unknown or zero:

- `author`: the login of whoever opened it, one line of at most 100 runes.
- `opened_at`: when it was opened, RFC 3339.
- `excerpt`: the body as one line. Whitespace runs become one space, other control characters and Unicode format characters (zero-width, bidi overrides and isolates, byte order mark) go, the ends are trimmed, and a body over 280 runes is cut there with `…` added. Left out when nothing is left.
- `sub_issues`: how many sub-issues an issue has.
- `parent`: the issue's GitHub parent, `{"id", "title", "url", "repo"?}`. `id` has the form of an order's own `id`, so a client finds the parent in a view by comparing ids; `repo` is the parent's repository URL, like an order's `repo`. Left out when the issue has no parent, when GitHub won't show the parent to the signed-in account (it answers `null` with an error on that field, which the search ignores while the rest of the answer stands), and always on a pull request. Only the direct parent is read, one level.
- `stack`: the GitHub stack a pull request sits in, `{"number", "url", "position", "size"}`. `conflicts_with_base` is added (the base branch name) to every pull request of a stack whose top, as a whole, conflicts with the base of its lowest open layer in the view; see `chain` for the check. `url` is `https://<host>/<owner>/<repo>/stack/<number>`, the shape a ship launched on a GitHub stack carries. `position` is GitHub's own and layers sort ascending from the bottom, so a client must not read it as 0- or 1-based; `size` is GitHub's count of layers in the stack, not how many a view shows. Left out when the pull request is in no GitHub stack (pull requests that only chain by base and head branch have none, and carry `chain` instead), when GitHub won't show it to the signed-in account (an error on that field, which the search ignores like a parent's), and always on an issue.
- `chain`: the chain of pull requests a pull request belongs to when they build on each other by branch but GitHub has not stacked them, `{"id", "position", "size", "head", "base", "mine"}` plus `conflicts_with_base` when the chain as a whole conflicts with the base of its bottom PR (the whole-stack check is `internal/moor`'s `StackChecker`, asked in the background per chain or stack of two or more open layers that are all `MERGEABLE`, and for a stack only when every layer between the lowest and highest in the view is in the view; the orders serve the last answer, and a check that cannot run leaves the field out). Admiral finds chains among the pull requests of one view, per repository: a chain starts at an open pull request based on the repository's default branch and climbs through the pull requests based on the head below it, and it holds at least two. Where several pull requests are based on one head, the chain follows the one with the strictly longest run above it and the others carry no `chain`; an even fork ends the chain below it, so a fork at the bottom gives none. `id` is the bottom pull request's URL, shared by the group; `position` counts from 1 at the bottom; `size` is the chain's length in the view, not on GitHub; `head` and `base` are this pull request's own branches. `mine` is true only when every pull request of the chain was authored by the account the view's search ran as, which is the only chain `POST /api/sources/<key>/stack` accepts. Left out on an issue, on a pull request that has a `stack`, and when the pull request is in no chain. A plugin's orders never carry it.
- `pr`: a pull request's state, `{"state", "review", "checks", "mergeable", "conflicts", "ready", "draft"?, "failing_check_count"?}`. `draft` is true while the pull request is a draft (GitHub's `isDraft`), and false when it is not; the key is left out when the source does not say, and a consumer then shows neither state. `failing_check_count` counts the failing checks, with the same states the moor poll calls failing (check runs `FAILURE`, `TIMED_OUT`, `STARTUP_FAILURE`, `ACTION_REQUIRED`; statuses `ERROR`, `FAILURE`), and is left out when none.
- `review_requested_at` (pull requests): when the signed-in account was last asked, by name, to review it, from the newest of its last 10 review requests; left out when that window holds none or the request went to a team.
- `reviewed_since_push` (pull requests): `true` when the account's latest review is submitted (`APPROVED`, `CHANGES_REQUESTED` or `COMMENTED`) on the pull request's current head commit, otherwise `false`.

A plugin may send the same fields. Each is checked on its own and a bad one, or one of the wrong JSON type, is dropped with the order kept: `opened_at` and `review_requested_at` must be RFC 3339, `author` one line of at most 100 runes with no control or format character, `excerpt` is read by the rule above, `reviewed_since_push` must be a boolean and `pr.failing_check_count` a non-negative integer. A `parent` that is not an object, or whose `id` is empty or holds a control character, or whose `url` is not a safe URL, is dropped and the order kept; its `title` is one line and falls back to the `id` when it is empty or not a string, and a `repo` that is not a repository URL is left out. An order served with a `pr` gets no `parent`; a `pr` that fails its own checks is dropped, and the `parent` then stays.

`connection` (GitHub sources only; no other source has it) is the source's sign-in status, `{"state", "host", "account"?, "login"?, "checked_at"?, "fix", "message"?}`, and the WebSocket `sources` push carries it too. `state` is `connected`, `signed_out`, `gh_missing`, `unreachable` (`Couldn't reach <host>`: the network failed, not a sign-in state; a gh call that runs out of time reads `GitHub took too long to answer` and leaves the state as it was) or `checking` before the first check finishes. `host` and `account` are the source's settings (`host` defaults to `github.com`), `login` is who gh is signed in as when known, `checked_at` is when the token was last checked (RFC 3339), and `message` is the text of the last refusal or error. It is set whenever the state isn't `connected`, and a Check again that GitHub refused for a reason other than the token leaves `connected` in place with that text in `message`. `fix` lists the commands to run, in order: `gh auth login -h <host>` when signed out, `brew install gh` then that when gh is missing, otherwise `[]`. Each refresh updates it, and it survives a settings save or restart. Only a query that GitHub answered sets `connected`. A token GitHub no longer accepts (a revoked or expired one: HTTP 401, "Bad credentials") is `signed_out` with the refusal as `message` and the login command as `fix`. Any other refusal is that view's `error` and leaves the connection as it was. `auth` and `state: "auth_required"` work as before.

### `POST /api/sources/<key>/refresh` (alias `POST /api/v1/sources/<key>/refresh`)

Asks the source to look again now. Body: `{"panel": "<view id>"}`, or none for every view. It answers `200 {"refreshing": "<key>"}` once the source has taken the request, not when it has an answer: the GitHub source only wakes its search worker, so the new orders and `refreshed_at` arrive afterwards, through the same stream as any other change. Progress shows as `refreshing` on the source. A view's search may run up to 60 seconds; any other gh call is cut off after 8, and a call cut off reads `GitHub took too long to answer` as the view's `error`. Errors: `400` for a body that is not valid JSON; `404` for an unknown source; `409` when the source does not list `refresh` in its `capabilities` (`The source cannot refresh orders`), is read-only, or is not running; a plugin that refuses the call answers `422`.

### `GET /api/sources/<key>/pr?url=<PR URL>` (alias `GET /api/v1/sources/<key>/pr?url=<PR URL>`)

Reads one pull request fresh from GitHub through the source's connection, for the Orders flyout's review status, with one query and a 15 second limit. Any running GitHub source serves it, whether or not it has a `refresh` capability, and it needs no merge token. Response `200` with the same body as `GET /api/ships/<session>/pr`, except that `reviewing` is always `false` and there is no `answer_all`, since both belong to a ship. Errors, each with a one-line message: `404` no such source; `409` the source is not running, is read-only, is not the built-in GitHub one, or has not signed in to GitHub; `422` a `url` that is not a pull request on the source's host; `502` GitHub failed or has no such pull request.

### `POST /api/sources/<key>/stack`

Stack on GitHub from a view: the engineer makes the chained pull requests of a GitHub source one stack, the same link as `POST /api/ships/<session>/stack` makes for a ship's. It takes the same `X-Admiral-Merge-Token` and origin check as Merge (a missing or wrong token answers `403` and runs no `gh`), and AdmiralBot may not call it. Body: `{"prs": ["<pull request URL>", …]}`, bottom to top as the view's `chain` shows them.

Admiral reads each pull request fresh through the source's GitHub connection and links only when they read `chained` and the account the source is signed in as authored every one: someone else's pull request is refused before any `gh stack link`. It then runs `gh stack link --base <branch> <n> <n> …` once, the way the ship route does, refreshes the source so the group comes back as a real `Stack #n`, and answers `200` with the shape read again, `{"shape", "stack_number"?, "prs"}`, the answer of `GET /api/ships/<session>/stack`. One link runs at a time per source. Errors: `403` as above; `404` no such source; `409` the source is not the built-in GitHub one, is read-only or not running, a link for it is under way, the pull requests are in more than one repository, are fewer than two, do not read `chained`, or are not all the account's; `422` a pull request whose URL is not on the source's host, refused before GitHub is read; `502` GitHub or `gh` failed, with the message; `504` `gh` ran past 2 minutes, so the result is unknown, and the next refresh shows it.

`GET /api/sources/<key>/settings` of a GitHub source adds the `id` the server gives each custom view in `views` (the slug of its title, `-2` and so on for a repeat), and `builtin: true` beside the `id` of each built-in entry (one whose `id` is a built-in's and that holds no `query`); a save ignores both. A save refuses a `host` that is not a hostname (letters, digits, dots and dashes, with an optional `:port`; empty keeps the default) with `400`.

A GitHub source's `views` setting, read from `GET /api/sources/<key>/settings` and written by `PUT /api/sources/<key>`, is one ordered list, and its order is the tab order. A built-in entry is `{"id", "hidden", "title"?}` with `id` one of `for-you`, `assigned-to-me`, `review-requested` and `my-prs`; `title` renames its label only, and its search always comes from Admiral. `for-you` is never a search, a panel or counted. A custom entry is `{"title", "query"}` and may carry `hidden`. The source's `views` in `GET /api/sources` hold only the visible search views, in list order, with their titles. A custom view whose title slugs to a built-in's id sits beside it and gets `<id>-2`; the one-time migration that adds the built-ins reads the source's old `panel_order` through that move. A built-in missing from a stored list is added after the entries present (a list with none gets all four in front), and a save through `PUT /api/sources/<key>` or `POST /api/sources` stores them. For a GitHub source `PUT /api/sources/<key>/panel-order` reorders `views`, and `panel_order` is not used.

### `GET /api/sources/<key>/repos`

What routes to the source's fleet from the source's host: `{"repos": ["acme/widgets", …], "owners": ["acme", …], "default": true, "warnings": ["…"]}`. `repos` are the checked-out repos the fleet wins and `owners` the owners it lists, both sorted, without the host and `[]` when empty. `default` is true when the fleet is the default one, which takes what no other fleet claims. `warnings` is the router's lines for the fleet, such as `acme/widgets is checked out in fleets a and b; a takes its items`, `[]` when none. Read-only and never cached (`Cache-Control: no-store`). Errors: `404` for an unknown source, `400` for a source that isn't GitHub. AdmiralBot is refused.

### `POST /api/sources/<key>/connection/check`

Checks the token and who gh is signed in as now, waits for the answer, stores it as above and answers `200` with the `connection` object. A check that finds gh signed in clears `auth_required` and wakes the source's searches. A viewer query refused for a bad token is `signed_out`; any other refusal keeps the last state and puts the refusal in `message`. A request the client abandons records nothing. Signing in happens outside Admiral; this route only reads. Errors: `404` for an unknown source, `400` for a source that isn't GitHub, `409` while the source isn't running.

### `POST /api/sources/<key>/search-count`

Body: `{"query": "<GitHub search>"}` or `{"view": "<view id>"}` (a built-in's or a custom view's id, hidden ones included). It answers `200 {"count": N}`, GitHub's total for the search (`issueCount`), with no `sort:` added, not cached, and not the Orders list: the list holds at most 50, drops items routed to another fleet and hides orders a ship holds. Errors: `400` for an empty query, one over 1024 bytes, neither field, `for-you` (not a search) or an unknown view, or a source that isn't GitHub; `404` for an unknown source; `409` while the source isn't running, and `409 {"error", "connection"}` when gh is signed out or missing, without searching; `409 {"error", "connection"}` too when GitHub rejects the token; `422 {"error": "Search failed: …"}` when GitHub refuses the search for another reason, and `422 {"error": "GitHub took too long to answer"}` when a call ran out of time (the connection stays as it was); `502` when GitHub can't be reached. A good count, like a good Check again, sets `connected`.

### `GET /api/sources/<key>/page` and `GET /api/sources/<key>/rows/<id>`

A module's page and one row's detail view; the plugin side is in [A module's page](plugins.md#a-modules-page). Both answer `404 {"error"}` for a source that does not exist, and `404 {"error":"The source has no page"}` for one whose plugin does not declare `page` once the plugin has answered `initialize` without it. Until that first `initialize` answer, the page answers `starting` as below and a row answers `404 {"error":"The page has no such row"}`.

The page answers `200 {"state","groups","waiting","notices","auth"?,"error"?}`. `notices` is a module's notices: `[{"id","text","tone","link"?,"action"?}]` in order, `[]` when there are none, with `tone` one of `info`, `warn` or `error` and `link` `{"label","url"}`, left out when there is none, and `action` a module action as below (a built-in action is dropped on a notice), left out when there is none. They are part of the last good page and never count toward `waiting`. `state` is one of:

- `starting`, with `groups: []` and `waiting: 0`, until the plugin's first good `page.get`. An answer with `loading: true` is not good for this: the state stays `starting` and serves that answer's notices, while its groups and `waiting` are ignored. After a good page, a `loading: true` answer changes nothing. A restart after a good page keeps `ready` and its groups.
- `ready`, once there is a good page.
- `auth_required`, while the source is: `auth` is `{"message","url","code"}`, the same fields the source's `auth` shows.
- `error`, when the source is in `error` (a crash, which is also `state: "error"` on the source, with `error` as its message) or when the plugin's last `page.get` failed with an error of its own (`error` is its message and the source stays `ok`). The next good `page.get` clears it.

`auth_required` and `error` keep the last good groups, `waiting` and notices, and are `groups: []` when there has been no good page. Restart is `POST /api/sources/<key>/restart`. A `page.get` that is refused (over a limit, not valid) or times out only logs: the state stays as it was, with the last good page. A group is `{"id","title","rows"}`, a row is `{"id","title","subtitle","url","chips":[{"label","tone"}],"reason","target","action","actions"}`, a target is `{"label","chips","step"}` and an action is `{"id","label","confirm","summary","url"}`, with a row's `url` and `target`, a target's `step`, and `action`, `actions` and an action's `url` left out when there are none. A step in a row's sections is `{"id","title","subtitle","chips","actions"}`, with `subtitle` left out when there is none.

A row answers `200 {"sections":[...]}`, from `row.get`, and passes each repeated `include` query parameter (`?include=closed&include=queued`) to it as a list. An `{id}` that is not a row on the last good page answers `404` and the plugin is not asked. More than 10 `include` values, or one over 200 characters, answers `400`. A plugin that is not running, or a `row.get` that errors, times out or is over its limit answers `502 {"error"}` with a one-line message.

### `POST /api/sources/<key>/rows/<id>/actions/<action>/form` and `…/run`

Fetch a module action's form, and run the module action; the plugin side is in [A module's page](plugins.md#a-modules-page). Both are the engineer's alone: AdmiralBot gets `403`. `<action>` is a module action id of the row: the row's `action`, one of its `actions`, or one in a step of the row's last good detail view (it is known only once `GET …/rows/<id>` has answered). The first module action with an id wins.

`/form` answers `200 {"title"?,"fields":[...]}`, the validated form (see the plugin docs for what Admiral drops). `/run` takes `{"values": {...}}`, an object of strings or lists of strings (a missing `values` is `{}`), and answers `200 {"message","url"?}`; `url` is left out unless it is an http(s) link of at most 2,000 bytes. A form can be fetched while a run is open on the row; only `/run` is refused then.

Checked in this order, and the plugin is not asked until all pass:

1. `404`: an unknown source; a source with no page; a row not on the last good page; a module action id the row does not have; `/form` on one whose `confirm` is not `form`; `/form` or `/run` on a built-in action (Open link, Launch or Message AdmiralBot).
2. `409`: the source is not running; the page's state is `error` (`auth_required` does not stop module actions); `/run` while another run is open on the row. The slot stays held until the plugin answers or the run timeout (60 seconds) passes, even when the client goes away.
3. `400`, `/run` only: a body that is not one JSON object (anything after it, such as `{}x`, counts), over 1 MiB, or `values` that is not an object of strings and lists of strings or is over a limit (50 fields, 100 items in a list, 1,000 characters in a string), with a one-line message. An empty body, `null` and a missing or `null` `values` count as `values: {}`.
4. The call: `action.form` within 10 seconds, `action.run` within 60. `422` when the plugin refuses it (its message, cut to one line of 300 characters), `504` when it does not answer in time, `502` when it can't be reached, or when its answer is invalid (a form over a limit or out of shape, such as a `choice` or `checklist` with no options, or a run answer with no `message`), with a one-line message.

A run changes the page through the plugin's own `page.changed`; no live message is sent for it.

### `POST /api/sources/<key>/notices/<id>/actions/<action>/form` and `…/run`

The same two routes for a notice's action, with the same bodies, answers and status codes, and the same check order. Both are the engineer's alone: AdmiralBot gets `403`. `<action>` is the `id` of the notice's one `action`, found among the notices Admiral serves, which include a `loading: true` answer's notices before the first good page. The `404` refusals are worded for the notice: `The page has no such notice` for an id that is not a notice (a row id is not one), and `The notice has no such module action` for a notice with no action or another id. `/run` while another run is open on the notice is `409 A module action is already running on this notice`. A notice and a row with the same id hold separate run slots. The plugin gets `action.form {"notice","action"}` and `action.run {"notice","action","values"}`, with `notice` where a row's call has `row`.

### `GET /api/sources/<key>/rows/<id>/actions/<action>/launch`

Looks up a Launch built-in action; the plugin side is in [A module's page](plugins.md#a-modules-page). The engineer's alone: AdmiralBot gets `403`. It reads the action from the stored page, so it works while the source is down or the page is in `error`, and never calls the plugin. Answers `200 {"url","fleet"}`: the issue in its claim form (`https`, lower case, no fragment) and the key of the fleet the issue routes to. The launch itself is the normal `POST /api/ships` with `issues: ["<url>"]` and that `fleet`.

Errors: `404` for an unknown source, a row or action not on the page, or an action that is not a Launch; `400` when the `url` is not an `https` GitHub issue on a host that fleet uses, or when the issue routes to no fleet; `503` when Admiral cannot read the ships' claims; `409` when the issue already has a ship, a pending launch or a launch in flight.

### `GET` and `POST /api/sources/<key>/rows/<id>/actions/<action>/message`

Previews and sends a Message AdmiralBot built-in action. The engineer's alone: AdmiralBot gets `403`. Both compose the text from the stored page and the kind's declaration, with no plugin call, so they work while the source is down.

`GET` answers `200 {"text","fleet","chat"}`: the exact text, the module's fleet, and the chat's shell path (`/app/chat?fleet=<fleet>`). The text is `*From the <page>:* <job> Row: <ref>`, `\n`, a fence of backticks (at least five, longer than any run in the title), `\n`, the title, `\n`, the same fence, `\n` and the link, with no trailing newline. `POST` takes `{"text"}`, the text the client showed, and posts it to that fleet's chat as the engineer only when it equals the text composed now, byte for byte. It answers `200 {"sent": true, "chat"}`.

Errors: `404` for an unknown source, a row or action not on the page, an action that is not a message, or a kind the plugin did not declare; `409` when the page is in `error`, or on `POST` when the text is not the composed one (nothing is posted; ask `GET` again); `400` for a body that is not one JSON object (data after it counts); `503` when Admiral has no chat to send to. The chat's own refusal passes through: `404` for no such fleet, `409` when its chat is off or not running, `502` when the paste failed.

### `POST /api/sources/<key>/page/refresh`

Asks the plugin to look again now, with `page.refresh {}` within the 10-second call limit, then asks `page.get`. It answers `200 {"refreshing": "<key>"}` when the plugin has taken the call; the new page arrives afterwards as a live update. Errors: `404` for an unknown source or one with no page (`The source has no page`); `409` when the source is not running; `422` when the plugin refuses the call, `504` when it does not answer in time and `502` for any other failure.

### A page's live update

A source that declares `page` carries `page: {"state","waiting","version","rows"?}` in its entry of `GET /api/sources` and of the WebSocket `sources` message, which goes out on every change. A source with no page has no `page` key, and a source has none before its first `initialize` answer. `state` and `waiting` are the page's, as above (`waiting` is the count for the module's own nav badge).

`version` goes up on every change of the page a client reads: a new good page, a change of `state`, and every `page.changed` the plugin sends, even when the `page.get` it caused is refused or fails. A client refetches `GET …/page` when `version` moves. `rows` holds the row ids the last `page.changed`s named, with the ones that coalesced into one `page.get` joined; it is absent when the last change named none (a `page.changed` without rows, a new page from a refresh or restart, a state change), and absent means every row. The server keeps no row details: a client asks `GET …/rows/<id>` again for each named row it has open, or for every open row when `rows` is absent. Two rules for a client: a `version` that jumps by more than 1 means every row, since the message may have joined several changes; and a named row that has left the page answers `404`. The `page` block keeps through a restart: while the source starts again it still shows the last `state`, `waiting` and `version`.

Both answer `409 {"error"}` for a GitHub source, which is always present, and change nothing. A settings save still restarts it internally.

### `GET /api/fleets/<key>/routines/<id>/runs[?limit=<n>]`

The routine's trigger-log records, newest first (default 20): `{"runs": [{"id", "at", "routine", "outcome", "tier", …}]}`. `outcome` is `launched`, `proposed`, `skipped`, `missed`, `failed`, `reported`, `queued` (a fleet digest turn waiting on the chat's report-turn queue) or `breaker`. `reported` is a Report only run, whose `action` says what it would have launched; `breaker` is the record written when three launches in a row failed or were undone and `before_acting` was set to `ask_first`. A launch whose ship later ended failed reads `failed` with the reason. A run that waits for a free ship slot, a resource or Admiral's terminal host writes no record until it has launched. An event run's record also carries `event` (the item's URL), `sender` (who did it), `rule` (the routine's id), `reason` (why it was held down or skipped, comma separated), `dedupe_key` (what two events about the same work share), `held_by` (the session of the ship that already had the item, on a `skipped` record with reason `ref_has_ship`) and `costs`, `[{"call", "usd"}]` for the judge calls made for the event; the day's spend sums every record's costs. An event on a pull request or issue that a listed ship already has (its order URL, a PR it opened, an issue it claims, or the event key of the event that launched it) is skipped for every matching routine with reason `ref_has_ship` and `held_by` naming that ship; it makes no proposal. The Lookout's costs sit on the first record an event writes; each reviewer call's cost (`call` `reviewer`, or `reviewer_estimated` for a capped timeout) sits on the record of the routine it judged. `tier` is `T1`, `T2` or `T3`. A run still waiting when the next scheduled run comes, when its routine is turned off or deleted, or once it is 12 hours late, writes a `skipped` record saying so. A `before_acting` that is not `report_only`, `ask_first` or `act` (a hand-edited file) is `failed` (`before_acting is not valid`) and launches nothing, Hold fire or not. The start-up catch-up waits for the terminal host to know the ships, and checks the circuit breaker like any run. A prompt run that fails counts toward the breaker like a refused launch. A prompt run is `launched` with no `ship`. A launch that was undone has `undone: true` and `undone_at`; one that was promoted has `promoted: true`, `promoted_ship` and `promoted_at`. `event`, `sender`, `rule`, `reason`, `action`, `ship` and `via` (`proposal` for a run launched from an Inbox proposal) appear when set. In a fleet with Checks, an event routine whose provisional level is A3 or higher is judged by the step reviewer, and its record carries `verdict` (`allow`, `ask` or `block`), `check_id` (the first 8 hex characters of the sha256 of the Check's text, empty when none decided) and `reviewer_reason` (the reviewer's reason, or why it was not or could not be asked, such as `reviewer failed: timeout`, `checks unreadable` or `daily spend reached`), apart from `reason`. A routine held at A1 or below by another budget is not judged and has none of the three. A launched event record also carries `restricted` (`investigate` or `draft_fix`, for an A3 ship) and `worker_launched` (`true`: the ship was started by an event, so it reads the event text and the fleet's Guidance); the record holds no event text. The log is `$ADMIRAL_HOME/routines/<key>/triggers.jsonl`, append-only.

### `GET /api/fleets/<key>/hold-fire`, `POST …/hold-fire/on` and `…/hold-fire/off`

```json
{"on": true, "fleet": {"on": false, "by": "engineer", "at": "2026-11-12T08:00:00Z"}, "global": {"on": true, "by": "engineer", "at": "2026-11-12T08:00:00Z"}, "worker_ships": 2, "all_worker_ships": 3}
```

`worker_ships` is how many worker-launched ships of the fleet are live (underway or needs you), and `all_worker_ships` how many in every fleet; the Routines screen reads them for its Stop all buttons. `on` is true when the fleet's switch or the all-fleets one is. `by` is `engineer` or `admiralbot` (a request with AdmiralBot's actor context); AdmiralBot may turn Hold fire on only in its own fleet and never off (`403`). Turning a fleet off leaves the all-fleets switch as it was.

### `GET /api/hold-fire`, `POST /api/hold-fire/on` and `…/off`

The all-fleets switch: `{"on": true, "by": "engineer", "at": "…", "worker_ships": 3}`, where `worker_ships` counts the live worker-launched ships in every fleet.

### `POST /api/fleets/<key>/worker-ships/stop` and `POST /api/worker-ships/stop`

Stop all worker-launched: stops every live (underway or needs you) ship an event launched in the fleet, or in every fleet, as `POST /api/ships/<ship>/stop` does. Its clones stay, so Undo and Promote still work. It never touches a promoted, hand or scheduled ship, an anchored ship, or Hold fire. `200 {"stopped": ["<session>", …], "failed": ["<session>", …]}`, with both lists empty when nothing is live; a ship that would not stop is in `failed` and the rest are still stopped. `404` for an unknown fleet. An actor token can't call it.

### The wall clock

A worker-launched ship that is still underway or needs you when its fleet's `wall_clock_minutes` (60 by default) have passed since it launched is stopped by Admiral: it ends the harness process and keeps the pane, so the ship is `anchored` with `exit_signal` and `stopped_by: "wall_clock:<minutes>"`. Its launch record turns `failed` with the reason `stopped at the <minutes>-minute wall clock`, which counts toward the routine's circuit breaker, and, as for any failed record, no longer counts toward launches per hour or per sender. Promoted, hand, scheduled and proposal-launched ships (an event ship the engineer launched from an accepted Inbox proposal) have no wall clock, take no worker slot and are not stopped by Stop all. The deadline counts from the launch record's time.

### Outside events: `POST /api/fleets/<key>/routines/<id>/mute`, event proposals and event cards

An outside event's text is untrusted and never reaches AdmiralBot. The Lookout turns it into fixed fields; the event ends as an event card in the fleet's chat (Report only) or an event proposal in Admiral's own inbox (Ask first).

- An event proposal is an Inbox item with `kind: "event_proposal"`, `session: "_admiral"`, id `event-<trigger id>` and an `event_proposal` object `{"fleet", "routine", "routine_name", "trigger", "tier", "expires_at"}`. It holds no event text. `launch` and `dismiss` work as for a routine proposal (`POST /api/inbox/_admiral/<id>/launch` answers `201 {"ship": {"session": "<ship>"}}`; `409` when the routine is busy (no room for another ship), is turned off, or the trigger is not an open event proposal for it, for instance one already launched; `410` when the proposal has expired or its trigger or routine is gone; `502` for any other launch failure, with the message; the item stays open after every refusal).
- `GET /api/inbox/_admiral/<id>/event` answers `{"summary", "title", "sender", "link", "dedupe_key", "metadata", "mute_by", "verdict", "check_id", "check", "reviewer_reason"}`: the Lookout's summary (or the metadata line when `metadata` is true), shown as untrusted plain text. The last four are the step reviewer's answer and are absent when it was not asked: `verdict` is `ask` here, `check_id` and `check` name the Check that decided it (absent when none did), and `reviewer_reason` is the reviewer's reason or why it could not be asked. Treat `check` and `reviewer_reason` as untrusted plain text. An actor token can't call it.
- An event card is a chat entry with `kind: "event_card"`, `id` the trigger record's id, `text` the summary and `card` `{"routine", "routine_name", "tier", "sender", "link", "dedupe_key", "metadata", "mute_by", "verdict", "check_id", "check", "reviewer_reason"}`. The last four are the step reviewer's answer, empty when it was not asked; a blocked event's card carries `verdict` `block` with the Check's id and its text as the reviewer judged it, and the reviewer's reason. Show them as untrusted plain text. It is never shown to AdmiralBot.
- A launch card is a chat entry with `kind: "launch_card"` that an event launch (A3, A4 or A5) posts for its ship: `id` the trigger record's id, `text` as on the event card, and `card` the event card's fields, without `verdict`, `check_id`, `check` and `reviewer_reason`, plus `{"ship", "level", "restricted"}` (`level` is `A3`, `A4` or `A5`; `restricted` is `investigate` or `draft_fix` at A3 and empty otherwise). It holds no event body, is posted once per record and never shown to AdmiralBot. A launch from an accepted proposal posts none.
- `GET /api/fleets/<key>/routines/<id>/runs/<trigger>` answers that one trigger record, as `…/runs` lists it, with `undone`; `404` for an unknown fleet, routine or record, or a record of another routine.
- `POST /api/fleets/<key>/routines/<id>/runs/<trigger>/undo` undoes an event launch: it stops the ship when the host lists a ship that this launch's record started (clone or no clone; a newer launch that reused the session name is not that ship and is left alone, with its clone), deletes `$ADMIRAL_HOME/checkouts/<session>` (the ship's clone and its `admiral/<session>` branch) unless a listed newer ship holds the name, and marks the record `undone`. Branches the ship already pushed and PRs it opened stay. `200` with the record (also when it is already undone, which changes nothing), `400` for a record that is not an event ship's launch (one whose ship ended failed still is), belongs to another routine or was promoted (`a promoted record cannot be undone`: its ship is the engineer's now), `404` for an unknown fleet, routine or record, `500` with the reason when the stop or the removal fails (the record stays unmarked and a retry is allowed). An undone launch counts toward the breaker as a failed one. An actor token can't call it.
- `POST /api/fleets/<key>/routines/<id>/runs/<trigger>/promote` starts a normal ship from a restricted Draft fix ship's work, the engineer's own act. It reads the work in `$ADMIRAL_HOME/checkouts/<session>` (the commits on `admiral/<session>` since the merge-base with the routine directory's HEAD, or, with no commits, its uncommitted changes with `.admiral/` left out), stops the restricted ship when the host lists it, and launches an autopilot ship (it counts toward the global ship cap and, from `promoted_at`, as one launch toward the fleet's launches per hour, but not toward the sender's launches or the worker cap, and holds no routine) in its own clone of the routine's directory, on `admiral/<new session>` at that tip, with the diff applied when there were no commits. The new ship is a new session: it never resumes the restricted one, gets no event file, no Guidance and no restricted profile, and its order is fixed text naming the record, the routine, the branch and the range. `200` with the record, whose `promoted_ship` is the new session (a second Promote answers the same ship and launches nothing). `400` for a record that is not a restricted event ship's launch, is an Investigate or normal ship's (`only a Draft fix ship can be promoted`), belongs to another routine, was undone, has no clone left, has nothing to promote, has commits or changes that touch `.admiral/` or harness project config (`.claude/`, `.mcp.json`, `CLAUDE.md`, `CLAUDE.local.md`, `AGENTS.md`, `.codex/`, `.github/copilot-instructions.md`, matched case-insensitively from the repo root; the reason says `touches harness config`, with no file names), adds a symlink (`adds a symlink`), whose clone's `objects/info/alternates` was changed, or whose clone holds a git carrier a ship planted: a `.git` (file, folder or link) or `.gitmodules` below the root, a root `.git` that is not a folder, or a submodule entry in its index or tip tree. This refusal names the path, as an exception to "no file names": `the clone holds a git carrier: <reason> at "<path>"`, the path relative to the clone, cut to 200 bytes (the raw path, before quoting) and then quoted with Go's `%q`, with the words `(path cut)` after it, so the engineer can find it. The check walks the work tree in Go before any git runs over it. Don't open a restricted clone, or any folder under it, in a shell or editor: a planted nested repository runs its own config under the engineer's tools; `404` for an unknown fleet, routine or record; the launcher's own status and reason when it refuses (for example the global cap, a quota hold, no free resources, an unknown host) and records nothing, so a retry is allowed; its setup failures (the work changed since it was read, the work no longer applies) answer `500` with a fixed message, and the detail goes to the server log; `500` also when the work cannot be read or a seam is missing. Every git call runs without hooks, config, filters or external programs. An actor token can't call it.
- `mute_by` lists the Mute rule choices the event allows: `sender` and `dedupe_key`.
- `POST /api/fleets/<key>/routines/<id>/mute` takes `{"by": "sender" | "dedupe_key", "value": "<text>"}` and adds a skip entry scoped to that routine to the fleet's Limits. `204` (also when the entry is already there), `400` for another `by`, an empty or over-long value, a control character or `(unknown)` as a sender, `404` for an unknown fleet or routine. An actor token can't call it.

### Routine proposals and Notify me

An Ask first run (or an `act` run while Hold fire is on) writes an Inbox item in Admiral's own inbox: `kind: "routine_proposal"`, id `routine-<trigger id>` (a fleet key has no length limit, an item id does), `fleet` set so a fleet's list shows it, and a `routine_proposal` object `{"fleet", "routine", "routine_name", "trigger", "action", "reason", "expires_at"}`. `reason` is set when the run was held for quota (`Held for quota: Claude's 5-hour window is at 93% (line 90%), resets 14:00`) and left out otherwise; the run's trigger record carries the same text as its `reason`. `expires_at` is the routine's next run or 24 h, whichever is first; the list drops an expired item. A newer proposal for the same routine closes the older one and writes a `skipped` trigger record (`proposal expired: a newer run replaced it`); an unanswered one writes `proposal expired: nobody answered it before it closed`, and a dismissed one writes `proposal dismissed by the engineer` instead. The open proposals are kept in memory: one still open across a restart gets no expiry record, though the list and Launch still treat it as expired.

`POST /api/inbox/_admiral/<id>/launch` runs the routine once under the same gates and key as a scheduled run (its trigger record has `via: "proposal"`) and answers `201 {"ship": {"session": …}}`; a prompt routine sends its prompt instead. It never waits: with no room or a ship holding the routine's key it answers 409 and leaves the item open. After `expires_at` it answers 410 and runs nothing; a second press answers 409. It also answers 409 when the routine is now switched off (by anyone), runs nothing and leaves the item open until it expires. A launch runs the routine as it is saved now, so an edit since the proposal changes what runs. `POST /api/inbox/_admiral/<id>/dismiss` answers 204.

A routine with Notify me on pushes `launched` (a tap opens the ship), `failed`, `breaker` and `proposed` (a tap opens the proposal's Peek). `skipped`, `missed` and `reported` push nothing. The fleet's Notify switch and the watched-window rule apply as for any push.

## Standing orders

A fleet's Checks (at most 20, each at most 300 characters, none empty or repeated), its Guidance (at most 2000 characters) and its Limits, which a fleet save also edits. The Checks and Guidance live in `$ADMIRAL_HOME/routines/<key>/standing-orders.json`; a worker-launched ship's prompt ends with the Guidance under `## Standing orders`. Every route is also served under `/api/v1/`. Errors are `{"error": "…"}`: 404 for an unknown fleet, 400 for a body that fails a check (the message reads `invalid standing orders: …` and names `checks[i]` or `guidance`), 409 when the config can't be edited. For AdmiralBot's actor only the `GET` is allowed (see "AdmiralBot's requests").

### `GET /api/fleets/<key>/standing-orders`

```json
{"checks": ["Run make check before a PR."], "guidance": "Prefer small PRs.", "preset": "work",
 "limits": {…}, "sentences": [{"field": "wall_clock_minutes", "sentence": "…"}], "overridden": ["wall_clock_minutes"]}
```

`checks` is `[]` and `guidance` `""` when none is filed. `limits` and `sentences` are the fleet's effective Limits, and `overridden` names the Limits the fleet sets over its preset.

### `PUT /api/fleets/<key>/standing-orders`

`{"checks": […], "guidance": "…"}`; a field left out keeps its stored value. Replaces what is stored once the whole result passes the checks. Checks are stored trimmed, so two that differ only by surrounding whitespace count as repeated. `200` with the `GET` shape.

### `POST /api/fleets/<key>/standing-orders/copy`

`{"to": "<fleet key>"}`. Copies this fleet's Checks, Guidance, preset and Limits to the target, replacing its own. `to` must be another fleet (400 otherwise, 404 when unknown); a repo allowlist the target can't satisfy is 400, and nothing changes when the copy is refused. `200` with the target's `GET` shape and `loosens`, the Limits the copy made looser than the target's were.

### `POST /api/fleets/<key>/standing-orders/draft`

`{"prose": "…"}` (1 to 4000 characters). One judge call turns the text into a draft; nothing is saved.

```json
{"draft": {"limits": {"wall_clock_minutes": 30} or null, "checks": ["…"], "guidance": "…" or null},
 "sentences": […], "changes": [{"field": "…", "sentence": "…"}], "loosens": ["wall_clock_minutes"],
 "problems": [{"field": "limits|checks|guidance", "message": "…"}]}
```

A Check or the Guidance that the prose does not hold (compared after whitespace is collapsed, and starting and ending on a word boundary) is dropped and named in `problems`, as is a Limits patch the fleet save would refuse, including a `repo_allowlist` entry outside the fleet's search roots (`draft.limits` is then `null`, as it is when the patch changes nothing the fleet has, so `changes` is empty). The draft counts what the fleet already stores: a Check equal to a stored one is dropped, only as many Checks as fit under 20 beside the stored ones are kept, and Guidance that would pass 2000 characters is dropped when added to the stored Guidance as the stored text, a blank line, then the drafted text. That is how the Guidance is added when the engineer confirms. `changes` are the sentences the patch changes, and `loosens` the Limits it would loosen, which the engineer confirms. `409` with `{"error", "reason"}` when no harness is proven safe for judge calls; `502` with `{"error", "kind"}` when the call fails (`timeout`, `bad reply`, `budget spent` or `error`).

### `POST /api/fleets/<key>/routines/draft`

`{"prose": "…"}`. The same judge call, for a routine: `{"draft": {"name", "enabled", "when", "do": {"prompt": "…"} or {"digest": {"extra": "…"}}, "before_acting", "notify"}, "problems": [{"field": "name|when|before_acting|do", "message": "…"}]}`. The draft is a prompt routine, or a fleet digest when the description asks for a summary of what changed (`do.digest`, with `extra` only when the engineer gave words), and is checked as a save would be; it is not saved as a routine. The 400, 409 and 502 answers are the standing-orders draft's.

The 200 answer is `{"id": "…", "draft": {…}, "problems": […]}`: the server also keeps the routine draft, in memory, for that fleet. `id` is unguessable URL-safe text and the `draft` object has no id. A routine draft is kept for 1 hour, a fleet keeps at most 50 (the oldest goes first), and a restart drops them all. A call that fails (400, 404, 409, 502) keeps nothing. Both "Describe a routine" and AdmiralBot's `draft_routine` tool come through here. The Routines screen opens a kept draft at `/app/routines/new?fleet=<key>&draft=<id>`, filled in and unsaved; an expired or unknown draft opens the empty form with a note saying so.

### `GET /api/fleets/<key>/routine-drafts/<id>`

`{"id", "draft", "problems", "expires_at"}` (RFC 3339): the routine draft kept under `id` for this fleet, as `routines/draft` answered it. 404 `{"error"}` for an unknown fleet, an unknown or expired id, and an id kept under another fleet, with the same answer for the last two. AdmiralBot's actor is 403 here.

### `POST /api/fleets/<key>/campaigns/draft`

`{"issues": [{"url": "…", "title": "…"}, …]}` (1 to 50) or `{"text": "…"}` (at most 4000 characters), exactly one of them; an empty `issues` or a blank `text` counts as absent. The same judge call, for the parent issue of a campaign that groups the issues, or one drafted from the engineer's own words: `{"title": "…", "body": "…"}`. The text's title is at most 100 characters and its body restates the text without inventing a plan or sub-issues. `400` for both fields, neither, more than 50 issues, or a text over the cap (`text: at most 4000 characters`), before any judge call. Nothing is saved or written to GitHub. `409` and `502` are the other drafters'; a reply without a title and a body is `502`.

## Harness capabilities

What each fleet's harnesses were probed to do (ADR 0035). These are not the server `capabilities` that `GET /api/version` lists. Both routes are also served under `/api/v1/`.

### `GET /api/harness-capabilities`

```json
{"fleets":[{"key":"work","name":"Work","restricted":true,
 "judge":{"harness":"claude","lookout_model":"haiku","strong_model":"sonnet","json_schema":true,"call_cap":true},
 "harnesses":[
  {"harness":"claude","version":"2.1.300","detected_at":"2026-11-11T09:00:00Z",
   "features":[{"id":"autopilot","label":"Autopilot","capabilities":[
     {"id":"autopilot.guard_hook","label":"Pre-tool guard hook",
      "status":"passed","checked_at":"2026-11-11T09:00:05Z","detail":"..."}]}]}]}]}
```

Fleets and harnesses follow the config's order; features follow the table (judge, bot, restricted, autopilot, scout). `status` is `passed`, `failed` or `not_checked`, against the last detected `version`. `version` is `""` when none was detected, and the guard's `detail` then says why. `checked_at` and `detected_at` are `null` when there is no time.

`judge` is the fleet's judge harness, from `judge.Choose` on the stored probes: the first of claude, codex and copilot that proved no tools and no network, with its Lookout and strong models and whether it proved a JSON schema flag and a per-call cap. A fleet with no such harness has `{"harness":null,"reason":"..."}`, the reason naming each harness and what it lacks, and runs no judge calls.

`restricted` is whether some harness of the fleet can run a restricted ship, computed on each read: both `restricted.*` capabilities passed and the autopilot guard passed against its last detected version, in a harness whose restricted probes are registered, and the fleet has a judge harness. Without one, an A3 ceiling computes as A1 for an event routine, and the Routines screen says so.

`autopilot.advisor` is never stored. Every harness of a fleet reads `not_checked` until some harness of the fleet has a stored judge result, then `passed` (naming the judge harness) when the fleet has a judge harness and `failed`, with the `judge.reason`, when it has none, so it follows the other harnesses' probes. The gate refuses in every state but `passed`. Autopilot on a harness is refused until it passes.

### `POST /api/harness-capabilities/check`

Body `{"fleet":"work","harness":"claude"}`. Runs the probes for that harness and waits (up to eight minutes: the guard run and up to four judge calls of up to 90 seconds each). It answers 200 with the harness object above plus `"fleet"` and the fleet's `"judge"` object, which the check may just have changed. 400 for a bad body, 404 for an unknown fleet or a harness the fleet has no dock for, 502 with `{"error":...}` when the harness's `--version` fails.

## Devices and pairing

An unpaired device reaches the built shell's files (`/app/…` pages, one-segment `/assets/<name>.<ext>` files and `/sw.js`), the install files, and `GET` or `HEAD /`, which answers 302 to `/app/` with no body, so an installed app can load and ask for a code; none of it holds data. Everything else, the old UI at `/classic/` included, needs a token.

A device is a browser or client that holds its own revocable token. A request from this Mac needs no token. Any other request needs the device's token, as `Authorization: Bearer <token>` or the cookie `admiral_token_<port>`; `?token=` is not accepted. The cookie is HttpOnly and SameSite=Strict, so a request that carries it must also pass the Origin check.

### `POST /api/v1/pairing-codes`

Behind the same auth as the other routes. Answers `{"code":"ABCD-EFGH","url":"http://<host>:<port>/pair?code=ABCD-EFGH","expires":"<RFC 3339>"}`. The code lasts 5 minutes and works once, and a new code replaces the live one.

### `POST /api/v1/pair`

Body `{"code","name"?,"cookie"?}`. A code is case-insensitive, with or without the hyphen. On success it answers `{"token","device":{"id","name"}}` and sets no cookie, so a client sends the token as a Bearer. With `"cookie": true` (the shell's Pair this app screen) it sets the HttpOnly device cookie and leaves `token` out, so the token never reaches a page's script; `name` defaults to a guess from the browser, such as `Safari on Mac`. A wrong, expired or used code is 400; ten failures in 5 minutes are 429 with `Retry-After`; a request from this Mac is 403. `GET /pair?code=<code>` and the form at `GET /pair` (which posts to `POST /pair`) pair a browser instead: they set the device cookie and redirect to `/`.

### `GET /api/v1/devices`

Answers `{"devices":[{"id","name","login"?,"pairedAt","lastSeen","current","notifications","thisMac"?,"forwarding","lastFollowed"}]}`. `login` is set for a device paired over the tailnet. `current` is true for the device making the request; on the Local route it is true for This Mac. `notifications` is true when the device holds at least one push subscription. `thisMac` is true on the This Mac row only, so a page can tell the Mac from a paired device. `forwarding` is `"on"`, `"stopped"` or null: null for a device that has never followed push events (or sent `push_unfollow` since), `on` while a follower socket of the device is open and for 5 minutes after the last one closed, `stopped` after that. The 5 minutes count from the later of the close and Admiral's start, so a restart never shows `stopped` early; a device Admiral lost while it followed counts from the start alone. `lastFollowed` is when its last follower socket closed (RFC 3339), null until one has. The subscription's keys are never listed.

### Web Push: `GET /api/v1/push/key`, `GET`, `PUT` and `DELETE /api/v1/push/subscription`

`GET /api/v1/push/key` answers `{"key":"<base64url>"}`, Admiral's VAPID public key (the `applicationServerKey` for `PushManager.subscribe`), or 503 when the key file could not be read.

`PUT /api/v1/push/subscription` takes the browser's `PushSubscription` JSON (`{"endpoint","keys":{"p256dh","auth"}}`, extra fields ignored) and answers 204. The endpoint must be `https`, `p256dh` a P-256 point and `auth` 16 bytes, both base64url; anything else is 400. It upserts by endpoint for the requesting device, taking the endpoint from another device if that held it. A device may hold several subscriptions, one per browser. `GET /api/v1/push/subscription?endpoint=<url>` answers 204 when the requesting device holds that endpoint and 404 when it does not, including when another device holds it. `DELETE /api/v1/push/subscription` takes `{"endpoint"}`, removes it from the requesting device only and answers 204 even when the device did not hold it.

A paired device subscribes as itself. A request on the Local route (no token) subscribes as the device named `This Mac`, made on the first such request and reused after; it lists and revokes like any device, and revoking it drops its subscriptions. Revoking any device, all devices, or the 90-day expiry drops that device's subscriptions, and so does a 404 or 410 from the push service. Admiral never pushes to a loopback, private, link-local, unspecified or tailnet (100.64.0.0/10) address.

A push is an `aes128gcm` message (RFC 8291) signed with VAPID (RFC 8292), `TTL: 3600`, `Urgency: high`, no `Topic`. Its plaintext is a JSON object: `name` and `line` (always), `tag`, and when set `fleet`, `fleet_name`, `target` (`"peek"`, `"ship"` or `"chat"`), `session`, `item`, `crew`, `merge`, `message`. A report reply (`tag` `report-reply-<ship card id>`) has `name` `<ship> <result in words>`, `line` the reply's first line as plain text, and `target` `"chat"` with `fleet` and `message`, the id of the first reply entry; a tap opens `/app/chat/<fleet>/message/<id>`. Control and bidi characters are stripped from `name`, `line` and `fleet_name`.

### `PATCH /api/v1/devices/<id>`

Body `{"name"}`. Answers `{"id","name"}`; 400 for a missing or empty name, 404 for an unknown id.

### `GET /api/remote` (alias `GET /api/v1/remote`)

Behind the same auth as the other routes. Answers `{"tailscale":bool,"allowedLogins":[…],"url":"","serveOff":"","listenExplicit":bool,"checks":[{"id","ok","detail"}]}`. `tailscale` is the mode and `allowedLogins` the tailnet logins allowed in. `listenExplicit` is true when `--listen` fixed Admiral's address, so the mode never moves the listener. `serveOff` is `tailscale serve --https=<port> off` for the HTTPS port serve proxies to Admiral on (read from `serve status`, so 443 or a hand-set 8443), empty with the mode off or no such handler. With the mode off `url` is empty, `checks` is `[]` and no `tailscale` command runs. With it on, each call runs the tailscale CLI (4 s limit per command) and answers four checks in order: `running` (tailscaled up and logged in), `https-magicdns`, `serve` (an HTTPS handler proxying to Admiral's loopback port; a raw TCP forward to that port fails it, since it bypasses Admiral's tailnet checks) and `funnel-off` (Funnel on for an HTTPS handler or a TCP forward to that port, in serve or a foreground serve; the detail names the command that turns it off). `detail` is one line. `url` is `https://<MagicDNS name>[:<port>]/` when serve has such a handler and the node is logged in, else empty. A check that can't be answered (tailscale missing, down, slow or unparsable) is `ok:false` with the reason. When the last move of the listener failed, a fifth check `listen` (`ok:false`, the bind error as `detail`) is added in either mode; the old listener is still in place, and the next successful move clears it.

### `POST /api/remote/logins` (alias `POST /api/v1/remote/logins`)

Body `{"add": login}` or `{"remove": login}`, one of them. The login is trimmed. Answers 200 with the same view as `GET /api/remote`, read after the write. 400 for a blank or already-allowed login to add, for neither or both keys, and for a body that isn't JSON; removing a login that isn't listed changes nothing. The write goes through the config manager (`Manager.SetRemote`) under one lock, so a removal keeps the other logins and edits made at once all land. The config change is what cuts the removed login's open tailnet sockets, just after the write returns; this route cuts nothing itself. A tailnet device may edit, including its own login.

### `POST /api/remote/setup` (alias `POST /api/v1/remote/setup`)

Body `{"confirm":true}`; anything else is 400 and nothing runs. Only a request from this Mac may run it: any other path gets 403 and nothing runs. It runs the same checks as `admiral setup` (running, HTTPS and MagicDNS, Funnel off), then, unless serve already proxies to Admiral's port (left as it is), `tailscale serve --bg --https=443 http://127.0.0.1:<Admiral's port>` under the serve timeout, then writes `remote.tailscale: true` and adds the Mac's login to `allowedLogins`. Answers 200 `{"ok":bool,"checks":[{"id","ok","detail"}]}`: one row per check up to the first failed one, then `serve` (passed, left as it is, or failed with the CLI's message) or `https-443` (failed: another handler holds 443; the detail has the `--https=8443` command). A failed row stops it before anything is written. 409 while another Set up runs, so a double click runs serve once. The mode applies live: the config change moves the listener (see the move message below).

### `POST /api/remote/off` (alias `POST /api/v1/remote/off`)

Turn off. Body `{"confirm":true}`; anything else is 400. Only a request from this Mac may run it: any other path gets 403 and nothing runs. It writes `remote.tailscale: false` and nothing else: the allowed logins stay and `tailscale serve` is left as it is. Answers 200 with the `GET /api/remote` view after the write, except that `serveOff` is the command read just before the write, so the page can keep showing it. 500 `{"error"}` when the write fails, without the path.

### The presence message

A window tells the server whether anyone is watching it with `{"type":"presence","visible":true,"idle_ms":1500}` on `/ws/v1`: `visible` is whether the page is visible, `idle_ms` how long ago the person last used it (pointer, key or touch). The shell sends it when the socket opens or reopens, when visibility changes, on the first input after 10 s of none, and every 30 s while visible. The server counts a window as watching while it is visible and `idle_ms` plus the time since the report is under 2 minutes; a window that has not reported, or whose socket closed, does not count. While any window watches, an event that would push is an alert for the watched windows instead. A malformed or negative `idle_ms` is ignored.

### Following push events

A device paired with a bearer token follows what would push on `/ws/v1` with `{"type":"push_follow","after":<seq or null>,"boot":"<id>"}`. A client stores the last `seq` and `boot` it saw and sends them back when it reconnects; a first follow sends `"after":null` and no `boot`. Following adds no Web Push target, and a socket that only follows never counts as watching: it must send `presence` to get `alert` instead of `push`, and then it counts like a window. A second `push_follow` on the same socket is a fresh catch-up from its `after`; it may repeat one event the first catch-up was already sending, so a client keys on `seq`.

**Who may follow.** Only a paired device's bearer token (`Authorization: Bearer <token>`) on the LAN or tailnet. A bearer header on the Local (loopback) route is refused, since that route has no device. A cookie-only socket (even a paired device's), a Local socket and an unpaired one get `{"type":"push_refused","reason":"bearer_required"}` and stay open; a refused socket still gets everything a window gets, but no push events. The check is on the request, so revoking the device closes its following socket with the rest.

**`push`** is sent for every event that would push, and never for an alert or for a fleet with Notify off: `{"type":"push","boot":"7f3a…","seq":12,"kind":"ship_question","attention":3,"fleet":"zulu","fleet_name":"Work","name":"Dory","line":"has a question","tag":"s-1","target":"peek","session":"s-1"}`. It holds the Web Push payload's fields (the same `name`, `line`, `tag`, `target`, `session`, `item`, `crew`, `merge`, `routine` and `message`), so nothing beyond what a lock screen already shows (bar `card` and `choices` below, whose option labels Web Push does not send), plus `boot`, `seq`, `kind` (the event's kind: `ship_question`, `inbox_question`, `chat_question`, `wake_proposal`, `findings`, `ready_to_merge`, `anchored`, `code_approval`, `routine_notify`, `report_reply` or `digest_reply`) and `attention`. A `push` also names the need card the need asks on and the choices one tap answers it with, on the follower feed only (Web Push and alerts do not carry them):

- `card` is the id of the need card (see Need cards) the event asks on: a ship's stop (`ship_question` for a permission prompt, whether or not its card has buttons, and for a ship that never started) or an Inbox item (`inbox_question`, `findings`). It is absent when the need has no card: a wake proposal, a chat question, a question of the `_admiral` session, a crew boat, a ship asking a `question`, ringing the `bell` or at an elicitation dialog, a stop with no identity yet, a fleet the config does not hold, and the kinds that are push-only (`anchored`, `ready_to_merge`, `report_reply`, `digest_reply`, `routine_notify`, `code_approval`). Ready to merge posts a ship card, not a need card, and has no answer route.
- `choices` is an array on every `push`, `[]` when one tap cannot answer the whole need. Each is `{"id","label"}`; the label is cleaned of control and bidi characters as `name` is, and a client decides how many become buttons. It is non-empty for an answerable permission stop (`allow` "Allow once", `deny` "Deny") and for a question item with exactly one question that is not multi-select and has options (one per option, `id` the option's index as a string: `"0"`, `"1"`, …; the free-text Other is not a choice). It is empty for findings, allow rules, a question item with several questions, a multi-select question or one with no options, a ship that never started, a permission the card has no buttons for and every event with no `card`. A review, a routine proposal and a campaign draft offer choices on their card route, but raise no push.
- To answer, `POST /api/v1/chat/<fleet>/need-cards/<card>/answer` with `{"choice":"<id>"}` (see Need cards); `fleet` is the push's `fleet`.
- A ship that is still asking but names a different card (a new stop, or a card where it named none) gets a second `push` under the same `tag` (the next `seq`, no `push_clear` between), naming the new card, so the device never holds a notification whose card is gone.

**`push_clear`** is `{"type":"push_clear","boot":"7f3a…","seq":13,"tag":"s-1","attention":2}`, sent when a key that pushed stops needing the engineer: a question or approval is answered, an item is answered, removed or moved on, an anchored ship leaves that state, a stack stops being ready to merge. It carries no title or ask text. `tag` is the `tag` of the `push` it clears, an opaque string a client does not parse. `report_reply`, `digest_reply` and `routine_notify` never clear.

**The count.** A follower gets one message per change of the attention count: the `push` or `push_clear` that carries it as `attention`, or `{"type":"attention","count":N}` when the count moved with no push. The count is the one above, worked out from the ship and inbox lists the push watcher has processed, so a message never carries a count newer or older than its own event. Until the ships and inbox are known, and while tmux is lost, a follower gets no `attention` message, and a `push`, `push_clear` or `push_reset` leaves the `attention` field out rather than carry a false 0.

**Catching up.** Admiral keeps the last 500 `push` and `push_clear` events, none older than a day, in memory only. `boot` is an id fresh for every run of Admiral and `seq` rises from 1 within it, one number across both kinds of event. After a `push_follow`:

- `after` inside the ring: the events after it, in order, then `{"type":"attention","count":N}` with the current count.
- `after` null: no replay, only an `attention` message with the current count. A client may see the connect-time `attention` every `/ws/v1` socket gets just before it, so it treats each `attention` as the current count.
- `after` with a missing or other `boot`, past the latest `seq`, or older than the oldest event kept: `{"type":"push_reset","boot":"7f3a…","attention":N}` and nothing else. The client drops what it has and starts from the new `boot`; `attention` is left out before the lists are known.

**Forwarding record.** A bearer-paired device's `push_follow` marks it as forwarding in `devices.json`, and the close of its last follower socket (counted across all its sockets) saves `lastFollowed`; a socket dropped for a slow queue counts as closed when the socket ends. `{"type":"push_unfollow"}` clears the record, flag and `lastFollowed`, and ends the follow on the socket that sent it; the device's other sockets keep following until they close; a later `push_follow` records the device again. A socket without a bearer token gets no answer to `push_unfollow`: it is ignored. `GET /api/v1/devices` shows the state as `forwarding` and `lastFollowed`.

A follower that cannot keep up (its queue of 1024 messages fills) is closed, never left with a gap, and catches up when it reconnects.

### The alert message

The server answers an alert with `{"type":"alert","fleet":"zulu","fleet_name":"Work","name":"Dory","line":"needs your approval","tag":"s-1","target":"peek","session":"s-1"}`, sent only to the windows it counts as watching, never to a hidden, idle or silent one. `name` and `line` are text (the line is the first line, at most 120 characters), `tag` identifies the entry so a repeat replaces the earlier toast, and `target` says where a tap lands: `"peek"` plus one of `item`, `crew` or `merge: true` (or none, for the ship's own stop) for a Peek on `session`, or `"ship"` for the ship's view, which an anchored ship uses because it is never an Inbox entry, or `"chat"` (with `fleet` and `message`, no `session`) for AdmiralBot's reply to a report turn, which opens `/app/chat/<fleet>/message/<id>`, or `"routine"` (with `"routine": "<id>"` and no `session`) for a routine run that has no ship: a prompt sent to AdmiralBot, a failed run or a breaker trip. The tap opens `/app/routines/<id>?fleet=<key>`; a run that launched a ship keeps the ship target. The shell chimes and shows a toast for it; a fleet with Notify off sends none.

### The move message

When a config change moves Admiral's listener, a ships-socket client whose path stops working gets `{"type":"move","url":"<address>"}` before it is cut. Mode on: clients that came in over the LAN get the tailnet URL (`GET /api/remote`'s `url`, empty when serve isn't set up). Mode off: clients that came in over the tailnet get the LAN address (`http://<ip>:<port>`). Loopback clients never get it. The server waits up to 2 s for the writes, then cuts the tailnet sockets the change no longer allows, then rebinds; with the mode on, every LAN socket still open is then closed (a client that ignores the message loses its socket). The shell sends the page to `url` when it is an http(s) address other than the page's own; an empty `url` leaves the page where it is. A device that moves to the tailnet pairs again there, since its token and cookie belong to the old origin.

### `DELETE /api/v1/devices/<id>` and `DELETE /api/v1/devices`

Revoke one device or all of them; 204, or 404 for an unknown id. The device's token stops working and its open WebSockets close. A save that fails leaves the device in place and answers 500 `{"error"}`, as it does for a rename.

## Update check

### `GET /api/update` (alias `GET /api/v1/update`)

Whether a newer public Admiral release exists, and how to upgrade. Admiral asks `GET https://api.github.com/repos/jbuffin/admiral/releases/latest` (unauthenticated, so drafts and prereleases never count) about a minute after it starts and every 12 hours after, and keeps the last good result in memory. A failed check (an error status, bad JSON, a body over 1 MiB, a `tag_name` that is not `v<x.y.z>`) keeps the last good result and `checked_at`. This route makes no request; it reports what the last check found.

```json
{
  "current_version": "0.9.1",
  "latest_version": "0.9.2",
  "update_available": true,
  "checked_at": "2026-11-17T09:00:00Z",
  "enabled": true,
  "install_method": "homebrew",
  "upgrade_commands": [{"label": "Upgrade with Homebrew", "command": "brew upgrade admiral"}, {"label": "Restart the service", "command": "launchctl kickstart -k gui/$UID/dev.jasonbuffin.admiral"}],
  "restart_note": "If Admiral did not start as a service, restart it the way you started it.",
  "executable_path": "/opt/homebrew/Cellar/admiral/0.9.1/bin/admiral",
  "release_url": "https://github.com/jbuffin/admiral/releases/tag/v0.9.2"
}
```

- `current_version` is the running version as stamped. `latest_version` and `checked_at` (RFC 3339, UTC) are `null` before the first good check.
- `update_available` is true only when `latest_version` is newer than the running version's base: a `git describe` version (`0.9.1-12-gabc123`, `-dirty`) counts as `0.9.1`, and `dev`, an empty or an unparseable version is never updatable.
- `enabled` is the top-level `update_check` setting in `config.json` (on unless `false`, so also with no `config.json` or one that is invalid at start), read live. With it off Admiral makes no request, `update_available` is false and `latest_version` and `checked_at` are `null`; turning it on runs a check about 10 seconds later.
- `install_method` is `homebrew` (the resolved executable is under `/Cellar/`), `source` (the version is `dev` or a `git describe` one, or the executable is `<dir>/bin/admiral` in a git checkout) or `script`. `upgrade_commands` are the steps in order, ending with the service restart, and `restart_note` says what to do when Admiral was not started as a service. They are plain text for a person to run; a client shows them as text, never as markup.
- `release_url` is the release's page, kept only when GitHub's `html_url` is an `https://` link, else a page built from the tag; before the first check it is the latest-release page.
- AdmiralBot may read it. `POST /api/update` is not a route.

## AdmiralBot's requests

A fleet's chat calls Admiral with its actor token in the `X-Admiral-Actor` header. The token is `HMAC-SHA256(secret, fleet + "\n" + nonce)`: the secret is a random key in `$ADMIRAL_HOME/actor-secret` (mode 0600) and the nonce is minted per chat session and kept in the tmux session option `@admiral-chat-nonce`, so a token survives an Admiral restart while its chat lives and is new with each chat session. The token is never logged and never put in a command line or a file.

- A request with no header is the engineer's own and is unchanged. A valid token on a loopback request makes it AdmiralBot's for that fleet; an unknown or stale token is 401. A request off loopback is refused: 401 without a device cookie (the auth layer answers first), 403 with one.
- AdmiralBot may call only: `GET /api/ships`, `GET /api/ships/<ship>/conversation`, `GET /api/inbox`, `GET /api/sources`, `GET /api/campaigns`, `GET /api/campaigns/<id>`, `GET /api/update`, `POST /api/ships`, `POST /api/sources/<key>/orders`, `POST /api/inbox/<ship>/<id>/answer`, `POST /api/ships/<ship>/stop`, `POST /api/ships/<ship>/dismiss`, `POST /api/ships/<ship>/next`, `POST /api/ships/<ship>/answer`, `POST /api/ships/<ship>/wake`, `GET /api/outcomes`, `POST /api/chat/questions`, `GET /api/chat/questions/<id>/answer`, `GET /api/fleets/<fleet>/routines`, `GET /api/fleets/<fleet>/standing-orders`, `GET /api/fleets/<fleet>/hold-fire`, `GET /api/fleets/<fleet>/repos`, `GET /api/fleets/<fleet>/cloneable`, `GET /api/fleets/<fleet>/docks`, `GET /api/fleets/<fleet>/crew`, `GET /api/fleets/<fleet>/crew/skills`, `GET /api/fleets/<fleet>/drafting`, `POST /api/fleets/<fleet>/routines/draft`, `POST /api/fleets/<fleet>/campaign-drafts`, `POST /api/fleets/<fleet>/routines/<id>/off`, `POST /api/fleets/<fleet>/hold-fire/on`, `GET /api/hold-fire`, `POST /api/chat/notes`, `POST /api/chat/commitments` and `POST /api/chat/campaign-commitments`, each also under `/api/v1`. A `<fleet>` that is not its own is 403; turning a routine on, turning Hold fire off, and saving, editing or deleting a routine are 403 too, as are `PUT` and `POST …/copy` on `standing-orders` and the other drafts (`standing-orders/draft`, `campaigns/draft`). A routine draft and a campaign draft are the only drafts it may make, each in its own fleet: a campaign draft is an Inbox item for the engineer to create or dismiss, and creating or dismissing it (`POST /api/inbox/_admiral/<id>/create` and `/dismiss`) is 403; reading a kept routine draft back is 403. Every other route is 403, and a path that needs cleaning or decoding to match is refused.
- The fleet-map reads (`repos`, `cloneable`, `docks`, `crew`, `crew/skills`) and the drafting-skill read (`drafting`, which AdmiralBot never writes: `PUT` is 403) are keyed by fleet: another fleet's key is 403 naming both fleets, and no read carries anything of another fleet. The cross-fleet `GET /api/harness-capabilities`, `GET /api/config` and `/api/launch-orders/*` stay closed to AdmiralBot.
- The list reads (`ships`, `inbox`, `sources`, `campaigns`) hold only the actor's fleet. Touching another fleet's ship, item, source or campaign, or an item or ship of no known fleet, is 403 naming the fleet; a launch must name the actor's fleet and a source of that fleet. A launch body must be one JSON object: data after it is 400 (for the engineer too), and the guard and the handler read the same value. A chat session's own question is the engineer's to answer, so AdmiralBot's answer to an Inbox item of a chat session is 403.
- `GET /api/outcomes[?ship=<ship>][&limit=<n>]` answers `{"outcomes": [<record>, ...]}`, oldest first, the latest `limit` (default 100, at most 1000; `400` for a bad value) of the month files' records. An actor sees only its fleet's: ship names are reused, so a record's fleet is the `fleet` of the latest `launched` record of its ship before it (read in file order); a record with no such record in the files read takes the fleet of the listed or moored ship that holds the name, unless the files hold a later `launched` record of that name, which hides it; a record of no known fleet is hidden. The fence applies before the limit. A `launched` or `woken` record carries `launched`, the ship's launch stamp (RFC 3339; a wake's is the wake time), which a commitment's ship trigger matches on; a record written before that field existed never matches. A `launched` record of a routine's ship has `trigger: {"fleet", "id"}`, pointing at that routine's trigger-log record.
- `answer_stop` is AdmiralBot's tool for `POST /api/ships/<ship>/answer` (a ship pane's permission or question menu, which has no Inbox file, so `answer_item` can't reach it). It requires `stop_id`, `card` and `reason` and forwards only the fields the caller gave: it never picks a choice. The crew boat route stays the engineer's, and a report turn refuses it like `next_prompt`.
- Writes are stamped `"via":"admiralbot"`: the `launched`, `stopped`, `dismissed`, `answered`, `resumed`, `woken` and `unmoored` outcome records and the launched ship's `via`.
