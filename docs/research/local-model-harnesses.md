# Harnesses built for local models, measured against a ship

Research for [#973](https://github.com/jbuffin/admiral/issues/973), on the map [#971](https://github.com/jbuffin/admiral/issues/971). It feeds [#978](https://github.com/jbuffin/admiral/issues/978) (which harness the first harness plugin brings in). This note compares; it does not pick.

Question: beyond Claude Code, Codex CLI and Copilot CLI, which agent harnesses run well on a **model server** (Ollama first), and how close does each come to Admiral's bar for a **ship** ([ADR 0030](../adr/0030-ship-conversations-come-from-a-first-party-adapter-per-harness.md), [ADR 0007](../adr/0007-needs-you-comes-from-harness-hooks.md), [ADR 0035](../adr/0035-harness-features-follow-probed-capabilities.md))? Also: are the big three on Ollama worse than a harness built for local models, and is the Ollama app's chat a harness?

Sources were read on 2026-11-27: each project's docs, README and source on its default branch, and the release named in the table. **Observed** means it was run on this Mac (Ollama 0.40.17). None of the harnesses was installed, and no config was changed. **Unverified** marks a claim taken from a secondary source, or inferred from docs that do not state it outright.

## Per harness

### Crush (Charm)

- **Hooks are Claude Code's, renamed where Claude Code has no equivalent.** There are 13 events: `PreToolUse`, `PostToolUse`, `PostToolUseFailure`, `PermissionRequest`, `PermissionResult`, `SessionStart`, `SessionEnd`, `TurnStart`, `TurnEnd`, `StopFailure`, `Interrupt`, `PreCompact`, `PostCompact`. Payloads use Claude Code's field names (`hook_event_name`, `session_id`, `cwd`, `tool_name`, `tool_input`, `last_assistant_message`, …), and the output accepts Claude Code's `hookSpecificOutput.permissionDecision` ([hooks guide](https://github.com/charmbracelet/crush/blob/main/docs/hooks/README.md)). `PermissionRequest` "fires only when a prompt is actually shown", so it is a clean needs-you, unlike Copilot's `permissionRequest`. There is no `transcript_path`, because sessions live in SQLite.
- **Questions.** The agent has a `question` tool, and the server streams `question_batch_request`. Whether `PreToolUse` with matcher `^question$` fires before the dialog is inferred, not documented.
- **Client/server mode is the beside route.** "A background `crush server` process runs the agent… and the TUI becomes a client that talks to the server over HTTP" ([server docs](https://github.com/charmbracelet/crush/blob/main/docs/server/README.md)). `--host unix:///path.sock` names a private socket. The [API](https://github.com/charmbracelet/crush/blob/main/docs/server/API.md) streams whole messages over SSE (`message` `created` and then `updated` per message ID, with `text`, `reasoning`, `tool_call` and `tool_result` parts), plus `permission_request` and `question_batch_request`. This has the same shape as Admiral's Codex wrapper: a server started in the pane, so tools and hooks keep the pane's environment, and an observer that never answers. Caveats: the server sends no replay ("events from while you were away are gone for good", so after a reconnect you fetch again), and a workspace "keeps the settings of the window that opened it" (`-y`, `--data-dir`), so it must be one server per ship, never per fleet.
- **Launch.** `crush --session <id>` and `--continue` resume. There is no flag that sets a new session's id, so Admiral would learn it from `SessionStart` ([root.go](https://github.com/charmbracelet/crush/blob/main/internal/cmd/root.go)). `--yolo` / `-y` / `-yy` skip prompts. `--prompt` exists (`addPromptFlag`); that it starts the TUI with the prompt submitted is unverified.
- **Gap: adding hooks per launch.** Hooks are read from the global `~/.config/crush/crushrc` and the project `.crushrc`. `CRUSH_GLOBAL_CONFIG` moves the global directory, and crushrc has an `include` ([README](https://github.com/charmbracelet/crush/blob/main/README.md)), so a per-fleet global directory that includes the engineer's file and adds Admiral's hooks looks possible. Unverified.
- **Local models.** Built-in provider types for `ollama`, `llamacpp`, `lmstudio`, `omlx` and `litellm`, with discovery code for llama.cpp.
- Written in Go, as Admiral is.

### OpenCode v2 (Anomaly, formerly SST)

- **v2 is a different program from v1.** OpenCode 2.0 shipped in autumn 2026 (sources disagree on the date) and moved the agent into "one shared background server for your user account. Every local OpenCode client connects to that server, which owns sessions, configuration, integrations, permissions, and tool execution" ([CLI intro](https://opencode.ai/docs/cli/)). v1 still ships (1.19.6 on 2026-11-17), so a plugin has to pin a major version.
- **The shared service is the Codex-per-fleet problem again**: tool calls run in the server's process, not the pane's. `--standalone` "runs with a private server". The TUI's source passes `environment: Env.session()` to a server it manages ([default.ts](https://github.com/anomalyco/opencode/blob/dev/packages/cli/src/commands/handlers/default.ts)); what that carries, and whether `TMUX_PANE` reaches a tool, is unverified. Ships would launch with `--standalone`.
- **Session id at launch.** In the same source, "A missing --session ID becomes the ID of the session the first prompt creates", so `opencode --session <id> --prompt …` gives Admiral the id before the first event, as `--session-id` does for Claude Code. This comes from source, not docs, and is unverified in a run.
- **Beside route.** The TUI talks to the server over HTTP, so a second client is how the product works. Endpoints include `GET /api/session/{id}/message` and `GET /api/experimental/session/{id}/log?follow=true`, "a durable event log" that "continues with live events" ([server reference](https://opencode.ai/docs/server/)). Auth is pairing or a session token; a standalone server's auth is unverified. `opencode acp` "starts a private OpenCode server" and "doesn't connect to the shared background service" ([ACP docs](https://opencode.ai/v2/docs/cli/acp/)), so ACP is not a beside route.
- **Signals need a TypeScript plugin.** v2 has no shell hooks. Server plugins get `ctx.permission.hook("evaluate")`, which "runs for `allow` and `ask` decisions", `ctx.tool.hook("execute.before" | "execute.after")` and `ctx.event.subscribe` ([server plugins](https://opencode.ai/docs/build/plugins/server)). The docs name no session-idle or question event. Plugins load from `plugins` in `opencode.json(c)` and from `.opencode/plugins/` or `~/.config/opencode/plugins/` ([plugins](https://opencode.ai/docs/plugins/)). Loading one per launch without a config file is unverified for v2. `ollama launch opencode` "starts OpenCode with an inline config… It does not overwrite `~/.config/opencode/opencode.json`" ([Ollama](https://docs.ollama.com/integrations/opencode)), so some inline route exists.
- **Permissions fit allow rules best.** Rules have an `action` (`shell`, `read`, `edit`, `subagent`), a `resource` and an `effect` (`allow` / `ask` / `deny`), with `*` and `?` wildcards, "The last matching rule wins", and a default of `ask` ([permissions](https://opencode.ai/docs/permissions/)).
- **Local models.** "OpenCode probes `http://127.0.0.1:11434`, discovers completion models, and adds them to `/models` without an account connection" ([providers](https://opencode.ai/docs/providers/)). Ollama says it "requires a context length of 64k or higher".
- Churn: 14 tagged releases between 2026-10-30 and 2026-11-26.

### Qwen Code (Alibaba)

- A fork of Gemini CLI that took Claude Code's hook vocabulary. Events include `PreToolUse`, `PostToolUse`, `UserPromptSubmit`, `SessionStart`, `SessionEnd`, `Stop`, `StopFailure`, `Notification` (`permission_prompt`, `idle_prompt`), `PermissionRequest` ("When permission dialog is shown"), `SubagentStart` and `SubagentStop`, and payloads carry `transcript_path` ([hooks](https://github.com/QwenLM/qwen-code/blob/main/docs/users/features/hooks.md)). Of the candidates, this is the closest match to Admiral's Claude Code bundle.
- Launch: `--session-id` ("Specify a session ID without session resumption"), `--resume`, `--continue`, `--fork-session`, `--acp` ([config.ts](https://github.com/QwenLM/qwen-code/blob/main/packages/cli/src/config/config.ts)).
- Permissions: `permissions.allow`, `ask` and `deny` rules, merged across user, project and system ([settings](https://github.com/QwenLM/qwen-code/blob/main/docs/users/configuration/settings.md)). The default approval mode is **Auto**: "an LLM classifier auto-approves safe actions and blocks risky ones" ([approval mode](https://github.com/QwenLM/qwen-code/blob/main/docs/users/features/approval-mode.md)). On a local model, that classifier is a weak model judging safety; a ship would pin `--approval-mode default`.
- Gaps: project hooks need approval or folder trust, the same kind of first-launch stop that Codex's hook trust causes. Adding settings per launch has only the system-settings path env var, which replaces the system file rather than adding to it. `qwen serve` (a daemon with REST and SDK clients) may give a live route; whether it runs beside an interactive TUI is unverified.
- Local models: OpenAI-compatible `modelProviders` with `baseUrl: http://localhost:11434/v1` and a `contextWindowSize` ([model providers](https://github.com/QwenLM/qwen-code/blob/main/docs/users/configuration/model-providers.md)), and `ollama launch qwen`.

### goose (Agentic AI Foundation, formerly Block)

- Strong on local models: a native Ollama provider, `GOOSE_PROVIDER` and `GOOSE_MODEL` per launch, a **tool shim** (`GOOSE_TOOLSHIM=true`) that has a second local model turn text into tool calls for models without tool support, and `goose local-models` for built-in GGUF and MLX inference ([env vars](https://github.com/aaif-goose/goose/blob/main/documentation/docs/guides/environment-variables.md), [CLI](https://github.com/aaif-goose/goose/blob/main/documentation/docs/guides/goose-cli-commands.md)).
- Weak as a ship. Hooks follow the Open Plugins spec (`SessionStart`, `SessionEnd`, `Stop`, `UserPromptSubmit`, `PreToolUse`, `PostToolUse`, …) but have **no approval event** ([hooks](https://github.com/aaif-goose/goose/blob/main/documentation/docs/guides/context-engineering/hooks.md)), so an approval in `approve` mode would never show as needs-you. Hooks are discovered only from `~/.agents/plugins/` or the project's `.agents/plugins/`. Sessions live in SQLite. `goose serve` and `goose acp` are ACP servers in their own right; the CLI session doesn't attach to them. The default mode is **Completely Autonomous**.

### Pi (Earendil, Mario Zechner)

- The lightest harness here: four tools (`read`, `write`, `edit`, `bash`), and "pi's system prompt and tool definitions together come in below 1000 tokens" ([author's post](https://www.mariozechner.at/posts/2025-11-30-pi-coding-agent/)). The same post says self-hosted models in other harnesses "usually [don't] work well", partly because of the Vercel AI SDK "when it comes to tool calling".
- Ship shape: `--session-id <id>` "creates it otherwise", sessions are JSONL files with a documented [format](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/session-format.md), `-e <extension>` and `--agent-dir` work per launch, and there is a [tmux page](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/tmux.md) ([CLI](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/cli.md)). Extension events `agent_start`, `agent_end`, `turn_end`, `tool_call` (which can block or rewrite) and `ui_prompt_start`/`ui_prompt_end` ("so host/status integrations can report 'waiting for user'") give every signal Admiral needs, from an extension Admiral would ship ([extensions](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/extensions.md)).
- The gap is permissions. Pi "does not ask for approval before every tool call" ([security](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/security.md)); the author calls it "full YOLO mode". Allow rules would be enforced by Admiral's own extension, which blocks or asks through `ctx.ui.confirm`, and that is a guard Admiral writes rather than a fence the harness provides (ADR 0035's probe would have to prove it).
- Local models: an `openai-completions` provider in `~/.pi/agent/models.json`, or `ollama launch pi`, which "installs Pi if needed, configures Ollama as a provider" ([Ollama](https://docs.ollama.com/integrations/pi)). That writes to the engineer's Pi config; `--agent-dir` avoids it.
- The README says new contributors' issues and PRs are closed automatically.

### Cline CLI

- Good launch surface: `--hooks-dir` ("additional hooks for runtime hook injection"), `--config`, `--data-dir`, `--id` to resume, `--acp` ([CLI reference](https://github.com/cline/cline/blob/main/docs/cli/cli-reference.mdx)).
- File hooks: `TaskStart`, `TaskResume`, `UserPromptSubmit`, `PreToolUse`, `PostToolUse`, `TaskComplete`, `TaskError`, `TaskCancel`, `SessionShutdown` ([hooks example](https://github.com/cline/cline/blob/main/sdk/examples/hooks/README.md)). There is **no approval event**, so needs-you on an approval would fall back to the 10-second rule at best.
- Risky defaults: a prompt on the command line "Runs in yolo mode by default", and `ollama launch cline` "sets Cline's provider to Ollama", which changes the engineer's other Cline sessions ([Ollama](https://docs.ollama.com/integrations/cline-cli)). The map's standing rule forbids that; `--config` per fleet avoids it.

### Aider

Not a candidate. No release since v0.86.0 (2025-08-09), no session id, no hooks beyond `--notifications-command`, no ACP, and no tool calls: it asks the model for text edit formats ([options](https://aider.chat/docs/config/options.html)). That last point is why it copes with weak models, and it sizes Ollama's `num_ctx` per request because "Ollama uses a 2k context window by default" and "silently discards context that exceeds the window" ([Aider on Ollama](https://aider.chat/docs/llms/ollama.html)).

### Gemini CLI

It meets Admiral's ship bar (hooks with `transcript_path`, `Notification` `ToolPermission`, `-r <id>`, `--acp`, a policy engine), but it **cannot use a model server** for the agent. Its only local-model feature is "a locally-running **Gemma** model to make routing decisions" ([local model routing](https://github.com/google-gemini/gemini-cli/blob/main/docs/core/local-model-routing.md)). Qwen Code is the fork that can.

### Others current now (not researched in depth)

`ollama launch --help` (observed) also lists **Copilot CLI** (one of the big three: `COPILOT_PROVIDER_BASE_URL`, [Ollama](https://docs.ollama.com/integrations/copilot-cli); that belongs to [#972](https://github.com/jbuffin/admiral/issues/972)), **Droid** (Factory, closed source), **Kimi Code CLI**, **OMP** (Oh My Pi, a Pi fork), **Muse Code**, **Pool**, **DeepSeek Harness** (runs in a browser), and **Hermes Agent** and **OpenClaw** (personal assistants, not coding harnesses). **Kilo CLI** (v7.8.40) is an OpenCode fork. None was checked against the table.

## Tool calling on common Ollama models

- **Context matters before tool format does.** Ollama gives a model a 4k context below 24 GiB of VRAM, 32k from 24 to 48 GiB, and 256k above that, and says "agents, and coding tools should be set to at least 64000 tokens" ([context length](https://docs.ollama.com/context-length)). Ollama's pages for Claude Code, Codex, Copilot CLI and OpenCode each ask for 64k or more. A harness on default settings on a 16 GB Mac drops most of its own system prompt. Aider documents that the drop is silent.
- **Observed, small sample.** A one-turn probe against `/api/chat` with six coding tools (`read`, `write`, `edit`, `bash`, `grep`, `ls`) and four tasks, run three times each at temperature 0.7, on the two models installed here:
  - `qwen3:4b-instruct` returned a well-formed structured tool call 12 times out of 12. The tool matched the task 3 times. The other 9 were reasonable first steps (`ls` before `read`, `read` before `edit`).
  - `llama3.2:3b` returned a tool call 12 times out of 12, and 9 matched the task. One was malformed: `grep` with an empty pattern and an invented `content` argument. Two ran `bash` with `cat`.
  - This shows only that Ollama's parser hands back structured calls for these models. It says nothing about multi-turn loops, long prompts or 30B-class models. No public benchmark was found that measures tool calling on Ollama-served quantized models; numbers in blog posts were not checked.
- **The tool shim** (goose) and **text edit formats** (Aider) are the two documented ways around models whose tool calls fail.

## Are the big three on Ollama worse than a harness built for local models?

Admiral's own adapters don't get worse. What gets worse is how the models cope with the requests, and the causes are documented:

- **Prompt and tool size.** A Claude Code issue logged `{"num_tools": 259, "model": "qwen3:8b"}`: 17 built-in tools that can't be filtered, plus 242 MCP tools. With one tool, the same model made a correct `tool_use` call ([claude-code#25857](https://github.com/anthropics/claude-code/issues/25857), closed as a duplicate of the MCP-filtering issue). Pi's prompt and tools fit in under 1,000 tokens. Claude Code's system prompt size is not published; community estimates of 6–10k tokens are unverified.
- **Context.** The big three expect large windows (Claude Code assumes about 200k, unverified), and Ollama allocates far less unless the server is set to more.
- **Compatibility layers.** Claude Code reaches Ollama through Ollama's Anthropic-compatible API, where "Hosted WebSearch and advanced tool controls are not fully supported" ([Ollama](https://docs.ollama.com/integrations/claude-code)). The same issue found 404s from a hard-coded Haiku token-count call. Codex uses `wire_api = "responses"` and a generated model catalog ([Ollama](https://docs.ollama.com/integrations/codex)). Ollama's examples use `gpt-oss`; that `gpt-oss` was trained on Codex-style tools is unverified.
- **On large or cloud models** served by Ollama (`:cloud`, or 30B and up with 64k context), these costs mostly go away, and the big three keep everything Admiral already has: hooks, adapters, autopilot and probes. That is why the map does the big three first. A harness built for local models earns its place on small local models that the big three swamp.

## The Ollama app's chat is not an agent harness

Confirmed as far as the docs go. Ollama's [quickstart](https://docs.ollama.com/quickstart) sends coding work to "Use a coding agent" through `ollama launch`, and sends desktop chat to Claude Desktop or ChatGPT Desktop connected through the app's **Apps** pane. The app's own chat has no documented file, shell or edit tools, no sessions a CLI can open, and no hooks. That it has no hidden agent mode is inferred from the docs, not tested.

## Candidates for the first harness plugin

1. **Crush.** It has the best signals of any harness outside the big three, Claude-compatible and including a real `PermissionRequest`, `TurnEnd` and `Interrupt`. A per-ship server on a Unix socket gives a live structured conversation beside the TUI in the same shape as Admiral's Codex adapter. It has native Ollama and llama.cpp providers, and it is written in Go. Costs: Admiral learns the session id from `SessionStart` and not at launch; the conversation is in SQLite or the API, not a file; and adding hooks per launch needs the `CRUSH_GLOBAL_CONFIG` plus `include` trick, which must be checked first.
2. **Qwen Code.** The least new design: Claude Code's hook names and payloads, `transcript_path`, `--session-id`, and `permissions.allow` rules. Admiral's Claude Code bundle and transcript adapter shapes transfer almost as they are. Costs: no live route (the transcript file is the floor, which ADR 0030 allows), the project-hook trust stop, no clean way to add settings per launch, and an LLM safety classifier on by default.
3. **OpenCode v2.** The most used, the integration Ollama puts first, a caller-chosen session id, a TUI that is already a server client, and the permission rules closest to Admiral's allow rules. Costs: signals need a TypeScript plugin rather than a hook bundle, the v2 event names and per-launch plugin loading are unverified, the shared service must be avoided with `--standalone`, and the release pace is fast.

**Pi** is the best runner on small local models and is easy to launch, but it has no permission model, so every guarantee Admiral makes would rest on Admiral's own extension. It is a better second plugin than a first.

## Unverified, to check before #978 decides

- Crush: adding hooks per fleet through `CRUSH_GLOBAL_CONFIG` and `include`; whether `--prompt` starts the TUI with the prompt submitted; whether `PreToolUse` `^question$` fires before the question dialog; that an SSE observer never counts as a client that can answer.
- OpenCode v2: the `--session <new id>` behavior in a run; `Env.session()` and `TMUX_PANE` reaching tools under `--standalone`; the event names for idle, permission and question; loading a plugin per launch; auth on a standalone server.
- Qwen Code: a settings or hooks file added per launch; whether `qwen serve` runs beside a TUI session.
- Cline: whether the hub is a beside route; whether `--id` accepts a new id.
- Tool calling: a multi-turn probe at 64k context through each candidate on the engineer's hardware, ideally as an ADR 0035 capability probe rather than a one-off.
