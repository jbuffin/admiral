# Codebase

This file holds the package map, API routes and ship statuses, idle memory figures, the setup terminal and the chat session. Read it before changing the server, the launcher, ships, the setup terminal or the chat session.

## Layout

- `designs/`: the clickable prototype, screenshots, design tokens, SVG assets and source design files. Start with `designs/README.md`.
- [Admiral MVP spec](https://github.com/jbuffin/admiral/issues/45): what the MVP does, as user stories, implementation decisions and testing decisions.
- `docs/architecture.md`: an early proposal for the build, superseded by the spec and the ADRs.
- `docs/adr/`: decisions.
- `GLOSSARY.md`: the words Admiral uses.
- `cmd/admiral/`, `internal/`: the Go server and CLI. `internal/auth` is access control (per-device tokens in `$ADMIRAL_HOME/devices.json`, pairing codes, the device API; see "Devices and pairing" below), `internal/server` is HTTP and WebSocket, `internal/home` finds `$ADMIRAL_HOME`, `internal/crew` resolves crew members and their notes from layer directories it is handed (read-only; it reads no environment variable), `internal/launcher` resolves a launch's pinned members over the built-in (the installed Commodore's `crew/`, found by `skillindex.CommodoreDir`), fleet and repo layers and `internal/launchorders` lists the members a launch could pin, `internal/crewapi` serves a fleet's Crew page (`/api/fleets/<key>/crew`), drafts a new member from a description with one judge call (`draft.go`, prompt `crewwriter.md`; the call is the `Service.Judge` seam, `judge.Run` when nil) and holds the write side of the crew directory: fleet member files and notes, written atomically through `Lstat`-checked paths that refuse a link (`ApplyNotes`, `KeepAdHoc` and `DropAdHoc` are what `internal/inbox` calls to write kept crew notes and ad hoc members, all under one `writeMu` hold and all-or-nothing: they plan every write in memory, refuse a misfit before writing, and put back what they wrote if a later write fails; `AppendNote` adds one note; they make the crew directories themselves), `internal/config` loads, validates, watches and writes `$ADMIRAL_HOME/config.json`; it also reads the top-level `max_ships` (see "Ship cap" below). `internal/sessionhost` is the only non-test package that runs tmux or builds its commands (`TestNoTmuxOutsideSessionhost` guards it: callers use its `Server` methods and `*Call` builders, and `admiral hook` its current-server runners) and holds the one tmux control-mode connection on `$ADMIRAL_HOME/tmux.sock` (it re-reads the sessions about every half second, and a global `alert-bell` hook stamps bells), `internal/launcher` creates ships (names, hook bundle in `$ADMIRAL_HOME/harness/`, command lines), `internal/chat` is the AdmiralBot chat session (see "The chat session" below), `internal/usage` parses the exit figures a harness leaves (tokens by disjoint class, money with its basis, Codex quota windows) from a Claude, Codex or Copilot transcript, and subtracts cumulative readings, and builds a `usage` outcome record's fields (`ExitFields`: a ship's totals are its own figures plus its crew boats', money only within one basis). `internal/ships` writes that record beside `ended` at each exit, once per exit and off the pass goroutine (`UsageRead`, filled by `TranscriptUsage`, reads the ship's and its crew boats' transcripts; `LastLive` is `usage.Store.LastLive`, see the next bullet), and `internal/chat` writes one at each reset; `internal/state` is `$ADMIRAL_HOME/state.json` (ship positions, each dock's last directory, the kept inbox records, the resume text), `internal/ships` serves `GET`/`POST /api/ships`, `PUT /api/ships/<session>/position`, `POST /api/ships/<session>/input-seen` (a browser sent input: clears needs you), `POST /api/ships/<session>/answer` and `.../crew/<name>/answer` (send `internal/keymap`'s keys for Allow once, Deny or a question's option, only while the pane's `@admiral-reason` matches the body's; Claude and Copilot panes are answered in place, Copilot's on `notification:permission_prompt`, `question` and `notification:elicitation_dialog` (its question form takes Down then Enter, not digits); `Service.Questions`, `shipconv.PendingQuestions`, gives the pending questions for the gate), `POST /api/ships/<session>/dismiss` (ends an anchored or a moored ship), `POST /api/ships/<session>/unfollow` (Don't follow reviews: ends a moored ship; any other ship is refused as Dismiss refuses it), `POST /api/ships/<session>/merge` (the engineer's Merge act on a moored ship's ready PR: `serveMerge` in `internal/ships/merge.go` re-reads the PRs from GitHub, runs `gh pr merge` through `moor.GitHub.MergePR` with the repository's default method, answers 202 and asks for a poll, and it needs the page's merge token or answers 403; a stack is refused with 422 and the poller, orders and agents never merge; the guard in `internal/cli/guard_merge.go` still refuses an agent's merge), `POST /api/ships/<session>/wake` (wakes a moored ship by hand: 201 with the ship, `ships.Service.Wake`; see below), `POST /api/ships/<session>/answer-review` (a hand feedback round on one PR, body `{"pr"}`, `ships.Service.answerReview`, or Answer all reviews on the ship's stack, body `{"stack"}`, `serveAnswerAll`; 201 with the ship; see "A hand round" below), `POST /api/moored/refresh` (kicks the moored poll, 202), `POST /api/ships/<session>/crew/<name>/close` (kills one crew boat's window, live or anchored, like `admiral crew close`; 404 `ship <session> not found` or `crew boat <name> not found`, the latter too when the window closed between the poll and the kill) and the WebSocket `ships` message. Each ship carries a `tail`, a line from its conversation: `internal/shipconv`'s `Tails` follows Claude ships' transcripts (re-reading one only when it changed) and `conversation.Tail` picks the line. `internal/shipconv` serves `GET /api/ships/<session>/conversation[?before=<id>]` and the WebSocket `conversation_open`, `conversation_close` and `conversation` messages (a Claude Code ship's conversation, `docs/api.md`); it finds the file from the ship's `@admiral-transcript` pane option, which the launcher sets at launch beside `--session-id`, and `internal/transcriptfs` holds the ADR 0019 path checks and the open it reads through. A ship carries `reason` (the validated code, `idle` for a ship no hook has spoken for) and `stop_since` (RFC 3339; the open stop's start from the log's track) only while its `status` is `needs_you`. A ship's `status` is `underway`, `needs_you`, `anchored` (with `exit_code` or `exit_signal`), `sailing_off` (exit 0, session killed after 3 s) or `moored` (a ship that exited 0 while its report listed a PR that GitHub confirms open on the fleet's built-in GitHub source's host and that routes to the ship's fleet: `internal/moor` reads the report (versions 1 and 2) and writes `$ADMIRAL_HOME/moored/<name>.json`, `internal/ships` ends the session, writes a `moored` outcome and lists the record, `internal/launcher` keeps the name reserved; `gh` is retried for `ADMIRAL_MOOR_RETRY`, 8 s by default, and a PR GitHub cannot confirm sails the ship off; the check runs for exit-0 ships found at startup too). `ships.Service.RunMoored` polls every moored ship's PRs (`moorpoll.go`): one batched `gh api graphql` per fleet client (`github.Client.PullRequests`, one aliased `repository{pullRequest}` per PR, parsed from `data` even when gh exits 1 for a `NOT_FOUND`) every `ADMIRAL_MOOR_POLL` (2 min) and on each kick; a kick during a poll coalesces. A PR GitHub answers `NOT_FOUND` for counts as closed; a failed call keeps the last chips, marks the ship `stale` and never ends mooring. The ship sails off (`endMoored`: the record is removed with `moor.Remove`, the cache and name are freed, one `unmoored` written; the first ending wins a race) when every PR is merged or closed, or on Dismiss or Don't follow reviews; there is no idle timeout and a merge wakes nothing. A wake (`internal/ships/wake.go`) recreates the moored ship's session under its own name and session: `Launcher.Launch` takes `Request.Name` and `Request.Session` (refusing 409 while that session is live, under `l.mu`, so no launch takes the name between) and `Request.Prompt` (the harness prompt verbatim, so the report's `resume` text is not prefixed with a skill again), and sets the session option `@admiral-round` from `Request.Round`. The wake goes through `admit` and `LaunchOrder` with the record's `source`, `order`, `url`, `panel`, `title` and `resources`, so the order stays hidden and the claim holds, but `LaunchOrder` skips the order read and its own-ship refusal when `Round` is set. The round count is `Record.Round + 1`; `moor()` writes the live `round` option and `resources` back into the record, so a ship that moors again keeps both. The report's `resume` text is kept only when it is `/skill resume <run>` or `$skill resume <run>` (`moor.ValidResume`), since it is the prompt. `Request.Before` runs under the launcher's lock just before the session is made: it re-checks that the record is still the one the wake read (a Dismiss, Don't follow reviews or merged PR that ended the mooring first wins and the wake answers 409) and writes the feedback file into the validated checkout; from then on `endMoored` loses to the wake (`Service.committed`). `woken` is written by `launched` for a round. The record is removed once the woken session exists. `Service.Wake` (by hand: no autopilot, counted toward the cap, never blocked by it, the engineer's text after the `resume` text) and `Service.FeedbackRound` (autopilot, refused at the cap or on an unguarded harness; the feedback text goes to `<checkout>/.admiral/untrusted/feedback-<N>.md` through `moor.WriteFeedback`, never into the prompt, argv, options or environment) are the two entries; neither carries crew pins. A wake writes `woken` (`round`, `by` `hand` or `feedback`, `pr` for a round) instead of `launched`, and the round's end writes `round` (`round`, `end`: `moored` beside `moored`, `sailed`, or `anchored`). `unmoored` carries `reason` (`merged`, `closed`, `prs_done`, `dismissed`, `unfollowed`) and `prs`, each `{url, state}` as last polled; hooks, a Codex bell and the 10 s no-hook rule decide needs you (every hook runs `admiral hook <event>`, internal and unlisted in the usage text, which reads the harness's JSON on stdin and sets `@admiral-state` on `$TMUX_PANE`; it always exits 0. With `needs_you` it also sets `@admiral-reason` in the same tmux call, a code and never payload text: `permission:<tool>`, `question`, `notification:<type>`, `stop`, or `bell` from a Codex bell; `working` unsets it, and `sessionhost` polls it into `Session.Reason`. A tool name or type is kept only if it matches `^[A-Za-z0-9_.:-]{1,64}$`, and a notification's reason is written only if none is set, so `permission:Bash` survives either order of Claude's two events. `internal/cli/hook.go` holds the event→state and event→reason rules, and Claude's `Stop` writes nothing while `background_tasks` has a running `subagent` or `teammate`, so a running `shell` task doesn't hold a ship back. A Monitor is the exception (#110): it also reports as a `shell` task, so a Monitor's `PostToolUse` keeps its `tool_response.taskId` in the pane option `@admiral-monitors`, and a `Stop` writes nothing while one of those ids is running (each `Stop` drops the ids no longer running). A persistent Monitor is not kept, since it has no timeout to wake the session. A crew pane's plain `Stop` writes `idle`, not `needs_you` (#189): it holds no lead's `Stop` and doesn't raise the ship. A lead's `Stop` held only by working crew sets `@admiral-crew-held`, which its next state write clears, and the last boat to go idle flags that lead with reason `stop`. `admiral guard pretooluse` (`internal/cli/guard.go`, also unlisted in the usage text) is Claude's other PreToolUse hook, in the settings for `Bash`, for `^mcp__.*pull_request_review.*$` and for `launcher.MergeToolMatcher`. All handlers have `"timeout": 10` and `"onFailure": "block"`, because Claude Code lets a call through when a PreToolUse command hook times out or fails (`onFailure` needs Claude Code 2.1.295 or later). It does nothing unless `ADMIRAL_AUTOPILOT` is exactly `1`; then it parses a Bash command with `mvdan.cc/sh/v3/syntax` (`guard_shell.go`, which also looks through wrappers, `sh -c`, `eval` and heredocs fed to a shell). When the command doesn't parse as bash, it walks the statements parsed before the error, then parses the whole text as zsh, then applies a text rule (a line that mentions a review and an approve or request-changes spelling) to the whole line. A program word with an expansion that is followed by `pr … review`, `pr … merge`, `pr … edit` or `api` is checked as `gh`; any other unknown program, or a shell reading a pipe, gets the text rule on its own call or statement, computed once per span. Where it has no text for what it judges (a program word that is only an expansion, a `-c`, `eval` or heredoc script that is only an expansion, a shell reading a pipe or a file, a GraphQL `query` that is only an expansion), it also reads the whole line, once, for long spellings only (`review` with `approve`, `request_changes` or `request-changes`); short flags are not matched there. A program word that is only an expansion (`$C`, `${=C}`, `"${C[@]}"`) that no rule names is refused as `shell_script`, because the command in it can't be seen, which is also how a long spelling split by quotes (`C="gh pr me""rge 5"; $C`) is caught. Other `gh` calls are allowed, `gh pr ready` among them, unless a rule below names them. It refuses, with exit 2 and the one reason line on stderr, a command or MCP call that would submit a review as APPROVE or REQUEST_CHANGES (`gh pr review`, `gh api` reviews calls and GraphQL), or a payload it can't read; those get the review reason. The merge rules (`guard_merge.go`, #120) refuse with a merge reason: every `gh pr merge` that can merge, `--auto` and `--admin` included (`gh_pr_merge`; #261, autopilot never merges); `gh api` writes to `pulls/<n>/merge` and `merges` (`gh_api_merge`); the GraphQL mutations `mergePullRequest`, `enablePullRequestAutoMerge`, `mergeBranch`, `enqueuePullRequest` and `dequeuePullRequest` (`graphql_merge`); writes to rulesets (repository and organization) and branch protection, through REST or GraphQL, which would lower the gate on a merge (`gh_api_gate_write`, `graphql_gate_write`); and any change of a pull request's base (`pr_base_change`: `gh pr edit -B` or `--base`, a REST write to `pulls/<n>` with a `base` field or an `--input` it can't read or that has one, GraphQL `updatePullRequest` with `baseRefName`, its input in a variable, or an expansion). A write is any `gh api` method but GET and HEAD, a method held in a variable, or gh's implicit POST (`-f`, `-F` or `--input` with no `-X`). API paths are percent-decoded and have empty and `.` segments dropped and `..` resolved before they are matched; one that climbs above its root is one expansion. An expansion in a path counts as any words there: a write is refused when the expansion ends the path after a prefix a merge or gate route extends (`repos/<o>/<r>`, `pulls/<n>`, anything under `branches`, `orgs/<o>`), or when the literal words after it end in `merge` or `merges` or hold `protection` or `rulesets`, so `gh api -X PATCH repos/o/r/issues/$N -f state=closed` and `-X PATCH repos/o/r/pulls/$N -f body=x` are allowed (only a PATCH may end a path in an expansion right after `pulls`, because the merge route is a PUT; a `base` field is refused as `pr_base_change`). MCP tools are matched by `launcher.MergeToolMatcher` (any `mcp__` tool with `merge` or `enqueue` in its name, in any case, spelled with character classes because Claude Code matchers are JavaScript regular expressions with no `(?i)`), and the guard refuses every tool the matcher selects except those whose last name segment starts with `list_`, `get_` or `search_` (`mcp_merge`); the guard compiles the same constant, so the two agree. Where the guard can't parse a command and falls back to text, the text rule also refuses text that mentions `pr … merge`, a `pulls/…merge` or `/merges` route, `rulesets`, `/protection`, or those mutation names (a merge in `eval "$C"`, `echo '…' | bash`; `pr` and `merge` count anywhere in the text, so `A='gh pr '; B='merge 1'; eval "$A$B"` is refused). A GraphQL `query` the guard can't read is refused (`graphql_merge`): a file or stdin that isn't shown on the line, a query that is only an expansion or has an expansion beside the word `mutation` or outside a value position, and an `operationName` beside an expanded query; pass values as GraphQL variables (`-f id="$ID"` with a literal query) instead. A script given as an expansion alone (`eval "$(cat m.sh)"`, `bash <<< "$X"`) is refused as `shell_script` unless the line itself shows a merge, which gets the merge rule. Rules that keep the guard from being routed around, with their own reason (`opaqueReason`): `gh alias` and `gh extension` (`gh_alias`, `gh_extension`); a first `gh` word that is not one of gh's built-in commands (`ghCommands`, including help topics; `gh co` is an alias and stays refused; `gh_unknown`); an expansion in the word after `gh pr` or `gh auth` (the first is refused with the merge rule, the second as `token_read`); the shell builtins `alias`, `unalias` and `hash name=path` / `hash -p`, and assignments to `aliases`, `functions`, `commands`, `BASH_ALIASES` and `BASH_CMDS` (`shell_alias`); and scripts the guard isn't shown. For `bash|sh|zsh FILE`, `source FILE` and `. FILE` the guard reads the file with the limits of any file it reads (a regular file of at most 1 MiB, from the call's cwd), checks it as a command line of its own, and uses that result; it refuses with `shell_script` only a file it can't read or parse, a script given by an expansion, a shell fed from a pipe, `-s` or `sh < f`, and the arguments of an `xargs` that runs `gh` or a shell. Stdin counts as shown only when the statement has exactly one input source and its text is literal: one heredoc or here-string with no expansion, or one `<` from a literal file, or no stdin redirect and a literal `echo`, `printf` or `cat` of a literal heredoc before the pipe (words with no escapes). A `<&`, a `<>` or a second redirect of fd 0 means stdin is not shown, because zsh reads several and bash the last. A GraphQL `query` on stdin, a write's `--input -` body and a `pulls/<n>` PATCH are refused otherwise. An `--input` body, from stdin or a file, is decoded as a JSON object before it is read, so a `\u` escape can't hide a name, an event or a key (this covers the review rules too); keys are read by their exact names, and a body with two keys that differ only in case, or that isn't a JSON object, is refused. Boolean flags are read as gh reads them, with `strconv.ParseBool` (`--disable-auto=0` is false), and a value that isn't a boolean is refused. The token is refused when it is read, not when it is named: an expansion of `GH_TOKEN`, `GITHUB_TOKEN` or the enterprise names in any form, `printenv` or a bare `env`, `gh auth token` or `status -t`, `git credential`, and `security find-generic-password` or `find-internet-password` with `-w` or `-g` (`token_read`); `grep -rn GITHUB_TOKEN .github` or a quoted heredoc that writes `${{ secrets.GITHUB_TOKEN }}` is allowed. `gh pr merge --disable-auto` without `--admin` is allowed: it merges nothing. Programs that run their arguments are looked through when they are `find` (`-exec`, `-execdir`, `-ok`, `-okdir`), `arch`, `script`, `flock`, `watch`, `unbuffer`, `doas`, `gtimeout`, `npx`, `xargs` and the usual wrappers; `git -c alias.x=!…` and `git config alias.x '!…'` are refused as `git_shell_alias`. A relative file is not read once the line has a `cd`, `pushd` or `popd` (the guard would read a different file from the one the call reads), `~/` is the home directory, and a shell is refused when `BASH_ENV`, `ENV` or `ZDOTDIR` is set on the line or when `--rcfile`, `--init-file` or `-i` comes beside a script. `gh auth status --show-token` is read as a boolean, and `git credential-*` helpers count as `git credential`. Known gaps. The guard is best effort, and the GitHub rules of the base branch are the gate: it narrows what a ship can do by accident or by habit, and it can't contain an agent that runs arbitrary programs with a token that can merge. The Merge route's token (`X-Admiral-Merge-Token`, injected into the `/app/` page's `<meta name="admiral-merge-token">` by `internal/server`) keeps a local curl from merging by accident; a process that fetches `/app/` and reads the meta, or impersonates a browser, still can. A script run as `./FILE` runs unread (`bash FILE` is read, but the same file as a command is not). A program word built from a literal and an expansion (`g$Y`, `$D/gh $S`), zsh glob qualifiers that run code (`*(e:'…':)`), the `(e)` parameter flag and arithmetic that evaluates a subscript (`$((X))` with `X='a[$(…)]'`) run a command the guard reads as data. Sourcing nvm (`. ~/.nvm/nvm.sh`) is refused, because nvm defines aliases (`shell_alias`); set Node up outside the ship. The guard is best effort and reads only the text of a Bash call (D8): a merge through anything that is not a literal shell `gh` call is invisible to it, such as an interpreter (`python3 -c`), `make`, `curl` with a token from somewhere else, a nested agent, a `gh` shim earlier on `PATH`, or a replaced `$ADMIRAL_HOME/bin/admiral`. Files the guard reads (`--input`, `-F @file`) can change before gh reads them. Direct writes to the base, `git push`, REST `PUT contents`, `PATCH git/refs`, GraphQL `createCommitOnBranch` and `updateRef`, and the GitHub MCP file tools, are not hooked, and neither are writes to repository settings that raise access (`collaborators`, `PATCH repos/<o>/<r>`); the branch rules on GitHub are what stop them. The GitHub MCP `update_pull_request` tool with a `base` argument changes a base and is not hooked. Codex and Copilot ships have no guard, and autopilot refuses any harness but Claude for that reason; so does `admiral crew launch` for a caller with `ADMIRAL_AUTOPILOT=1`, whose `--arg` values must also fit the autopilot args allowlist (`launcher.AutopilotArgs`, `internal/launcher/autopilotargs.go`, a per-harness table of flags with their arity; codex's and copilot's tables are ready but unreachable until a guard probe is registered for them in `probes`), checked in `LaunchCrew` after the hook refusal and before the window is made. A refusal writes one `guard_denied` line (`tool`, `rule`, no command text) under the home of `ADMIRAL_REPORT`, or else `ADMIRAL_HOME`; with no ship or home, or a failed write, it still refuses. Every ship also gets `ADMIRAL_SHIP` (its session name), `ADMIRAL_REPORT` (`$ADMIRAL_HOME/reports/<session>.json`) and `ADMIRAL_INBOX` (`$ADMIRAL_HOME/inbox/<session>/`) and `ADMIRAL_CREW_DIR` (`$ADMIRAL_HOME/fleets/<fleet key>/crew/`, made 0700 when missing, kept across ships, and refused with a 500 when `fleets`, the key or `crew` is a link or not a directory), which win over a fleet's env; a launch with `crew` pins (Commodore only) also gets `ADMIRAL_RUN_CREW`, the per-ship run layer `$ADMIRAL_HOME/run-crew/<session>/` (0700) that Admiral fills with the pinned members' files, and a launch without pins has it unset even when a fleet's env sets it (`launcher/crewpins.go`; `RemoveShipFiles` removes it with the report and inbox); Commodore ships on Claude also get `CLAUDE_CODE_AUTO_COMPACT_WINDOW=200000`, a fleet's `env` overrides it, and `1000000` turns it off; an autopilot-mode launch also gets `ADMIRAL_AUTOPILOT=1` and `ADMIRAL_LOW_STAKES=advisor`, and a launch by hand has neither (nothing sets `ADMIRAL_AUTO_MERGE` any more, and it is still dropped from inherited env): Admiral owns these names, so it drops them from the fleet's env and runs `set-environment -r` for each on the session (`-r`, because the tmux server inherits Admiral's own environment, which may hold them; `-u` would fall back to it). A panel's autopilot args go after the fleet's dock args; Admiral removes any report and inbox a reused name left, then creates `reports/` and the inbox before the harness starts. Every start links `$ADMIRAL_HOME/bin/admiral` to the running binary and puts that directory first on a ship's `PATH`), and `HiddenOrders` lists the orders ships hide. `internal/outcomes` is the outcome log: one goroutine appends a JSON line per record (a ship's guard is a second appender, a separate process writing its own short `guard_denied` line) to `$ADMIRAL_HOME/outcomes/<YYYY-MM>.jsonl` (month of `ts`, UTC), queues 1024 records and drops the rest (`Enqueue` passes `outcomes.ErrDropped` to a dropped record's `onDone`), and logs a failed write once until one succeeds. Admiral only writes the log; `admiral outcomes` reads it back. A line over `outcomes.MaxLine` and any name that is not a regular file, and nothing else reads it. `ships.Service` feeds it: `launched` from `Service.LaunchOrder`, the one launch path for `serveLaunch` and autopilot, which holds the order's key while it runs so a second launch of that order gets 409, and sets `"autopilot"` from the request (and only then does `Run` follow the ship), `needs_you` and `underway` from the status each pass of `Run` sees against the last (`internal/ships/outcomes.go`; a stop whose reason changes is one stop, and a ship no hook has spoken for needs you with reason `idle`), `ended` when a pane is dead without `@admiral-ended` (also at start-up, before an exit-0 ship is killed) `dismissed` from Dismiss, `stopped` from Stop ship (a live ship gets an `ended` with signal `KILL` first, queued by `recordKilled` in `internal/ships/input.go`; an anchored one follows Dismiss's order), `answered` from the inbox (`internal/inbox`, ADR 0016). `ended` carries the parsed `$ADMIRAL_REPORT` (at most 1 MiB; `null` and a log line when invalid), and once it is written the writer sets the session option `@admiral-ended` and deletes the report and inbox of a ship that was dismissed or sailed off. Admiral kills such a ship whether or not the log works (`Service.killShip`), so one killed while its `ended` fails loses that `ended` and keeps its files; a dead pane still in tmux is retried at the next start, and Dismiss queues a failed `ended` once more before `dismissed`. The deletes go through an `os.Root` on `$ADMIRAL_HOME` and are skipped, keeping the files, while a launch is under way (a name is not known before `Launch` returns) or when a newer ship's track holds the name: none leaves the home, though a link swapped in inside the home can still send one elsewhere within it. `launcher.ShipFiles` builds the report and inbox paths for both the environment and the cleanup. The needs-you tally survives a restart in the session options `@admiral-needs-count`, `@admiral-needs-s` and `@admiral-stop-since`. The ship's own status stays in `FromSession`, `status()` and `sess.State`, which `InputSeen`'s decision, Dismiss, sail-off, the bell, the startup exit-0 kill and the outcome log use, and `@admiral-state` is never written for a crew boat. The ships push signature covers crew membership, each boat's status and reason and the subagent ids, not `last_activity`. Sail-off and Dismiss kill the whole session (`kill-session`), which ends crew windows and their harness processes; an anchored ship's live crew keep running until Dismiss. `launcher.CloseCrew(ctx, windowID)` is the one kill both `admiral crew close` and the close route use.
- Ship cap (`internal/config/maxships.go`, ADR 0034). Top-level `max_ships` (positive integer, default 3, `config.Config.MaxShips`) caps the ships underway or needing you that autopilot-mode launches may start; hand launches are never capped and count towards it. There is no per-panel autopilot config: a `sources.<key>.autopilot` entry or a top-level `autopilot` object is removed by the startup migration. `launcher.Request` carries `Autopilot` and `Resources` (JSON `autopilot` and `resources`, so `POST /api/ships` sets them), and `ExtraArgs` and `Panel` (`json:"-"`). Autopilot mode is a launch mode (ADR 0034). `serveLaunch` refuses a resource not in the config (400), an `autopilot` request on a harness whose guard probe has not passed in the launch's fleet (400, `autopilotgate.Check`), an autopilot launch when `max_ships` ships are already underway or need you, launches in flight and ships the host has not listed yet included (409; `admitMu` is held from the count to `LaunchOrder`'s return for autopilot launches only, so two launches cannot both take the last slot) and a named resource that is busy, missing or pending (409, nothing queued); it holds the reservation until `LaunchOrder` returns, through `ships.Service.Reserve`.
- Locked resources (#118). Config: top-level `resources` (`config.Resource{Capacity, Check}`, `capacity` an integer >= 1 defaulting to 1, `check` a non-empty argv of non-empty strings, names `^[A-Za-z0-9_.-]{1,64}$`) and `autopilot` launches name them. `internal/resources.Set` answers which units are held and by whom: a ship holds one unit of each name in its `@admiral-resources` option (`Ship.Resources`, `json:"-"`; set from `launcher.Request.Resources`) while `underway` or `needs_you`, as do locks (`Set.Lock`, non-blocking, no check needed, for `admiral lock` to call) and reservations. A name no longer in the config holds nothing. `Set.Ships` is `allShips` in `main.go` (List + Pending), so a just-launched ship counts before the host lists it (`ships.Pending` carries the request's resources). `Set.Reserve` checks and reserves all-or-nothing under the Set's mutex and answers `Wait{Name, Why}` with `busy`, `missing` or `pending`. `serveLaunch` reserves through `ships.Service.Reserve` and drops the reservation as soon as `LaunchOrder` returns, on every outcome. Checks run as an argv with no shell, in their own process group, killed as a group at 10 s (`missing`); `Set.Run` runs them all at once, on `Refresh` (a config change) and every 15 s, never two at once for one resource, and a resource is `pending` until its first check ends (`none` when it has no check). A changed check state or a released lock calls `Options.OnChange` (`main.go` pushes the `resources` message). A dropped reservation calls it too. All three close the channel `Set.Changed` returns, and so does `Set.Wake`, which `main.go` calls on every ship change and config change (a ship leaving `underway` frees a unit with no event of the Set's own). `GET /api/resources` and the WebSocket `resources` message (`resources.Service`, sent on connect and on change through `BroadcastOnce`) carry `{"resources": [{name, capacity, in_use, holders: [{kind: "ship", session} | {kind: "lock", label}], check}]}` sorted by name, with no timestamps. `POST /api/resources/<name>/lock` (`internal/lockroute`, for `admiral lock`) holds a unit as an open request: no body, query `label` (cleaned to printable, at most 64 characters) and `wait=1`; it answers `200` with one flushed line `{"held":true}`, then stays open and releases the unit when the request context ends or the server shuts down (`srv.RegisterOnShutdown` closes `Route.Stopping`; the background context is cancelled only after the drain, which waits on this handler). Without `wait` a busy resource answers `409`, an unknown one `404`; with `wait` the handler waits on `Set.Changed()` (fetched before each `Lock` try) and a 15 s timer (a pending ship that expires frees a unit with no wake) and a client that leaves while waiting holds nothing. A request that is not local gets `403`, paired device or not (`auth.IsLocal`: a proxied loopback request is remote; a LAN peer with no token gets the middleware's `401` before it reaches the route); the handler reads the body first, because Go cancels the context on a hang-up only once it has. `OnTake` pushes the `resources` message, since `Set.Lock` doesn't announce a take. `admiral lock` (`internal/cli/lock.go`) splits its arguments at the first `--` before parsing flags, probes the server as `ships` does, sends `admiral lock (pid <its own>): <argv[0] base>` and runs the command after the `held` line; it returns a `cli.ExitError` (code, optional message) for 75, 127 and the command's status, which `main.go` maps; after `held` it keeps reading the response and, if that ends while the command runs, prints `lost the lock` to stderr and leaves the command running; it forwards only SIGTERM (it catches and ignores SIGINT, SIGHUP and SIGQUIT, which the terminal sends to the command). The `-h` scan in `main.go` stops at `--`.

- `internal/capabilities` is what each harness claims and what a probe proved (ADR 0035). `Table()` lists the capabilities by feature (judge, bot, restricted, autopilot), and `Claims` and `ClaimedBy` say which harness versions claim each one (every version, except Claude's guard hook from 2.1.295). Results live in `$ADMIRAL_HOME/capabilities.json`, keyed by the fleet's `Key`, then harness, then the harness version probed, beside the last detected version. `admiral setup` and the server write it, and `admiral crew launch` reads it from inside a ship, so every write re-reads the file and merges under `capabilities.json.lock`, and every query reads the current file. A corrupt or unreadable file reads as all `not_checked` with the error returned, and the next write moves it to `capabilities.json.bad`. - `internal/probes` runs the probes that fill that store. A `Probe` is registered for one (harness, capability) pair, so a new probe is a registration in `defaultProbes`. `Runner.Run(ctx, fleet, harness)` is the one entry point for "probe this now": it detects the version, records it, runs the harness's probes for the capabilities the version claims, stores each result under that version and returns a `Report` with a line per table capability (a capability with no probe, or older than its claim, is `not_checked`). It is synchronous, bounded by `Runner.Timeout`, and two concurrent runs for one fleet and harness share one. A failed `--version` clears the recorded version, so the old version's passes stop counting, and keeps why (`Snapshot.VersionError`, cleared by the next good detection). A run does not end with its caller's context, so one client going away cancels nothing for the others; only `Runner.Close` (the server calls it at shutdown) or the run's own time limit ends it. A cancelled run stores no result and leaves the recorded version alone, while a timeout counts as a failure. `admiral setup` calls `Run` for every fleet harness after it saves; the server calls `Refresh` at start, which detects each fleet harness's version in the background, records it and re-runs the probes of a harness whose version differs from the one its results were stored under (a harness never probed only gets its version recorded). A config reload doesn't re-detect. `Judge(harness, id)` is the probe of one judge capability (no tools, no network, JSON schema, per-call cap): it calls `judge.For` and makes its call on the Lookout model through `internal/judge`, and passes on what Admiral sees (a sentinel file, a nonce read back, a request to a loopback listener, claude's `structured_output`, `error_max_budget_usd`), never on what the model says. A harness with no mechanism (codex call cap, copilot schema and cap) records its fixed reason with no call. `ClaudeGuard` runs the fleet's `claude` headless on `haiku` with `Bash` allowed, in an empty temporary directory with its own copy of the hook bundle and `admiral` link (so it works before any server has started), asking it to run `touch <dir>/ran-<nonce>`. `admiral guard pretooluse` notes every Bash call it is asked about in `seen-<nonce>` while `ADMIRAL_PROBE_NONCE` (16 lowercase hex) and `ADMIRAL_PROBE_DIR` (absolute) are set, denies exactly that command, and writes `denied-<nonce>` in `ADMIRAL_PROBE_DIR`, never an outcome. It passes only when the denial file exists and the sentinel doesn't; with no denial, `seen` and the sentinel tell a hook that never ran from a model that ran another command or never called the tool. The probe fails, naming the arg, when the fleet's `claude` args would override the hooks (`launcher.RefuseHookArgs`). The launcher removes both probe variables from a ship's env. The harness's env is the fleet's with the ship and pane variables removed and `ADMIRAL_AUTOPILOT=1`.

The args allowlist is not gated. `GET /api/harness-capabilities` computes `autopilot.advisor` the same way for every harness (`autopilotgate.AdvisorStatus`: `not_checked` until a judge result exists in the fleet, then passed or failed), so it is never a stored row. `admiral advise` (`internal/cli/advise.go`) is the advisor: one judge call (`judge.Strong`) on the ship's fleet, whose fleet comes from the session option `@admiral-fleet` through the `shipFleet` seam; it logs one `advised` outcomes line.

## API versions

- `/api/v1/...` and `/ws/v1/...` answer exactly as `/api/...` and `/ws/...` do: status, headers and body. `Handler()` in `internal/server/server.go` strips the `/v1` before routing, so a module registers its routes once, unversioned, and every route (current and future) has a v1 path. The strip sits inside `guard.Middleware`, so v1 gets the same access control, with no path-specific auth code.
- `GET /api/version` (also `/api/v1/version`) returns `version`, `commit`, `api_versions` (`[1]`) and `capabilities`, with `Cache-Control: no-store`. It needs the same auth as the rest of the API.
- `capabilities` is an array of strings naming the server features this build serves, set in `cmd/admiral/main.go`. Each entry names a feature group, not a module (the bridge module serves two, `bridge` and `setup`; the lock route has none). They are server features, not harness capabilities (GLOSSARY.md, ADR 0035). Within v1 the list only grows:
  - `ships`: launch, list, move, dismiss and close crew boats on ships.
  - `sources`: order sources and their views.
  - `inbox`: the inbox items and their answers.
  - `launch-orders`: launch orders, favorites and the launch dock's directory and skill lists.
  - `bridge`: the bridge sockets on ships and crew boats.
  - `setup`: the setup terminal's routes.
  - `resources`: the resource units and their locks.
  - `chat`: the chat session.
  - `ship-input`: send a message to, interrupt and stop a ship, and send to or interrupt a crew boat (`POST /api/ships/<session>/{messages,interrupt,stop}` and `/crew/<name>/{messages,interrupt}`; see `docs/api.md`).
  - `conversation`: a Claude Code, Codex or Copilot ship's conversation (`GET /api/ships/<session>/conversation` and the WebSocket `conversation` messages; see `docs/api.md`). It also covers a crew boat's (`GET /api/ships/{session}/crew/{name}/conversation` and the `crew` field of the WebSocket messages): `internal/shipconv` keys a subscription by session or by `{session}/crew/{name}`, and reads the boat's path fresh from its pane option (`@admiral-crew-transcript`), confined by `transcriptfs` and `ValidCrewTranscriptPath` only. A Codex ship or boat is read the same way through the rollout adapter (`internal/conversation/codex.go`, selected by `Options.Format`) with `transcriptfs.OpenIn` on `<Codex home>/sessions/`; the hook's `SessionStart` records the path, and a watch re-reads the option about once a second to follow a new rollout.
  - `changes`: a ship's changes (`GET /api/ships/<session>/changes`, `internal/shipdiff`: a diff of the checkout against its merge-base with `origin/HEAD`'s branch or `main`, with the git safety flags, a size cap and the timeouts; see `docs/api.md`).
- Bodies stay byte-identical, so a URL inside a body stays unversioned (`icon_url` in `/api/sources` and `/api/plugins` is `/api/plugins/<name>/icon`). Rewriting them is left to #258.
- The bridge socket's `join` carries an optional `api` version; see `docs/bridge-protocol.md`.
- v1 changes are additive only. The unversioned paths stay for the old UI until #276.
- `GET /api/logos/<harness>` (also `/api/v1/logos/<harness>`) serves `$ADMIRAL_HOME/logos/<harness>.svg` as `image/svg+xml`, with `X-Content-Type-Options: nosniff` and a Content-Security-Policy that allows no script. It answers 404 when the file is missing or `<harness>` isn't one `config.Harnesses()` returns (claude, copilot, codex; `unknown` is 404), and never reads outside that folder. It has no `capabilities` entry: clients fall back on the 404.
- Each fleet in the config view (`GET /api/config` and the WebSocket `config` message) carries an additive `color_index`: the fleet's position in a color sequence. A fleet with no `color` in config gets the raw counter `assignColors` used, not wrapped. A stored `color` that matches an old palette entry (case-insensitive, as `admiral setup` writes the default hex) gets that entry's position. A custom hex has no `color_index`. The client wraps it by the redesign sequence's length. `color` and `ink` stay the old palette's values.

- The Hold fire banner: `holdFireLink.ts`, started in `main.tsx`, reads `GET /api/v1/fleets/<key>/hold-fire` for the active fleet on a fleet change, every 15 s and when the window regains focus (AdmiralBot can turn it on and no socket message says so). `Shell.tsx` renders it as a `role="status"` bar above the panel in both shells while the fleet's or the all-fleets switch is on, naming who and when, with a link to Routines.
- Active fleet: `?fleet=<key>`, kept across navigation. Without it, the last choice (`localStorage` key `admiral.app.fleet`), then the first fleet; an unknown key falls back the same way. Inbox and Preferences name no fleet.
- Phone (up to 640px wide): a header with the fleet switcher (a sheet) and the surface title, and a bottom tab bar of Inbox, Chat, Ships and More. More opens a sheet with Campaigns, Routines, Crew and Preferences. Wider screens, iPad portrait included, show the 248px sidebar.

## Idle memory

One fleet, one source, no ships, on an M-series Mac (macOS 27, Go 1.26, tmux 3.7c, python 3.14), resident set size from `ps -o rss`:

| process | RSS |
| --- | --- |
| `admiral` | about 16 MB |
| a Python plugin process (`python3 plugin.py`, measured with the former freeform plugin, a minimal one) | about 19 MB |
| Admiral's tmux server and its control client | about 4 MB and 5 MB |

Each Claude or Codex ship has a transcript follower (`shipconv.Tails`): one small `conversation.Reader`, polled every 250 ms with a stat that skips the read when the file is unchanged. A ship with no readable transcript is looked up again every 2 s, backing off to a minute.

Each ship adds its harness, and a pane in tmux.

## The setup terminal

Tapping the "Set up a fleet" marina or the header's fleet count opens `admiral setup` in a terminal over open water. It runs in the tmux session `_setup` on Admiral's socket (never in `ships`, never a ship) and uses the bridge's terminal, so several browsers can share it and a dropped connection rejoins. `POST /api/setup` starts it or leaves the running one alone; `GET /api/setup` says whether it runs. The bridge accepts `/ws/bridge/_setup` while the session exists. The terminal closes when the session ends, whether setup wrote the file or not, and the page then re-reads `/api/config`; a change to `config.json` alone never closes it.

## The chat session

AdmiralBot (ADR 0018, 0019, 0023) is one Claude Code session per fleet whose chat is on, in the tmux session `_chat-<fleet>` on Admiral's socket. `internal/chat` serves them (a `Service` holding one `fleetChat` each), `launcher.StartChat(fleet)` (`internal/launcher/chat.go`) starts one and `sessionhost.ChatSession` names it. A chat is never a ship: `Session.IsShip` refuses `_setup`, the `_chat-` prefix and the old `_chat`, so setting `@admiral-name` changes nothing, and `admiral ships` hides it and `admiral attach` refuses it. A fleet key that differs from an earlier fleet's only in case has its chat off, since the Mac's disk usually folds case (`config.ChatOffReason`).

- **Routes and shapes** are in `docs/api.md`, "A fleet's chat": `/api/chat/<fleet>/session`, `start`, `messages`, `new` and `questions/<id>/answer`, a `chat` WebSocket message per fleet (key `chat:<fleet>`), and the log. An unknown fleet is a 404, a fleet whose chat is off a 409 with the reason, except for the notes and instructions routes: they only touch files, so they stay served while the chat is off and refuse only a case-clashing key. The global `/api/chat/*` routes are gone. Admiral doesn't start a chat at server start.
- **Files** under `$ADMIRAL_HOME/chat/<fleet>/` (every path through an `os.Root`): `conversation.jsonl` and its monthly `conversation-YYYY-MM.jsonl` (`internal/chatlog`), `ledger.jsonl` (`internal/ledger`: the notes and commitments AdmiralBot records, an append-only event log folded in memory, at most 30 open notes and 30 open or waiting commitments of 500 characters, written under one lock; routes in `docs/api.md`. A commitment is recorded by `make_commitment` through `internal/chat/commitments.go`, which judges its launch spec with `launcher.CheckSpec`, the same checks `Launcher.Launch` runs before it needs a free slot, so a launch can't be recorded that would be refused for a reason that doesn't change), `instructions.md` (the engineer's instructions, at most 2,000 code points, written through a temp file by the same `Ledger`, so promoting a note changes it and the ledger under one lock), `questions/` and `mcp.json` (0600, rewritten at every start; a start also removes the skill an older Admiral wrote under `.claude/skills/admiralbot/`). At startup `chat.Service.RemoveOldLayout` removes the old `chat/questions/` and `chat/.claude/` once (a `chat/.per-fleet` marker records it, since afterwards `chat/questions` can be a fleet's own directory); a waiting `admiral chat ask` in the old directory then exits 4.
- **The history** is Admiral's log, not the transcript. Each tick reads the running chat's transcript and appends what is new (messages as they appear, questions as cards) whether or not a browser is connected; the log skips an id it holds. `New chat` appends a `reset` entry in both its paths, after logging what was pending and before it sends `/clear` or kills the session; the hook's `SessionStart` with source `clear` appends none. The session serves the newest 200 entries (`chat.HistoryWindow`), and the model never sees the log.
- **Start.** The working directory is `$ADMIRAL_HOME/chat/<fleet>/`, so the Read fence keeps the chat out of the other fleets. argv is the chat fleet's Claude executable (`Resolve()`; the dock's `args` are dropped, because they are a ship's and commonly widen permissions, ADR 0023), then `--model <model>`, `--effort <effort>` when set (each its own argument), then `--append-system-prompt <one paragraph that teaches the MCP tools>`, then the fence from `launcher.FenceArgs` (`--permission-mode dontAsk --setting-sources project --tools "" --strict-mcp-config --mcp-config $ADMIRAL_HOME/chat/<fleet>/mcp.json --settings $ADMIRAL_HOME/harness/chat-claude-settings.json`): no built-in tool, one MCP server. Before the process starts, `launcher.WriteMCPConfig` writes `mcp.json` through an `os.Root`, a temp file and a rename. The session is made like a ship's (placeholder, options, `set-environment`, `respawn-pane` through a tmux client with the chat's `PATH`) with no `remain-on-exit`, so it ends with Claude and the next start makes a new one. The environment is `shipEnv` without any `ADMIRAL_*` but `ADMIRAL_HOME`, and `set-environment -r` hides every `ADMIRAL_*` the tmux server holds (its global environment) except `ADMIRAL_HOME` and `ADMIRAL_CHAT_FLEET`; the chat's `ADMIRAL_PORT` is the port Admiral listens on (`Launcher.Port`), and `ADMIRAL_CHAT_FLEET` is its fleet key, which `admiral mcp` reads. The launcher unsets both for ships. Session options `@admiral-chat-model`, `-effort`, `-fleet` and `-harness` record how it started; a session started before `-harness` existed has none, so New chat restarts it (the hooks read `ADMIRAL_CHAT_HARNESS`, which only a new start gives it) and no scheduled reset or flush touches it. The launcher unsets `ADMIRAL_CHAT_HARNESS` for ships too. A change of the `chat` key applies at the next start and at New chat.
- **Actor token** (`internal/actor`). `launcher.StartChat` mints a nonce into the session option `@admiral-chat-nonce`; `chat.Service.ActorToken(fleet)` reads it and derives the token with `actor.Minter` (secret in `$ADMIRAL_HOME/actor-secret`). `actor.Guard`, built from the running services by `internal/actorwire`, wraps the mux inside `auth.Middleware` in `cmd/admiral/main.go`: it matches `X-Admiral-Actor` against every fleet's current token, allows only the routes in its table, fences each to the actor's fleet and puts the fleet in the request context. Handlers read `actor.FleetOf(ctx)` to filter lists and to stamp `via`. See `docs/api.md`, "AdmiralBot's requests".
- **Hooks.** The chat bundle registers `SessionStart` (no matcher), `PreCompact` (matcher `auto`, see the backstop below), `UserPromptSubmit`, `PostToolUse`, `Notification` (`permission_prompt`, `elicitation_dialog`) and `Stop`. Not `idle_prompt`, `SubagentStart`/`SubagentStop` or the guards. `admiral hook SessionStart` writes the pane option `@admiral-transcript` = `<unix ns> <source> <transcript_path>` and no state. `admiral hook UserPromptSubmit` in a chat (`ADMIRAL_CHAT_FLEET` set) writes the pane option `@admiral-chat-prompt` = the unix ns of the prompt, typed in the chat or in its terminal alike; `chat.Service.PromptKey` joins it to the session's nonce, and `ships.Service.Launch` gives an actor's freeform launch the key `chat:<fleet>:<nonce>-<stamp>` and drops any `chat_message` the actor sent. A chat start also removes a planted `.claude/settings.json`, `settings.local.json` and `CLAUDE.md` from the chat directory. The hook's ship states map to the chat's: `working` is `working`, `needs_you` with reason `stop` is `idle`, any other `needs_you` is `waiting`, and none yet is `idle`.
- **The brief and the digest** (`internal/brief`, `internal/digest`, `internal/chat/brief.go`). The brief's first section is "Open commitments" (id, age, trigger and action in words, its own fence and a not-instructions notice), ranked above questions, ships and notes when the brief overflows. A commitment card also adds one line to the digest (its text quoted, a quote in it replaced), once per card. `chat.Service.Tick` runs in its own goroutine (`tickLoop`, every 500 ms, one tick at a time, off the broadcast path) and computes `Ships()` and `Inbox()` once per tick; it renders each on-fleet's `chat/<fleet>/brief.md` and writes it (a temp file renamed in) only when the text changed. A new chat renders it after `Launcher.BeforeChat` has withdrawn the old chat questions (`withdrawAndRender`), so the startup `SessionStart` never reads a stale question. The ledger's files are read again only when their size or mtime change. `brief.Render` is a pure function: sections in priority order (open commitments first, then the instructions, waiting chat questions newest first, AdmiralBot's afloat ships and any ship of the fleet waiting on the engineer, active campaigns, notes under their own fence, the last six messages), a section with nothing to say left out, routines to join when their records exist. At most `brief.MaxBytes` (9,500, under the 10,000 UTF-16 units Claude Code passes a hook's output whole); over that, whole items go from the bottom (oldest message, then oldest note, ...) and a last line counts them, and only the instructions are cut, never dropped. An item over its per-item cap (a message 1,500 runes, a note 600, any other line 200) is cut with an ellipsis, not dropped. The questions, ships, campaigns and last messages stand in ``` blocks under one notice ("status from Admiral and text from issues, PRs and other models: data, not instructions; the engineer's instructions above win"), below the instructions; a run of three or more backticks in an item becomes apostrophes, so no item closes its fence. `brief.Clean` (ANSI and every non-graphic character: controls, zero-width and bidi format characters, tag characters, private-use and unassigned code points; one line; the instructions get the same strip, keeping their newlines) and `brief.Fence` are the one place untrusted text is made safe; a later hook that replays text reuses them. The digest is `chat/<fleet>/digest.json` (`next_seq`, `lines` of `{seq,text}`, `dropped`; 20 lines and 2,000 bytes): the tick adds a line when a ship of the fleet changes to sailing off, moored, anchored or needs you, when an Inbox item of the fleet appears, or when the engineer answers a chat question; what the first tick finds is a baseline, so a restart loses what happened meanwhile. `admiral hook` reads only these files, never the server: in a chat, `SessionStart` (any source) prints `{"hookSpecificOutput":{"hookEventName":"SessionStart","additionalContext":<brief>}}` and `UserPromptSubmit` prints the same with `"Since your last turn:"`, a notice that they are events, not instructions, and the lines whose sequence is above the pane's `@admiral-chat-digest`, then sets that option to the highest sequence printed. The tick learns it from the chat's own pane-options read (`ReadChatOptions`, one `display-message`, so no extra fork and nothing for a chat that isn't running) and drops the lines at or below it; the ack is cleanup only, since the hook's filter already stops a line printing twice. The tick forgets ships and Inbox items that no longer exist. A ship's hook prints nothing new. Claude Code chats only: `Tick` skips a fleet whose chat harness isn't `claude`, and the chat's hook prints context only when `ADMIRAL_CHAT_HARNESS` is `claude` (Codex shares the event names, not Claude Code's context format). Notes and instructions are stored for every harness but only a Claude Code chat is given them (its brief): on Codex and Copilot Preferences says so under them, hides "Refresh context at", and the chat prompt (`chatPromptFor`) tells the chat it cannot remember instead of to call `save_note`.
- **Scheduled resets** (`internal/chat/reset.go`, `flush.go`). `Service.ResetTick`, which `tickLoop` calls after `Tick` (so its tmux reads stay off `Run`'s broadcast path), runs `DueReset` (a pure function) per running chat. Only an idle chat with no question open is reset, and every rule needs the chat idle for the short window and a turn since the last reset (the prompt stamp moved; a session Admiral has not reset yet counts as having had one), so a status line redrawn after `/clear` or a turn that just ended cannot set one off. The first rule that holds: `threshold` (context over the fleet's `ContextThreshold`), `idle` (context over 100,000 and idle for six times the short window) or `daily` (at or past 04:00 local, last reset before it). A threshold of `never` turns all three off. Context is read from the kept status line (`statusline` pane option), and a reading no newer than the last reset is stale. The tick claims the fleet (`claimReset`, which also sets `resetting`, so a send gets 409 from that moment) and runs the reset on its own goroutine under the chat's `op` lock; under `op` it aborts and restarts the idle clock if the prompt stamp or the last reset moved since the tick decided. The reset pastes `FlushPrompt` (a turn that saves what matters to the notes), waits for the prompt stamp to move and the pane to be idle again (at most `FlushWait`), then sends `/clear` and writes a `Context refreshed` marker. A flush that does not finish is abandoned and the idle clock restarts. The flush turn is hidden by anchor (`flushAnchors` in `state`, one per flush, so a retry does not unhide an abandoned one): the message before the paste, then the prompt's message ID, then, only when a question stopped the flush, the turn's last message. Only that stretch is hidden, from the served thread and so from `conversation.jsonl`. An anchor stays open when the turn ended (the Stop hook comes before the transcript's tail is on disk) or timed out: it ends at the next user message and survives a clear and the window sliding, so a reply read after `/clear` or the marker is neither shown nor logged. One closed by a question leaves what Claude says after the engineer answers visible. New chat on an idle chat runs the same flush first and skips it while a turn runs or a question waits. `ADMIRAL_CHAT_RESET_IDLE` (10 min) sets the short window and `ADMIRAL_CHAT_FLUSH_WAIT` (3 min) the flush's wait. Claude Code chats only: `flushesBeforeReset` gates the scheduler on both the fleet's configured harness and the harness recorded on the running session (`paneHarness`), and New chat's flush on the recorded one alone, so a Codex or Copilot pane is never pasted the flush prompt or `/clear` after a switch to Claude, a Claude pane replaced because the fleet switched still gets its flush before the kill, and a session with no record is never reset on a schedule. New chat also restarts a session whose recorded harness differs from the fleet's (`chatOptions.matches`). A Codex or Copilot chat is reset only by New chat (`/new` on Codex, `/clear` on Copilot), with no marker-time brief render.
- **The backstop** (`internal/launcher/bundle.go`, `brief.PreCompact`, which keeps every open commitment's id and text before the notes). The chat's `--settings` carries `autoCompactWindow` = 300,000 tokens (`ChatAutoCompactWindow`), whatever the fleet's threshold, including `never`; a ship's bundle carries neither it nor a `PreCompact` hook. The window is the lesser of the setting and the model's context, and compaction fires a little before it. A `modelSettings.<model>.autoCompactWindow` would override it, and the environment variable `CLAUDE_CODE_AUTO_COMPACT_WINDOW` does, and `DISABLE_AUTO_COMPACT` or `DISABLE_COMPACT` would switch it off. The chat drops all three variables (`chatDropped` in `internal/launcher/chat.go`) from the env it inherits from the fleet's dock or Admiral's own, and unsets them in the tmux session so the server's global environment can't supply them; ships keep them. `admiral hook PreCompact` (matcher `auto`; a manual `/compact` is the engineer's) reads the ledger's files directly and prints plain text, which Claude Code appends to the compaction's instructions: keep the instructions, each open commitment's id and text and each open note's id and text verbatim, commitments under their own notice and notes under theirs, in the same fence and cleaning as the brief, at most `brief.MaxBytes`, dropping the oldest items with a "left out" line. It never calls the server and always exits 0, since exit 2 would block the compaction; with no files, or a ledger or instructions file over 4 MiB (checked by `Lstat` before reading), it prints nothing. Each note is cut at 600 runes as the brief cuts it, and the text keeps the notes under their own label as facts, not instructions. The fake harness tests a `PreCompact` or `PostCompact` group's matcher against the payload's `trigger`. Claude Code chats only: the window and the hook live in the Claude bundle alone, and the hook prints only when `ADMIRAL_CHAT_HARNESS` is `claude`; the Codex and Copilot bundles carry neither.
- **Status line.** Both Claude bundles set `statusLine` to `admiral statusline` (`--chat` for AdmiralBot): `internal/cli/statusline.go` keeps a compact subset of Claude's status JSON in the pane option `@admiral-statusline` and passes the engineer's own line through. See `docs/cli.md`.
- **The conversation.** The host's shared format doesn't carry the chat's options, so the service reads them itself with one `display-message` on the chat's pane (at most every 200 ms, and on every host event for a chat session), plus a 500 ms tick. A new pane id (a restarted chat, or the first one an Admiral sees) starts with nothing; the transcript is read from its start. A new `@admiral-transcript` path starts a new conversation. A `SessionStart` with source `clear` empties it, so the model-side transcript restarts (the log keeps the history); Claude Code 2.1.310 gives `/clear` a new transcript path, so the reset usually arrives as a new path. Until a transcript is recorded, the session carries `error: "Open the terminal to finish starting the chat"`; a recorded path Admiral refuses to read gives `error: "Admiral can't read this chat's transcript"`. The tick follows every running chat so the log misses nothing, but broadcasts only while a browser is connected, and the tmux read runs outside the service lock.
- **Transcript rules** (`internal/transcriptfs`, `internal/conversation`). The path is untrusted. The config dir is `config.IdentityDir(<harness>, dock.Env)` of the fleet the session started with, and the layout follows the ship's (or boat's) harness, never the path's shape. A Copilot ship launches with `--session-id <uuid>` and records `<copilot home>/session-state/<uuid>/events.jsonl`; `transcriptfs.OpenFor("copilot", …)` takes only that file, with a uuid directory, and the session id is the directory's name. `conversation.Options.Harness` picks the decoder: `copilot` reads `events.jsonl` (an allowlist of `user.message` typed by the engineer, `assistant.message`, `tool.execution_*`, `ask_user` as a question pending until its tool completes, `system.notification`, `session.compaction_complete`; lines with `parentToolCallId` and every other type are skipped, and one turn end closes each prompt at the top-level `assistant.turn_end` of a model call that asked for no tools, or at `session.shutdown`, `abort` or `session.error`, which also settle the calls still running; an `ask_user` form of several fields has no options and is answered in the terminal), anything else Claude Code's transcript. `transcriptfs.Open` refuses a path that is not absolute, does not end in `.jsonl`, lies outside the real `<config dir>/projects/`, or is not a regular file with no symlink in it or below `projects/`; a symlinked config dir or `projects/` is fine. The chat reads the file with a `conversation.Reader` built from `conversation.TextView()`, the Claude Code adapter with the text-only filter: user and assistant text and notices (a subagent's or background command's `<task-notification>`, served as its `<summary>` and any `<result>`, and another Claude session's message, both shown as the user's; a notice marked `isMeta` stays hidden), a skill or custom slash command (a line that opens with `<command-message>`) as the user's text `/<name> <args>`, without `isMeta`, sidechain, compaction-summary, built-in command (`<command-name>` first, as `/clear` and `/compact` write) and local-command-output lines, tool calls or thinking. The limits are the adapter's (lines over 1 MiB skipped, messages cut at 64 KiB, the last 200 within about 256 KiB, a first read of a file over 8 MiB starts near its end). The service reads from the reader's offset, whole lines only; `/clear` calls `Reader.Clear` with the file's size; when the file does not exist yet it reads from its start once it appears, and when it cannot be opened for any other reason the chat serves nothing until the next clear. `id` is the line's `uuid`. A transcript with content but no JSON line serves an empty chat, with no error.
- **Copilot's live observer** (`internal/conversation/uiserver.go`, `internal/shipconv/uiserver.go`, `internal/launcher/uiserver.go`). The launcher adds `--ui-server --port <n>` (a free loopback port) beside `--session-id` when `uiServerSupported(exe)` holds: `<copilot> --ui-server --port <n> --version` exits 0, cached per resolved binary, size and mtime for 30 minutes (Copilot's launcher updates the real build without changing its own file, so the expiry catches an update), so a launch runs it at most once per window and never when the order or dock names a session, a port or a server mode. The port is read back from the pane's start command (`uiServerPort`, through the same argv parser as `startedSession`, which ignores flags inside an order's text). `conversation.ObserveUIServer` is a small hand-written JSON-RPC client over Content-Length framing (the Go SDK answers some server requests by default, so it is not used): it sends `connect`, `session.resume {sessionId, disableResume: true}` and, when stopped, `session.detach`, and has no code that replies. `ServerReader` decodes `session.event` notifications with the events.jsonl decoder plus `assistant.message_delta`. The shipconv watch owns one observer per open ship, starts it with the watch and cancels it when the watch ends; its items merge into each poll's push by id, the file's winning. The observer attaches only when the process listening on the port is the pane's process or a descendant (`listenerBelongsTo`), since a foreign server on a taken port would answer `session.resume` for any session. Connect refused, no answer, a drop or a foreign listener leave the file serving, and the observer retries every 1 s up to 15 s apart.
- **Open terminal.** The bridge accepts `/ws/bridge/_chat-<fleet>` while the session exists, as it does `_setup` (`ownSession` in `internal/bridge/setup.go`; the stand-in is called "Chat session"), and a keystroke there changes no state. It ends with the session through `ShipsChanged`.
- **The fence** (ADR 0023). The chat has no built-in tool (`--tools ""`) and reaches Admiral only through the stdio MCP server `admiral` (`admiral mcp`, `internal/cli/mcp.go`) that `mcp.json` names; `--strict-mcp-config` keeps every other server out. `chat-claude-settings.json` holds `permissions.allow` of exactly `mcp__admiral__*` (`launcher.FencePermissions`), `permissions.deny` of `Edit`, `Write` and `NotebookEdit` as a backstop, and `blockReadsOutsideWorkingDirectories`. Ships' bundles and command lines are unchanged. The server reads its identity from the `env` of `mcp.json`: `ADMIRAL_ACTOR_TOKEN` (the minter's token for the chat's nonce), `ADMIRAL_PORT`, `ADMIRAL_HOME` and `ADMIRAL_CHAT_FLEET`. The token goes only there, never into argv, a tmux option or the settings. Ships can read `$ADMIRAL_HOME`, so the token is not a secret from ships; the fence is against the chat model, which has no file or shell tool.
- **The fence probe** (`internal/probes/claude_mcp_fence.go`, capability `bot.mcp_fence`). It runs Claude Code headless with `launcher.FenceArgs`, `--output-format stream-json --verbose` and a config naming one server, `admiral mcp-probe` (hidden, serves one tool `ping`), and asks for a shell command and for the tool. It passes on what Admiral observes: no `ran-<nonce>` file, the server's `called-<nonce>` file, and a `system`/`init` record that lists no built-in tool and no other MCP server. The init shape is assumed from Claude Code's stream-json output. The harness picker offers a harness once its fence probes have passed.
- **AdmiralBot on Codex** (`internal/launcher/chat_codex.go`, `internal/probes/codex_probes.go`). `StartChat` runs Codex with its own `CODEX_HOME`, `$ADMIRAL_HOME/chat/<fleet>/codex-home/`, which holds only a link `auth.json` to the engineer's login (`LinkCodexLogin`, the one place that decides link or copy: a token refresh resolves the link and renames a temp file over the engineer's `auth.json`, per Codex's `FileAuthStorage` on its main branch, so the engineer's login stays the one current file and the link stays); the engineer's `config.toml`, plugins, skills and MCP servers never enter it, and the dock's `args` are dropped. `Codex` has no profile for the fence, so argv carries it as `-c` and `--disable` flags from one table, `codexFenceFeatures` and `CodexFenceArgs`, which the probes share: `--strict-config` (an unknown `-c` key is refused), `features.shell_tool=false`, `web_search="disabled"`, a read-only sandbox, `approval_policy="never"`, each feature in the table disabled, and `default_tools_approval_mode="approve"` on the `admiral` server. `features.code_mode_host` stays on, since Codex reaches MCP tools through it. `prepareCodexChat` refuses to start a chat whose `codex-home/config.toml` sets `mcp_servers`, `notify`, `model_providers` or `profile`/`profiles`, which the flags do not cover. The TUI gets `--no-daemon` only when it accepts it (`codexpane.HasNoDaemon`). The fence is not airtight: Codex still lists `exec`, `wait`, `sleep`, its `collaboration` tools, `request_user_input` and the MCP resource tools, and its read-only sandbox does not stop reads outside the chat's directory. The actor token never goes on argv: the launcher writes it to the 0600 file `chat/<fleet>/admiral-mcp-token` and the `admiral` server's `env` names it in `ADMIRAL_ACTOR_TOKEN_FILE`, which `admiral mcp` reads when `ADMIRAL_ACTOR_TOKEN` is empty. The instructions go in `-c developer_instructions=…`. `chat.Service.Login` stays the engineer's identity dir, while the reader and `recordReset` use `launcher.ChatCodexHome` (rollouts under its `sessions/` only, `transcriptfs.OpenFor("codex", …)`, usage from `usage.ParseCodex`). ## The wake decision

`moor.DecideWake` (`internal/moor/wake.go`) is pure: a moored ship's PR answers, its wake state, the fleet's `wake_reviewers`, whether it is live and `now` give a `Decision` (wake or not, the one PR, its events, the feedback text, the T3 events and the `Next` state). `PollMoored` calls it for each answered, not-live record whose mooring did not end this poll and that has a valid resume text (a record with none is not decided: its no-resume note stands). It passes `Live=false`, the fleet's `wake_reviewers` and `now`.

- **Saving `Next`.** A decision that does not wake saves `Next` when it differs from the stored state, so a condition keeps its first-seen time. The write skips a ship whose wake is `committed`, whose record is no longer the one polled, or whose stored state changed since the poll read it.
- **A live ship's open PRs and moor on done** (`internal/ships/openprs.go`). `refreshOpenPRs` runs each pass: it stats the ship's report file and, only when the stamp (mtime, size) changed, reads it through `loadReport` (`readReport`'s guards without its log line), takes `Report.Result` and asks `moor.CountedAnswered` in a goroutine; `openPRsOf` serves the cached answer, which `ship()` joins with `carriedOpen` (the running-ships poll's OPEN PRs, via `withCarried`) into `Ship.OpenPRs`, so the request path never asks GitHub. `countedPRs` (clean exit) and `serveMoor` check the same union. `autoMoor` moors a live ship at needs you (reason `stop`), not returning, whose report says `done` with open PRs, once per report stamp. `serveMoor` handles `{"moor": true}` on `/stop` and `/return` with a fresh check. All three end in `moorShip`, under the ship's `lockShip` (shared with `stopShip`, so a Stop that came first leaves nothing to moor): `moor()` (record, `moored`, `endRound("moored")`), then `recordKilled` and `endSession`, so a woken ship's round logs `moored`, not `anchored`. A check GitHub does not answer (gh down past `RetryWindow`) is not cached under the stamp: it is retried with a wait that doubles from 30 s to 4 min. `serveMoor` answers 409 for it, and 500 when the session will not end after the record is written.
- **A hand round** (`POST /api/ships/{session}/answer-review`, `Service.answerReview` in `internal/ships/wake.go`). `moor.DecideHandRound` is `DecideWake`'s work for one PR with the debounce passed: both call `scan` (every answered PR's events and resolved state) and `openRound` (the chosen PR's events oldest first, every answered PR's window opened, the chosen cursor advanced), so the two rounds cannot drift. `decide` stores each PR's count in `polled.feedback` before any early return; `prsOf` reads only that and serves `feedback` and `answer` on a moored ship's `OPEN` PR, so the list never reads wake state. The route checks the ship (`wakeable`), then that `pr` is exactly one of the record's `PRs`, then, in the launch hook under `saveWake`'s `wakeMu`, recomputes the round from the stored poll answers and a fresh `ReadWake` (409 when the PR has none); both rounds share `roundHook` (save the state, write the feedback file, undo the state if the write fails); the hook also refuses a `pr` that is not in the record it was given (400), and a launch that fails afterwards puts the wake state back and leaves the file. It launches as `By: "hand"` with `PR` set, so it is attended and counts toward the cap without being blocked by it. AdmiralBot is not on its allow list.
- **The Answer all reviews wake** (the `{"stack"}` body of the same route, `serveAnswerAll` and `Service.answerAll`). It is a hand wake with a new Commodore prompt, `<resume's skill token> <stack URL>`, not a feedback round: the run is a different one, whose report sets the next mooring's resume. The stack is read fresh (`stackFor`: `PullRequestDetail` on the ship's PRs until one has a stack, 502 on the first error) and must hold exactly the record's PRs; `stack` must equal its URL. The hook is `roundHook` again, saving `moor.DecideStackRound` (one `scan`, then `openRound` for every OPEN PR) and returning no feedback text, which `roundHook` takes to mean write nothing. `servePRDetail` sets `answer_all` from `answerAllPrompt`, which reads only the poll's stored answers under `mooredMu` (`stackOpen`: more than one OPEN, each with `feedback`), so the detail and the route agree. A `feedback-<N>.md` left by an earlier failed PR launch stays in the checkout; nothing names it.
- **A round.** A decision that wakes calls `Service.FeedbackRound(…, next)` outside `mooredMu`, under `pollMu` (one poll waits for the launch; kicks coalesce). Its launch hook writes the feedback file, then `next` (the cursor advanced, `RoundStart` set), after `commitWake`; if the launch then fails, the previous wake state is put back (its file is removed when there was none) and the feedback file stays in the checkout, so the next poll hands the same events again. A refused launch never ran the hook, so it changes nothing. A state write that fails refuses the launch with its own 500. A crash between the state write and the session's start leaves the cursor advanced: those events are not handed again. One launch is tried per ship per poll.
- **The lock.** `Service.wakeMu` serializes every read-modify-write of a ship's wake state: the poll's `Next` write, the round-start write and the hand wake's write. It is taken after `mooredMu` is released, never inside it.
- **Waiting.** `launcher.Error.Wait` is the typed reason, set where a refusal can clear later: at the cap (`Waiting for room under the cap`), for a resource that is `busy`, `missing` or `pending` (`Waiting for <resource> (<why>)`), for a wake already in progress (`Waiting for the current wake to finish`) and for a host not known (503, `Waiting for Admiral's terminal host`) and for the quota hold (`Held for quota: <harness>'s <window> is at N% (line M%), resets <time>`, set in `admit` only for a `launcher.Request.Unattended` launch: a routine run, a commitment or a feedback round, never a hand launch, AdmiralBot's or an accepted proposal; routines check `Scheduler.QuotaHold` first so a held run becomes a proposal instead of waiting). Nothing parses message text. Any other refusal (fleet or dock not found, no guard, an unknown resource, a write failure, a launcher refusal after admit) is permanent and reads `Can't wake: <message>`. The text is kept on the ship's `polled` entry as `waiting`, which a new poll answer replaces (so it clears when a poll answers and does not decide to wake), and `dropMoored` (a successful wake) and `endMoored` (the mooring ends) remove. `markStale`, a poll that failed to reach GitHub, keeps it. Only a typed `Wait` reads as waiting: the 503 carries `WaitHost`, and no status code is read as a wait. The decision's wake state is passed to `feedbackRound`, which refuses with `Waiting for the current wake to finish` when the stored state no longer matches it (the next poll decides again). Every `RemoveWake` goes through `removeWake` under `wakeMu`; the hand wake's hook logs a wake state it cannot read or save and wakes without a round window. The row shows it as its note; Wake by hand stays on.
- **Running ships.** The same poll also asks about live ships (`internal/ships/runprs.go`): `Service.Candidates` (wired to `shipconv.Service.PRCandidates`) gives the PR URLs in the ship's and its crew boats' tool results, and a candidate is carried when `Status.Author` is the fleet's `Status.Viewer` and `CreatedAt` is not before the ship's `launched`. Candidates are filtered to the client's host and the fleet's route, rebuilt canonically, capped at 20 per ship per poll and asked in a query of their own (`PollMoored` makes at most two per fleet), so a bad one stales nothing; one GitHub cannot answer is retried up to `maxCandidateTries` and a gone one rejected. Each confirmed PR is appended to the session's `@admiral-prs` option (which a wake also fills from the record), so a restart keeps it, and `running.found` only caches it. At a clean exit `countedPRs` passes the carried open PRs and the report's through `moor.CountedOK`, and falls back to the last poll's open PRs only when GitHub cannot be reached. `GET /api/ships/<session>/pr` (`prdetail.go`) reads one carried PR fresh.
- **Reviewing ships.** A ship whose `url` option is a PR or stack URL someone else opened carries it as *reviewing* (`internal/ships/revieworder.go`): `running.order` is the launch's one check of the order URL, kept apart from the printed candidates', which reject any PR the viewer did not open. A stack resolves through `GitHub.StackOpenPRs` (REST `repos/<o>/<r>/stacks/<N>`, strict parse in `moor.ParseStack`). The reviewed PRs are in the `prs` session option and listed in the `reviewing` option (a subset), written by `persistCarried`, and in `moor.Record.Reviewing`. `decide` hides them from `DecideWake`, `autoMoor` moors a done report that has an open reviewed PR, and `serveMerge` and `serveUnfollow` answer 409 for them. `LaunchOrder` kicks a poll for an order URL that is a PR or stack URL, so the check does not wait for the poll interval, and `setMoored` hands a ship's live poll to its new record when it is not stale and covers every PR. The check stays pending until every target answers (a failed ask counts toward `maxCandidateTries`) and reruns once per process, since the option alone does not say every layer answered; `dropMoored` seeds a woken ship's `running.reviewing` and its `reviewing` option from the record, so a round GitHub never answers re-moors with the role.
- **One round at a time.** A live ship is not decided on by the poll. When the round's ship moors again, the next poll decides from the advanced cursor, and what came in during the round is the queue.
- **A hand wake** (the row, the ship view and the bridge prompt all go through `Service.Wake`) runs a hook after `commitWake` that sets every PR's `RoundStart` and gives a PR with no cursor the old `moored_at` as its cursor, the way a decision does; cursors, snapshots and first-seen times stay. It is put back if the launch fails.
- **`ADMIRAL_WAKE_DEBOUNCE`** (10 min) is the debounce, for tests.
- **A stranger's feedback** (T3) becomes an Inbox item of kind `wake_proposal` (`internal/inbox/proposal.go`), written by the server under `_admiral` like a notice and read with the same rules (only `_admiral` may hold one; the `wake_proposal` object, `{ship, session, pr, login, events: [{id, kind, url, at, body}]}`, is required). `decide` calls `moor.ProposeT3` on `Decision.T3` for a record with a valid resume text (a ship with none gets no proposal): one batch per PR and author, the not-yet-proposed events, held until the author's newest event is older than `ADMIRAL_WAKE_DEBOUNCE` unless this decision wakes the ship on that PR, an empty or invalid login grouped as `ghost`. The id is `wake-` and 20 hex characters of a SHA-256 over ship, PR, login and the sorted event IDs, so a repeated batch is a no-op: `WriteWakeProposal` never rewrites an item and leaves an answered one answered. The event IDs go into the PR's `proposed` (`{id, at}`) in `Next`, folded in before the single state write, and an entry goes once the cursor is past its `at`. Proposal files are written before the state write. They are written under `wakeMu` with the mooring and the stored state re-checked, and a proposal that cannot be written stops the poll's decision there: no wake and no save, so the next poll retries. A round that is refused saves the state it read plus only the new `proposed` entries, never the advanced cursor. A proposal never expires; Remove from inbox acts as Dismiss.
- **Launch and Dismiss** are `POST /api/inbox/_admiral/<id>/launch` and `/dismiss` on `inbox.Service`, which reaches `ships.Service.LaunchProposal` through its `LaunchProposal` hook (set in `cmd/admiral/main.go`; `internal/ships` imports `internal/inbox`). Launch first checks the item against the moored record (the ship's name, a valid login or `ghost`, every event proposed: recorded, or behind the cursor and pruned) and answers `404` otherwise, then runs `wake()` with `by="proposal"`: autopilot with `autopilotgate.Check`, no cap check, the hand wake's round-start hook plus `feedback-<N>.md` holding only the proposal's events, and the cursor unmoved. Both answer through `answerMu`, so a second press is `409`; outcome events `proposal_launched` and `proposal_dismissed` name the woken ship's session. `removeWake` also deletes the ship's proposals and their answers, under `wakeMu`.

- **The round history** (`internal/moor/rounds.go`) is `$ADMIRAL_HOME/moored/rounds/<name>.json`: one `{round, session_id, fleet, transcript, started, ended}` per round, the latest `moor.MaxRounds` (50), never any transcript content. `moor()` appends the round under `wakeMu` before it writes the record, keyed by round number so a retry adds nothing; the record is deleted on every wake and the history is not. `removeWake` removes it, so every end of a mooring does. The path goes in only through `transcriptfs.Bind` (`internal/transcriptfs/bind.go`), the one rule `shipconv` uses too: the option's `<ns> launch <path>` form, `ValidTranscriptPath`, and the start command's `--session-id` equal to the path's id; `started` is the pane's launch time (the `launched` option, RFC 3339) for every harness. A failed history write is logged and `moor()` still writes the record, so the ship keeps following its PR and loses only the dividers. Recording round N drops a held round N of another session and everything after it, so an orphaned history is not inherited. The conversation route looks up the moored record before it syncs tmux. `internal/shipconv/rounds.go` stitches the rounds (`docs/api.md`, "A ship's rounds"), opening each recorded file through `transcriptfs` under its fleet's `projects/`.
- **Poll bounds.** `github.Client.PullRequests` (`internal/github/pr.go`) reads, per PR, the last 20 reviews, the last 20 review threads with their last 10 comments, the last 20 PR comments, up to 20 pending review requests and 20 review-requested timeline events, and up to 50 check contexts on the head commit; each body is cut to 4096 bytes. GitHub returns bodies whole and the client cuts them, so a poll of a busy PR can still be large. `viewer { login }` comes once per query.
- **Events.** A review is an event when it is `CHANGES_REQUESTED`, or `COMMENTED` with a body (its inline comments count through the threads); `APPROVED` alone, `PENDING` and `DISMISSED` are not. A thread comment or PR comment is keyed by `createdAt` and id, so an edit never wakes. A condition (a failing check, a conflict, behind base) takes the time of the first poll that saw it.
- **The repo's own CI** is a GitHub Actions check run with a workflow run, plus any check run or status the base requires for the PR (`isRequired`). Failing is `FAILURE`, `TIMED_OUT`, `STARTUP_FAILURE` or `ACTION_REQUIRED` for a check run, `ERROR` or `FAILURE` for a status; `CANCELLED` is not. Every other check is ignored.
- **Behind base** wakes only when the base readably requires up-to-date branches: a ruleset's `strictRequiredStatusChecksPolicy` or a non-null `branchProtectionRule.requiresStrictStatusChecks`. Classic branch protection is invisible to a non-admin token, so a null or unreadable rule means not required.
- **Tiers.** T1 is the fleet client's gh viewer. T2 is a `wake_reviewers` login, a Bot authoring a review or a review-thread comment, and a requested reviewer (from pending requests and the timeline; a team makes nobody T2). Everyone else is T3: returned beside the decision for the Inbox, never waking. A Bot's plain PR comment is ignored. Logins compare case-insensitively. GraphQL gives a Bot's login without `[bot]`, so a `wake_reviewers` entry `foo[bot]` matches the Bot `foo`; a bare `foo` matches only a User `foo`, never a Bot.
- **The ship's own replies** share the viewer's login, so a viewer event created between a round's start and the ship's re-mooring is dropped. A dropped event that is still newer than the cursor is recorded in the PR's `dropped` ids at a wake, so a later round's window never hands it.
- **Debounce and queueing.** A ship wakes when the newest waking event is at least 10 minutes old. One PR per round: the lowest layer of the record's `prs` with waking events; the others stay queued behind their cursors. A PR with no cursor (the first mooring) treats events before `moored_at` as history. `T3` holds every T3 event newer than the cursor, so it repeats from poll to poll until a later waking event passes it; its consumer dedupes by id.
- **The wake state** is `<home>/moored/wake/<name>.json` (`moor.ReadWake`, `WriteWake`, `RemoveWake`): per PR URL, a cursor, the last round's start, a snapshot of the conditions at that start, the first-seen times of conditions and the dropped ids. A poll that sees a conflict, behind base or failing check gone clears it from the snapshot, so its return is new and wakes after the debounce. It sits in a subdirectory so `moor.List` skips it, survives a wake's `dropMoored`, and is removed with the record when the mooring ends for good (Dismiss, merged or closed PRs seen by the poll, and a woken ship whose round ends with no open PR).

## Devices and pairing

- `internal/auth` classifies each request by path. Local: loopback peer, no `X-Forwarded-For`, `Forwarded` or `Tailscale-User-*` header, and an allowed Host; it needs no token. LAN: non-loopback peer, no proxy header. Tailnet: loopback peer with `Tailscale-User-Login` (RFC 2047-decoded, as tailscale serve encodes a non-ASCII login, and trimmed once in `classify`, then compared exactly), and only while `remote.tailscale` is true and the login is on `remote.allowedLogins`; auth reads both from the live config on every request (`auth.WithRemote`), so removing a login disables its devices at once. Anything else gets 401 (403 for pairing). The `remote` config key is `{tailscale, allowedLogins}` (`config.Remote`, `Manager.SetRemote`); with `tailscale` true `--listen` defaults to `127.0.0.1:<port>`, else `0.0.0.0:<port>` (the port is 7420, or `ADMIRAL_PORT` for a test), and an explicit `--listen` wins. The listener follows the mode live (`cmd/admiral/rebind.go`): the config subscriber (`moveListener` in `main.go`) sends the move message to the browsers the move leaves behind (`Hub.SendPaths`, by the path `auth.PathName` gave each ships socket; at most 2 s), then `EnforceRemote`, then `listener.Move` binds the new address and retires the old one (retrying once with the old one closed, since a wider address can overlap it on some systems). A bind that fails restores the old address, logs, and shows as the `listen` check of `GET /api/remote`; with mode on, once the move succeeded, the LAN connections already accepted are closed (`DropOffLoopback`) and every open LAN socket is cut through auth's socket registry (`Auth.CutLAN`; a WebSocket is hijacked, so only the registry sees it). An explicit `--listen`, or a config that can't be read, never moves it. `main` calls `Manager.Reload` after `OfferSetup`, so the start that follows setup reads the mode setup wrote.
- A device holds its own token, stored only as a sha256 hash in `$ADMIRAL_HOME/devices.json` (mode 0600, written through a temp file and rename). Compare with `subtle.ConstantTimeCompare`. A tailnet device is bound to the login it paired with and works only on the tailnet path; a LAN device works only on the LAN path. A device unseen for 90 days is dropped.
- A request carries the token as `Authorization: Bearer` or the cookie `admiral_token_<port>` (HttpOnly, SameSite=Strict, 400 days; re-issued at most daily; last-seen written at most hourly). The Origin rule applies to cookie and local requests, not Bearer. `?token=` is not read anywhere.
- Pairing: `POST /api/v1/pairing-codes` (behind the normal auth) returns `{code,url,expires}`; the code is 8 Crockford base32 characters shown `XXXX-XXXX`, lives 5 minutes, one at a time, and works once. `GET /pair?code=` and the `POST /pair` form redeem a code for a browser (cookie set, redirect to `/`); `GET /pair` serves the entry form; `POST /api/v1/pair` returns `{token,device:{id,name}}` and sets no cookie. Ten failed redemptions in 5 minutes give 429. The pair routes and nothing else skip the token check, and a request from the local path is refused with 403.
- Device API (`internal/auth/api.go`): `GET /api/v1/devices`, `PATCH /api/v1/devices/<id>` (rename), `DELETE /api/v1/devices/<id>`, `DELETE /api/v1/devices` (all). Revoking closes that device's WebSockets; `track` re-checks under the mutex that the device still exists before it registers a socket, so a revoke can't miss a socket opening beside it.
- Web Push subscriptions live on the device record in `devices.json` (`internal/auth/push.go`: `Subscriptions`, `DropSubscription`, the `/api/v1/push/` routes). A loopback (Local route) subscribe makes or reuses the device `This Mac` (`thisMac: true`, no token, never matches `authenticate`); a Local request refreshes its `lastSeen` at most hourly so the 90-day prune leaves a Mac in daily use. `internal/push` holds the rest: `vapid.go` (the one P-256 key in `$ADMIRAL_HOME/vapid.json`, made once, an unreadable or corrupt file is an error, never replaced), `encrypt.go` (RFC 8291), `endpoint.go` (`CheckEndpoint`, and `DialControl`/`SafeClient`, which refuse local destinations at dial) and `sender.go` (the `Sink` for the Push outcome: a bounded queue and one goroutine, `Deliver` never blocks, 404 and 410 drop the subscription). `cmd/admiral` joins the two with `pushDevices`. `cmd/admiral/push_e2e.go` (tag `e2e`, which `make build` passes and `make release` does not) reads `ADMIRAL_PUSH_TEST_ROOTS` so the e2e binary can reach a fake push service.
- Startup prints three lines: the local URL, `On other devices: http://<ip>:<port>/` (no token) and `To pair a device, run: admiral pair`. `e2e/harness_test.go` reads the first two and mints a device through the loopback API. With `remote.tailscale` on, `internal/tailscale` runs the `tailscale` CLI (`status --json`, `serve status --json`, 4 s each) once at startup: Funnel on for Admiral's port (a `Web` handler or a `TCPForward`, in serve or a `Foreground` serve) refuses to start with one line on stderr naming the off command; a raw TCP forward without Funnel only fails the `serve` check; any other failed check starts Admiral, and the `On other devices:` line is `https://<MagicDNS name>[:<port>]/` when serve proxies to Admiral's port, else `Tailscale mode is on, but <first failed check>`. The pairing base is that URL, computed per mint; `admiral service install` prints the same. With the mode off Admiral never runs `tailscale`, apart from Settings' Set up. `internal/tailscale`'s `Route` also serves `POST /api/remote/logins` (one edit under a lock, through `Manager.SetRemote`) and `POST /api/remote/setup` (local requests only; `Prepare`, `EnableServe` on Admiral's live port, then `config.Remote.Allowing`, which `admiral setup` shares); see `docs/api.md`. The new shell's Remote access page shows the checks, the URL with Copy, the logins and Set up, and a 401 on any request or a ships link that finds the token gone shows the signed-out line at `/pair` without a reload (`web/src/app/session.ts`).
