# Codebase

This file holds the package map, API routes and ship statuses, idle memory figures, the setup terminal and the chat session. Read it before changing the server, the launcher, ships, the setup terminal or the chat session.

## Layout

- `designs/`: the clickable prototype, screenshots, design tokens, SVG assets and source design files. Start with `designs/README.md`.
- [Admiral MVP spec](https://github.com/jbuffin/admiral/issues/45): what the MVP does, as user stories, implementation decisions and testing decisions.
- `docs/architecture.md`: an early proposal for the build, superseded by the spec and the ADRs.
- `docs/adr/`: decisions.
- `GLOSSARY.md`: the words Admiral uses.
- `cmd/admiral/`, `internal/`: the Go server and CLI. `internal/auth` is access control, `internal/server` is HTTP and WebSocket, `internal/home` finds `$ADMIRAL_HOME`, `internal/config` loads, validates, watches and writes `$ADMIRAL_HOME/config.json`; it also reads the autopilot keys (see "Autopilot config" below). `internal/sessionhost` is the one tmux control-mode connection on `$ADMIRAL_HOME/tmux.sock` (it re-reads the sessions about every half second, and a global `alert-bell` hook stamps bells), `internal/launcher` creates ships (names, hook bundle in `$ADMIRAL_HOME/harness/`, command lines), `internal/chat` is the AdmiralBot chat session (see "The chat session" below), `internal/state` is `$ADMIRAL_HOME/state.json` (ship positions, each dock's last directory, the autopilot panels paused, the kept inbox records, the resume orders), `internal/ships` serves `GET`/`POST /api/ships`, `PUT /api/ships/<session>/position`, `POST /api/ships/<session>/input-seen` (a browser sent input: clears needs you), `POST /api/ships/<session>/dismiss` (ends an anchored ship), `POST /api/ships/<session>/crew/<name>/close` (kills one crew boat's window, live or anchored, like `admiral crew close`; 404 `ship <session> not found` or `crew boat <name> not found`, the latter too when the window closed between the poll and the kill) and the WebSocket `ships` message. A ship carries `reason` (the validated code, `idle` for a ship no hook has spoken for) and `stop_since` (RFC 3339; the open stop's start from the log's track) only while its `status` is `needs_you`. A ship's `status` is `underway`, `needs_you`, `anchored` (with `exit_code` or `exit_signal`) or `sailing_off` (exit 0, session killed after 3 s); hooks, a Codex bell and the 10 s no-hook rule decide needs you (every hook runs `admiral hook <event>`, internal and unlisted in the usage text, which reads the harness's JSON on stdin and sets `@admiral-state` on `$TMUX_PANE`; it always exits 0. With `needs_you` it also sets `@admiral-reason` in the same tmux call, a code and never payload text: `permission:<tool>`, `question`, `notification:<type>`, `stop`, or `bell` from a Codex bell; `working` unsets it, and `sessionhost` polls it into `Session.Reason`. A tool name or type is kept only if it matches `^[A-Za-z0-9_.:-]{1,64}$`, and a notification's reason is written only if none is set, so `permission:Bash` survives either order of Claude's two events. `internal/cli/hook.go` holds the event→state and event→reason rules, and Claude's `Stop` writes nothing while `background_tasks` has a running `subagent` or `teammate`, so a running `shell` task doesn't hold a ship back. `admiral guard pretooluse` (`internal/cli/guard.go`, also unlisted in the usage text) is Claude's other PreToolUse hook, in the settings for `Bash`, for `^mcp__.*pull_request_review.*$` and for `launcher.MergeToolMatcher`. All handlers have `"timeout": 10` and `"onFailure": "block"`, because Claude Code lets a call through when a PreToolUse command hook times out or fails (`onFailure` needs Claude Code 2.1.295 or later). It does nothing unless `ADMIRAL_AUTOPILOT` is exactly `1`; then it parses a Bash command with `mvdan.cc/sh/v3/syntax` (`guard_shell.go`, which also looks through wrappers, `sh -c`, `eval` and heredocs fed to a shell). When the command doesn't parse as bash, it walks the statements parsed before the error, then parses the whole text as zsh, then applies a text rule (a line that mentions a review and an approve or request-changes spelling) to the whole line. A program word with an expansion that is followed by `pr … review`, `pr … merge`, `pr … edit` or `api` is checked as `gh`; any other unknown program, or a shell reading a pipe, gets the text rule on its own call or statement, computed once per span. Where it has no text for what it judges (a program word that is only an expansion, a `-c`, `eval` or heredoc script that is only an expansion, a shell reading a pipe or a file, a GraphQL `query` that is only an expansion), it also reads the whole line, once, for long spellings only (`review` with `approve`, `request_changes` or `request-changes`); short flags are not matched there. A program word that is only an expansion (`$C`, `${=C}`, `"${C[@]}"`) that no rule names is refused as `shell_script`, because the command in it can't be seen, which is also how a long spelling split by quotes (`C="gh pr me""rge 5"; $C`) is caught. Other `gh` calls are allowed, `gh pr ready` among them, unless a rule below names them. It refuses, with exit 2 and the one reason line on stderr, a command or MCP call that would submit a review as APPROVE or REQUEST_CHANGES (`gh pr review`, `gh api` reviews calls and GraphQL), or a payload it can't read; those get the review reason. The merge rules (`guard_merge.go`, #120) refuse with a merge reason: `gh pr merge` without `--auto` or with `--admin` (`gh_pr_merge`); `gh api` writes to `pulls/<n>/merge` and `merges` (`gh_api_merge`); the GraphQL mutations `mergePullRequest`, `enablePullRequestAutoMerge`, `mergeBranch`, `enqueuePullRequest` and `dequeuePullRequest` (`graphql_merge`); writes to rulesets (repository and organization) and branch protection, through REST or GraphQL, which would lower the gate the auto-merge rule relies on (`gh_api_gate_write`, `graphql_gate_write`); and any change of a pull request's base, since auto-merge is checked against the base it had (`pr_base_change`: `gh pr edit -B` or `--base`, a REST write to `pulls/<n>` with a `base` field or an `--input` it can't read or that has one, GraphQL `updatePullRequest` with `baseRefName`, its input in a variable, or an expansion). A write is any `gh api` method but GET and HEAD, a method held in a variable, or gh's implicit POST (`-f`, `-F` or `--input` with no `-X`). API paths are percent-decoded and have empty and `.` segments dropped and `..` resolved before they are matched; one that climbs above its root is one expansion. An expansion in a path counts as any words there: a write is refused when the expansion ends the path after a prefix a merge or gate route extends (`repos/<o>/<r>`, `pulls/<n>`, anything under `branches`, `orgs/<o>`), or when the literal words after it end in `merge` or `merges` or hold `protection` or `rulesets`, so `gh api -X PATCH repos/o/r/issues/$N -f state=closed` and `-X PATCH repos/o/r/pulls/$N -f body=x` are allowed (only a PATCH may end a path in an expansion right after `pulls`, because the merge route is a PUT; a `base` field is refused as `pr_base_change`). MCP tools are matched by `launcher.MergeToolMatcher` (any `mcp__` tool with `merge` or `enqueue` in its name, in any case, spelled with character classes because Claude Code matchers are JavaScript regular expressions with no `(?i)`), and the guard refuses every tool the matcher selects except those whose last name segment starts with `list_`, `get_` or `search_` (`mcp_merge`); the guard compiles the same constant, so the two agree. Where the guard can't parse a command and falls back to text, the text rule also refuses text that mentions `pr … merge`, a `pulls/…merge` or `/merges` route, `rulesets`, `/protection`, or those mutation names (a merge in `eval "$C"`, `echo '…' | bash`; `pr` and `merge` count anywhere in the text, so `A='gh pr '; B='merge 1'; eval "$A$B"` is refused). A GraphQL `query` the guard can't read is refused (`graphql_merge`): a file or stdin that isn't shown on the line, a query that is only an expansion or has an expansion beside the word `mutation` or outside a value position, and an `operationName` beside an expanded query; pass values as GraphQL variables (`-f id="$ID"` with a literal query) instead. A script given as an expansion alone (`eval "$(cat m.sh)"`, `bash <<< "$X"`) is refused as `shell_script` unless the line itself shows a merge, which gets the merge rule. Rules that keep the guard from being routed around, with their own reason (`opaqueReason`): `gh alias` and `gh extension` (`gh_alias`, `gh_extension`); a first `gh` word that is not one of gh's built-in commands (`ghCommands`, including help topics; `gh co` is an alias and stays refused; `gh_unknown`); an expansion in the word after `gh pr` or `gh auth` (the first is refused with the merge rule, the second as `token_read`); the shell builtins `alias`, `unalias` and `hash name=path` / `hash -p`, and assignments to `aliases`, `functions`, `commands`, `BASH_ALIASES` and `BASH_CMDS` (`shell_alias`); and scripts the guard isn't shown. For `bash|sh|zsh FILE`, `source FILE` and `. FILE` the guard reads the file with the limits of any file it reads (a regular file of at most 1 MiB, from the call's cwd), checks it as a command line of its own, and uses that result; it refuses with `shell_script` only a file it can't read or parse, a script given by an expansion, a shell fed from a pipe, `-s` or `sh < f`, and the arguments of an `xargs` that runs `gh` or a shell. Stdin counts as shown only when the statement has exactly one input source and its text is literal: one heredoc or here-string with no expansion, or one `<` from a literal file, or no stdin redirect and a literal `echo`, `printf` or `cat` of a literal heredoc before the pipe (words with no escapes). A `<&`, a `<>` or a second redirect of fd 0 means stdin is not shown, because zsh reads several and bash the last. A GraphQL `query` on stdin, a write's `--input -` body and a `pulls/<n>` PATCH are refused otherwise. An `--input` body, from stdin or a file, is decoded as a JSON object before it is read, so a `\u` escape can't hide a name, an event or a key (this covers the review rules too); keys are read by their exact names, and a body with two keys that differ only in case, or that isn't a JSON object, is refused. Boolean flags are read as gh reads them, with `strconv.ParseBool` (`--disable-auto=0` is false), and a value that isn't a boolean is refused. The token is refused when it is read, not when it is named: an expansion of `GH_TOKEN`, `GITHUB_TOKEN` or the enterprise names in any form, `printenv` or a bare `env`, `gh auth token` or `status -t`, `git credential`, and `security find-generic-password` or `find-internet-password` with `-w` or `-g` (`token_read`); `grep -rn GITHUB_TOKEN .github` or a quoted heredoc that writes `${{ secrets.GITHUB_TOKEN }}` is allowed. `gh pr merge --disable-auto` is allowed. `gh pr merge --auto` is allowed only when all of these hold: (1) `ADMIRAL_AUTO_MERGE` is a valid method and the command names exactly that method (`auto_merge_method`); (2) the pull request is one literal full URL, `https://<host>/<owner>/<repo>/pull/<n>`, with no `-R` or `--repo` and no other positional (`auto_merge_steered`). gh takes the repository and host from such an argument and from nothing else (`cli/cli` `pkg/cmd/pr/shared/finder.go`: `Find` sets the base repo from `ParseURL` and calls `baseRepoFn`, which reads `GH_REPO`, `-R` and the remotes of the cwd, only when there is no URL), so the pull request the lookup resolves is the one gh merges; (3) nothing on the line steers gh, wherever the shell would run it (`auto_merge_steered`): the check runs once the whole line is read, so a `cd` after the merge in a function, loop or `trap` counts. The steering words are an inline, exported, `env` or builtin-assigned `GH_REPO`, `GH_HOST`, `GH_CONFIG_DIR`, `GIT_DIR`, `GIT_WORK_TREE`, `GH_TOKEN` or `GITHUB_TOKEN` (`set -a` and `set -o allexport` count, with `read`, `printf -v`, `mapfile`, `getopts`, `: ${X:=…}` and `for X in` on those names), `cd`, `pushd`, `popd`, `git checkout|switch|remote|config|worktree`, `gh pr checkout`, `gh repo set-default`, wrapper flags that move or clear the environment (`env -C`, `-u`, `-i`, `sudo -D`, `--chdir`) and `xargs`; (4) GitHub confirms the base branch (`auto_merge_unconfirmed`). The lookup (`approvalLookup`, a func variable tests replace) runs after the line is read, in one 7 s deadline inside the hook's 10: `gh pr view <URL> --json url,baseRefName`, then `GET repos/<o>/<r>/rules/branches/<base>`, and, failing that, `GET repos/<o>/<r>/branches/<base>/protection`. A `pull_request` rule confirms only when it needs at least one approving review and dismisses stale reviews on push or requires approval of the last push, and its ruleset (`GET repos/<o>/<r>/rulesets/<id>`, or the organization's) is active and says `current_user_can_bypass: never`. Classic protection confirms only with at least one approving review, `dismiss_stale_reviews` or `require_last_push_approval`, `enforce_admins` on, and no user, team or app in `bypass_pull_request_allowances`. An error, a timeout, a missing field or any other answer refuses. To use `auto_merge` on a repository, then, its base branch needs a ruleset (or classic protection) that requires at least one approving review, dismisses stale approvals when new commits are pushed (or requires approval of the most recent push), has no bypass for the account Admiral's ships use (no bypass actors, or in classic protection admins enforced and no bypass allowances), and so a second account has to approve the pull request. Programs that run their arguments are looked through when they are `find` (`-exec`, `-execdir`, `-ok`, `-okdir`), `arch`, `script`, `flock`, `watch`, `unbuffer`, `doas`, `gtimeout`, `npx`, `xargs` and the usual wrappers; `git -c alias.x=!…` and `git config alias.x '!…'` are refused as `git_shell_alias`. A relative file is not read once the line has a `cd`, `pushd` or `popd` (the guard would read a different file from the one the call reads), `~/` is the home directory, and a shell is refused when `BASH_ENV`, `ENV` or `ZDOTDIR` is set on the line or when `--rcfile`, `--init-file` or `-i` comes beside a script. `gh auth status --show-token` is read as a boolean, and `git credential-*` helpers count as `git credential`. Known gaps. The guard is best effort, and the GitHub rules of the base branch are the gate: it narrows what a ship can do by accident or by habit, and it can't contain an agent that runs arbitrary programs with a token that can merge. A script run as `./FILE` runs unread (`bash FILE` is read, but the same file as a command is not). A program word built from a literal and an expansion (`g$Y`, `$D/gh $S`), zsh glob qualifiers that run code (`*(e:'…':)`), the `(e)` parameter flag and arithmetic that evaluates a subscript (`$((X))` with `X='a[$(…)]'`) run a command the guard reads as data. Sourcing nvm (`. ~/.nvm/nvm.sh`) is refused, because nvm defines aliases (`shell_alias`); set Node up outside the ship. The account a merge runs under can be switched with nothing on the line: `GH_CONFIG_DIR`, or a token exported from an rc file in an earlier call, is not seen by the lookup, which checks the hook's own account. The guard is best effort and reads only the text of a Bash call (D8): a merge through anything that is not a literal shell `gh` call is invisible to it, such as an interpreter (`python3 -c`), `make`, `curl` with a token from somewhere else, a nested agent, a `gh` shim earlier on `PATH`, or a replaced `$ADMIRAL_HOME/bin/admiral`. Files the guard reads (`--input`, `-F @file`) can change before gh reads them. Direct writes to the base, `git push`, REST `PUT contents`, `PATCH git/refs`, GraphQL `createCommitOnBranch` and `updateRef`, and the GitHub MCP file tools, are not hooked, and neither are writes to repository settings that raise access (`collaborators`, `PATCH repos/<o>/<r>`); the branch rules on GitHub are what stop them. The GitHub MCP `update_pull_request` tool with a `base` argument changes a base and is not hooked. Codex and Copilot ships have no guard, and autopilot refuses any harness but Claude for that reason. A refusal writes one `guard_denied` line (`tool`, `rule`, no command text) under the home of `ADMIRAL_REPORT`, or else `ADMIRAL_HOME`; with no ship or home, or a failed write, it still refuses. Every ship also gets `ADMIRAL_SHIP` (its session name), `ADMIRAL_REPORT` (`$ADMIRAL_HOME/reports/<session>.json`) and `ADMIRAL_INBOX` (`$ADMIRAL_HOME/inbox/<session>/`), which win over a fleet's env; Commodore ships on Claude also get `CLAUDE_CODE_AUTO_COMPACT_WINDOW=200000`, a fleet's `env` overrides it, and `1000000` turns it off; an autopilot launch also gets `ADMIRAL_AUTOPILOT=1`, `ADMIRAL_LOW_STAKES` (`advisor` or `never`) and, when its panel has `auto_merge`, `ADMIRAL_AUTO_MERGE`, and a launch by hand has none of them (nor does an autopilot launch whose panel has no `auto_merge`, for the last): Admiral owns these names, so it drops them from the fleet's env and runs `set-environment -r` for each on the session (`-r`, because the tmux server inherits Admiral's own environment, which may hold them; `-u` would fall back to it). A panel's autopilot args go after the fleet's dock args; Admiral removes any report and inbox a reused name left, then creates `reports/` and the inbox before the harness starts. Every start links `$ADMIRAL_HOME/bin/admiral` to the running binary and puts that directory first on a ship's `PATH`), and `HiddenOrders` lists the orders ships hide. `internal/outcomes` is the outcome log: one goroutine appends a JSON line per record (a ship's guard is a second appender, a separate process writing its own short `guard_denied` line) to `$ADMIRAL_HOME/outcomes/<YYYY-MM>.jsonl` (month of `ts`, UTC), queues 1024 records and drops the rest (`Enqueue` passes `outcomes.ErrDropped` to a dropped record's `onDone`), and logs a failed write once until one succeeds. Admiral reads the log back for one purpose only, counting autopilot runs toward retro orders (ADR 0017): `outcomes.Read(dir)` returns every `<YYYY-MM>.jsonl` line that is a JSON object with a `v`, an RFC 3339 `ts` and an `event`, in file-name then line order, holding only the keys the count uses (`source`, `panel`, `autopilot`, `order_id`, `title`, `resume_source`, `resume_panel`, `text`, `uncertain`) and skipping the rest, a line over `outcomes.MaxLine` and any name that is not a regular file, and nothing else reads it. `ships.Service` feeds it: `launched` from `Service.LaunchOrder`, the one launch path for `serveLaunch` and autopilot, which holds the order's key while it runs so a second launch of that order gets 409, and sets `"autopilot"` from the request (and only then does `Run` follow the ship), `needs_you` and `underway` from the status each pass of `Run` sees against the last (`internal/ships/outcomes.go`; a stop whose reason changes is one stop, and a ship no hook has spoken for needs you with reason `idle`), `ended` when a pane is dead without `@admiral-ended` (also at start-up, before an exit-0 ship is killed) `dismissed` from Dismiss, `answered` from the inbox (`internal/inbox`, ADR 0016), and the ship-less `retro_queued` from the autopilot engine (see "Retro orders"). `ended` carries the parsed `$ADMIRAL_REPORT` (at most 1 MiB; `null` and a log line when invalid), and once it is written the writer sets the session option `@admiral-ended` and deletes the report and inbox of a ship that was dismissed or sailed off. Admiral kills such a ship whether or not the log works (`Service.killShip`), so one killed while its `ended` fails loses that `ended` and keeps its files; a dead pane still in tmux is retried at the next start, and Dismiss queues a failed `ended` once more before `dismissed`. The deletes go through an `os.Root` on `$ADMIRAL_HOME` and are skipped, keeping the files, while a launch is under way (a name is not known before `Launch` returns) or when a newer ship's track holds the name: none leaves the home, though a link swapped in inside the home can still send one elsewhere within it. `launcher.ShipFiles` builds the report and inbox paths for both the environment and the cleanup. The needs-you tally survives a restart in the session options `@admiral-needs-count`, `@admiral-needs-s` and `@admiral-stop-since`. A session removed with no dead pane gets no `ended`. `admiral outcomes` (`internal/cli/outcomes.go`) prints the log: it reads the month files directly, line by line, and filters on `ts` and `ship`, with `--ship` mapped through `launcher.Slug`.
- Crew boats (teammates, #152, ADR 0014): `admiral crew` (`internal/cli/crew.go`) talks to tmux on `$ADMIRAL_HOME/tmux.sock` directly and needs no server; it finds the home from `ADMIRAL_HOME`, else from `ADMIRAL_REPORT`. `launcher.LaunchCrew` (`internal/launcher/crew.go`) makes a `new-window -d` in the ship's session on a placeholder, sets the window options (`@admiral-crew-name`, `-harness`, `-dir`, `-launched`, `remain-on-exit`, `monitor-bell`), then respawns it as the harness with the chosen dock's env, with `env -u` clearing the ship's `ADMIRAL_SHIP`, `ADMIRAL_REPORT` and `ADMIRAL_INBOX` and every key the ship's dock `env` sets that the chosen dock's doesn't; `-e` carries only the chosen dock's `env`, never the caller's environment. It never calls `Launch`/`shipContract`. `sessionhost.ReadCrew` (`internal/sessionhost/crew.go`) is the one reader of crew from tmux (window rows with `@admiral-crew-name`), with `CrewState`, so `crew list` and the server compute the same `state`. `parseRows` skips crew rows in its ship loop and folds them into `Session.Crew` through `parseCrew` (the one crew rule, shared with `ReadCrew`), but a crew row never sets a ship field (`PaneDead`, `ExitStatus`, `State`, `Options`, `PaneID` and the rest come only from the ship's own row, wherever it sits in the list), a session with only crew rows is no session, and crew fields stay out of `set()`'s event diff, because a window option shadows the session's of the same name; `Session.PaneID` is the ship's own pane, which `Host.SetNeedsYou`/`SetWorking` target instead of `=session:` (the current window's active pane). `admiral hook` stamps `@admiral-activity` (RFC 3339) on `$TMUX_PANE` on every event: a crew boat's `last_activity`. **Lead rule** (`leadDecision`, `internal/cli/hook.go`): a lead's `Stop` (Claude Code, Codex) or Copilot lead `agentStop` leaves `@admiral-state` alone while a crew window of its session has a live pane (`pane_dead` 0) that is working, so the lead stays `underway`; otherwise `needs_you` `stop` as before. A lead is a `$TMUX_PANE` whose window has no `@admiral-crew-name`; a crew boat's own `Stop` keeps `needs_you`, and no crew hook re-evaluates its lead. A pane is working when its own `@admiral-state` is `working` (`show-options -pqv`, per live crew pane after one `list-panes -s`), or when it has no state and no `@admiral-activity` yet and its window's `@admiral-launched` is under 10 s old (ADR 0007's no-hook window; `crew launch` writes no state). So a crew boat with no hook yet, such as one stuck on Codex's hook review dialog, holds a lead `Stop` that arrives within its first 10 s. A held `Stop` is never re-evaluated: that lead shows underway until its own next hook. A dead pane keeps its state and never counts. Each tmux read the hook makes has a 2 s deadline; a crew pane whose state read fails counts as having no state, so it falls to the launch-window check. Claude's `background_tasks` rule runs first and the crew is read only when `Stop` would otherwise write `needs_you`; a failed crew read writes `needs_you` `stop`. `ReadCrew` reads the state through the `#{@admiral-state}` format, which falls back to the window's and session's value; the two agree because nothing sets `@admiral-state` above pane level. **`@admiral-subagents`** (`sessionhost.EncodeSubagents`/`DecodeSubagents`, `internal/sessionhost/subagents.go`; the server reads it with the same code) is kept by `admiral hook` on `$TMUX_PANE` as a JSON array of `{"id","type","start"}` (`start` RFC 3339, at most 64 entries; an empty list unsets the option). Ids and types come from the payload and are kept only as safe tokens (a bad id drops the entry, a bad type is stored as `""`). Adds: `SubagentStart` (Claude Code, Codex: `agent_id`, `agent_type`) and Copilot `subagentStart` (`agentId`, `agentType`); a listed id keeps its start. Clears: a Claude Code `Stop` replaces the list from `background_tasks` entries of type `subagent` or `teammate` that are running; `SubagentStop`/`subagentStop` removes a listed id; Codex clears only on `SubagentStop` (its `Stop` has no `background_tasks`); a Copilot lead's `agentStop` or `userPromptSubmitted` clears all. A stop for an unlisted id is ignored. The harness for a `Stop` comes from `display -p -t "$TMUX_PANE" '#{@admiral-harness}'`, falling back to the payload's `background_tasks` (present, even `[]`, is Claude Code). Subagent events never change `@admiral-state`. A reader treats the list of a dead pane as empty (`parseRows` does, on `PaneDead`). `DecodeSubagents` re-checks every entry on read with `sessionhost.SafeToken` (the hook uses it too): an id that is not a safe token, a `start` that is not RFC 3339 or a repeated id (the first wins) drops the entry, a type that is not a safe token reads as `""`, and the list is capped at 64. A raw `\x1f` in an option makes its row the wrong length (the ship is unreadable); a raw newline in the last field leaves a fragment that is read as a row if it is well formed. Only raw tmux on the socket can plant either; `admiral hook` writes JSON, which escapes both. The read-modify-write takes no lock, so two hooks at once on one pane can lose an update. The bundle registers `SubagentStart`/`SubagentStop` (Claude Code, Codex) and `subagentStart`/`subagentStop` (Copilot); the new Codex events bring back its hook review dialog once. The `alert-bell` hook script stamps `@admiral-bell` on the ringing window's pane, and for a Codex crew boat also sets that pane `needs_you` (reason `bell`). `sessionhost.Crew` also carries the pane's exit (`ExitStatus`, `Signal`, read in `parseCrew` for an anchored boat), which `ships.CrewExit` turns into `exit_code`/`exit_signal` on a `CrewBoat` (omitted while it lives). **The bridge on a crew boat** (#152 u4): `GET /ws/bridge/{session}/crew/{name}` (`serveCrew`, `internal/bridge/browser.go`) finds the boat by name through `Ships.Crew` (a `find`, so `_setup`, `_admiral` and a non-ship 404), then holds its pane and window ids. `internal/bridge/bridge.go` has one `conn` per watched session, the shared control client, with a `watch` per pane (key `""` for the ship, the window id for a boat); the same `watch` code serves both, with `state` (the ship's wire status, or the boat's own), the input clear (`InputSeen`, or `Ships.CrewInputSeen`, which writes `working` on the boat's pane by id through `Host.SetPaneWorking`) and the live gate differing. `conn.start` reads each window's size before attaching and pins them all with `refresh-client -C @id:WxH` (attaching sets unpinned windows to 80x24); every later size is per window. The ship's watch resolves `=<session>:^`, never `=<session>:`, which is the current window. A boat's watch ends in `shipChanged` (reached by `ShipsChanged`) when its window id is no longer in `Ships.Crew`; the client detaches `ADMIRAL_BRIDGE_IDLE` after the last watch is gone. **Option text is untrusted.** A crew boat writes its own window's `@admiral-crew-name`, and tmux prints option values raw, so the `list-panes` reader (`Host.poll`, `ReadOnce`, `ReadCrew`) does three things. (1) Every row starts with a per-read random nonce (`rowFormat`, built for each command, 16 hex characters from `crypto/rand`), and `ownRows` drops any row that doesn't start with it before fields are counted: option text is written before the read and can't know it, so the lines a raw newline leaves, or a row an agent forged in its option, are dropped. (2) As a second layer `format` wraps `#{session_name}` and every `#{@admiral-*}` in `#{s/[\x01-\x1f\x7f]/ /:...}` (`unprintable`), so a control character reads as a space. tmux copies a value that is not valid UTF-8 through raw, whatever the substitution says, so this alone doesn't hold. (The class is a range of literal bytes: the colon in `[[:cntrl:]]` ends a format modifier.) (3) `parseCrew` reads a name only if it matches `launcher.CrewName`, and when two windows of one session claim a name it reads neither and `Host.poll` logs `admiral: crew boat <session>/<name>: two windows claim this name, so neither is listed` once. What the reader doesn't do: a row that a value still breaks (an invalid UTF-8 byte next to a control character) keeps its nonce and loses its field count, and `parseRows` then holds that session unreadable at its last state, so a boat can freeze its own ship's reads. `hook.go`'s crew read and the launcher's name checks read raw options of their own. A boat dropped by (3) leaves `crew[]`: its bridge closes, its needs-you leaves the ship's wire status, and no inbox item or closed push is made for it. A crew bridge also ends on tmux's `%window-close` / `%unlinked-window-close` for its window. `admiral attach` reads `sessionhost.ReadOnce` and targets `=<session>:^` or `=<session>:<window id>`.
- Crew boats and subagents on the wire (#152 u3). Words: `crew` is the crew boats that are teammates (crew windows), `subagents` the subagent marks; GLOSSARY.md's "crew boat" covers both. Every ship in `GET /api/ships` and the `ships` WebSocket message carries three fields, always present (`[]`, never `null`): `crew`, sorted by name, each `{"name","harness","dir","status","reason","launched","last_activity"}`; `subagents`, each `{"id","type","start"}`, from the ship's own pane (a crew boat's own subagents stay off the wire until #153); and `crew_live`. A crew boat's `status` is the value `admiral crew list --json` calls `state`: `underway`, `needs_you` or `anchored`. `reason` only while `needs_you` (the crew pane's `@admiral-reason` if it is a safe token, else `unknown`); `last_activity` is the pane's `@admiral-activity`, omitted before its first hook. `crew_live` counts crew boats with a live pane (`underway` or `needs_you`), so the UI can warn before Dismiss; it is not the hook's "working", which means only `@admiral-state` `working`. The data comes from the rows `Host.poll` already reads (`#{@admiral-subagents}` is the last tail field, outside `optionNames`), so there is no extra tmux call per ship and a restart needs nothing beyond the next poll. **The wire status counts crew** (`wireStatus`, `internal/ships/crew.go`, applied in `Service.ship()` only): while a ship's own status is `underway` and a crew boat is `needs_you`, the ship's `status` is `needs_you`, `reason` `crew` and `stop_since` the earliest, over the needing boats, of the boat's `last_activity` or else its `launched`. This reaches the API, the WebSocket, `Get()` (so the bridge's `ship` message) and `InputSeen`'s response. The inbox builds a stop for the ship only while it needs you itself (`status` `needs_you` and `reason` not `crew`) and one stop per `needs_you` entry of `crew`, keyed `stop:<session>/<crew>`, whatever the ship's status except `sailing_off`. The ship's own status stays in `FromSession`, `status()` and `sess.State`, which `InputSeen`'s decision, Dismiss, sail-off, the bell, the startup exit-0 kill and the outcome log use, and `@admiral-state` is never written for a crew boat. The ships push signature covers crew membership, each boat's status and reason and the subagent ids, not `last_activity`. Sail-off and Dismiss kill the whole session (`kill-session`), which ends crew windows and their harness processes; an anchored ship's live crew keep running until Dismiss. `launcher.CloseCrew(ctx, windowID)` is the one kill both `admiral crew close` and the close route use.
- Autopilot config (`internal/config/autopilot.go`, #114). Top-level `autopilot.max_ships` (positive integer, default 3) caps every ship underway or needing you, hand-launched ones included: when that many are running, autopilot launches nothing. `sources.<key>.autopilot.<panel id>` holds `enabled` (default false), `fleet`, `harness` (`claude` only; anything else fails with "autopilot runs on Claude Code only for now") and `skill` (`{"kind": "commodore"}`, `{"kind": "skill", "name": …}` or `{"kind": "none"}`), all three required, plus `args` (default `[]`), `max_ships` (positive integer, default 1), `retro_every` (integer of 0 or more, default 5, `config.PanelAutopilot.RetroEvery`; 0 turns retro orders off, and the default is not written into the file) and `low_stakes` (`advisor`, the default, or `never`) and `auto_merge` (`squash`, `merge` or `rebase`; absent means off; the launcher sets `ADMIRAL_AUTO_MERGE` from it, and a build panel runs one ship at a time through `max_ships`, default 1). Unknown keys are errors. The fleet must exist and have a `claude` dock; the check runs after the fleets parse, and `SetSources` re-parses the whole file, so it holds for UI writes too. Removing such a fleet or its claude dock through `admiral fleet` or setup now fails validation. Config can't know the panel ids (they come from the running plugin), so a misspelled panel key does nothing. Top-level `autopilot.resume_source` is `{"source": "<source key>", "panel": "<panel id>"}` and optional (`config.Config.ResumeSource`, nil without it); config checks the shape only, since the source and panel are looked up when an order is added, and deleting the source in the UI must keep working. See "Resume orders". `SourcesJSON` writes each source's `autopilot` object back as it was read, so a UI save adds no defaults to the file. `launcher.Request` carries `Autopilot`, `LowStakes`, `ExtraArgs` and `Panel` (`json:"-"`, so `POST /api/ships` can't set them); `Launch` refuses an autopilot request whose `LowStakes` is not `advisor` or `never`.
- Autopilot engine (`internal/autopilot`, #114). `main.go` runs one pass goroutine, poked without blocking by `ships.Service.OnChange`, `Supervisor.OnChange` (chained onto the existing closures), a config change and the pause route (through `Supervisor.changed`), and by a one-minute ticker. A pass counts the ships whose status is `underway` or `needs_you` (hand launches too) against `autopilot.max_ships` and, by their `@admiral-panel` option (`Ship.Panel`), against each panel's `max_ships`. It takes the eligible panels (enabled, not paused) in sidebar order, `sources.SortPanels` over the config's source order, and in each launches the first visible order not in the launched set, through `ships.Service.LaunchOrder`, until a cap is full. A source in `error`, `auth` or restarting still offers its last-known orders. The directory is the one the launch dialog pre-selects from the order's `repo` hint or a repository URL in its text (`launchorders.Service.Dir`, sharing the dialog's ranking, ADR 0009 rules 1 and 2); no match writes a `skipped` outcome record and leaves the order visible. A launch by autopilot moves the dock's last directory, as a hand launch does. The launched set and the failure state live in `$ADMIRAL_HOME/autopilot.json` (`autopilot.Store`, written at once, atomically, `"version": 1`): a pair is added when an order launches, by autopilot or by hand (`sources.Service.OnLaunched`), and dropped once the source's raw listing no longer holds the order, only for a source that is `ok` and whose every panel has had a successful `orders.list` since the source started (`Panel.Listed`, set in `runner.pullOrders`, cleared when the runner starts), so a panel whose listing failed never loses its pairs. Every launch from a source joins the set, from a panel on autopilot or not. A launch that fails writes `launch_failed` and backs the order off 10 minutes, then 1 hour; the third failure stops autopilot trying and sets `hot` on the order in the sources view; `Engine.OnHot` pushes the view when an order turns hot or cools (`sources.Service.Hot` overlays `Order.Hot`; the engine decides from its own state, never from the plugin's `hot`). A 409, and a 503 `ships are not known yet`, are not failures: the order is tried again at the next pass. `ships.Service.LaunchOrder` also holds an order's key until the host lists its ship (at most 30 s; only `LaunchOrder` consults the hold, not `HiddenOrders`), and `ships.Service.Pending` lists those unlisted ships, which `main.go` adds to the ships the engine and the sources view see so they count toward the caps, and answers 503 while the host is not ready or has lost tmux, because the ship list is then empty. Pause is runtime state in `state.json` (`state.Store.Paused`, keyed by source key and panel id; it outlives a removed source): `PUT /api/sources/<key>/panels/<panel>/autopilot` with `{"paused": bool}` answers 404 for an unknown source or a panel with no entry. `GET /api/sources` carries `autopilot: {enabled, paused, max_ships, resources, waiting_for}` on each panel (`null` without an entry) and `GET /api/config` carries `autopilot: {max_ships}`. A pass counts a ship by its `@admiral-origin-source` and `@admiral-origin-panel` options (`Ship.OriginSource`, `OriginPanel`) when it has them, and otherwise by source and panel; autopilot sets them on every launch, to the panel whose entry the launch ran under.
- Retro orders (`internal/autopilot/retro.go`, `retro_count.go`, #117, ADR 0017). Every pass ends with a retro step, deferred in `Pass` so it runs when the launch loop returns early. It skips when no panel is enabled, unpaused and has `retro_every` above 0; otherwise it reads the log with `Engine.Log` (`outcomes.Read`) and `CountRuns` counts, per `(source, panel)`, the `ended` records that join to the latest earlier `launched` of the same ship (position in the log, never `ts`), once per `launched`, where that `launched` is `autopilot: true` for the panel and is not a retro ship (its `source`, `panel` and `order_id` match a `retro_queued`'s `resume_source`, `resume_panel` and `order_id`; for an uncertain record, its `title` matches the `text`; `Retro.matches` is the one rule). `ForTarget` first drops the `retro_queued` records that name another resume target than `autopilot.resume_source`. Only runs after the panel's last `retro_queued` count. A panel with `retro_every` or more runs, and no pending retro, gets one order added to `autopilot.resume_source` through `Engine.AddOrder` (`sources.Service.AddOrder`), and only while `Engine.Known` (`Host.Known`) says the ship list is known: `/retro <source>/<panel> --since <ts>`, with `ts` the previous `retro_queued`'s `ts`, or the first counted run's `launched` `ts`, formatted as RFC 3339 UTC. A panel id with whitespace or a control character is refused and logged once. The add holds `Engine.pass` but no other lock. The ship-less `retro_queued` record (`source`, `panel`, `since`, `text`, `resume_source`, `resume_panel` and `order_id`, or `uncertain: true` for an add that may have landed) is written through `Engine.Record` with an `onDone`; the panel stays pending until it is confirmed, and a failed or dropped write is logged once and written again, never re-adding the order. A panel has a retro pending while its record is unconfirmed (noted before the log is read), or any of its `retro_queued` records has its order in the resume panel's listing, or the resume source is configured and has not listed, or a ship in `Ships()` in any status has its order; the log carries all but the first across a restart. No `resume_source` is warned once. A retryable or final refusal is logged once per message and tried again on a later pass (a resume order is dropped on a final one); an uncertain result writes the uncertain record, so the same retro is never added twice. `admiral outcomes` keeps `retro_queued` lines. Gaps are in ADR 0017.
- Locked resources (#118). Config: top-level `resources` (`config.Resource{Capacity, Check}`, `capacity` an integer >= 1 defaulting to 1, `check` a non-empty argv of non-empty strings, names `^[A-Za-z0-9_.-]{1,64}$`) and `sources.<key>.autopilot.<panel>.resources` (`PanelAutopilot.Resources`, nil when none). `checkPanelResources` runs after the whole file parses, beside `checkAutopilotFleets`, so a panel naming an undefined resource fails every load and write. `internal/resources.Set` answers which units are held and by whom: a ship holds one unit of each name in its `@admiral-resources` option (`Ship.Resources`, `json:"-"`; set from `launcher.Request.Resources` only on an autopilot launch) while `underway` or `needs_you`, as do locks (`Set.Lock`, non-blocking, no check needed, for `admiral lock` to call) and reservations. A name no longer in the config holds nothing. `Set.Ships` is `allShips` in `main.go` (List + Pending), so a just-launched ship counts before the host lists it (`ships.Pending` carries the request's resources). `Set.Reserve` checks and reserves all-or-nothing under the Set's mutex and answers `Wait{Name, Why}` with `busy`, `missing` or `pending`. The engine reserves in `Pass` after the `Dir` check and drops the reservation as soon as `Launch` returns, on every outcome. Checks run as an argv with no shell, in their own process group, killed as a group at 10 s (`missing`); `Set.Run` runs them all at once, on `Refresh` (a config change) and every 15 s, never two at once for one resource, and a resource is `pending` until its first check ends (`none` when it has no check). A changed check state or a released lock calls `Options.OnChange` (`main.go` pushes the `resources` message and pokes the engine). A dropped reservation calls `Options.OnDrop` instead, which only pushes: the engine drops its own reservations inside a pass, and a poke there would make a refused launch (a 503 or a 409) start the next pass at once. All three close the channel `Set.Changed` returns, and so does `Set.Wake`, which `main.go` calls on every ship change and config change (a ship leaving `underway` frees a unit with no event of the Set's own). An order whose gate fails waits: the engine writes one `resource_wait` record when the wait starts, once every named check has finished at least once, and goes on to the next panel. `Engine.WaitingFor(source, panel)` and `OnWait` feed the sources view (`sources.Service.WaitingFor`). `GET /api/resources` and the WebSocket `resources` message (`resources.Service`, sent on connect and on change through `BroadcastOnce`) carry `{"resources": [{name, capacity, in_use, holders: [{kind: "ship", session} | {kind: "lock", label}], check}]}` sorted by name, with no timestamps. `POST /api/resources/<name>/lock` (`internal/lockroute`, for `admiral lock`) holds a unit as an open request: no body, query `label` (cleaned to printable, at most 64 characters) and `wait=1`; it answers `200` with one flushed line `{"held":true}`, then stays open and releases the unit when the request context ends or the server shuts down (`srv.RegisterOnShutdown` closes `Route.Stopping`; the background context is cancelled only after the drain, which waits on this handler). Without `wait` a busy resource answers `409`, an unknown one `404`; with `wait` the handler waits on `Set.Changed()` (fetched before each `Lock` try) and a 15 s timer (a pending ship that expires frees a unit with no wake) and a client that leaves while waiting holds nothing. A peer that is not loopback gets `403`, token or not (`auth.IsLoopbackPeer`, after the Host and Origin checks; a LAN peer with no token gets the middleware's `401` before it reaches the route); the handler reads the body first, because Go cancels the context on a hang-up only once it has. `OnTake` pushes the `resources` message, since `Set.Lock` doesn't announce a take. `admiral lock` (`internal/cli/lock.go`) splits its arguments at the first `--` before parsing flags, probes the server as `ships` does, sends `admiral lock (pid <its own>): <argv[0] base>` and runs the command after the `held` line; it returns a `cli.ExitError` (code, optional message) for 75, 127 and the command's status, which `main.go` maps; after `held` it keeps reading the response and, if that ends while the command runs, prints `lost the lock` to stderr and leaves the command running; it forwards only SIGTERM (it catches and ignores SIGINT, SIGHUP and SIGQUIT, which the terminal sends to the command). The `-h` scan in `main.go` stops at `--`.
- `internal/inbox` is the Needs You inbox (ADR 0016). It reads the item files in `$ADMIRAL_HOME/inbox/<session>/` through an `os.Root` (a link, a dot file, a name that is not `<id>.json` with `<id>` matching `^[A-Za-z0-9][A-Za-z0-9_-]{0,63}$`, a file over 1 MiB, or an invalid item is skipped; so is an item with `<id>.answer.json` beside it), watches `$ADMIRAL_HOME`, `inbox/` and each ship's directory with fsnotify (100 ms settle, watches re-synced before each rescan), and serves `GET /api/inbox` (`{"items":[...]}`, oldest `created` first; each item is the file's fields plus `session`, and `name` and `harness` when the ship is known) and the WebSocket `inbox` message (`{"type":"inbox","items":[...]}`). `POST /api/inbox/<session>/<id>/answer` takes a question's answers (`{"answers":{"<qid>":{"choice","other"}},"note"}`): 400 for an invalid answer, 404 for an unknown item, 409 for one already answered. `Service.Answer` is the shared writer: `build` gets the item and returns the answer file and the outcome records (no network I/O, since it runs under one lock that also re-reads the item and checks for an answer), then the file is written to a temp file and published with `os.Root.Link` (`fs.ErrExist` is a 409, so an answer is never replaced). A question's record is `answered` with `item` and `kind`.
  - `POST /api/inbox/<session>/<id>/submit` (`{"event":"COMMENT"|"APPROVE"|"REQUEST_CHANGES","edited":bool}`) and `.../discard` (`{}`) act on a review item through `gh` (`internal/inbox/review.go`). `gh` is found on Admiral's own `PATH` and run with `exec.CommandContext`, an argument list, a 30 s timeout and no retry. Its environment is Admiral's overlaid with the env of the ship's dock (`fleets[].harnesses.<name>.env`, from the ship's `fleet` and `harness` read at action time from the current config), plus `GH_PROMPT_DISABLED=1` and `GH_NO_UPDATE_NOTIFIER=1`; a ship with no dock runs `gh` in Admiral's own environment, and a failure says so. The host, owner, repo and PR number come only from the item's `pr_url` (`https://<host>/<owner>/<repo>/pull/<n>`, nothing else; always `--hostname <host>`) and `review_id` must be a positive whole number; otherwise 400 and `gh` is not run. Submit reads the review (`GET repos/<o>/<r>/pulls/<n>/reviews/<id>`) and posts its current body, or the item's `summary` when that is empty, with the event (`POST .../events`, JSON on stdin through `--input -`, so item text is never an argument). Discard is `DELETE` of the same endpoint, or, for a review whose `pr_url` or `review_id` is invalid, no `gh` call at all: the answer is `{"action":"discarded"}` and `review_discarded` carries `invalid_target: true`; the 200 response also says `"invalid_target": true`. A 404, a 422 whose parsed `message` or `errors` name "pending" (not `documentation_url`), or on Submit a review whose `state` is not `PENDING` (no POST), means the review is gone: the answer is `{"action":"gone"}`, `review_discarded` is recorded with `external: true`, and the response is 200. After a 404, though, Admiral also reads the pull request (`GET repos/<o>/<r>/pulls/<n>`), because a token that cannot see the repo gets 404 as well; if that fails too, it answers 502 and writes and records nothing, with the "token may not reach it" text only when the pull request answered 404, and gh's own text otherwise. Any other `gh` failure writes no answer and no record, and answers 502 (503 when `gh` is missing) with `{"error": ...}` carrying gh's message, the whole message cut at 4 KiB, before the note on where gh ran. A 200 carries `"action"` (`inbox.ActionSubmitted`, `ActionDiscarded`, `ActionGone`). Only one action runs on an item at a time (409 `ErrBusy`). `.../discard` with `{"forget": true}` (Remove from inbox, for a review that fails forever) runs no `gh`: it writes `{"action":"discarded"}`, records `review_discarded` with `unreachable: true` only, and answers 200 with `"forgotten": true`, so the UI can say nothing changed on GitHub. It is allowed on any review item, and Submit has no such option.
  - `POST /api/inbox/<session>/<id>/findings` (`{"cards":[{"id","decision":"approved"|"edited"|"rejected","proposal":{"kind":"diff"|"reply","content"}}]}`) needs a decision for every card id of the item, once each, and a proposal on an edited card only (400 otherwise); an item with no cards takes `{"cards":[]}`. It writes the answer's `cards` map and one record per card, and posts nothing to GitHub.
  - Outcome events (fields besides `item` and `kind`): `answered` (question), `review_submitted` (`review_event`, `edited`; a log line's `event` is the record name, so the review's event cannot be called `event`), `review_discarded` (`external: true` when gone, `invalid_target: true` when Admiral ran nothing for an invalid target, `unreachable: true` for Remove from inbox), `resumed` (see "Resume orders"; `ship` is the session, with `source`, `panel` and `order`, or `uncertain: true` and no `order`), `card_approved`, `card_edited` and `card_rejected` (`card`). A review or findings answer writes no `answered`.
  - **Kept inbox.** An exit-0 ship's session is killed at sail-off, and its report and inbox are removed once its `ended` is written (ADR 0015), unless its inbox still holds an item with no answer (`inbox.Unanswered`). Then `ships.killShip` first copies the session's `name`, `fleet`, `fleet_name`, `fleet_color`, `harness`, `dir`, `origin_source` and `origin_panel` into `state.json` (`kept_inboxes`, by session; `state.KeepInbox`, written at once) and `removeShipFiles` skips a session with a record. The record names the item's ship for the inbox reader (`Ship`) and gives `gh` its dock (`Dock`), and `launcher.pickName` never draws a name with a record (`Launcher.Kept`), because a launch clears the inbox of the name it takes. When an answer leaves no item unanswered, `Service.release` removes the files (`launcher.RemoveShipFiles`, through an `os.Root`) and drops the record; `Service.Run` does the same at start-up for records whose items were answered meanwhile. Dismiss never keeps (and so adds no resume order for an item it leaves unanswered). A directory with no record and no session is left alone, as before.
  - **Resume orders** (`internal/inbox/resume.go`, ADR 0016). When every id in a ship's report `inbox` has an item file and an answer file, the report's `resume` text becomes an order in the panel `autopilot.resume_source` names, through `sources.Service.AddOrder` (the code under `POST /api/sources/<key>/orders`; the source must run and have the `add` capability, so any freeform source works). The text goes into `state.json` (`resume_orders`, by session and a hash of the `resume` text and `inbox` ids, written at once) before anything can delete the report; the add then runs in `Service.resumeLoop`, never under `answerMu`, and `FinishResume` keeps only a done marker. `CaptureResume` runs from the answer path (before `Answer` releases a kept inbox), every inbox scan (`Refresh`, so answers written by someone else count), start-up (before `sweepKept`), `release`, and `ships.removeShipFiles` (`BeforeRemoveFiles`, for a ship that exits after answering everything). `sources.RequestError` says which way an add failed (`AddKind`: retryable, uncertain or final; a write that never went out is retryable, one that failed after the send is uncertain): a failure that changed nothing (source missing, not running or read-only, panel not found, plugin refusal) is retried on a source or config change and every 15 s, and logged once per message; a text the source refuses (empty, over 12,000 bytes, control characters) is logged and dropped; one that may have landed (timeout, plugin died, no order id) counts as done and records `resumed` with `uncertain: true`, never a second order. The answer path tries only the answered ship's order; the loop tries the rest. A success records `resumed` with `ship` set to the session, so `admiral outcomes --ship` lists it. Without `resume_source` nothing is captured and the log says so once. A report with no `resume`, an empty `inbox`, or an id with no item file adds nothing. The order then runs under autopilot if its panel is on, in the checkout of the ship that wrote the report, so a `resume` needs no repository URL. `CaptureResume` keeps that ship's directory and origin panel (`inbox.Origin`, from `Service.Origin`: a live ship, or the `kept_inboxes` record; `removeShipFiles` passes the session's own options to `BeforeRemoveFiles`), `state.Resume` holds them until the add, and `Service.ResumeAdd` (`Engine.BeginResume`) brackets each add: while it is in flight `Pass` skips the panel's unrecorded orders, and the order's id, directory and origin go to `autopilot.json` (`resumes`; `Store.prune` drops one once its order has been listed and is not any more). `Pass` launches a recorded order in the recorded directory if `Engine.Checkout` says it is still a checkout of the fleet (else a `skipped` record, "the checkout of the ship that wrote the report is gone"), under the origin panel's entry with the resume panel's skill, counted against the origin panel's `max_ships`; while the origin panel is paused, off or full the order waits and `Pass` goes on to the panel's other orders. Finished entries go once the session's report is gone.

Review items (`ReviewBody`) and findings items (`FindingsBody`) share the action path in `inboxState.ts` (`act`): the badge drops at the tap and returns on a refusal, which shows inline and keeps the choices. `findings.ts` is the pure decision state of a findings item (vitest tests it): Save makes a card `edited`, Approve after a Save keeps it, Reject drops it. A PR link must be `https:` (`prLink`). "Remove from inbox" on a review sends `discard {"forget":true}` (`FORGET_SUPPORTED` in `inboxState.ts` hides it when false).
  - Boarding a crew boat: `board(session, crew?)` and the `boarded` signal (`{ session, crew? }`, `ships.ts`) are the one way in (the sea and the inbox call it too); `window.__admiral.boarded` records `<session>/<crew>`. `Bridge.tsx` keys the view by ship and passes the crew name to `useBridgeTerminal`, which reconnects to `/ws/bridge/<session>/crew/<name>` (`bridgePath` in `crew.ts`). Typing, key buttons, pill and footer follow the boarded boat's status (`takesInput`), not the ship's. A crew link's reconnect probe asks whether the boat is still in the ship's `crew[]`, and a boat gone from a `ships` push sends the bridge back to the ship.
  - Crew boats and subagents on the sea: `.ship-slot` in `OpenWater.tsx` is a positioned `<div>` that owns the drag (`press`); the ship button, one button per rafted crew boat (up to three, `crewRaft` spots), the `+N crew` pill and the deck button are its siblings, and `press` ignores presses that start on the last three, so a tap on a boat boards it and never drags the ship. `crewSea.ts` holds the pure rules (plaque `<crew> needs you`, the raft and pill, `shouldChime` for ships and crew boats, the deck tip and label); `CrewBoat.tsx` draws the boat for the sea and the flotilla. Every new ship keeps `REACH` free on its left in `placeShip`, so its crew fits; ships already placed don't move. A crew boat that joins after the first push pops (`popping` in `ships.ts`).
- The `chat` config key (#119): `{fleet, model, effort}` for the AdmiralBot chat session. `internal/config` resolves it in `Parse`: a missing or unset `fleet` becomes the first fleet with a Claude dock (else the first fleet), `model` defaults to `sonnet`, and a `fleet` naming a gone fleet never fails the load. `config.View` carries it as `chat`, and `effort` is `""` for the harness default. `PUT /api/chat` (`internal/launchorders`) takes `{fleet, model, effort}`, answers 400 for a model outside `sonnet|opus|haiku` or an effort outside `""|low|medium|high`, and writes through `config.SetChat`: `fleet` and `model` always, `effort` only when set. `SetChat` itself refuses a model or effort outside the lists and a fleet the file doesn't hold (`Parse` would replace each with a default), leaving the file unchanged. An empty fleet with no fleets writes nothing. The UI edits it in `web/src/AppSettings.tsx`, the Settings modal opened from the header gear (General: Sound; Chat). It is not `SettingsDialog.tsx`, which edits a source's settings.
- `packaging/`: the Homebrew formula, the curl install script and the notices generator. `make release` builds the tarball.
- `e2e/`: server tests that run the real binary.

## The setup terminal

Tapping the "Set up a fleet" marina or the header's fleet count opens `admiral setup` in a terminal over open water. It runs in the tmux session `_setup` on Admiral's socket (never in `ships`, never a ship) and uses the bridge's terminal, so several browsers can share it and a dropped connection rejoins. `POST /api/setup` starts it or leaves the running one alone; `GET /api/setup` says whether it runs. The bridge accepts `/ws/bridge/_setup` while the session exists. The terminal closes when the session ends, whether setup wrote the file or not, and the page then re-reads `/api/config`; a change to `config.json` alone never closes it.

## The chat session

AdmiralBot (ADR 0018, 0019) is one Claude Code session in the tmux session `_chat` on Admiral's socket. `internal/chat` serves it, `launcher.StartChat` (`internal/launcher/chat.go`) starts it and `sessionhost.ChatName` names it. It is never a ship: `Session.IsShip` refuses `_setup` and `_chat` by name, so setting `@admiral-name` on it changes nothing, and `admiral attach` refuses it.

- **Routes** (all behind the same auth as the rest; none skips the LAN token):
  - `GET /api/chat/session` answers `{"running","state","messages","questions","error"?}`. `state` is `idle`, `working` or `waiting`, and `""` while not running; it is `waiting` whenever a chat question is unanswered, whatever the hooks say. A message is `{"id","role","text","at"}`, `role` `user` or `assistant`. `questions` is described under "Chat questions". `error` also carries why the last start was refused (the 409 below) while the chat is not running.
  - `POST /api/chat/start` starts the session or leaves a running one alone, and answers `{"running":true}`. Admiral doesn't start it at server start. 409 when the chat fleet has no Claude dock or there are no fleets, or when the dock's `args` hold a flag that skips or changes permissions (`--dangerously-skip-permissions`, `--allow-dangerously-skip-permissions`, `--permission-mode`, `--setting-sources`, `--tools`, also as `--flag=value`); the error names the flag.
  - `POST /api/chat/messages` `{"text"}` pastes the text and presses Enter. 400 for empty text, or over 16 KiB. 409 when the chat isn't running or no transcript has been recorded yet. Control characters other than LF and tab are dropped (an escape could end the bracketed paste early) and CRLF becomes LF.
  - `POST /api/chat/questions/{id}/answer` takes the inbox's question answer body (`inbox.QuestionRequest`) and writes the answer file. 404 for an unknown id, 409 when it is already answered, 400 for an invalid answer. It writes no outcome record and adds no resume order.
  - `POST /api/chat/new` resets the conversation, and withdraws every chat question: `/clear` and Enter when the running session's model, effort and fleet match the config, else it ends the session and starts a new one. 409 when not running. A running session without a recorded transcript, whose settings match, is also 409: `/clear` would land in the trust dialog.
  - The WebSocket `chat` message has the fields of the session, beside `type`. It is sent on connect and, within about a second, whenever the messages, state, running or error change, to every browser (`SendOnce`/`BroadcastOnce`, key `chat`). The `chat` message belongs to the main socket, not the bridge.
- **Start.** The working directory is `$ADMIRAL_HOME/chat/`. argv is the chat fleet's Claude dock (`Resolve()`, `dock.Args`), then `--model <model>`, `--effort <effort>` when set (each its own argument), then the fence (`--permission-mode dontAsk --setting-sources project --tools Bash,Skill,Read --append-system-prompt <one paragraph>`, ADR 0020), then `--settings $ADMIRAL_HOME/harness/chat-claude-settings.json`. Before the process starts, `launcher.WriteChatSkill` writes `chat/.claude/skills/admiralbot/SKILL.md` (embedded from `internal/launcher/admiralbot/SKILL.md`) through an `os.Root`, a temp file and a rename. The session is made like a ship's (placeholder, options, `set-environment`, `respawn-pane` through a tmux client with the chat's `PATH`) with no `remain-on-exit`, so it ends with Claude and the next start makes a new one. The environment is `shipEnv` without any `ADMIRAL_*` but `ADMIRAL_HOME`, and `set-environment -r` hides every `ADMIRAL_*` the tmux server holds (its global environment) except `ADMIRAL_HOME`; the chat's `ADMIRAL_PORT` is the port Admiral listens on (`Launcher.Port`), and the launcher unsets it for ships. Session options `@admiral-chat-model`, `-effort` and `-fleet` record how it started. A change of the `chat` key applies at the next start and at New chat.
- **Hooks.** The chat bundle registers `SessionStart` (no matcher), `UserPromptSubmit`, `PreToolUse` `AskUserQuestion`, `PostToolUse`, `Notification` (`permission_prompt`, `elicitation_dialog`) and `Stop`. Not `idle_prompt`, `SubagentStart`/`SubagentStop` or the guards. `admiral hook SessionStart` writes the pane option `@admiral-transcript` = `<unix ns> <source> <transcript_path>` and no state. The hook's ship states map to the chat's: `working` is `working`, `needs_you` with reason `stop` is `idle`, any other `needs_you` is `waiting`, and none yet is `idle`.
- **The conversation.** The host's shared format doesn't carry the chat's options, so the service reads them itself with one `display-message` on the chat's pane (at most every 200 ms, and on every host event for `_chat`), plus a 500 ms tick. A new pane id (a restarted chat, or the first one an Admiral sees) starts with nothing; the transcript is read from its start. A new `@admiral-transcript` path starts a new conversation. The same path with source `clear` empties it and serves only what is written after. Until a transcript is recorded, the session carries `error: "Open the terminal to finish starting the chat"`; a recorded path Admiral refuses to read gives `error: "Admiral can't read this chat's transcript"`. The tick does nothing while no browser is connected, and the tmux read runs outside the service lock.
- **Transcript rules** (`internal/chat/transcript.go`). The path is untrusted. The Claude config dir is `config.IdentityDir("claude", dock.Env)` of the fleet the session started with; the file must be absolute, end in `.jsonl`, lie under the real `<config dir>/projects/`, and be a regular file with no symlink in it or below `projects/`. A symlinked config dir or `projects/` is fine. A line is skipped when it isn't JSON, is over 1 MiB, has no `uuid`, is `isMeta`, `isSidechain`, `isCompactSummary` or `isVisibleInTranscriptOnly` (the summary Claude writes after compaction), isn't a `user` or `assistant` line, or (user) starts with `<command-name>` or `<local-command-`. A user line's text is its string content or its `text` blocks (a `tool_result` has none); an assistant line's is its `text` blocks, so `thinking` and `tool_use` give nothing. `id` is the line's `uuid`. The service reads from its last offset, whole lines only, and serves the last 200 messages within about 256 KiB; a message is cut at 64 KiB, and a first read of a file over 8 MiB starts near its end.
- **Open terminal.** The bridge accepts `/ws/bridge/_chat` while the session exists, as it does `_setup` (`ownSessions` in `internal/bridge/setup.go`; the stand-in is called "Chat session"), and a keystroke there changes no state. It ends with the session through `ShipsChanged`.
- **The fence** (ADR 0020). `chat-claude-settings.json` holds `permissions.allow` of exactly `Bash(admiral ships *)`, `Bash(admiral outcomes *)`, `Bash(admiral inbox *)`, `Bash(admiral orders *)`, `Bash(admiral chat ask *)` and `Skill(admiralbot)`, `permissions.deny` of `Edit`, `Write` and `NotebookEdit`, and `blockReadsOutsideWorkingDirectories`. Ships' bundles and command lines are unchanged. The skill's only write is `admiral orders add`.
- **Chat questions** (`internal/chat/questions.go`, ADR 0020). `admiral chat ask` writes `$ADMIRAL_HOME/chat/questions/<id>.json` (#112's question item) and waits for `<id>.answer.json`. The service reads the directory through an `os.Root` (no links, `O_NONBLOCK`, at most 1 MiB, the id rule, `inbox.ReadItem` with kind `question` only; a file that fails is skipped), on the chat's 500 ms tick and at most every 100 ms for requests, whether or not the chat runs. `questions` holds the newest 20, oldest first, each the inbox's question item with `session` `"_chat"` and `answer`: the answer file's content (read just as defensively; a link, an oversized or non-JSON file is no answer) or `null`. The answer route builds the file with `inbox.BuildQuestionAnswer` and writes it with `inbox.WriteAnswerFile` under the chat's own mutex. Chat questions never touch `inbox/`, `GET /api/inbox` or the `inbox` message. New chat, and a fresh session started after the old one ended, remove every file in `chat/questions/`; a waiting `admiral chat ask` then exits 4.
- **Kept out.** No ships, outcomes, autopilot, caps or resources; no crew rows (#154).
