# Codebase

This file holds the package map, API routes and ship statuses, idle memory figures and the setup terminal. Read it before changing the server, the launcher, ships or the setup terminal.

## Layout

- `designs/`: the clickable prototype, screenshots, design tokens, SVG assets and source design files. Start with `designs/README.md`.
- [Admiral MVP spec](https://github.com/jbuffin/admiral/issues/45): what the MVP does, as user stories, implementation decisions and testing decisions.
- `docs/architecture.md`: an early proposal for the build, superseded by the spec and the ADRs.
- `docs/adr/`: decisions.
- `GLOSSARY.md`: the words Admiral uses.
- `cmd/admiral/`, `internal/`: the Go server and CLI. `internal/auth` is access control, `internal/server` is HTTP and WebSocket, `internal/home` finds `$ADMIRAL_HOME`, `internal/config` loads, validates, watches and writes `$ADMIRAL_HOME/config.json`; it also reads the autopilot keys (see "Autopilot config" below). `internal/sessionhost` is the one tmux control-mode connection on `$ADMIRAL_HOME/tmux.sock` (it re-reads the sessions about every half second, and a global `alert-bell` hook stamps bells), `internal/launcher` creates ships (names, hook bundle in `$ADMIRAL_HOME/harness/`, command lines), `internal/state` is `$ADMIRAL_HOME/state.json` (ship positions, each dock's last directory, the autopilot panels paused, the kept inbox records, the resume orders), `internal/ships` serves `GET`/`POST /api/ships`, `PUT /api/ships/<session>/position`, `POST /api/ships/<session>/input-seen` (a browser sent input: clears needs you), `POST /api/ships/<session>/dismiss` (ends an anchored ship) and the WebSocket `ships` message. A ship carries `reason` (the validated code, `idle` for a ship no hook has spoken for) and `stop_since` (RFC 3339; the open stop's start from the log's track) only while its `status` is `needs_you`. A ship's `status` is `underway`, `needs_you`, `anchored` (with `exit_code` or `exit_signal`) or `sailing_off` (exit 0, session killed after 3 s); hooks, a Codex bell and the 10 s no-hook rule decide needs you (every hook runs `admiral hook <event>`, internal and unlisted in the usage text, which reads the harness's JSON on stdin and sets `@admiral-state` on `$TMUX_PANE`; it always exits 0. With `needs_you` it also sets `@admiral-reason` in the same tmux call, a code and never payload text: `permission:<tool>`, `question`, `notification:<type>`, `stop`, or `bell` from a Codex bell; `working` unsets it, and `sessionhost` polls it into `Session.Reason`. A tool name or type is kept only if it matches `^[A-Za-z0-9_.:-]{1,64}$`, and a notification's reason is written only if none is set, so `permission:Bash` survives either order of Claude's two events. `internal/cli/hook.go` holds the event→state and event→reason rules, and Claude's `Stop` writes nothing while `background_tasks` has a running `subagent` or `teammate`, so a running `shell` task doesn't hold a ship back. `admiral guard pretooluse` (`internal/cli/guard.go`, also unlisted in the usage text) is Claude's other PreToolUse hook, in the settings for `Bash` and for `^mcp__.*pull_request_review.*$`. Both handlers have `"timeout": 10` and `"onFailure": "block"`, because Claude Code lets a call through when a PreToolUse command hook times out or fails (`onFailure` needs Claude Code 2.1.295 or later). It does nothing unless `ADMIRAL_AUTOPILOT` is exactly `1`; then it parses a Bash command with `mvdan.cc/sh/v3/syntax` (`guard_shell.go`, which also looks through wrappers, `sh -c`, `eval` and heredocs fed to a shell). When the command doesn't parse as bash, it walks the statements parsed before the error, then parses the whole text as zsh, then applies a text rule (a line that mentions a review and an approve or request-changes spelling) to the whole line. A program word with an expansion that is followed by `pr … review` or `api` is checked as `gh`; any other unknown program, or a shell reading a pipe, gets the text rule on its own call or statement, computed once per span. Where it has no text for what it judges (a program word that is only an expansion, a `-c`, `eval` or heredoc script that is only an expansion, a shell reading a pipe or a file, a GraphQL `query` that is only an expansion), it also reads the whole line, once, for long spellings only (`review` with `approve`, `request_changes` or `request-changes`); short flags are not matched there, so `CMD='gh pr review 1 -a'; $CMD` is a known gap. `gh` calls other than `pr review` and `api` are allowed. It refuses, with exit 2 and the one reason line on stderr, a command or MCP call that would submit a review as APPROVE or REQUEST_CHANGES (`gh pr review`, `gh api` reviews calls and GraphQL), or a payload it can't read. A refusal writes one `guard_denied` line (`tool`, `rule`, no command text) under the home of `ADMIRAL_REPORT`, or else `ADMIRAL_HOME`; with no ship or home, or a failed write, it still refuses. Every ship also gets `ADMIRAL_SHIP` (its session name), `ADMIRAL_REPORT` (`$ADMIRAL_HOME/reports/<session>.json`) and `ADMIRAL_INBOX` (`$ADMIRAL_HOME/inbox/<session>/`), which win over a fleet's env; Commodore ships on Claude also get `CLAUDE_CODE_AUTO_COMPACT_WINDOW=200000`, a fleet's `env` overrides it, and `1000000` turns it off; an autopilot launch also gets `ADMIRAL_AUTOPILOT=1` and `ADMIRAL_LOW_STAKES` (`advisor` or `never`), and a launch by hand has neither: Admiral owns both names, so it drops them from the fleet's env and runs `set-environment -r` for each on the session (`-r`, because the tmux server inherits Admiral's own environment, which may hold them; `-u` would fall back to it). A panel's autopilot args go after the fleet's dock args; Admiral removes any report and inbox a reused name left, then creates `reports/` and the inbox before the harness starts. Every start links `$ADMIRAL_HOME/bin/admiral` to the running binary and puts that directory first on a ship's `PATH`), and `HiddenOrders` lists the orders ships hide. `internal/outcomes` is the outcome log: one goroutine appends a JSON line per record (a ship's guard is a second appender, a separate process writing its own short `guard_denied` line) to `$ADMIRAL_HOME/outcomes/<YYYY-MM>.jsonl` (month of `ts`, UTC), never reads it back, queues 1024 records and drops the rest, and logs a failed write once until one succeeds. `ships.Service` feeds it: `launched` from `Service.LaunchOrder`, the one launch path for `serveLaunch` and autopilot, which holds the order's key while it runs so a second launch of that order gets 409, and sets `"autopilot"` from the request (and only then does `Run` follow the ship), `needs_you` and `underway` from the status each pass of `Run` sees against the last (`internal/ships/outcomes.go`; a stop whose reason changes is one stop, and a ship no hook has spoken for needs you with reason `idle`), `ended` when a pane is dead without `@admiral-ended` (also at start-up, before an exit-0 ship is killed) `dismissed` from Dismiss, and `answered` from the inbox (`internal/inbox`, ADR 0016). `ended` carries the parsed `$ADMIRAL_REPORT` (at most 1 MiB; `null` and a log line when invalid), and once it is written the writer sets the session option `@admiral-ended` and deletes the report and inbox of a ship that was dismissed or sailed off. Admiral kills such a ship whether or not the log works (`Service.killShip`), so one killed while its `ended` fails loses that `ended` and keeps its files; a dead pane still in tmux is retried at the next start, and Dismiss queues a failed `ended` once more before `dismissed`. The deletes go through an `os.Root` on `$ADMIRAL_HOME` and are skipped, keeping the files, while a launch is under way (a name is not known before `Launch` returns) or when a newer ship's track holds the name: none leaves the home, though a link swapped in inside the home can still send one elsewhere within it. `launcher.ShipFiles` builds the report and inbox paths for both the environment and the cleanup. The needs-you tally survives a restart in the session options `@admiral-needs-count`, `@admiral-needs-s` and `@admiral-stop-since`. A session removed with no dead pane gets no `ended`. `admiral outcomes` (`internal/cli/outcomes.go`) prints the log: it reads the month files directly, line by line, and filters on `ts` and `ship`, with `--ship` mapped through `launcher.Slug`.
- Autopilot config (`internal/config/autopilot.go`, #114). Top-level `autopilot.max_ships` (positive integer, default 3) caps every ship underway or needing you, hand-launched ones included: when that many are running, autopilot launches nothing. `sources.<key>.autopilot.<panel id>` holds `enabled` (default false), `fleet`, `harness` (`claude` only; anything else fails with "autopilot runs on Claude Code only for now") and `skill` (`{"kind": "commodore"}`, `{"kind": "skill", "name": …}` or `{"kind": "none"}`), all three required, plus `args` (default `[]`), `max_ships` (positive integer, default 1) and `low_stakes` (`advisor`, the default, or `never`). Unknown keys are errors. The fleet must exist and have a `claude` dock; the check runs after the fleets parse, and `SetSources` re-parses the whole file, so it holds for UI writes too. Removing such a fleet or its claude dock through `admiral fleet` or setup now fails validation. Config can't know the panel ids (they come from the running plugin), so a misspelled panel key does nothing. Top-level `autopilot.resume_source` is `{"source": "<source key>", "panel": "<panel id>"}` and optional (`config.Config.ResumeSource`, nil without it); config checks the shape only, since the source and panel are looked up when an order is added, and deleting the source in the UI must keep working. See "Resume orders". `SourcesJSON` writes each source's `autopilot` object back as it was read, so a UI save adds no defaults to the file. `launcher.Request` carries `Autopilot`, `LowStakes`, `ExtraArgs` and `Panel` (`json:"-"`, so `POST /api/ships` can't set them); `Launch` refuses an autopilot request whose `LowStakes` is not `advisor` or `never`.
- Autopilot engine (`internal/autopilot`, #114). `main.go` runs one pass goroutine, poked without blocking by `ships.Service.OnChange`, `Supervisor.OnChange` (chained onto the existing closures), a config change and the pause route (through `Supervisor.changed`), and by a one-minute ticker. A pass counts the ships whose status is `underway` or `needs_you` (hand launches too) against `autopilot.max_ships` and, by their `@admiral-panel` option (`Ship.Panel`), against each panel's `max_ships`. It takes the eligible panels (enabled, not paused) in sidebar order, `sources.SortPanels` over the config's source order, and in each launches the first visible order not in the launched set, through `ships.Service.LaunchOrder`, until a cap is full. A source in `error`, `auth` or restarting still offers its last-known orders. The directory is the one the launch dialog pre-selects from the order's `repo` hint or a repository URL in its text (`launchorders.Service.Dir`, sharing the dialog's ranking, ADR 0009 rules 1 and 2); no match writes a `skipped` outcome record and leaves the order visible. A launch by autopilot moves the dock's last directory, as a hand launch does. The launched set and the failure state live in `$ADMIRAL_HOME/autopilot.json` (`autopilot.Store`, written at once, atomically, `"version": 1`): a pair is added when an order launches, by autopilot or by hand (`sources.Service.OnLaunched`), and dropped once the source's raw listing no longer holds the order, only for a source that is `ok` and whose every panel has had a successful `orders.list` since the source started (`Panel.Listed`, set in `runner.pullOrders`, cleared when the runner starts), so a panel whose listing failed never loses its pairs. Every launch from a source joins the set, from a panel on autopilot or not. A launch that fails writes `launch_failed` and backs the order off 10 minutes, then 1 hour; the third failure stops autopilot trying and sets `hot` on the order in the sources view; `Engine.OnHot` pushes the view when an order turns hot or cools (`sources.Service.Hot` overlays `Order.Hot`; the engine decides from its own state, never from the plugin's `hot`). A 409, and a 503 `ships are not known yet`, are not failures: the order is tried again at the next pass. `ships.Service.LaunchOrder` also holds an order's key until the host lists its ship (at most 30 s; only `LaunchOrder` consults the hold, not `HiddenOrders`), and `ships.Service.Pending` lists those unlisted ships, which `main.go` adds to the ships the engine and the sources view see so they count toward the caps, and answers 503 while the host is not ready or has lost tmux, because the ship list is then empty. Pause is runtime state in `state.json` (`state.Store.Paused`, keyed by source key and panel id; it outlives a removed source): `PUT /api/sources/<key>/panels/<panel>/autopilot` with `{"paused": bool}` answers 404 for an unknown source or a panel with no entry. `GET /api/sources` carries `autopilot: {enabled, paused, max_ships, resources, waiting_for}` on each panel (`null` without an entry) and `GET /api/config` carries `autopilot: {max_ships}`.
- Locked resources (#118). Config: top-level `resources` (`config.Resource{Capacity, Check}`, `capacity` an integer >= 1 defaulting to 1, `check` a non-empty argv of non-empty strings, names `^[A-Za-z0-9_.-]{1,64}$`) and `sources.<key>.autopilot.<panel>.resources` (`PanelAutopilot.Resources`, nil when none). `checkPanelResources` runs after the whole file parses, beside `checkAutopilotFleets`, so a panel naming an undefined resource fails every load and write. `internal/resources.Set` answers which units are held and by whom: a ship holds one unit of each name in its `@admiral-resources` option (`Ship.Resources`, `json:"-"`; set from `launcher.Request.Resources` only on an autopilot launch) while `underway` or `needs_you`, as do locks (`Set.Lock`, non-blocking, no check needed, for `admiral lock` to call) and reservations. A name no longer in the config holds nothing. `Set.Ships` is `allShips` in `main.go` (List + Pending), so a just-launched ship counts before the host lists it (`ships.Pending` carries the request's resources). `Set.Reserve` checks and reserves all-or-nothing under the Set's mutex and answers `Wait{Name, Why}` with `busy`, `missing` or `pending`. The engine reserves in `Pass` after the `Dir` check and drops the reservation as soon as `Launch` returns, on every outcome. Checks run as an argv with no shell, in their own process group, killed as a group at 10 s (`missing`); `Set.Run` runs them all at once, on `Refresh` (a config change) and every 15 s, never two at once for one resource, and a resource is `pending` until its first check ends (`none` when it has no check). A changed check state or a released lock calls `Options.OnChange` (`main.go` pushes the `resources` message and pokes the engine). A dropped reservation calls `Options.OnDrop` instead, which only pushes: the engine drops its own reservations inside a pass, and a poke there would make a refused launch (a 503 or a 409) start the next pass at once. All three close the channel `Set.Changed` returns, and so does `Set.Wake`, which `main.go` calls on every ship change and config change (a ship leaving `underway` frees a unit with no event of the Set's own). An order whose gate fails waits: the engine writes one `resource_wait` record when the wait starts, once every named check has finished at least once, and goes on to the next panel. `Engine.WaitingFor(source, panel)` and `OnWait` feed the sources view (`sources.Service.WaitingFor`). `GET /api/resources` and the WebSocket `resources` message (`resources.Service`, sent on connect and on change through `BroadcastOnce`) carry `{"resources": [{name, capacity, in_use, holders: [{kind: "ship", session} | {kind: "lock", label}], check}]}` sorted by name, with no timestamps. `POST /api/resources/<name>/lock` (`internal/lockroute`, for `admiral lock`) holds a unit as an open request: no body, query `label` (cleaned to printable, at most 64 characters) and `wait=1`; it answers `200` with one flushed line `{"held":true}`, then stays open and releases the unit when the request context ends or the server shuts down (`srv.RegisterOnShutdown` closes `Route.Stopping`; the background context is cancelled only after the drain, which waits on this handler). Without `wait` a busy resource answers `409`, an unknown one `404`; with `wait` the handler waits on `Set.Changed()` (fetched before each `Lock` try) and a 15 s timer (a pending ship that expires frees a unit with no wake) and a client that leaves while waiting holds nothing. A peer that is not loopback gets `403`, token or not (`auth.IsLoopbackPeer`, after the Host and Origin checks; a LAN peer with no token gets the middleware's `401` before it reaches the route); the handler reads the body first, because Go cancels the context on a hang-up only once it has. `OnTake` pushes the `resources` message, since `Set.Lock` doesn't announce a take. `admiral lock` (`internal/cli/lock.go`) splits its arguments at the first `--` before parsing flags, probes the server as `ships` does, sends `admiral lock (pid <its own>): <argv[0] base>` and runs the command after the `held` line; it returns a `cli.ExitError` (code, optional message) for 75, 127 and the command's status, which `main.go` maps; after `held` it keeps reading the response and, if that ends while the command runs, prints `lost the lock` to stderr and leaves the command running; it forwards only SIGTERM (it catches and ignores SIGINT, SIGHUP and SIGQUIT, which the terminal sends to the command). The `-h` scan in `main.go` stops at `--`.
- `internal/inbox` is the Needs You inbox (ADR 0016). It reads the item files in `$ADMIRAL_HOME/inbox/<session>/` through an `os.Root` (a link, a dot file, a name that is not `<id>.json` with `<id>` matching `^[A-Za-z0-9][A-Za-z0-9_-]{0,63}$`, a file over 1 MiB, or an invalid item is skipped; so is an item with `<id>.answer.json` beside it), watches `$ADMIRAL_HOME`, `inbox/` and each ship's directory with fsnotify (100 ms settle, watches re-synced before each rescan), and serves `GET /api/inbox` (`{"items":[...]}`, oldest `created` first; each item is the file's fields plus `session`, and `name` and `harness` when the ship is known) and the WebSocket `inbox` message (`{"type":"inbox","items":[...]}`). `POST /api/inbox/<session>/<id>/answer` takes a question's answers (`{"answers":{"<qid>":{"choice","other"}},"note"}`): 400 for an invalid answer, 404 for an unknown item, 409 for one already answered. `Service.Answer` is the shared writer: `build` gets the item and returns the answer file and the outcome records (no network I/O, since it runs under one lock that also re-reads the item and checks for an answer), then the file is written to a temp file and published with `os.Root.Link` (`fs.ErrExist` is a 409, so an answer is never replaced). A question's record is `answered` with `item` and `kind`.
  - `POST /api/inbox/<session>/<id>/submit` (`{"event":"COMMENT"|"APPROVE"|"REQUEST_CHANGES","edited":bool}`) and `.../discard` (`{}`) act on a review item through `gh` (`internal/inbox/review.go`). `gh` is found on Admiral's own `PATH` and run with `exec.CommandContext`, an argument list, a 30 s timeout and no retry. Its environment is Admiral's overlaid with the env of the ship's dock (`fleets[].harnesses.<name>.env`, from the ship's `fleet` and `harness` read at action time from the current config), plus `GH_PROMPT_DISABLED=1` and `GH_NO_UPDATE_NOTIFIER=1`; a ship with no dock runs `gh` in Admiral's own environment, and a failure says so. The host, owner, repo and PR number come only from the item's `pr_url` (`https://<host>/<owner>/<repo>/pull/<n>`, nothing else; always `--hostname <host>`) and `review_id` must be a positive whole number; otherwise 400 and `gh` is not run. Submit reads the review (`GET repos/<o>/<r>/pulls/<n>/reviews/<id>`) and posts its current body, or the item's `summary` when that is empty, with the event (`POST .../events`, JSON on stdin through `--input -`, so item text is never an argument). Discard is `DELETE` of the same endpoint, or, for a review whose `pr_url` or `review_id` is invalid, no `gh` call at all: the answer is `{"action":"discarded"}` and `review_discarded` carries `invalid_target: true`; the 200 response also says `"invalid_target": true`. A 404, a 422 whose parsed `message` or `errors` name "pending" (not `documentation_url`), or on Submit a review whose `state` is not `PENDING` (no POST), means the review is gone: the answer is `{"action":"gone"}`, `review_discarded` is recorded with `external: true`, and the response is 200. After a 404, though, Admiral also reads the pull request (`GET repos/<o>/<r>/pulls/<n>`), because a token that cannot see the repo gets 404 as well; if that fails too, it answers 502 and writes and records nothing, with the "token may not reach it" text only when the pull request answered 404, and gh's own text otherwise. Any other `gh` failure writes no answer and no record, and answers 502 (503 when `gh` is missing) with `{"error": ...}` carrying gh's message, the whole message cut at 4 KiB, before the note on where gh ran. A 200 carries `"action"` (`inbox.ActionSubmitted`, `ActionDiscarded`, `ActionGone`). Only one action runs on an item at a time (409 `ErrBusy`). `.../discard` with `{"forget": true}` (Remove from inbox, for a review that fails forever) runs no `gh`: it writes `{"action":"discarded"}`, records `review_discarded` with `unreachable: true` only, and answers 200 with `"forgotten": true`, so the UI can say nothing changed on GitHub. It is allowed on any review item, and Submit has no such option.
  - `POST /api/inbox/<session>/<id>/findings` (`{"cards":[{"id","decision":"approved"|"edited"|"rejected","proposal":{"kind":"diff"|"reply","content"}}]}`) needs a decision for every card id of the item, once each, and a proposal on an edited card only (400 otherwise); an item with no cards takes `{"cards":[]}`. It writes the answer's `cards` map and one record per card, and posts nothing to GitHub.
  - Outcome events (fields besides `item` and `kind`): `answered` (question), `review_submitted` (`review_event`, `edited`; a log line's `event` is the record name, so the review's event cannot be called `event`), `review_discarded` (`external: true` when gone, `invalid_target: true` when Admiral ran nothing for an invalid target, `unreachable: true` for Remove from inbox), `resumed` (see "Resume orders"; `ship` is the session, with `source`, `panel` and `order`, or `uncertain: true` and no `order`), `card_approved`, `card_edited` and `card_rejected` (`card`). A review or findings answer writes no `answered`.
  - **Kept inbox.** An exit-0 ship's session is killed at sail-off, and its report and inbox are removed once its `ended` is written (ADR 0015), unless its inbox still holds an item with no answer (`inbox.Unanswered`). Then `ships.killShip` first copies the session's `name`, `fleet`, `fleet_name`, `fleet_color` and `harness` into `state.json` (`kept_inboxes`, by session; `state.KeepInbox`, written at once) and `removeShipFiles` skips a session with a record. The record names the item's ship for the inbox reader (`Ship`) and gives `gh` its dock (`Dock`), and `launcher.pickName` never draws a name with a record (`Launcher.Kept`), because a launch clears the inbox of the name it takes. When an answer leaves no item unanswered, `Service.release` removes the files (`launcher.RemoveShipFiles`, through an `os.Root`) and drops the record; `Service.Run` does the same at start-up for records whose items were answered meanwhile. Dismiss never keeps (and so adds no resume order for an item it leaves unanswered). A directory with no record and no session is left alone, as before.
  - **Resume orders** (`internal/inbox/resume.go`, ADR 0016). When every id in a ship's report `inbox` has an item file and an answer file, the report's `resume` text becomes an order in the panel `autopilot.resume_source` names, through `sources.Service.AddOrder` (the code under `POST /api/sources/<key>/orders`; the source must run and have the `add` capability, so any freeform source works). The text goes into `state.json` (`resume_orders`, by session and a hash of the `resume` text and `inbox` ids, written at once) before anything can delete the report; the add then runs in `Service.resumeLoop`, never under `answerMu`, and `FinishResume` keeps only a done marker. `CaptureResume` runs from the answer path (before `Answer` releases a kept inbox), every inbox scan (`Refresh`, so answers written by someone else count), start-up (before `sweepKept`), `release`, and `ships.removeShipFiles` (`BeforeRemoveFiles`, for a ship that exits after answering everything). `sources.RequestError` says which way an add failed (`AddKind`: retryable, uncertain or final; a write that never went out is retryable, one that failed after the send is uncertain): a failure that changed nothing (source missing, not running or read-only, panel not found, plugin refusal) is retried on a source or config change and every 15 s, and logged once per message; a text the source refuses (empty, over 12,000 bytes, control characters) is logged and dropped; one that may have landed (timeout, plugin died, no order id) counts as done and records `resumed` with `uncertain: true`, never a second order. The answer path tries only the answered ship's order; the loop tries the rest. A success records `resumed` with `ship` set to the session, so `admiral outcomes --ship` lists it. Without `resume_source` nothing is captured and the log says so once. A report with no `resume`, an empty `inbox`, or an id with no item file adds nothing. The order then runs under autopilot if its panel is on; the engine launches only when it finds a repository URL (or `repo` hint) in the text, so a `resume` should carry the PR or repo URL, or the order is `skipped` and waits in the panel. Finished entries go once the session's report is gone.
- `web/`: the Preact UI. `web/embed.go` embeds the built `web/dist` into the binary.
  - The inbox UI: `web/src/inbox.ts` is the pure queue (served items and needs-you stops merged oldest first, the cursor, the 5 s hold after an action; vitest tests it), `inboxState.ts` wires it to the signals, the `inbox` WebSocket message, the clock and the answer request, and `InboxPanel.tsx` draws the header button, the wide layout's drawer (a flex child of `.harbor`; the bridge ends at `main`'s right edge beside it, and Orders collapses while it is open without changing the stored state) and the narrow layout's modal sheet. Item files are untrusted: render them as text and link only what `safeHref` allows. Review items (`ReviewBody`) and findings items (`FindingsBody`) share the action path in `inboxState.ts` (`act`): the badge drops at the tap and returns on a refusal, which shows inline and keeps the choices. `findings.ts` is the pure decision state of a findings item (vitest tests it): Save makes a card `edited`, Approve after a Save keeps it, Reject drops it. A PR link must be `https:` (`prLink`). "Remove from inbox" on a review sends `discard {"forget":true}` (`FORGET_SUPPORTED` in `inboxState.ts` hides it when false).
- `packaging/`: the Homebrew formula, the curl install script and the notices generator. `make release` builds the tarball.
- `e2e/`: server tests that run the real binary.

## Idle memory

One fleet, the Orders source, no ships, on an M-series Mac (macOS 27, Go 1.26, tmux 3.7c, python 3.14), resident set size from `ps -o rss`:

| process | RSS |
| --- | --- |
| `admiral` | about 16 MB |
| the freeform plugin (`python3 plugin.py`) | about 19 MB |
| Admiral's tmux server and its control client | about 4 MB and 5 MB |

Each ship adds its harness, and a pane in tmux.

## The setup terminal

Tapping the "Set up a fleet" marina or the header's fleet count opens `admiral setup` in a terminal over open water. It runs in the tmux session `_setup` on Admiral's socket (never in `ships`, never a ship) and uses the bridge's terminal, so several browsers can share it and a dropped connection rejoins. `POST /api/setup` starts it or leaves the running one alone; `GET /api/setup` says whether it runs. The bridge accepts `/ws/bridge/_setup` while the session exists. The terminal closes when the session ends, whether setup wrote the file or not, and the page then re-reads `/api/config`; a change to `config.json` alone never closes it.
