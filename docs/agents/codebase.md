# Codebase

This file holds the package map, API routes and ship statuses, idle memory figures, the setup terminal and the chat session. Read it before changing the server, the launcher, ships, the setup terminal or the chat session.

## Layout

- `designs/`: the clickable prototype, screenshots, design tokens, SVG assets and source design files. Start with `designs/README.md`.
- [Admiral MVP spec](https://github.com/jbuffin/admiral/issues/45): what the MVP does, as user stories, implementation decisions and testing decisions.
- `docs/architecture.md`: an early proposal for the build, superseded by the spec and the ADRs.
- `docs/adr/`: decisions.
- `GLOSSARY.md`: the words Admiral uses.
- `cmd/admiral/`, `internal/`: the Go server and CLI. `internal/auth` is access control, `internal/server` is HTTP and WebSocket, `internal/home` finds `$ADMIRAL_HOME`, `internal/crew` resolves crew members and their notes from layer directories it is handed (read-only; it reads no environment variable), `internal/launcher` resolves a launch's pinned members over the built-in (the installed Commodore's `crew/`, found by `skillindex.CommodoreDir`), fleet and repo layers and `internal/launchorders` lists the members a launch could pin, `internal/config` loads, validates, watches and writes `$ADMIRAL_HOME/config.json`; it also reads the top-level `max_ships` (see "Ship cap" below). `internal/sessionhost` is the only non-test package that runs tmux or builds its commands (`TestNoTmuxOutsideSessionhost` guards it: callers use its `Server` methods and `*Call` builders, and `admiral hook` its current-server runners) and holds the one tmux control-mode connection on `$ADMIRAL_HOME/tmux.sock` (it re-reads the sessions about every half second, and a global `alert-bell` hook stamps bells), `internal/launcher` creates ships (names, hook bundle in `$ADMIRAL_HOME/harness/`, command lines), `internal/chat` is the AdmiralBot chat session (see "The chat session" below), `internal/state` is `$ADMIRAL_HOME/state.json` (ship positions, each dock's last directory, the kept inbox records, the resume text), `internal/ships` serves `GET`/`POST /api/ships`, `PUT /api/ships/<session>/position`, `POST /api/ships/<session>/input-seen` (a browser sent input: clears needs you), `POST /api/ships/<session>/answer` and `.../crew/<name>/answer` (send `internal/keymap`'s keys for Allow once, Deny or a question's option, only while the pane's `@admiral-reason` matches the body's; Claude and Copilot panes are answered in place, Copilot's on `notification:permission_prompt`, `question` and `notification:elicitation_dialog` (its question form takes Down then Enter, not digits); `Service.Questions`, `shipconv.PendingQuestions`, gives the pending questions for the gate), `POST /api/ships/<session>/dismiss` (ends an anchored or a moored ship), `POST /api/ships/<session>/unfollow` (Don't follow reviews: ends a moored ship; any other ship is refused as Dismiss refuses it), `POST /api/ships/<session>/wake` (wakes a moored ship by hand: 201 with the ship, `ships.Service.Wake`; see below), `POST /api/moored/refresh` (kicks the moored poll, 202), `POST /api/ships/<session>/crew/<name>/close` (kills one crew boat's window, live or anchored, like `admiral crew close`; 404 `ship <session> not found` or `crew boat <name> not found`, the latter too when the window closed between the poll and the kill) and the WebSocket `ships` message. Each ship carries a `tail`, a line from its conversation: `internal/shipconv`'s `Tails` follows Claude ships' transcripts (re-reading one only when it changed) and `conversation.Tail` picks the line. `internal/shipconv` serves `GET /api/ships/<session>/conversation[?before=<id>]` and the WebSocket `conversation_open`, `conversation_close` and `conversation` messages (a Claude Code ship's conversation, `docs/api.md`); it finds the file from the ship's `@admiral-transcript` pane option, which the launcher sets at launch beside `--session-id`, and `internal/transcriptfs` holds the ADR 0019 path checks and the open it reads through. A ship carries `reason` (the validated code, `idle` for a ship no hook has spoken for) and `stop_since` (RFC 3339; the open stop's start from the log's track) only while its `status` is `needs_you`. A ship's `status` is `underway`, `needs_you`, `anchored` (with `exit_code` or `exit_signal`), `sailing_off` (exit 0, session killed after 3 s) or `moored` (a ship that exited 0 while its report listed a PR that GitHub confirms open on the fleet's built-in GitHub source's host and that routes to the ship's fleet: `internal/moor` reads the report (versions 1 and 2) and writes `$ADMIRAL_HOME/moored/<name>.json`, `internal/ships` ends the session, writes a `moored` outcome and lists the record, `internal/launcher` keeps the name reserved; `gh` is retried for `ADMIRAL_MOOR_RETRY`, 8 s by default, and a PR GitHub cannot confirm sails the ship off; the check runs for exit-0 ships found at startup too). `ships.Service.RunMoored` polls every moored ship's PRs (`moorpoll.go`): one batched `gh api graphql` per fleet client (`github.Client.PullRequests`, one aliased `repository{pullRequest}` per PR, parsed from `data` even when gh exits 1 for a `NOT_FOUND`) every `ADMIRAL_MOOR_POLL` (2 min) and on each kick; a kick during a poll coalesces. A PR GitHub answers `NOT_FOUND` for counts as closed; a failed call keeps the last chips, marks the ship `stale` and never ends mooring. The ship sails off (`endMoored`: the record is removed with `moor.Remove`, the cache and name are freed, one `unmoored` written; the first ending wins a race) when every PR is merged or closed, or on Dismiss or Don't follow reviews; there is no idle timeout and a merge wakes nothing. A wake (`internal/ships/wake.go`) recreates the moored ship's session under its own name and session: `Launcher.Launch` takes `Request.Name` and `Request.Session` (refusing 409 while that session is live, under `l.mu`, so no launch takes the name between) and `Request.Prompt` (the harness prompt verbatim, so the report's `resume` text is not prefixed with a skill again), and sets the session option `@admiral-round` from `Request.Round`. The wake goes through `admit` and `LaunchOrder` with the record's `source`, `order`, `url`, `panel`, `title` and `resources`, so the order stays hidden and the claim holds, but `LaunchOrder` skips the order read and its own-ship refusal when `Round` is set. The round count is `Record.Round + 1`; `moor()` writes the live `round` option and `resources` back into the record, so a ship that moors again keeps both. The report's `resume` text is kept only when it is `/skill resume <run>` or `$skill resume <run>` (`moor.ValidResume`), since it is the prompt. `Request.Before` runs under the launcher's lock just before the session is made: it re-checks that the record is still the one the wake read (a Dismiss, Don't follow reviews or merged PR that ended the mooring first wins and the wake answers 409) and writes the feedback file into the validated checkout; from then on `endMoored` loses to the wake (`Service.committed`). `woken` is written by `launched` for a round. The record is removed once the woken session exists. `Service.Wake` (by hand: no autopilot, counted toward the cap, never blocked by it, the engineer's text after the `resume` text) and `Service.FeedbackRound` (autopilot, refused at the cap or on an unguarded harness; the feedback text goes to `<checkout>/.admiral/untrusted/feedback-<N>.md` through `moor.WriteFeedback`, never into the prompt, argv, options or environment) are the two entries; neither carries crew pins. A wake writes `woken` (`round`, `by` `hand` or `feedback`, `pr` for a round) instead of `launched`, and the round's end writes `round` (`round`, `end`: `moored` beside `moored`, `sailed`, or `anchored`). `unmoored` carries `reason` (`merged`, `closed`, `prs_done`, `dismissed`, `unfollowed`) and `prs`, each `{url, state}` as last polled; hooks, a Codex bell and the 10 s no-hook rule decide needs you (every hook runs `admiral hook <event>`, internal and unlisted in the usage text, which reads the harness's JSON on stdin and sets `@admiral-state` on `$TMUX_PANE`; it always exits 0. With `needs_you` it also sets `@admiral-reason` in the same tmux call, a code and never payload text: `permission:<tool>`, `question`, `notification:<type>`, `stop`, or `bell` from a Codex bell; `working` unsets it, and `sessionhost` polls it into `Session.Reason`. A tool name or type is kept only if it matches `^[A-Za-z0-9_.:-]{1,64}$`, and a notification's reason is written only if none is set, so `permission:Bash` survives either order of Claude's two events. `internal/cli/hook.go` holds the event→state and event→reason rules, and Claude's `Stop` writes nothing while `background_tasks` has a running `subagent` or `teammate`, so a running `shell` task doesn't hold a ship back. A Monitor is the exception (#110): it also reports as a `shell` task, so a Monitor's `PostToolUse` keeps its `tool_response.taskId` in the pane option `@admiral-monitors`, and a `Stop` writes nothing while one of those ids is running (each `Stop` drops the ids no longer running). A persistent Monitor is not kept, since it has no timeout to wake the session. A crew pane's plain `Stop` writes `idle`, not `needs_you` (#189): it holds no lead's `Stop` and doesn't raise the ship. A lead's `Stop` held only by working crew sets `@admiral-crew-held`, which its next state write clears, and the last boat to go idle flags that lead with reason `stop`. `admiral guard pretooluse` (`internal/cli/guard.go`, also unlisted in the usage text) is Claude's other PreToolUse hook, in the settings for `Bash`, for `^mcp__.*pull_request_review.*$` and for `launcher.MergeToolMatcher`. All handlers have `"timeout": 10` and `"onFailure": "block"`, because Claude Code lets a call through when a PreToolUse command hook times out or fails (`onFailure` needs Claude Code 2.1.295 or later). It does nothing unless `ADMIRAL_AUTOPILOT` is exactly `1`; then it parses a Bash command with `mvdan.cc/sh/v3/syntax` (`guard_shell.go`, which also looks through wrappers, `sh -c`, `eval` and heredocs fed to a shell). When the command doesn't parse as bash, it walks the statements parsed before the error, then parses the whole text as zsh, then applies a text rule (a line that mentions a review and an approve or request-changes spelling) to the whole line. A program word with an expansion that is followed by `pr … review`, `pr … merge`, `pr … edit` or `api` is checked as `gh`; any other unknown program, or a shell reading a pipe, gets the text rule on its own call or statement, computed once per span. Where it has no text for what it judges (a program word that is only an expansion, a `-c`, `eval` or heredoc script that is only an expansion, a shell reading a pipe or a file, a GraphQL `query` that is only an expansion), it also reads the whole line, once, for long spellings only (`review` with `approve`, `request_changes` or `request-changes`); short flags are not matched there. A program word that is only an expansion (`$C`, `${=C}`, `"${C[@]}"`) that no rule names is refused as `shell_script`, because the command in it can't be seen, which is also how a long spelling split by quotes (`C="gh pr me""rge 5"; $C`) is caught. Other `gh` calls are allowed, `gh pr ready` among them, unless a rule below names them. It refuses, with exit 2 and the one reason line on stderr, a command or MCP call that would submit a review as APPROVE or REQUEST_CHANGES (`gh pr review`, `gh api` reviews calls and GraphQL), or a payload it can't read; those get the review reason. The merge rules (`guard_merge.go`, #120) refuse with a merge reason: every `gh pr merge` that can merge, `--auto` and `--admin` included (`gh_pr_merge`; #261, autopilot never merges); `gh api` writes to `pulls/<n>/merge` and `merges` (`gh_api_merge`); the GraphQL mutations `mergePullRequest`, `enablePullRequestAutoMerge`, `mergeBranch`, `enqueuePullRequest` and `dequeuePullRequest` (`graphql_merge`); writes to rulesets (repository and organization) and branch protection, through REST or GraphQL, which would lower the gate on a merge (`gh_api_gate_write`, `graphql_gate_write`); and any change of a pull request's base (`pr_base_change`: `gh pr edit -B` or `--base`, a REST write to `pulls/<n>` with a `base` field or an `--input` it can't read or that has one, GraphQL `updatePullRequest` with `baseRefName`, its input in a variable, or an expansion). A write is any `gh api` method but GET and HEAD, a method held in a variable, or gh's implicit POST (`-f`, `-F` or `--input` with no `-X`). API paths are percent-decoded and have empty and `.` segments dropped and `..` resolved before they are matched; one that climbs above its root is one expansion. An expansion in a path counts as any words there: a write is refused when the expansion ends the path after a prefix a merge or gate route extends (`repos/<o>/<r>`, `pulls/<n>`, anything under `branches`, `orgs/<o>`), or when the literal words after it end in `merge` or `merges` or hold `protection` or `rulesets`, so `gh api -X PATCH repos/o/r/issues/$N -f state=closed` and `-X PATCH repos/o/r/pulls/$N -f body=x` are allowed (only a PATCH may end a path in an expansion right after `pulls`, because the merge route is a PUT; a `base` field is refused as `pr_base_change`). MCP tools are matched by `launcher.MergeToolMatcher` (any `mcp__` tool with `merge` or `enqueue` in its name, in any case, spelled with character classes because Claude Code matchers are JavaScript regular expressions with no `(?i)`), and the guard refuses every tool the matcher selects except those whose last name segment starts with `list_`, `get_` or `search_` (`mcp_merge`); the guard compiles the same constant, so the two agree. Where the guard can't parse a command and falls back to text, the text rule also refuses text that mentions `pr … merge`, a `pulls/…merge` or `/merges` route, `rulesets`, `/protection`, or those mutation names (a merge in `eval "$C"`, `echo '…' | bash`; `pr` and `merge` count anywhere in the text, so `A='gh pr '; B='merge 1'; eval "$A$B"` is refused). A GraphQL `query` the guard can't read is refused (`graphql_merge`): a file or stdin that isn't shown on the line, a query that is only an expansion or has an expansion beside the word `mutation` or outside a value position, and an `operationName` beside an expanded query; pass values as GraphQL variables (`-f id="$ID"` with a literal query) instead. A script given as an expansion alone (`eval "$(cat m.sh)"`, `bash <<< "$X"`) is refused as `shell_script` unless the line itself shows a merge, which gets the merge rule. Rules that keep the guard from being routed around, with their own reason (`opaqueReason`): `gh alias` and `gh extension` (`gh_alias`, `gh_extension`); a first `gh` word that is not one of gh's built-in commands (`ghCommands`, including help topics; `gh co` is an alias and stays refused; `gh_unknown`); an expansion in the word after `gh pr` or `gh auth` (the first is refused with the merge rule, the second as `token_read`); the shell builtins `alias`, `unalias` and `hash name=path` / `hash -p`, and assignments to `aliases`, `functions`, `commands`, `BASH_ALIASES` and `BASH_CMDS` (`shell_alias`); and scripts the guard isn't shown. For `bash|sh|zsh FILE`, `source FILE` and `. FILE` the guard reads the file with the limits of any file it reads (a regular file of at most 1 MiB, from the call's cwd), checks it as a command line of its own, and uses that result; it refuses with `shell_script` only a file it can't read or parse, a script given by an expansion, a shell fed from a pipe, `-s` or `sh < f`, and the arguments of an `xargs` that runs `gh` or a shell. Stdin counts as shown only when the statement has exactly one input source and its text is literal: one heredoc or here-string with no expansion, or one `<` from a literal file, or no stdin redirect and a literal `echo`, `printf` or `cat` of a literal heredoc before the pipe (words with no escapes). A `<&`, a `<>` or a second redirect of fd 0 means stdin is not shown, because zsh reads several and bash the last. A GraphQL `query` on stdin, a write's `--input -` body and a `pulls/<n>` PATCH are refused otherwise. An `--input` body, from stdin or a file, is decoded as a JSON object before it is read, so a `\u` escape can't hide a name, an event or a key (this covers the review rules too); keys are read by their exact names, and a body with two keys that differ only in case, or that isn't a JSON object, is refused. Boolean flags are read as gh reads them, with `strconv.ParseBool` (`--disable-auto=0` is false), and a value that isn't a boolean is refused. The token is refused when it is read, not when it is named: an expansion of `GH_TOKEN`, `GITHUB_TOKEN` or the enterprise names in any form, `printenv` or a bare `env`, `gh auth token` or `status -t`, `git credential`, and `security find-generic-password` or `find-internet-password` with `-w` or `-g` (`token_read`); `grep -rn GITHUB_TOKEN .github` or a quoted heredoc that writes `${{ secrets.GITHUB_TOKEN }}` is allowed. `gh pr merge --disable-auto` without `--admin` is allowed: it merges nothing. Programs that run their arguments are looked through when they are `find` (`-exec`, `-execdir`, `-ok`, `-okdir`), `arch`, `script`, `flock`, `watch`, `unbuffer`, `doas`, `gtimeout`, `npx`, `xargs` and the usual wrappers; `git -c alias.x=!…` and `git config alias.x '!…'` are refused as `git_shell_alias`. A relative file is not read once the line has a `cd`, `pushd` or `popd` (the guard would read a different file from the one the call reads), `~/` is the home directory, and a shell is refused when `BASH_ENV`, `ENV` or `ZDOTDIR` is set on the line or when `--rcfile`, `--init-file` or `-i` comes beside a script. `gh auth status --show-token` is read as a boolean, and `git credential-*` helpers count as `git credential`. Known gaps. The guard is best effort, and the GitHub rules of the base branch are the gate: it narrows what a ship can do by accident or by habit, and it can't contain an agent that runs arbitrary programs with a token that can merge. A script run as `./FILE` runs unread (`bash FILE` is read, but the same file as a command is not). A program word built from a literal and an expansion (`g$Y`, `$D/gh $S`), zsh glob qualifiers that run code (`*(e:'…':)`), the `(e)` parameter flag and arithmetic that evaluates a subscript (`$((X))` with `X='a[$(…)]'`) run a command the guard reads as data. Sourcing nvm (`. ~/.nvm/nvm.sh`) is refused, because nvm defines aliases (`shell_alias`); set Node up outside the ship. The guard is best effort and reads only the text of a Bash call (D8): a merge through anything that is not a literal shell `gh` call is invisible to it, such as an interpreter (`python3 -c`), `make`, `curl` with a token from somewhere else, a nested agent, a `gh` shim earlier on `PATH`, or a replaced `$ADMIRAL_HOME/bin/admiral`. Files the guard reads (`--input`, `-F @file`) can change before gh reads them. Direct writes to the base, `git push`, REST `PUT contents`, `PATCH git/refs`, GraphQL `createCommitOnBranch` and `updateRef`, and the GitHub MCP file tools, are not hooked, and neither are writes to repository settings that raise access (`collaborators`, `PATCH repos/<o>/<r>`); the branch rules on GitHub are what stop them. The GitHub MCP `update_pull_request` tool with a `base` argument changes a base and is not hooked. Codex and Copilot ships have no guard, and autopilot refuses any harness but Claude for that reason; so does `admiral crew launch` for a caller with `ADMIRAL_AUTOPILOT=1`, whose `--arg` values must also fit the autopilot args allowlist (`launcher.AutopilotArgs`, `internal/launcher/autopilotargs.go`, a per-harness table of flags with their arity; codex's and copilot's tables are ready but unreachable until a guard probe is registered for them in `probes`), checked in `LaunchCrew` after the hook refusal and before the window is made. A refusal writes one `guard_denied` line (`tool`, `rule`, no command text) under the home of `ADMIRAL_REPORT`, or else `ADMIRAL_HOME`; with no ship or home, or a failed write, it still refuses. Every ship also gets `ADMIRAL_SHIP` (its session name), `ADMIRAL_REPORT` (`$ADMIRAL_HOME/reports/<session>.json`) and `ADMIRAL_INBOX` (`$ADMIRAL_HOME/inbox/<session>/`) and `ADMIRAL_CREW_DIR` (`$ADMIRAL_HOME/fleets/<fleet key>/crew/`, made 0700 when missing, kept across ships, and refused with a 500 when `fleets`, the key or `crew` is a link or not a directory), which win over a fleet's env; a launch with `crew` pins (Commodore only) also gets `ADMIRAL_RUN_CREW`, the per-ship run layer `$ADMIRAL_HOME/run-crew/<session>/` (0700) that Admiral fills with the pinned members' files, and a launch without pins has it unset even when a fleet's env sets it (`launcher/crewpins.go`; `RemoveShipFiles` removes it with the report and inbox); Commodore ships on Claude also get `CLAUDE_CODE_AUTO_COMPACT_WINDOW=200000`, a fleet's `env` overrides it, and `1000000` turns it off; an autopilot-mode launch also gets `ADMIRAL_AUTOPILOT=1` and `ADMIRAL_LOW_STAKES=advisor`, and a launch by hand has neither (nothing sets `ADMIRAL_AUTO_MERGE` any more, and it is still dropped from inherited env): Admiral owns these names, so it drops them from the fleet's env and runs `set-environment -r` for each on the session (`-r`, because the tmux server inherits Admiral's own environment, which may hold them; `-u` would fall back to it). A panel's autopilot args go after the fleet's dock args; Admiral removes any report and inbox a reused name left, then creates `reports/` and the inbox before the harness starts. Every start links `$ADMIRAL_HOME/bin/admiral` to the running binary and puts that directory first on a ship's `PATH`), and `HiddenOrders` lists the orders ships hide. `internal/outcomes` is the outcome log: one goroutine appends a JSON line per record (a ship's guard is a second appender, a separate process writing its own short `guard_denied` line) to `$ADMIRAL_HOME/outcomes/<YYYY-MM>.jsonl` (month of `ts`, UTC), queues 1024 records and drops the rest (`Enqueue` passes `outcomes.ErrDropped` to a dropped record's `onDone`), and logs a failed write once until one succeeds. Admiral only writes the log; `admiral outcomes` reads it back. A line over `outcomes.MaxLine` and any name that is not a regular file, and nothing else reads it. `ships.Service` feeds it: `launched` from `Service.LaunchOrder`, the one launch path for `serveLaunch` and autopilot, which holds the order's key while it runs so a second launch of that order gets 409, and sets `"autopilot"` from the request (and only then does `Run` follow the ship), `needs_you` and `underway` from the status each pass of `Run` sees against the last (`internal/ships/outcomes.go`; a stop whose reason changes is one stop, and a ship no hook has spoken for needs you with reason `idle`), `ended` when a pane is dead without `@admiral-ended` (also at start-up, before an exit-0 ship is killed) `dismissed` from Dismiss, `stopped` from Stop ship (a live ship gets an `ended` with signal `KILL` first, queued by `recordKilled` in `internal/ships/input.go`; an anchored one follows Dismiss's order), `answered` from the inbox (`internal/inbox`, ADR 0016). `ended` carries the parsed `$ADMIRAL_REPORT` (at most 1 MiB; `null` and a log line when invalid), and once it is written the writer sets the session option `@admiral-ended` and deletes the report and inbox of a ship that was dismissed or sailed off. Admiral kills such a ship whether or not the log works (`Service.killShip`), so one killed while its `ended` fails loses that `ended` and keeps its files; a dead pane still in tmux is retried at the next start, and Dismiss queues a failed `ended` once more before `dismissed`. The deletes go through an `os.Root` on `$ADMIRAL_HOME` and are skipped, keeping the files, while a launch is under way (a name is not known before `Launch` returns) or when a newer ship's track holds the name: none leaves the home, though a link swapped in inside the home can still send one elsewhere within it. `launcher.ShipFiles` builds the report and inbox paths for both the environment and the cleanup. The needs-you tally survives a restart in the session options `@admiral-needs-count`, `@admiral-needs-s` and `@admiral-stop-since`. A session removed with no dead pane gets no `ended`. `admiral outcomes` (`internal/cli/outcomes.go`) prints the log: it reads the month files directly, line by line, and filters on `ts` and `ship`, with `--ship` mapped through `launcher.Slug`.
- Campaigns (ADR 0027, #286). `internal/github` reads a GitHub issue's tree (`Client.Tree`); `internal/campaigns` folds it into statuses, modes and skills (`Build`) and parses issue references; `internal/campaigns/follow` keeps the followed campaigns in `$ADMIRAL_HOME/campaigns.json` (atomic write), rereads them (on a child ship's anchor or sail-off, on page open at most every 30 s, every 5 min, and a launch rereads first when the read is over a minute old; one read in flight per campaign, each under a 60 s deadline) and serves `GET`/`POST /api/campaigns`, `GET /api/campaigns/<id>`, `POST .../unfollow`, `PUT .../override`, `PUT .../work-repo` and `POST .../launch`. It is also the `ships.Orders` that answers orders of source `campaign` (`order_id` is `<campaign id>/<child issue URL>`, `panel` the campaign id) and hands every other order to the sources service; `main.go` gives it to `ships` and `launchorders`. The claim (`ships.ClaimKey`, `Service.Claims`) is keyed by the lower-cased issue URL, one entry per issue of every ship (`Ship.IssueURLs`: the `issues` list of a slice ship, else its `url`; the tmux option `issues` is comma-joined, and the moored record keeps the list): any listed ship, pending listing or launch in flight holding any of them refuses a second launch with 409, whatever launches it, and the GitHub views hide an order whose issue is held. `Service.Launch` is the one launch path behind `POST /api/ships` and the campaign route. `sources.Supervisor.GitHubClient(fleet, host)` hands out the fleet's built-in GitHub client. A source cannot take the key `campaign`. Order JSON from the GitHub source carries `sub_issues`.
- Clone on launch (ADR 0009, ADR 0010 amendment). `POST /api/ships` with `clone: true` and no `dir` runs `serveLaunch` -> `launcher.Clone` (`internal/launcher/clone.go`) before `admit` and outside `l.mu`: `repofinder.Hint` picks the repo (order `repo`, else the first URL in the text), `repofinder.CloneName` validates `host/owner/repo` against github.com and the fleet's GitHub source hosts, gh clones into a temporary `.admiral-clone-*` sibling in the clone root, and `renameNoReplace` moves it into `<clone_root>/<repo>` (it refuses an existing target). `repofinder.CloneRoot` expands `~` and defaults to the first search root; `repofinder.FleetRoots` adds the clone root to the roots every project and checkout lookup reads. The dirs route's `clone` field comes from `launcher.CloneTarget`. Statuses are in `docs/api.md`.
- Launching as a crew member: `Launcher.resolveMember` (`internal/launcher/member.go`) is the one path a ship (`Launch`, `Request.Member`) and a crew boat (`LaunchCrew`, `CrewRequest.Member`) take: it resolves over `CrewLayers` plus the memory and run layers, applies the harness lock, the model rule and the notes block (`crew.NotesBlock`, repo slug from `originSlug` via `git remote get-url origin`), and returns the harness, model args and prompt. `CheckMember` refuses what needs no disk, before any clone. Warnings go to `Launcher.Warn` (the CLI prints them, the server logs them). The launch form's "Launch as" select (`LaunchDialog.tsx`, `memberRun` in `launchForm.ts`) shows only with Just launch.

(1) Every row starts with a per-read random nonce (`rowFormat`, built for each command, 16 hex characters from `crypto/rand`), and `ownRows` drops any row that doesn't start with it before fields are counted: option text is written before the read and can't know it, so the lines a raw newline leaves, or a row an agent forged in its option, are dropped. (2) As a second layer `format` wraps `#{session_name}` and every `#{@admiral-*}` in `#{s/[\x01-\x1f\x7f]/ /:...}` (`unprintable`), so a control character reads as a space. tmux copies a value that is not valid UTF-8 through raw, whatever the substitution says, so this alone doesn't hold. (The class is a range of literal bytes: the colon in `[[:cntrl:]]` ends a format modifier.) (3) `parseCrew` reads a name only if it matches `launcher.CrewName`, and when two windows of one session claim a name it reads neither and `Host.poll` logs `admiral: crew boat <session>/<name>: two windows claim this name, so neither is listed` once. What the reader doesn't do: a row that a value still breaks (an invalid UTF-8 byte next to a control character) keeps its nonce and loses its field count, and `parseRows` then holds that session unreadable at its last state, so a boat can freeze its own ship's reads. `hook.go`'s crew read and the launcher's name checks read raw options of their own. A boat dropped by (3) leaves `crew[]`: its bridge closes, its needs-you leaves the ship's wire status, and no inbox item or closed push is made for it. A crew bridge also ends on tmux's `%window-close` / `%unlinked-window-close` for its window. `admiral attach` reads `sessionhost.ReadOnce` and targets `=<session>:^` or `=<session>:<window id>`.
- Crew boats and subagents on the wire (#152 u3). Words: `crew` is the crew boats that are teammates (crew windows), `subagents` the subagent marks; GLOSSARY.md's "crew boat" covers both. Every ship in `GET /api/ships` and the `ships` WebSocket message carries three fields, always present (`[]`, never `null`): `crew`, sorted by name, each `{"name","harness","dir","status","reason","role","launched","last_activity","conversation"}` (`role` is left out when none; `conversation` is always present and true for a Claude boat with a recorded transcript, whose path never leaves the server); `subagents`, each `{"id","type","start"}`, from the ship's own pane (a crew boat's own subagents stay off the wire until #153); and `crew_live`. A crew boat's `status` is the value `admiral crew list --json` calls `state`: `underway`, `needs_you` or `anchored`. `reason` only while `needs_you` (the crew pane's `@admiral-reason` if it is a safe token, else `unknown`); `last_activity` is the pane's `@admiral-activity`, omitted before its first hook. `crew_live` counts crew boats with a live pane (`underway` or `needs_you`), so the UI can warn before Dismiss; it is not the hook's "working", which means only `@admiral-state` `working`. The data comes from the rows `Host.poll` already reads (`#{@admiral-subagents}` is the last tail field, outside `optionNames`), so there is no extra tmux call per ship and a restart needs nothing beyond the next poll. **The wire status counts crew** (`wireStatus`, `internal/ships/crew.go`, applied in `Service.ship()` only): while a ship's own status is `underway` and a crew boat is `needs_you`, the ship's `status` is `needs_you`, `reason` `crew` and `stop_since` the earliest, over the needing boats, of the boat's `last_activity` or else its `launched`. This reaches the API, the WebSocket, `Get()` (so the bridge's `ship` message) and `InputSeen`'s response. The inbox builds a stop for the ship only while it needs you itself (`status` `needs_you` and `reason` not `crew`) and one stop per `needs_you` entry of `crew`, keyed `stop:<session>/<crew>`, whatever the ship's status except `sailing_off`. The ship's own status stays in `FromSession`, `status()` and `sess.State`, which `InputSeen`'s decision, Dismiss, sail-off, the bell, the startup exit-0 kill and the outcome log use, and `@admiral-state` is never written for a crew boat. The ships push signature covers crew membership, each boat's status and reason and the subagent ids, not `last_activity`. Sail-off and Dismiss kill the whole session (`kill-session`), which ends crew windows and their harness processes; an anchored ship's live crew keep running until Dismiss. `launcher.CloseCrew(ctx, windowID)` is the one kill both `admiral crew close` and the close route use.
- Ship cap (`internal/config/maxships.go`, ADR 0034). Top-level `max_ships` (positive integer, default 3, `config.Config.MaxShips`) caps the ships underway or needing you that autopilot-mode launches may start; hand launches are never capped and count towards it. There is no per-panel autopilot config: a `sources.<key>.autopilot` entry or a top-level `autopilot` object is removed by the startup migration. `launcher.Request` carries `Autopilot` and `Resources` (JSON `autopilot` and `resources`, so `POST /api/ships` sets them), and `ExtraArgs` and `Panel` (`json:"-"`). Autopilot mode is a launch mode (ADR 0034). `serveLaunch` refuses a resource not in the config (400), an `autopilot` request on a harness whose guard probe has not passed in the launch's fleet (400, `autopilotgate.Check`), an autopilot launch when `max_ships` ships are already underway or need you, launches in flight and ships the host has not listed yet included (409; `admitMu` is held from the count to `LaunchOrder`'s return for autopilot launches only, so two launches cannot both take the last slot) and a named resource that is busy, missing or pending (409, nothing queued); it holds the reservation until `LaunchOrder` returns, through `ships.Service.Reserve`.
- Locked resources (#118). Config: top-level `resources` (`config.Resource{Capacity, Check}`, `capacity` an integer >= 1 defaulting to 1, `check` a non-empty argv of non-empty strings, names `^[A-Za-z0-9_.-]{1,64}$`) and `autopilot` launches name them. `internal/resources.Set` answers which units are held and by whom: a ship holds one unit of each name in its `@admiral-resources` option (`Ship.Resources`, `json:"-"`; set from `launcher.Request.Resources`) while `underway` or `needs_you`, as do locks (`Set.Lock`, non-blocking, no check needed, for `admiral lock` to call) and reservations. A name no longer in the config holds nothing. `Set.Ships` is `allShips` in `main.go` (List + Pending), so a just-launched ship counts before the host lists it (`ships.Pending` carries the request's resources). `Set.Reserve` checks and reserves all-or-nothing under the Set's mutex and answers `Wait{Name, Why}` with `busy`, `missing` or `pending`. `serveLaunch` reserves through `ships.Service.Reserve` and drops the reservation as soon as `LaunchOrder` returns, on every outcome. Checks run as an argv with no shell, in their own process group, killed as a group at 10 s (`missing`); `Set.Run` runs them all at once, on `Refresh` (a config change) and every 15 s, never two at once for one resource, and a resource is `pending` until its first check ends (`none` when it has no check). A changed check state or a released lock calls `Options.OnChange` (`main.go` pushes the `resources` message). A dropped reservation calls it too. All three close the channel `Set.Changed` returns, and so does `Set.Wake`, which `main.go` calls on every ship change and config change (a ship leaving `underway` frees a unit with no event of the Set's own). `GET /api/resources` and the WebSocket `resources` message (`resources.Service`, sent on connect and on change through `BroadcastOnce`) carry `{"resources": [{name, capacity, in_use, holders: [{kind: "ship", session} | {kind: "lock", label}], check}]}` sorted by name, with no timestamps. `POST /api/resources/<name>/lock` (`internal/lockroute`, for `admiral lock`) holds a unit as an open request: no body, query `label` (cleaned to printable, at most 64 characters) and `wait=1`; it answers `200` with one flushed line `{"held":true}`, then stays open and releases the unit when the request context ends or the server shuts down (`srv.RegisterOnShutdown` closes `Route.Stopping`; the background context is cancelled only after the drain, which waits on this handler). Without `wait` a busy resource answers `409`, an unknown one `404`; with `wait` the handler waits on `Set.Changed()` (fetched before each `Lock` try) and a 15 s timer (a pending ship that expires frees a unit with no wake) and a client that leaves while waiting holds nothing. A peer that is not loopback gets `403`, token or not (`auth.IsLoopbackPeer`, after the Host and Origin checks; a LAN peer with no token gets the middleware's `401` before it reaches the route); the handler reads the body first, because Go cancels the context on a hang-up only once it has. `OnTake` pushes the `resources` message, since `Set.Lock` doesn't announce a take. `admiral lock` (`internal/cli/lock.go`) splits its arguments at the first `--` before parsing flags, probes the server as `ships` does, sends `admiral lock (pid <its own>): <argv[0] base>` and runs the command after the `held` line; it returns a `cli.ExitError` (code, optional message) for 75, 127 and the command's status, which `main.go` maps; after `held` it keeps reading the response and, if that ends while the command runs, prints `lost the lock` to stderr and leaves the command running; it forwards only SIGTERM (it catches and ignores SIGINT, SIGHUP and SIGQUIT, which the terminal sends to the command). The `-h` scan in `main.go` stops at `--`.
- Fleet-owned sources and the startup migration (#259, ADR 0006, ADR 0010 amendment). Every entry under `sources` has a required `fleet` naming a fleet in `fleets`: `parseSources` wants it non-empty and `Parse` (`checkSourceFleets`) checks it exists, so removing or renaming a fleet a source names is refused. A fleet also takes `owners` (GitHub orgs and users) and `clone_root`. `POST /api/sources` takes `fleet`, defaults to the first fleet, answers 409 when there are no fleets and 422 for an unknown one; `PUT /api/sources/{key}` with a different `fleet` moves a plugin source there (422 for an unknown fleet, and for a built-in GitHub source, which stays with its fleet); `SourceView` carries `fleet`. A fresh install seeds no source. `serve()` calls `config.Migrate(dir, version)` before `config.Open` (`internal/config/migrate.go`): when a source has no `fleet`, uses `freeform` or holds an `autopilot` entry, or the file has a top-level `autopilot` object, it keeps the old file as `config.json.pre-<version>` (an existing backup stays), gives every fleet-less source the first fleet (the GitHub source too), removes freeform sources (their pending orders are read from `data/<key>/orders.json`, capped and kept inside the home) and any fleet-less source when there are no fleets, removes every `sources.<key>.autopilot` entry, moves `autopilot.max_ships` to the top-level `max_ships` (unless one is there) and drops the `autopilot` object (`resume_source` with it), and writes through `replaceFile`. A file that would not `Parse` after that is left untouched, with no backup and no notice, so the banner shows. Commands that load the config (`Fleets`, `ReadConfig`) refuse such a file with `ErrNeedsMigration` and never migrate. `serve()` then posts the notice (`Migration.Notice`, never the sources' settings). The notice lists the enabled panel entries it removed (source name, key, panel), with no settings, and says they can come back as routines once scheduled routines land. `serve()` also deletes the engine's `autopilot.json` at start.

- Views. `/api/sources` and the WebSocket `sources` message call a source's lists `views` (`SourceView.Views`); the old key was `panels`. - `internal/capabilities` is what each harness claims and what a probe proved (ADR 0035). `Table()` lists the capabilities by feature (judge, bot, restricted, autopilot), and `Claims` and `ClaimedBy` say which harness versions claim each one (every version, except Claude's guard hook from 2.1.295). Results live in `$ADMIRAL_HOME/capabilities.json`, keyed by the fleet's `Key`, then harness, then the harness version probed, beside the last detected version. `admiral setup` and the server write it, and `admiral crew launch` reads it from inside a ship, so every write re-reads the file and merges under `capabilities.json.lock`, and every query reads the current file. A corrupt or unreadable file reads as all `not_checked` with the error returned, and the next write moves it to `capabilities.json.bad`. A capability is `passed` only with a passing result for the last detected version (`Store.Proven`), whatever the table claims. `DetectVersion` runs the harness's `--version` under the fleet's env.
- `internal/probes` runs the probes that fill that store. A `Probe` is registered for one (harness, capability) pair, so a new probe is a registration in `defaultProbes`. `Runner.Run(ctx, fleet, harness)` is the one entry point for "probe this now": it detects the version, records it, runs the harness's probes for the capabilities the version claims, stores each result under that version and returns a `Report` with a line per table capability (a capability with no probe, or older than its claim, is `not_checked`). It is synchronous, bounded by `Runner.Timeout`, and two concurrent runs for one fleet and harness share one. A failed `--version` clears the recorded version, so the old version's passes stop counting, and keeps why (`Snapshot.VersionError`, cleared by the next good detection). A run does not end with its caller's context, so one client going away cancels nothing for the others; only `Runner.Close` (the server calls it at shutdown) or the run's own time limit ends it. A cancelled run stores no result and leaves the recorded version alone, while a timeout counts as a failure. `admiral setup` calls `Run` for every fleet harness after it saves; the server calls `Refresh` at start, which detects each fleet harness's version in the background, records it and re-runs the probes of a harness whose version differs from the one its results were stored under (a harness never probed only gets its version recorded). A config reload doesn't re-detect. `Judge(harness, id)` is the probe of one judge capability (no tools, no network, JSON schema, per-call cap): it calls `judge.For` and makes its call on the Lookout model through `internal/judge`, and passes on what Admiral sees (a sentinel file, a nonce read back, a request to a loopback listener, claude's `structured_output`, `error_max_budget_usd`), never on what the model says. A harness with no mechanism (codex call cap, copilot schema and cap) records its fixed reason with no call. `ClaudeGuard` runs the fleet's `claude` headless on `haiku` with `Bash` allowed, in an empty temporary directory with its own copy of the hook bundle and `admiral` link (so it works before any server has started), asking it to run `touch <dir>/ran-<nonce>`. `admiral guard pretooluse` notes every Bash call it is asked about in `seen-<nonce>` while `ADMIRAL_PROBE_NONCE` (16 lowercase hex) and `ADMIRAL_PROBE_DIR` (absolute) are set, denies exactly that command, and writes `denied-<nonce>` in `ADMIRAL_PROBE_DIR`, never an outcome. It passes only when the denial file exists and the sentinel doesn't; with no denial, `seen` and the sentinel tell a hook that never ran from a model that ran another command or never called the tool. The probe fails, naming the arg, when the fleet's `claude` args would override the hooks (`launcher.RefuseHookArgs`). The launcher removes both probe variables from a ship's env. The harness's env is the fleet's with the ship and pane variables removed and `ADMIRAL_AUTOPILOT=1`.
- `internal/autopilotgate` decides which harness may carry autopilot mode in a fleet: only when the code registers a guard probe for the harness (`probes.GuardHarnesses`, so a stored pass for any other harness proves nothing) and that probe passed there for the last detected version (`Proven`, which reads the store fresh on every call, with no cache; a corrupt or unreadable store is not proven). `Check` returns a `*Refusal` and posts one dismiss-only Inbox notice, "Couldn't launch unattended on the harness: guard not proven", unless an open notice with the same title and body (the body names the fleet by name and key) exists. Its environment is Admiral's overlaid with the env of the ship's dock (`fleets[].harnesses.<name>.env`, from the ship's `fleet` and `harness` read at action time from the current config), plus `GH_PROMPT_DISABLED=1` and `GH_NO_UPDATE_NOTIFIER=1`; a ship with no dock runs `gh` in Admiral's own environment, and a failure says so. After a 404, though, Admiral also reads the pull request (`GET repos/<o>/<r>/pulls/<n>`), because a token that cannot see the repo gets 404 as well; if that fails too, it answers 502 and writes and records nothing, with the "token may not reach it" text only when the pull request answered 404, and gh's own text otherwise. A 200 carries `"action"` (`inbox.ActionSubmitted`, `ActionDiscarded`, `ActionGone`). ## API versions

- `/api/v1/...` and `/ws/v1/...` answer exactly as `/api/...` and `/ws/...` do: status, headers and body. `Handler()` in `internal/server/server.go` strips the `/v1` before routing, so a module registers its routes once, unversioned, and every route (current and future) has a v1 path. The strip sits inside `guard.Middleware`, so v1 gets the same access control, with no path-specific auth code.
- `GET /api/version` (also `/api/v1/version`) returns `version`, `commit`, `api_versions` (`[1]`) and `capabilities`, with `Cache-Control: no-store`. It needs the same auth as the rest of the API.
- `capabilities` is an array of strings naming the server features this build serves, set in `cmd/admiral/main.go`. Each entry names a feature group, not a module (the bridge module serves two, `bridge` and `setup`; the lock route has none). They are server features, not harness capabilities (GLOSSARY.md, ADR 0035). Within v1 the list only grows:
  - `ships`: launch, list, move, dismiss and close crew boats on ships.
  - `sources`: order sources and their views.
  - `inbox`: the inbox items and their answers.
  - `launch-orders`: launch orders, favorites and the launch dock's directory and skill lists.
  - `bridge`: the bridge sockets on ships and crew boats.
  - `setup`: the setup terminal's routes.
  - `resources`: the resource units and their locks.
  - `chat`: the chat session.
  - `ship-input`: send a message to, interrupt and stop a ship, and send to or interrupt a crew boat (`POST /api/ships/<session>/{messages,interrupt,stop}` and `/crew/<name>/{messages,interrupt}`; see `docs/api.md`).
  - `conversation`: a Claude Code or Copilot ship's conversation (`GET /api/ships/<session>/conversation` and the WebSocket `conversation` messages; see `docs/api.md`). It also covers a crew boat's (`GET /api/ships/{session}/crew/{name}/conversation` and the `crew` field of the WebSocket messages): `internal/shipconv` keys a subscription by session or by `{session}/crew/{name}`, and reads the boat's path fresh from its pane option (`@admiral-crew-transcript`), confined by `transcriptfs` and `ValidCrewTranscriptPath` only.
  - `changes`: a ship's changes (`GET /api/ships/<session>/changes`, `internal/shipdiff`: a diff of the checkout against its merge-base with `origin/HEAD`'s branch or `main`, with the git safety flags, a size cap and the timeouts; see `docs/api.md`).
- Bodies stay byte-identical, so a URL inside a body stays unversioned (`icon_url` in `/api/sources` and `/api/plugins` is `/api/plugins/<name>/icon`). Rewriting them is left to #258.
- The bridge socket's `join` carries an optional `api` version; see `docs/bridge-protocol.md`.
- v1 changes are additive only. The unversioned paths stay for the old UI until #276.
- `GET /api/logos/<harness>` (also `/api/v1/logos/<harness>`) serves `$ADMIRAL_HOME/logos/<harness>.svg` as `image/svg+xml`, with `X-Content-Type-Options: nosniff` and a Content-Security-Policy that allows no script. It answers 404 when the file is missing or `<harness>` isn't one `config.Harnesses()` returns (claude, copilot, codex; `unknown` is 404), and never reads outside that folder. It has no `capabilities` entry: clients fall back on the 404.
- Each fleet in the config view (`GET /api/config` and the WebSocket `config` message) carries an additive `color_index`: the fleet's position in a color sequence. A fleet with no `color` in config gets the raw counter `assignColors` used, not wrapped. A stored `color` that matches an old palette entry (case-insensitive, as `admiral setup` writes the default hex) gets that entry's position. A custom hex has no `color_index`. The client wraps it by the redesign sequence's length. `color` and `ink` stay the old palette's values.

## Idle memory

## The setup terminal

Tapping the "Set up a fleet" marina or the header's fleet count opens `admiral setup` in a terminal over open water. It runs in the tmux session `_setup` on Admiral's socket (never in `ships`, never a ship) and uses the bridge's terminal, so several browsers can share it and a dropped connection rejoins. `POST /api/setup` starts it or leaves the running one alone; `GET /api/setup` says whether it runs. The bridge accepts `/ws/bridge/_setup` while the session exists. ## The chat session

AdmiralBot (ADR 0018, 0019) is one Claude Code session in the tmux session `_chat` on Admiral's socket. `internal/chat` serves it, `launcher.StartChat` (`internal/launcher/chat.go`) starts it and `sessionhost.ChatName` names it. It is never a ship: `Session.IsShip` refuses `_setup` and `_chat` by name, so setting `@admiral-name` on it changes nothing, and `admiral attach` refuses it.

- **Routes** (all behind the same auth as the rest; none skips the LAN token):
  - `GET /api/chat/session` answers `{"running","state","messages","questions","error"?}`. `state` is `idle`, `working` or `waiting`, and `""` while not running; it is `waiting` whenever a chat question is unanswered, whatever the hooks say. A message is `{"id","role","text","at"}`, `role` `user` or `assistant`. `questions` is described under "Chat questions". `error` also carries why the last start was refused (the 409 below) while the chat is not running. With the chat not running `state` is `""` even when a chat question is unanswered.
  - `POST /api/chat/start` starts the session or leaves a running one alone, and answers `{"running":true}`. Admiral doesn't start it at server start. 409 when the chat fleet has no Claude dock or there are no fleets.
  - `POST /api/chat/messages` `{"text"}` pastes the text and presses Enter. 400 for empty text, or over 16 KiB. 409 when the chat isn't running or no transcript has been recorded yet. Control characters other than LF and tab are dropped (an escape could end the bracketed paste early) and CRLF becomes LF.
  - `POST /api/chat/questions/{id}/answer` takes the inbox's question answer body (`inbox.QuestionRequest`) and writes the answer file. 404 for an unknown id, 409 when it is already answered, 400 for an invalid answer. It writes no outcome record and adds no resume order.
  - `POST /api/chat/new` resets the conversation, and withdraws every chat question: `/clear` and Enter when the running session's model, effort and fleet match the config, else it ends the session and starts a new one. 409 when not running. A running session without a recorded transcript, whose settings match, is also 409: `/clear` would land in the trust dialog.
  - The WebSocket `chat` message has the fields of the session, beside `type`. It is sent on connect and, within about a second, whenever the messages, state, running or error change, to every browser (`SendOnce`/`BroadcastOnce`, key `chat`). The `chat` message belongs to the main socket, not the bridge.
- **Start.** The working directory is `$ADMIRAL_HOME/chat/`. argv is the chat fleet's Claude executable (`Resolve()`; the dock's `args` are dropped, because they are a ship's and commonly widen permissions, ADR 0020), then `--model <model>`, `--effort <effort>` when set (each its own argument), then the fence (`--permission-mode dontAsk --setting-sources project --tools Bash,Skill,Read --append-system-prompt <one paragraph>`, ADR 0020), then `--settings $ADMIRAL_HOME/harness/chat-claude-settings.json`. Before the process starts, `launcher.WriteChatSkill` writes `chat/.claude/skills/admiralbot/SKILL.md` (embedded from `internal/launcher/admiralbot/SKILL.md`) through an `os.Root`, a temp file and a rename. The session is made like a ship's (placeholder, options, `set-environment`, `respawn-pane` through a tmux client with the chat's `PATH`) with no `remain-on-exit`, so it ends with Claude and the next start makes a new one. The environment is `shipEnv` without any `ADMIRAL_*` but `ADMIRAL_HOME`, and `set-environment -r` hides every `ADMIRAL_*` the tmux server holds (its global environment) except `ADMIRAL_HOME`; the chat's `ADMIRAL_PORT` is the port Admiral listens on (`Launcher.Port`), and the launcher unsets it for ships. Session options `@admiral-chat-model`, `-effort` and `-fleet` record how it started. A change of the `chat` key applies at the next start and at New chat.
- **Hooks.** The chat bundle registers `SessionStart` (no matcher), `UserPromptSubmit`, `PreToolUse` `AskUserQuestion`, `PostToolUse`, `Notification` (`permission_prompt`, `elicitation_dialog`) and `Stop`. Not `idle_prompt`, `SubagentStart`/`SubagentStop` or the guards. `admiral hook SessionStart` writes the pane option `@admiral-transcript` = `<unix ns> <source> <transcript_path>` and no state. The hook's ship states map to the chat's: `working` is `working`, `needs_you` with reason `stop` is `idle`, any other `needs_you` is `waiting`, and none yet is `idle`.
- **The conversation.** The host's shared format doesn't carry the chat's options, so the service reads them itself with one `display-message` on the chat's pane (at most every 200 ms, and on every host event for `_chat`), plus a 500 ms tick. A new pane id (a restarted chat, or the first one an Admiral sees) starts with nothing; the transcript is read from its start. A new `@admiral-transcript` path starts a new conversation. A `SessionStart` with source `clear` empties it and serves only what is written after; Claude Code 2.1.310 gives `/clear` a new transcript path, so the reset usually arrives as a new path. Until a transcript is recorded, the session carries `error: "Open the terminal to finish starting the chat"`; a recorded path Admiral refuses to read gives `error: "Admiral can't read this chat's transcript"`. The tick does nothing while no browser is connected, and the tmux read runs outside the service lock.
- **Transcript rules** (`internal/transcriptfs`, `internal/conversation`). The path is untrusted. The config dir is `config.IdentityDir(<harness>, dock.Env)` of the fleet the session started with, and the layout follows the ship's (or boat's) harness, never the path's shape. A Copilot ship launches with `--session-id <uuid>` and records `<copilot home>/session-state/<uuid>/events.jsonl`; `transcriptfs.OpenFor("copilot", …)` takes only that file, with a uuid directory, and the session id is the directory's name. `conversation.Options.Harness` picks the decoder: `copilot` reads `events.jsonl` (an allowlist of `user.message` typed by the engineer, `assistant.message`, `tool.execution_*`, `ask_user` as a question pending until its tool completes, `system.notification`, `session.compaction_complete`; lines with `parentToolCallId` and every other type are skipped, and one turn end closes each prompt at the top-level `assistant.turn_end` of a model call that asked for no tools, or at `session.shutdown`, `abort` or `session.error`, which also settle the calls still running; an `ask_user` form of several fields has no options and is answered in the terminal), anything else Claude Code's transcript. `transcriptfs.Open` refuses a path that is not absolute, does not end in `.jsonl`, lies outside the real `<config dir>/projects/`, or is not a regular file with no symlink in it or below `projects/`; a symlinked config dir or `projects/` is fine. The chat reads the file with a `conversation.Reader` built from `conversation.TextView()`, the Claude Code adapter with the text-only filter: user and assistant text and notices (a subagent's `<task-notification>` and another Claude session's message, both shown as the user's; a notice marked `isMeta` stays hidden), without `isMeta`, sidechain, compaction-summary and slash-command lines, tool calls or thinking. The limits are the adapter's (lines over 1 MiB skipped, messages cut at 64 KiB, the last 200 within about 256 KiB, a first read of a file over 8 MiB starts near its end). The service reads from the reader's offset, whole lines only; `/clear` calls `Reader.Clear` with the file's size; when the file does not exist yet it reads from its start once it appears, and when it cannot be opened for any other reason the chat serves nothing until the next clear. `id` is the line's `uuid`. A transcript with content but no JSON line serves an empty chat, with no error.
- **Copilot's live observer** (`internal/conversation/uiserver.go`, `internal/shipconv/uiserver.go`, `internal/launcher/uiserver.go`). The launcher adds `--ui-server --port <n>` (a free loopback port) beside `--session-id` when `uiServerSupported(exe)` holds: `<copilot> --ui-server --port <n> --version` exits 0, cached per resolved binary, size and mtime for 30 minutes (Copilot's launcher updates the real build without changing its own file, so the expiry catches an update), so a launch runs it at most once per window and never when the order or dock names a session, a port or a server mode. The port is read back from the pane's start command (`uiServerPort`, through the same argv parser as `startedSession`, which ignores flags inside an order's text). `conversation.ObserveUIServer` is a small hand-written JSON-RPC client over Content-Length framing (the Go SDK answers some server requests by default, so it is not used): it sends `connect`, `session.resume {sessionId, disableResume: true}` and, when stopped, `session.detach`, and has no code that replies. `ServerReader` decodes `session.event` notifications with the events.jsonl decoder plus `assistant.message_delta`. The shipconv watch owns one observer per open ship, starts it with the watch and cancels it when the watch ends; its items merge into each poll's push by id, the file's winning. The observer attaches only when the process listening on the port is the pane's process or a descendant (`listenerBelongsTo`), since a foreign server on a taken port would answer `session.resume` for any session. Connect refused, no answer, a drop or a foreign listener leave the file serving, and the observer retries every 1 s up to 15 s apart.
- **Open terminal.** The bridge accepts `/ws/bridge/_chat` while the session exists, as it does `_setup` (`ownSessions` in `internal/bridge/setup.go`; the stand-in is called "Chat session"), and a keystroke there changes no state. It ends with the session through `ShipsChanged`.
- **The fence** (ADR 0020). `chat-claude-settings.json` holds `permissions.allow` of exactly `Bash(admiral ships *)`, `Bash(admiral outcomes *)`, `Bash(admiral inbox *)`, `Bash(admiral orders *)`, `Bash(admiral chat ask *)` and `Skill(admiralbot)`, `permissions.deny` of `Edit`, `Write` and `NotebookEdit`, and `blockReadsOutsideWorkingDirectories`. Ships' bundles and command lines are unchanged. The skill's only write is `admiral orders add`.
- **Chat questions** (`internal/chat/questions.go`, ADR 0020). `admiral chat ask` writes `$ADMIRAL_HOME/chat/questions/<id>.json` (#112's question item) and waits for `<id>.answer.json`. The service reads the directory through an `os.Root` (no links, `O_NONBLOCK`, at most 1 MiB, the id rule, `inbox.ReadItem` with kind `question` only; a file that fails is skipped), on the chat's 500 ms tick (while a browser is connected) and at most every 100 ms; `GET /api/chat/session` and a new connection read it fresh. It runs whether or not the chat runs, outside `s.mu`, newest names first until 20 valid questions are found, and a file whose modification time and size haven't changed is not read again. `questions` holds the newest 20, oldest first, each the inbox's question item with `session` `"_chat"` and `answer`: the answer file's content (read just as defensively and decoded into `answers.<id>.choice`/`other`, `note`, `answered` and the envelope, so nothing else a writer put there is served; a link, an oversized file, or one that doesn't decode is no answer) or `null`. The answer route builds the file with `inbox.BuildQuestionAnswer` and writes it with `inbox.WriteAnswerFile` under the chat's own mutex. Chat questions never touch `inbox/`, `GET /api/inbox` or the `inbox` message. New chat, and a fresh session started after the old one ended (just before the launcher creates it, `Launcher.BeforeChat`), remove every file in `chat/questions/`; a waiting `admiral chat ask` then exits 4.
- **The chat UI** (`web/src/chat.ts`, `ChatPane.tsx`, `QuestionCard.tsx`). Opening the chat posts `POST /api/chat/start` (idempotent); `chat.ts` holds the `chat` message and the engineer's draft, and `ChatPane` is one pane in three hosts: the phone's Chat tab, a full-screen sheet at the middle size (the header's Chat button; it and the inbox sheet close each other) and a floating panel on wide (the round button, which sits left of the inbox drawer through `--inbox-drawer-w`). The dot on the entry and the tab is set by an assistant message id or a question id that is new while the chat isn't showing; the page's first `chat` message counts as seen, and a reconnect doesn't re-seed. Questions show in the thread at their `created` time through the card the inbox uses (`QuestionCard`, with `questions.ts` for the pure draft helpers and the answer body) and keep their own drafts, since the inbox drops every key that isn't a live inbox item. A lone single-choice question answers on one tap, and a card folds only when the served `answer` arrives. The box stays enabled while a question waits: the text goes to the TUI behind the blocked `admiral chat ask`. Escape closes Settings, then the New chat bar, then the chat, but not from inside the chat's terminal, where Esc is Claude's interrupt key.
- **Kept out.** No ships, outcomes, autopilot, caps or resources; no crew rows (#154).

## The wake decision

`moor.DecideWake` (`internal/moor/wake.go`) is pure: a moored ship's PR answers, its wake state, the fleet's `wake_reviewers`, whether it is live and `now` give a `Decision` (wake or not, the one PR, its events, the feedback text, the T3 events and the `Next` state). `PollMoored` calls it for each answered, not-live record whose mooring did not end this poll and that has a valid resume text (a record with none is not decided: its no-resume note stands). It passes `Live=false`, the fleet's `wake_reviewers` and `now`.

- **Saving `Next`.** A decision that does not wake saves `Next` when it differs from the stored state, so a condition keeps its first-seen time. The write skips a ship whose wake is `committed`, whose record is no longer the one polled, or whose stored state changed since the poll read it.
- **A round.** A decision that wakes calls `Service.FeedbackRound(…, next)` outside `mooredMu`, under `pollMu` (one poll waits for the launch; kicks coalesce). Its launch hook writes the feedback file, then `next` (the cursor advanced, `RoundStart` set), after `commitWake`; if the launch then fails, the previous state is put back (the file is removed when there was none), so the next poll hands the same events again. A refused launch never ran the hook, so it changes nothing. A state write that fails refuses the launch with its own 500. A crash between the state write and the session's start leaves the cursor advanced: those events are not handed again. One launch is tried per ship per poll.
- **The lock.** `Service.wakeMu` serializes every read-modify-write of a ship's wake state: the poll's `Next` write, the round-start write and the hand wake's write. It is taken after `mooredMu` is released, never inside it.
- **Waiting.** `launcher.Error.Wait` is the typed reason, set where a refusal can clear later: at the cap (`Waiting for room under the cap`), for a resource that is `busy`, `missing` or `pending` (`Waiting for <resource> (<why>)`), for a wake already in progress (`Waiting for the current wake to finish`) and for a host not known (503, `Waiting for Admiral's terminal host`). Nothing parses message text. Any other refusal (fleet or dock not found, no guard, an unknown resource, a write failure, a launcher refusal after admit) is permanent and reads `Can't wake: <message>`. The text is kept on the ship's `polled` entry as `waiting`, which a new poll answer replaces (so it clears when a poll answers and does not decide to wake), and `dropMoored` (a successful wake) and `endMoored` (the mooring ends) remove. `markStale`, a poll that failed to reach GitHub, keeps it. Only a typed `Wait` reads as waiting: the 503 carries `WaitHost`, and no status code is read as a wait. The decision's wake state is passed to `feedbackRound`, which refuses with `Waiting for the current wake to finish` when the stored state no longer matches it (the next poll decides again). Every `RemoveWake` goes through `removeWake` under `wakeMu`; the hand wake's hook logs a wake state it cannot read or save and wakes without a round window. The row shows it as its note; Wake by hand stays on.
- **One round at a time.** A live ship is not polled. When the round's ship moors again, the next poll decides from the advanced cursor, and what came in during the round is the queue.
- **A hand wake** (the row, the ship view and the bridge prompt all go through `Service.Wake`) runs a hook after `commitWake` that sets every PR's `RoundStart` and gives a PR with no cursor the old `moored_at` as its cursor, the way a decision does; cursors, snapshots and first-seen times stay. It is put back if the launch fails.
- **`ADMIRAL_WAKE_DEBOUNCE`** (10 min) is the debounce, for tests.
- **A stranger's feedback** (T3) becomes an Inbox item of kind `wake_proposal` (`internal/inbox/proposal.go`), written by the server under `_admiral` like a notice and read with the same rules (only `_admiral` may hold one; the `wake_proposal` object, `{ship, session, pr, login, events: [{id, kind, url, at, body}]}`, is required). `decide` calls `moor.ProposeT3` on `Decision.T3` for a record with a valid resume text (a ship with none gets no proposal): one batch per PR and author, the not-yet-proposed events, held until the author's newest event is older than `ADMIRAL_WAKE_DEBOUNCE` unless this decision wakes the ship on that PR, an empty or invalid login grouped as `ghost`. The id is `wake-` and 20 hex characters of a SHA-256 over ship, PR, login and the sorted event IDs, so a repeated batch is a no-op: `WriteWakeProposal` never rewrites an item and leaves an answered one answered. The event IDs go into the PR's `proposed` (`{id, at}`) in `Next`, folded in before the single state write, and an entry goes once the cursor is past its `at`. Proposal files are written before the state write. They are written under `wakeMu` with the mooring and the stored state re-checked, and a proposal that cannot be written stops the poll's decision there: no wake and no save, so the next poll retries. A round that is refused saves the state it read plus only the new `proposed` entries, never the advanced cursor. A proposal never expires; Remove from inbox acts as Dismiss.
- **Launch and Dismiss** are `POST /api/inbox/_admiral/<id>/launch` and `/dismiss` on `inbox.Service`, which reaches `ships.Service.LaunchProposal` through its `LaunchProposal` hook (set in `cmd/admiral/main.go`; `internal/ships` imports `internal/inbox`). Launch first checks the item against the moored record (the ship's name, a valid login or `ghost`, every event proposed: recorded, or behind the cursor and pruned) and answers `404` otherwise, then runs `wake()` with `by="proposal"`: autopilot with `autopilotgate.Check`, no cap check, the hand wake's round-start hook plus `feedback-<N>.md` holding only the proposal's events, and the cursor unmoved. Both answer through `answerMu`, so a second press is `409`; outcome events `proposal_launched` and `proposal_dismissed` name the woken ship's session. `removeWake` also deletes the ship's proposals and their answers, under `wakeMu`.

- **The round history** (`internal/moor/rounds.go`) is `$ADMIRAL_HOME/moored/rounds/<name>.json`: one `{round, session_id, fleet, transcript, started, ended}` per round, the latest `moor.MaxRounds` (50), never any transcript content. `moor()` appends the round under `wakeMu` before it writes the record, keyed by round number so a retry adds nothing; the record is deleted on every wake and the history is not. `removeWake` removes it, so every end of a mooring does. The path goes in only through `transcriptfs.Bind` (`internal/transcriptfs/bind.go`), the one rule `shipconv` uses too: the option's `<ns> launch <path>` form, `ValidTranscriptPath`, and the start command's `--session-id` equal to the path's id; `started` is the option's nanoseconds. `internal/shipconv/rounds.go` stitches the rounds (`docs/api.md`, "A ship's rounds"), opening each recorded file through `transcriptfs` under its fleet's `projects/`.
- **Poll bounds.** `github.Client.PullRequests` (`internal/github/pr.go`) reads, per PR, the last 20 reviews, the last 20 review threads with their last 10 comments, the last 20 PR comments, up to 20 pending review requests and 20 review-requested timeline events, and up to 50 check contexts on the head commit; each body is cut to 4096 bytes. GitHub returns bodies whole and the client cuts them, so a poll of a busy PR can still be large. `viewer { login }` comes once per query.
- **Events.** A review is an event when it is `CHANGES_REQUESTED`, or `COMMENTED` with a body (its inline comments count through the threads); `APPROVED` alone, `PENDING` and `DISMISSED` are not. A thread comment or PR comment is keyed by `createdAt` and id, so an edit never wakes. A condition (a failing check, a conflict, behind base) takes the time of the first poll that saw it.
- **The repo's own CI** is a GitHub Actions check run with a workflow run, plus any check run or status the base requires for the PR (`isRequired`). Failing is `FAILURE`, `TIMED_OUT`, `STARTUP_FAILURE` or `ACTION_REQUIRED` for a check run, `ERROR` or `FAILURE` for a status; `CANCELLED` is not. Every other check is ignored.
- **Behind base** wakes only when the base readably requires up-to-date branches: a ruleset's `strictRequiredStatusChecksPolicy` or a non-null `branchProtectionRule.requiresStrictStatusChecks`. Classic branch protection is invisible to a non-admin token, so a null or unreadable rule means not required.
- **Tiers.** T1 is the fleet client's gh viewer. T2 is a `wake_reviewers` login, a Bot authoring a review or a review-thread comment, and a requested reviewer (from pending requests and the timeline; a team makes nobody T2). Everyone else is T3: returned beside the decision for the Inbox, never waking. A Bot's plain PR comment is ignored. Logins compare case-insensitively. GraphQL gives a Bot's login without `[bot]`, so a `wake_reviewers` entry `foo[bot]` matches the Bot `foo`; a bare `foo` matches only a User `foo`, never a Bot.
- **The ship's own replies** share the viewer's login, so a viewer event created between a round's start and the ship's re-mooring is dropped. A dropped event that is still newer than the cursor is recorded in the PR's `dropped` ids at a wake, so a later round's window never hands it.
- **Debounce and queueing.** A ship wakes when the newest waking event is at least 10 minutes old. One PR per round: the lowest layer of the record's `prs` with waking events; the others stay queued behind their cursors. A PR with no cursor (the first mooring) treats events before `moored_at` as history. `T3` holds every T3 event newer than the cursor, so it repeats from poll to poll until a later waking event passes it; its consumer dedupes by id.
- **The wake state** is `<home>/moored/wake/<name>.json` (`moor.ReadWake`, `WriteWake`, `RemoveWake`): per PR URL, a cursor, the last round's start, a snapshot of the conditions at that start, the first-seen times of conditions and the dropped ids. A poll that sees a conflict, behind base or failing check gone clears it from the snapshot, so its return is new and wakes after the debounce. It sits in a subdirectory so `moor.List` skips it, survives a wake's `dropMoored`, and is removed with the record when the mooring ends for good (Dismiss, merged or closed PRs seen by the poll, and a woken ship whose round ends with no open PR).
