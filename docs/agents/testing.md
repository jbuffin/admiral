# Testing

What to test, where each test goes, and how the tests are set up.

## What to test

Each behavior gets one test, at the lowest layer that can see it:

| The behavior | Its layer |
| --- | --- |
| Validation, parsing, config shape and migration, state logic, masking secrets | Go unit test in the package |
| What a route returns for a request | Go `httptest` against the handler |
| The new shell's UI state logic (stores, ordering, protocol replay) | Vitest |
| A journey that crosses browser, server and tmux or a harness | E2E: Go `e2e/` for server and tmux, Playwright for the page |

A test earns its place when it would catch a bug a person could hit:

- Assert outcomes: the response, the page, the ship's status, the file on disk. A test that still passes after the code under it breaks, or fails after a refactor that keeps the behavior, is a change detector; rewrite it or delete it.
- Take expected values from the spec, the story or a worked example, never by recomputing them the way the code does.
- Pick one case per distinct rule. Spelling variants of one flag, every bidi code point, every way to write the same argument: one representative each.
- Test the inputs real callers send. The boundary validates; test it there, and trust the code behind it.
- Mock only what Admiral doesn't control: `gh`, the network, the clock. Use the real binary, tmux and the fake harness for the rest.
- Wait on a condition (a file, an API state, a locator), never on a fixed sleep. To show that something does not happen, poll it with `holdThat` for `hold` (`e2e/harness_test.go`) after the test has seen what it starts from.
- A red test describes the behavior it expects. Once the code exists, the test file carries no header spelling out the interface it assumed.
- Text, class names, colors, layout and focus order are the designs' job. A Playwright test finds elements by role and accessible name, and asserts what the person sees happen.

Playwright drives the new shell at `/app/` only; the old UI is frozen and has no browser tests. The journeys are a short list of what a person does with Admiral (set up, launch, board, answer, chat, reconnect). The `@critical` tag marks the ones Admiral cannot ship broken.

## How the tests are set up

Admiral keeps its data in `$ADMIRAL_HOME` (default `~/.admiral/`). Every test starts the binary with a fresh temporary one on a free port, so tests never touch yours.

Every Go e2e test owns its home, tmux socket and port, so the tests run in parallel: each top-level test calls `t.Parallel()`, and `make e2e` runs `E2E_PARALLEL` (4) at a time. The packaging tests stay serial, because they run `make release` in the checkout.

The e2e harness shortens Admiral's production delays through environment variables that take a Go duration (`internal/delay`):

- `ADMIRAL_WAKE_DEBOUNCE` (10 min): how long the newest waking event must have waited before a moored ship wakes. The e2e sets it small and writes the review's `submittedAt` just after the ship moors (`fakeGH.prEvents`).
- `ADMIRAL_SAIL_OFF_DELAY` (3 s): every Admiral in the suite runs with `sailOff` (1 s).
- `ADMIRAL_NO_HOOK_WAIT` (10 s): set only by the tests of the no-hook rule.
- `ADMIRAL_CALL_TIMEOUT` (10 s, a plugin's time to answer): set only by the tests of a hung plugin.
- `ADMIRAL_BRIDGE_IDLE` (30 s): set only by the tests of the bridge's linger.
- `ADMIRAL_CHAT_RESET_IDLE` (10 min): AdmiralBot's short idle window before a scheduled reset; the long window is 6 times it. Set only by the tests of scheduled resets.
- `ADMIRAL_CHAT_FLUSH_WAIT` (3 min): how long a reset or an idle New chat waits for the hidden flush turn. Set only by the tests of an abandoned flush.

A test sets its own value through `world.extra`.

Tests sit at two seams. `e2e/` (Go) starts `bin/admiral` and drives it over HTTP and WebSocket. Its packaging checks (the release tarball, the install script, the formula and the service) carry the `packaging` build tag: `make e2e` leaves them out and the release runs them (see [releasing](releasing.md)). `web/e2e/` (Playwright, WebKit, touch) loads the new shell at `/app/` in two projects: `ipad-landscape` (1194x834) runs every spec but the `*-phone.spec.ts` ones, and `phone` (402x874) runs only those. Vitest covers the new shell's pure UI state logic only; the frozen old UI has one vitest, `web/src/ships.test.ts`, which checks that its ship feed drops a moored ship.

The push path is tested against `internal/push/pushtest` (a fake TLS push service, a subscriber that decrypts per RFC 8291 and a VAPID verifier). Unit tests hand the sender that service's client. The Go e2e starts `bin/admiral` with `ADMIRAL_PUSH_TEST_ROOTS=<path to a PEM file holding the fake's certificate>`, which only a `-tags e2e` build honours (`make build` does; `make release` does not, and a packaging test checks the release lacks the name), and which also lifts the refusal of loopback destinations for that run.

The Playwright journey for Web Push (`web/e2e/shell.spec.ts`, `installed app`, helper `web/e2e/push.ts`) fakes the browser's side: WebKit under Playwright has no `PushManager` and a real subscription would point at Apple's or Google's service. An init script stubs `PushManager`, `ServiceWorkerRegistration.prototype.pushManager` and `Notification` (permission granted, state in `localStorage` so a reload keeps it), and its `subscribe` hands out an endpoint on an HTTPS fake push service in Node (an openssl certificate in `admiral.home`, passed to Admiral as `ADMIRAL_PUSH_TEST_ROOTS`). The test holds the subscription's key pair and decrypts what the Mac posts. The worker's `push` and `notificationclick` handlers are not run in a browser; vitest covers their pure parts and `swBuild.test.ts` checks the built `sw.js` carries them.

`internal/crew/testdata/crew-resolution/` is a byte-exact copy of the shared fixtures in `jbuffin/skills` (symlinks kept; `SOURCE` names the commit). Re-sync it with `internal/crew/testdata/sync.sh <skills checkout>`.

Tests that launch ships use the fake harnesses in `e2e/fakeharness/` (`claude`, `codex` and `copilot` are symlinks to `fake.sh`). A test puts one as the `executable` of a fleet and passes two variables in the fleet's `env`: `FAKE_RECORD_DIR` (where to record) and `FAKE_CUE` (an optional cue file). Started in a ship's pane, the fake writes `<FAKE_RECORD_DIR>/<tmux session>/` (a crew boat, whose window has `@admiral-crew-name`, writes `<FAKE_RECORD_DIR>/<tmux session>/crew/<crew name>/` instead) with `harness`, `argv` (each argument followed by a NUL byte), `env` (one `NAME=value` per line), `cwd`, `name` (the `@admiral-name` option as read at start), `options` (all session options at start), `window-options` (the options of its pane's window at start), `dirs` (`inbox=yes reports=yes` when `$ADMIRAL_INBOX` and the directory of `$ADMIRAL_REPORT` existed before the harness ran anything, `no` for each that did not, `reports=unset` when `$ADMIRAL_REPORT` is empty) and last an empty `recorded` file to wait for. Then it runs the cue file, one cue per line: `hook <needs_you|working>` runs `tmux set -p -t "$TMUX_PANE" @admiral-state <state>` (a bare `set -p` would land on the session's active pane, not a crew boat's), `event <Event> <json>` runs every handler of every group the Claude hook bundle holds for `<Event>` whose matcher matches, each with the JSON on its stdin (it needs `jq`; a matcher is a regex tested against the payload's `tool_name`, or `notification_type` for `Notification`, and a group with none always matches; the match is unanchored, so `Bash` also matches `BashOutput`, looser than Claude; each handler appends `<Event>`, its exit code and its command, tab separated, to `handlers` and writes its stderr to `handler-<n>.stderr`, n counting from 1; it appends the event name to `events-done`, one line per cue, and a fault of the fake itself goes to `event-error`; a handler's non-zero exit is not a fault), `mcp <name>` (Claude only, needs `python3`) waits for the file `<name>` in the recording directory holding `{"name":<tool>,"arguments":{...}}`, makes that one `tools/call` through the first server of the argv's `--mcp-config` (with the server's `env`) and lists the tools first and fails the cue, with no reply and a line in `mcp-error`, when a tool's `inputSchema` is not an object with `"type":"object"` and an object `properties` (Claude Code drops every tool of the server then), and writes the tool result to `<name>.reply`, an RPC error becoming an `isError` result; a `-p` run with `--mcp-config` is the fence probe, which the fake answers with an init line listing the server's tools and a call of its first tool, leaving `headless-runs` alone, `statusline <json>` runs the `statusLine` command of the `--settings` file (Claude only, needs jq) with the JSON on its stdin and appends its stdout to `statusline-stdout`, its stderr to `statusline-stderr`, its exit code to `statusline-exit` and a fault of the fake to `statusline-error`, creating `statusline-done` after each run, `usage` appends the usage line the harness writes at its end, with fixed figures (Claude 0.25 USD, 100 in, 40 out, 10 reasoning; Copilot 2.5 credits, 3 premium requests; Codex 300 in, 40 out, 20 reasoning and no money; the exact lines are in the header of `fake.sh`), to the transcript in the pane's `@admiral-transcript` (a Codex rollout under its `sessions` directory), and writes `usage-error` and exits 1 when there is none to write to, `bell` rings the bell, `sleep <n>` waits n seconds, `exit <n>` exits with status n, `lines <n>` prints n numbered lines (`line 0001`…) in cycling SGR colours, `altscreen` switches to the alternate screen with application cursor keys and bracketed paste on and prints `ALT SCREEN`, `bracketedpaste` turns bracketed paste on without the alternate screen (tmux's `paste-buffer -p` brackets only when the app has asked), `record` starts the raw-mode `stdin` recorder in the background at once and creates `recording` (the terminal is raw from then on, so put it first in a cue file that prints nothing; without it `stdin` records only after the cues end, so a later `wait <name>` then `event SessionStart …` can follow input), `wait <name>` blocks until the file `<tmux session>/<name>` exists in the recording directory, `menu <json>` (the last cue; needs `python3`) replaces the fake with `fakemenu.py`, which draws Claude's AskUserQuestion menu for `[{"text","labels","multi"}]` (tabs, Other, Next or Submit, the review screen), keeping only the bottom of a frame taller than the pane and redrawing on a resize, as Claude does, and logs the keys it takes to `stdin`, so a test sees a stepwise answer land, and `reply <text>` (Claude only, needs `jq`, and the last cue: it never ends) answers every message pasted into the pane. It creates `cues-done` and goes raw, as a message ends at the first CR (LFs are kept, escape sequences (`ESC [ … final byte`, the paste markers among them) and a lone ESC are removed), so put `bracketedpaste` before it, and `toolresult <text>` (Claude only, needs `jq`; it is not the last cue) appends a completed Bash tool call (an assistant `tool_use` line and a user `tool_result` line holding `<text>`) to the same transcript, as a `gh pr create` that printed a URL would leave, and exits 1 with `toolresult-error` written when `$CLAUDE_CONFIG_DIR` is unset or the `--session-id` is missing or holds a `/`, and `replydelay <n>` before it makes it wait n seconds before recording each message. It exits 1 with `reply-error` written when `$CLAUDE_CONFIG_DIR` is unset or the `--session-id` is missing or holds a `/`. Per message it appends a user line holding the text and an assistant line holding `<text>` to `$CLAUDE_CONFIG_DIR/projects/zz/<id>.jsonl`, with `<id>` the `--session-id` in its argv, and it appends every byte it reads to `stdin`, so an Interrupt's Esc still shows. When the cues end it puts the terminal in raw mode (`stty raw -echo`), creates `cues-done` and stays running unless a cue exited; from then on it records every byte it reads from the terminal, exactly as received, in `stdin` (a test sends input only after `cues-done`). `events <text>` (Copilot only, needs `jq`; it is not the last cue) appends a prompt (`Question <n>`), an assistant message holding `<text>` and its turn end to `$COPILOT_HOME/session-state/<id>/events.jsonl` in the shape Copilot records, with `<id>` the `--session-id` in its argv; put `wait <name>` before it to append after the page opened the ship. It exits 1 with `events-error` written when `$COPILOT_HOME` is unset or the `--session-id` is missing or holds a `/`. The fake handles two things before it touches tmux, so neither needs a pane. `--version` as the first argument prints the content of the file `FAKE_VERSION_FILE` if it exists, else `FAKE_VERSION`, else `2.1.300 (fake)`, and exits 0; the content `FAIL` prints `boom` to stderr and exits 1. A test changes the version by rewriting the file. Any run with `-p <prompt>` is a headless probe run: it appends a line to `<FAKE_RECORD_DIR>/headless-runs`, takes the command after the last colon and space of the prompt, plays it as a Bash call through the `--settings` file's PreToolUse hooks (it needs `jq`; a handler that exits 2 denies the call) and runs the command only when none denied it. `FAKE_PROBE` picks the behavior: `pass` (default), `skip-hook` (runs no hooks, runs the command and says it was denied), `run-anyway` (runs the hooks, then runs the command despite a deny), `different-command` (asks the hooks about, and runs, the command with `&& true` added) and `no-tool` (never calls the tool). Setup tests put these variables in the process env, which the probe passes on to the harness. `codex exec --json` is a fourth kind, a fenced probe run, and never a judge call: the fake reads the MCP server from the `-c mcp_servers.<name>.{command,args,env}` flags, and with one it calls the server's first tool and prints `thread.started`, an `mcp_tool_call` item, an `agent_message` item and `turn.completed`; without one (the config-home probe) it prints the thread and a `pong` message. `FAKE_CODEX_PROBE` in the dock env picks `pass` (default), `shell-ran` (creates the probe's `ran-<nonce>` file and prints a `command_execution` item), `login-failed` (401 on stderr, exit 1) or `plugin-loaded` (makes `plugins/cache/github` in `$CODEX_HOME`). The cue `mcp <name>` also works for Codex, taking the server from those flags, and `codexreply <text>` (Codex only, needs `jq`, the last cue) shows Codex's composer, records the hooks trust Codex would write to `$CODEX_HOME/config.toml`, and answers every pasted message with a user and an assistant line holding `<text>` in a rollout under `$CODEX_HOME/sessions`; the first message writes the rollout's token_count line and sets the pane's `@admiral-transcript`, as a first turn's SessionStart does, so nothing is bound before it, recording stdin. A judge call is a fifth kind of run, recognised before the `-p` check: claude with an empty `--tools` argument and no `--mcp-config` (the chat session and the fence probe pass both), `codex exec` without `--json`, or copilot with piped stdin and no `-p`. It reads the prompt from stdin, answers `{"reply":"ok"}` in the harness's real shape (claude's `structured_output` when `--json-schema` is given, the `-o` file for codex, stdout for copilot), and never appends to `headless-runs`, so setup tests' exact counts count only guard runs. A Playwright journey that needs a real GitHub event calls `seedReviewRequest(admiral, {sender})` (`web/e2e/shell.ts`): it writes the fake gh's review-requested search answer (`search/review.match` and `.json`), the `viewer` file and the REST item the Lookout reads. Tests that need `gh` put the fake in `e2e/testdata/fakegh/gh` first on Admiral's `PATH` and steer it through `$FAKEGH_DIR`. Its header lists every call it answers: `--version`, `auth token`, `api graphql` (the GitHub plugin's search, or the moor poll's batched pull request query), REST `api` calls, `pr view URL --json state`, `repo clone [--] REPO DIR` and the single-PR detail query (an `api graphql` call holding `isDraft`, answered with the JSON object in `pr_detail/<key>`, GitHub's shape and the key as for `pr_state/`; no file is NOT_FOUND, `pr_detail.fail` fails it and `pr_detail.sleep` holds it). A clone makes DIR a git checkout whose `origin` is the repo, so the finder matches it; `repo_clone.fail` (its content is gh's stderr) leaves a partial DIR and exits 1, and `repo_clone.sleep` (seconds) makes two clones overlap. A REST call takes `-X`/`--method`, `-f`/`--raw-field`, `--hostname`, `--input FILE|-` and one endpoint; the method is GET unless a flag or a field says otherwise. The fake refuses `-F`/`--field`, `--jq` and `--template` (exit 2), so a test fails if Admiral lets an item's text be read as a file, or leans on gh's own filtering. Each call writes `$FAKEGH_DIR/calls/call.*/` with `argv`, `env`, and for REST `method`, `endpoint`, `host` and `stdin`. A test scripts an answer with `fakeGH.rest(key, method, endpoint, status, body, stderr)`: a status of 300 or more exits 1 with the stderr, as gh does, and a call with no canned answer exits 1. `callsTo` and `restCalls` read the calls back, and `restCall.field` finds a body field in a `-f` argument or in JSON on stdin. A test that must not reach GitHub asserts that `restCalls()` is empty. `pr view URL --json state` is the moor check's lookup: `fakeGH.prState(url, "OPEN")` answers it (OPEN, CLOSED or MERGED), a URL with no canned state exits 1, and `fakeGH.asked(url)` reports whether any call named it as a URL. It cannot see a batched poll, which names a PR by owner and number (`repository(owner: "acme", name: "widgets") { pullRequest(number: 12)`), so a test that waits for one polls for that fragment instead (`fakeGH.asked` with the fragment as its argument matches any argument that contains it). The batched query (any `api graphql` call with a `pullRequest(number:` in an argument, answered before the search match) reads each aliased `repository(owner: "O", name: "N") { pullRequest(number: 7)` out of the query and answers from the same `pr_state/` file plus `pr_review/`, `pr_checks/` and `pr_mergeable/` (`fakeGH.prChips(url, review, checks, mergeable)`, `""` for none); a PR with no `pr_state` file, or with a `pr_notfound/` file, is NOT_FOUND, answered as gh does: the other PRs under `data`, a `NOT_FOUND` entry in `errors`, exit 1. a `repo_notfound/<owner>_<name>` file makes the repository itself NOT_FOUND (its alias is `null` and the error's path is just the alias, so its PRs are unanswered, not closed). `pr_events/<key>` holds a JSON object whose members are added to that PR's node (`headRefOid`, `mergeStateStatus`, `baseRef`, `reviews`, `reviewThreads`, `comments`, `reviewRequests`, `timelineItems`, `commits`, `author`, `createdAt`), shaped as GitHub answers; `fakeGH.prEvents(t, url, json)` writes it (Go, `internal/github`). `$FAKEGH_DIR/viewer` is the login of `data.viewer` (default `fake-viewer`). `pr_batch.fail` (its content is gh's stderr) fails the whole call with no `data`. The Merge act's calls are answered too. `pr merge URL --merge|--squash|--rebase` needs exactly one method flag and refuses any other flag (`--admin` and `--auto` included); `stack merge N --yes --merge-method M` takes GitHub's stack number as its one positional integer (anything else exits 2, a number no `pr_detail/` fixture holds exits 1) and refuses a call without `--yes` or a valid method; there is no `stack view`, because Admiral reads a stack from the detail query. `stack link N N ...` is the Stack on GitHub act: two or more PR numbers, bottom to top, and no flag (anything else exits 2). It finds each PR's `pr_detail/` fixture under `https://$GH_REPO/pull/N` (Admiral pins `GH_REPO` to `HOST/OWNER/NAME`; no fixture exits 1), refuses a PR whose fixture already holds a stack (exit 1; real gh would update the stack, so the guard is the fake's, to catch a server that links a stacked shape) and replaces each fixture's `"stack":null` with one stack object, number first, entries in argument order, so the next detail read sees GitHub's stack. The stack's number is the content of `stack_link.number` (default 1). `stack_link.fail` (its content is gh's stderr) fails the call and links nothing, and `stack_link.sleep` (seconds) holds it. `fakeGH.stackLinkNumber(n)` and `fakeGH.stackCalls("link")` (Go, in `e2e/stack_test.go`) steer and read it. A test seeds a stack with `fakeGH.githubStack(n, prs...)` (Go, in `e2e/merge_test.go`) or `seedGitHubStack(admiral, numbers)` (Playwright): each PR's `pr_detail/` fixture holds `"stack":{"number":N,` in compact JSON, which is the text the fake matches. `chainedPRs` and `independentPRs` seed PRs in no stack. All record `GH_REPO` in `env` and the working directory in `cwd`. A merge writes MERGED into the PR's `pr_state/` file, so the next poll sees it; `stack merge N` writes MERGED to the `pr_state/` file of every PR whose detail holds stack N and rewrites each `"state":"OPEN"` in those `pr_detail/` files, as does `pr merge` for its one PR. `pr_merge.fail` and `stack_merge.fail` (their content is gh's stderr) fail the call and merge nothing, and `pr_merge.sleep` and `stack_merge.sleep` (seconds) hold the merge before it merges. An `api graphql` call holding `viewerDefaultMergeMethod` is answered with `default_merge_method` (MERGE, SQUASH or REBASE; default MERGE; `fakeGH.defaultMergeMethod`), or fails with `default_merge_method.fail`. `fakeGH.mergeCalls()` reads the merge calls back and `fakeGH.prReady(url)` makes a PR open, approved, green and mergeable. `ADMIRAL_MOOR_POLL` (2 min) is the moored poll's interval; a test kicks a poll with `POST /api/moored/refresh` (`world.kickMoored`) instead. `ADMIRAL_COMMITMENT_GH_POLL` (2 min) is how often the commitment runner asks GitHub about the PRs and issues its commitments wait on; an e2e that needs a verdict sets it short through `world.extra`, and a runner unit test moves its fake clock by `commitments.GHPoll` instead. A verdict needs a poll that began a second after the commitment was recorded, so a test that records a commitment and expects a verdict waits for the second poll.

Tests that need `tailscale` put `e2e/testdata/faketailscale/tailscale` first on `PATH` (the real one is in `/usr/local/bin`) and steer it through `$FAKETS_DIR`. It answers `status --json` and `serve status --json` from `status.json` and `serve.json`, and `serve --bg --https=N http://127.0.0.1:P`, which records the call and on success rewrites `serve.json` to proxy that host:N to P. `status.exit`, `serve.exit` and `servebg.exit` (with `.err` for stderr) make a call fail, `sleep` (seconds) makes every call hang, `servebg.sleep` hangs only `serve --bg`, `servebg.delay` waits and then lets it succeed, and `servebg.out` is printed to stdout first, as the real CLI prints its enable-Serve link before it hangs. Each call's argv is appended to `calls`. Any other argv exits 2. Setup tests set `ADMIRAL_TAILSCALE_SERVE_TIMEOUT` (for example `2s`) to shorten the 60 s serve timeout. `internal/tailscale` tests use it directly; the JSON rules are unit tests on `Evaluate`.

The server tests that connect through the Mac's own LAN address skip, with a message, when that address doesn't answer. On CI (`macos.yml` and the release) they fail instead.
