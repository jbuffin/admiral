# Testing

What to test, where each test goes, and how the tests are set up.

## What to test

Each behavior gets one test, at the lowest layer that can see it:

| The behavior | Its layer |
| --- | --- |
| Validation, parsing, config shape and migration, state logic, masking secrets | Go unit test in the package |
| What a route returns for a request | Go `httptest` against the handler |
| The new shell's UI state logic (stores, ordering, protocol replay) | Vitest |
| A journey that crosses browser, server and tmux or a harness | E2E: Go `e2e/` for server and tmux, Playwright for the page |

A test earns its place when it would catch a bug a person could hit:

- Assert outcomes: the response, the page, the ship's status, the file on disk. A test that still passes after the code under it breaks, or fails after a refactor that keeps the behavior, is a change detector; rewrite it or delete it.
- Take expected values from the spec, the story or a worked example, never by recomputing them the way the code does.
- Pick one case per distinct rule. Spelling variants of one flag, every bidi code point, every way to write the same argument: one representative each.
- Test the inputs real callers send. The boundary validates; test it there, and trust the code behind it.
- Mock only what Admiral doesn't control: `gh`, the network, the clock. Use the real binary, tmux and the fake harness for the rest.
- Wait on a condition (a file, an API state, a locator), never on a fixed sleep. To show that something does not happen, poll it with `holdThat` for `hold` (`e2e/harness_test.go`) after the test has seen what it starts from.
- A red test describes the behavior it expects. Once the code exists, the test file carries no header spelling out the interface it assumed.
- Text, class names, colors, layout and focus order are the designs' job. A Playwright test finds elements by role and accessible name, and asserts what the person sees happen.

Playwright drives the new shell at `/app/` only; the old UI is frozen and has no browser tests. The journeys are a short list of what a person does with Admiral (set up, launch, board, answer, reconnect). The `@critical` tag marks the ones Admiral cannot ship broken.

## How the tests are set up

Admiral keeps its data in `$ADMIRAL_HOME` (default `~/.admiral/`). Every test starts the binary with a fresh temporary one on a free port, so tests never touch yours.

Every Go e2e test owns its home, tmux socket and port, so the tests run in parallel: each top-level test calls `t.Parallel()`, and `make e2e` runs `E2E_PARALLEL` (4) at a time. The packaging tests stay serial, because they run `make release` in the checkout.

The e2e harness shortens Admiral's production delays through environment variables that take a Go duration (`internal/delay`):

- `ADMIRAL_SAIL_OFF_DELAY` (3 s): every Admiral in the suite runs with `sailOff` (1 s).
- `ADMIRAL_NO_HOOK_WAIT` (10 s): set only by the tests of the no-hook rule.
- `ADMIRAL_CALL_TIMEOUT` (10 s, a plugin's time to answer): set only by the tests of a hung plugin.
- `ADMIRAL_BRIDGE_IDLE` (30 s): set only by the tests of the bridge's linger.

A test sets its own value through `world.extra`.

Tests sit at two seams. `e2e/` (Go) starts `bin/admiral` and drives it over HTTP and WebSocket. Its packaging checks (the release tarball, the install script, the formula and the service) carry the `packaging` build tag: `make e2e` leaves them out and the release runs them (see [releasing](releasing.md)). `web/e2e/` (Playwright, WebKit, touch) loads the new shell at `/app/` in two projects: `ipad-landscape` (1194x834) runs every spec but the `*-phone.spec.ts` ones, and `phone` (402x874) runs only those. Vitest covers the new shell's pure UI state logic only; the frozen old UI has no tests.

Tests that launch ships use the fake harnesses in `e2e/fakeharness/` (`claude`, `codex` and `copilot` are symlinks to `fake.sh`). A test puts one as the `executable` of a fleet and passes two variables in the fleet's `env`: `FAKE_RECORD_DIR` (where to record) and `FAKE_CUE` (an optional cue file). Started in a ship's pane, the fake writes `<FAKE_RECORD_DIR>/<tmux session>/` (a crew boat, whose window has `@admiral-crew-name`, writes `<FAKE_RECORD_DIR>/<tmux session>/crew/<crew name>/` instead) with `harness`, `argv` (each argument followed by a NUL byte), `env` (one `NAME=value` per line), `cwd`, `name` (the `@admiral-name` option as read at start), `options` (all session options at start), `window-options` (the options of its pane's window at start), `dirs` (`inbox=yes reports=yes` when `$ADMIRAL_INBOX` and the directory of `$ADMIRAL_REPORT` existed before the harness ran anything, `no` for each that did not, `reports=unset` when `$ADMIRAL_REPORT` is empty) and last an empty `recorded` file to wait for. Then it runs the cue file, one cue per line: `hook <needs_you|working>` runs `tmux set -p -t "$TMUX_PANE" @admiral-state <state>` (a bare `set -p` would land on the session's active pane, not a crew boat's), `event <Event> <json>` runs every handler of every group the Claude hook bundle holds for `<Event>` whose matcher matches, each with the JSON on its stdin (it needs `jq`; a matcher is a regex tested against the payload's `tool_name`, or `notification_type` for `Notification`, and a group with none always matches; the match is unanchored, so `Bash` also matches `BashOutput`, looser than Claude; each handler appends `<Event>`, its exit code and its command, tab separated, to `handlers` and writes its stderr to `handler-<n>.stderr`, n counting from 1; it appends the event name to `events-done`, one line per cue, and a fault of the fake itself goes to `event-error`; a handler's non-zero exit is not a fault), `bell` rings the bell, `sleep <n>` waits n seconds, `exit <n>` exits with status n, `lines <n>` prints n numbered lines (`line 0001`…) in cycling SGR colours, `altscreen` switches to the alternate screen with application cursor keys and bracketed paste on and prints `ALT SCREEN`, `bracketedpaste` turns bracketed paste on without the alternate screen (tmux's `paste-buffer -p` brackets only when the app has asked), `record` starts the raw-mode `stdin` recorder in the background at once and creates `recording` (the terminal is raw from then on, so put it first in a cue file that prints nothing; without it `stdin` records only after the cues end, so a later `wait <name>` then `event SessionStart …` can follow input), and `wait <name>` blocks until the file `<tmux session>/<name>` exists in the recording directory. When the cues end it puts the terminal in raw mode (`stty raw -echo`), creates `cues-done` and stays running unless a cue exited; from then on it records every byte it reads from the terminal, exactly as received, in `stdin` (a test sends input only after `cues-done`). The fake handles two things before it touches tmux, so neither needs a pane. `--version` as the first argument prints the content of the file `FAKE_VERSION_FILE` if it exists, else `FAKE_VERSION`, else `2.1.300 (fake)`, and exits 0; the content `FAIL` prints `boom` to stderr and exits 1. A test changes the version by rewriting the file. Any run with `-p <prompt>` is a headless probe run: it appends a line to `<FAKE_RECORD_DIR>/headless-runs`, takes the command after the last colon and space of the prompt, plays it as a Bash call through the `--settings` file's PreToolUse hooks (it needs `jq`; a handler that exits 2 denies the call) and runs the command only when none denied it. `FAKE_PROBE` picks the behavior: `pass` (default), `skip-hook` (runs no hooks, runs the command and says it was denied), `run-anyway` (runs the hooks, then runs the command despite a deny), `different-command` (asks the hooks about, and runs, the command with `&& true` added) and `no-tool` (never calls the tool). Setup tests put these variables in the process env, which the probe passes on to the harness. A judge call is a third kind of run, recognised before the `-p` check: claude with an empty `--tools` argument (the chat session's `--tools Bash,Skill,Read` is not one), `codex exec`, or copilot with piped stdin and no `-p`. It reads the prompt from stdin, answers `{"reply":"ok"}` in the harness's real shape (claude's `structured_output` when `--json-schema` is given, the `-o` file for codex, stdout for copilot), and never appends to `headless-runs`, so setup tests' exact counts count only guard runs. A claude judge call under `--max-budget-usd` below 0.001 answers `error_max_budget_usd`, as the per-call cap probe expects. `FAKE_JUDGE=leak` makes every judge probe fail: the fake creates the files the prompt names (and echoes the contents of one that exists), fetches the URL it names, answers a plain `hello` instead of JSON and ignores the cap; unset, every probe that has a mechanism passes. The same protocol is in the header of `fake.sh`. Tests that run tmux set `TMUX_TMPDIR` to a temporary directory and talk to tmux only with `tmux -S <home>/tmux.sock`.

Tests that need orders to launch from use the test source that stores orders, not a shipped plugin. It is `e2e/testplugin/plugin.py` with `storeOrders: true` in its settings: an order added through `orders.add` is kept in the source's data directory (apart from the `orders.json` the test owns in `flagdir`), listed after those, and dropped once launched or removed. A test sets it up in one place: `world.orderSource` and `world.ordersSource` (Go, `e2e/sources_helpers_test.go`) and `admiral.ordersSource()` (Playwright, `web/e2e/fixtures.ts`). The source has key `orders` and one panel `orders` titled `Orders`, with the `add`, `edit` and `remove` protocol capabilities. A fresh install seeds no source. Every source in a fixture names a fleet (`fleet`): `srcDef.Fleet` defaults to `stay`, `inFleet` fills in the rest, and `admiral.ordersSource()` uses `work`. A source with no fleet, or a `freeform` one, makes the server migrate the file at startup, which writes `config.json.pre-<version>` and an Inbox notice; the Go harness fails a test whose home got a backup (`expectNoMigration`), except the `TestMigrate…` test, which exists for it.

Tests that need `gh` put the fake in `e2e/testdata/fakegh/gh` first on Admiral's `PATH` and steer it through `$FAKEGH_DIR`. Its header lists every call it answers: `--version`, `auth token`, `api graphql` (the GitHub plugin's search), REST `api` calls and `repo clone [--] REPO DIR`. A clone makes DIR a git checkout whose `origin` is the repo, so the finder matches it; `repo_clone.fail` (its content is gh's stderr) leaves a partial DIR and exits 1, and `repo_clone.sleep` (seconds) makes two clones overlap. A REST call takes `-X`/`--method`, `-f`/`--raw-field`, `--hostname`, `--input FILE|-` and one endpoint; the method is GET unless a flag or a field says otherwise. The fake refuses `-F`/`--field`, `--jq` and `--template` (exit 2), so a test fails if Admiral lets an item's text be read as a file, or leans on gh's own filtering. Each call writes `$FAKEGH_DIR/calls/call.*/` with `argv`, `env`, and for REST `method`, `endpoint`, `host` and `stdin`. A test scripts an answer with `fakeGH.rest(key, method, endpoint, status, body, stderr)`: a status of 300 or more exits 1 with the stderr, as gh does, and a call with no canned answer exits 1. `callsTo` and `restCalls` read the calls back, and `restCall.field` finds a body field in a `-f` argument or in JSON on stdin. A test that must not reach GitHub asserts that `restCalls()` is empty.

The server tests that connect through the Mac's own LAN address skip, with a message, when that address doesn't answer. On CI (`macos.yml` and the release) they fail instead.
