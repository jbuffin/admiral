# The Needs You inbox

Inbox items, review submit and discard, the kept inbox and resume text. Read it before changing `internal/inbox`.

- `internal/inbox` is the Needs You inbox (ADR 0016).
  - It reads the item files in `$ADMIRAL_HOME/inbox/<session>/` through an `os.Root` (a link, a dot file, a name that is not `<id>.json` with `<id>` matching `^[A-Za-z0-9][A-Za-z0-9_-]{0,63}$`, a file over 1 MiB, or an invalid item is skipped; so is an item with `<id>.answer.json` beside it), watches `$ADMIRAL_HOME`, `inbox/` and each ship's directory with fsnotify (100 ms settle, watches re-synced before each rescan), and serves `GET /api/inbox` (`{"items":[...]}`, oldest `created` first; each item is the file's fields plus `session`, and `name`, `ship_title`, `harness`, `fleet`, `fleet_name` and `fleet_color` when the ship is known) and the WebSocket `inbox` message (`{"type":"inbox","items":[...]}`).
  - `POST /api/inbox/<session>/<id>/answer` takes a question's answers (`{"answers":{"<qid>":{"choice","other"}},"note"}`): 400 for an invalid answer, 404 for an unknown item, 409 for one already answered.
  - `Service.Answer` is the shared writer: `build` gets the item and returns the answer file and the outcome records (no network I/O, since it runs under one lock that also re-reads the item and checks for an answer), then the file is written to a temp file and published with `os.Root.Link` (`fs.ErrExist` is a 409, so an answer is never replaced). A question's record is `answered` with `item` and `kind`.
  - **Crew items** (`internal/inbox/crew_items.go`, `crew_answer.go`).
    - When a ship launched in a configured fleet ends, `queueEnded` reads the report's crew note proposals and ad hoc members into `crew_notes` and `crew_member` items in `inbox/_admiral/`, and its mission proposals (`internal/inbox/mission_items.go`, `mission_answer.go`) into `mission` items; the fleet's crew files and missions directory change only when the engineer answers (`.../crew-notes`, `.../crew-member`, `.../mission`), through `internal/crewapi`'s `ApplyNotes`, `KeepAdHoc`, `DropAdHoc` and `KeepMission` (create-once, `fleets/<key>/missions/<name>.md`).
    - The inbox's answer lock is taken before crewapi's `writeMu`, and crewapi never imports inbox.
  - **Notices** (`internal/inbox/notice.go`). Kind `notice`: a read-only item with a title and a plain-text body (`notice: {body}`), written by the server under the pseudo-session `_admiral` (`WriteNotice`; listed with name "Admiral", no ship). The web card shows the body with `white-space: pre-wrap`, never as HTML, and a Dismiss that uses the remove path. The startup migration posts one; a later migration posts its own the same way.
  - `POST /api/inbox/<session>/<id>/submit` (`{"event":"COMMENT"|"APPROVE"|"REQUEST_CHANGES","edited":bool}`) and `.../discard` (`{}`) act on a review item through `gh` (`internal/inbox/review.go`).
    - `gh` is found on Admiral's own `PATH` and run with `exec.CommandContext`, an argument list, a 30 s timeout and no retry.
    - Its environment is Admiral's overlaid with the env of the ship's dock (`fleets[].harnesses.<name>.env`, from the ship's `fleet` and `harness` read at action time from the current config), plus `GH_PROMPT_DISABLED=1` and `GH_NO_UPDATE_NOTIFIER=1`; a ship with no dock runs `gh` in Admiral's own environment, and a failure says so.
    - The host, owner, repo and PR number come only from the item's `pr_url` (`https://<host>/<owner>/<repo>/pull/<n>`, nothing else; always `--hostname <host>`) and `review_id` must be a positive whole number; otherwise 400 and `gh` is not run.
    - Submit reads the review (`GET repos/<o>/<r>/pulls/<n>/reviews/<id>`) and posts its current body, or the item's `summary` when that is empty, with the event (`POST .../events`, JSON on stdin through `--input -`, so item text is never an argument).
    - Discard is `DELETE` of the same endpoint, or, for a review whose `pr_url` or `review_id` is invalid, no `gh` call at all: the answer is `{"action":"discarded"}` and `review_discarded` carries `invalid_target: true`; the 200 response also says `"invalid_target": true`.
    - A 404, a 422 whose parsed `message` or `errors` name "pending" (not `documentation_url`), or on Submit a review whose `state` is not `PENDING` (no POST), means the review is gone: the answer is `{"action":"gone"}`, `review_discarded` is recorded with `external: true`, and the response is 200.
    - After a 404, though, Admiral also reads the pull request (`GET repos/<o>/<r>/pulls/<n>`), because a token that cannot see the repo gets 404 as well; if that fails too, it answers 502 and writes and records nothing, with the "token may not reach it" text only when the pull request answered 404, and gh's own text otherwise.
    - Any other `gh` failure writes no answer and no record, and answers 502 (503 when `gh` is missing) with `{"error": ...}` carrying gh's message, the whole message cut at 4 KiB, before the note on where gh ran.
    - A 200 carries `"action"` (`inbox.ActionSubmitted`, `ActionDiscarded`, `ActionGone`). Only one action runs on an item at a time (409 `ErrBusy`).
    - `.../discard` with `{"forget": true}` (Remove from inbox, for a review that fails forever) runs no `gh`: it writes `{"action":"discarded"}`, records `review_discarded` with `unreachable: true` only, and answers 200 with `"forgotten": true`, so the UI can say nothing changed on GitHub.
    - `POST /api/inbox/<session>/<id>/remove` (Remove from inbox, any item; `internal/inbox/remove.go`) does that for a review, and for a question or findings item writes `{"version":1,"id","kind","answered","removed":true}`, records `item_removed` (`item`, `kind`) and answers 200 with `"forgotten": true`. A removed item never queues its ship's resume text.
    - A sailed-off ship keeps its inbox only while an unanswered item is one its report lists in `inbox`, or any unanswered item when there is no report or the report has no `inbox` list (`inbox.Waiting`).
    - It is allowed on any review item, and Submit has no such option.
  - `POST /api/inbox/<session>/<id>/findings` (`{"cards":[{"id","decision":"approved"|"edited"|"rejected","proposal":{"kind":"diff"|"reply","content"}}]}`) needs a decision for every card id of the item, once each, and a proposal on an edited card only (400 otherwise); an item with no cards takes `{"cards":[]}`. It writes the answer's `cards` map and one record per card, and posts nothing to GitHub.
  - Outcome events (fields besides `item` and `kind`): `answered` (question), `review_submitted` (`review_event`, `edited`; a log line's `event` is the record name, so the review's event cannot be called `event`), `review_discarded` (`external: true` when gone, `invalid_target: true` when Admiral ran nothing for an invalid target, `unreachable: true` for Remove from inbox), `resumed` (`ship` is the session, with `live: true`, for a resume typed at a live ship's prompt), `card_approved`, `card_edited` and `card_rejected` (`card`).
    - A review or findings answer writes no `answered`; `crew_note_kept`, `crew_note_edited`, `crew_note_dropped` (`note` is the proposal's id, with `member` and `scope`); `crew_member_kept`, `crew_member_dropped` (`member`); `mission_kept`, `mission_dropped` (`name`).
  - **Kept inbox.** An exit-0 ship's session is killed at sail-off, and its report and inbox are removed once its `ended` is written (ADR 0015), unless its inbox still holds an item with no answer (`inbox.Unanswered`).
    - Then `ships.killShip` first copies the session's `name`, `fleet`, `fleet_name`, `fleet_color`, `harness`, and `dir` into `state.json` (`kept_inboxes`, by session; `state.KeepInbox`, written at once) and `removeShipFiles` skips a session with a record.
    - The record names the item's ship for the inbox reader (`Ship`) and gives `gh` its dock (`Dock`), and `launcher.pickName` never draws a name with a record (`Launcher.Kept`), because a launch clears the inbox of the name it takes.
    - When an answer leaves no item unanswered, `Service.release` removes the files (`launcher.RemoveShipFiles`, through an `os.Root`) and drops the record; `Service.Run` does the same at start-up for records whose items were answered meanwhile. Dismiss never keeps.
    - A directory with no record and no session is left alone.
  - **Resume text** (`internal/inbox/resume.go`, ADR 0016, amended by ADR 0034).
    - When every id in a ship's report `inbox` has an item file and an answer file, the report's `resume` text is captured into `state.json` (`resume_orders`, by session and a hash of the `resume` text and `inbox` ids, written at once) before anything can delete the report, but only when the ship is still afloat (`Service.Afloat`: underway or needs you).
    - There are no resume orders and no `autopilot.resume_source`.
    - `CaptureResume` runs from the answer path (before `Answer` releases a kept inbox), every inbox scan (`Refresh`), start-up (before `sweepKept`), and `release`.
    - A report with no `resume`, an empty `inbox`, or an id with no item file captures nothing. Finished entries go once the session's report is gone.
  - **Resuming a live ship** (ADR 0016).
    - `CaptureResume` queues the text of a ship that is still afloat (`Service.Afloat`: underway or needs you) at its prompt.
    - Each pass of `addResumes` first calls `typeResume`, which calls `Service.TypeResume` (`ships.Service.TypeResume`).
    - It types into the ship's own pane (`PaneID`) only while the ship needs you with reason `stop`: one line through `send-keys -l`, more as a bracketed paste from a buffer, then Enter, with Codex's 300 ms pause before it.
    - A typed text is finished at once and records `resumed` with `live: true`.
    - A ship that is busy or waits on a permission or a question is tried again on the next ship change (`Notify` kicks the loop) and every 15 s.
    - A ship that is gone, anchored or sailing off finishes the entry with one stderr line and no outcome record; the entry is kept so the text is never typed twice.
    - A text with a control character other than newline and tab is never typed.
