# Launching ships

Clone on launch, launching as a crew member, the ship cap, locked resources, worktrees, restricted temp dirs and the clone scan. Read it before changing `internal/launcher` or a launch route.

- Clone on launch (ADR 0009, ADR 0010 amendment).
  - `POST /api/ships` with `clone: true` and no `dir` runs `serveLaunch` -> `launcher.Clone` (`internal/launcher/clone.go`) before `admit` and outside `l.mu`: `repofinder.Hint` picks the repo (order `repo`, else the first URL in the text), `repofinder.CloneName` validates `host/owner/repo` against github.com and the fleet's GitHub source hosts, gh clones into a temporary `.admiral-clone-*` sibling in the clone root, and `renameNoReplace` moves it into `<clone_root>/<repo>` (it refuses an existing target).
  - `repofinder.CloneRoot` expands `~` and defaults to the first search root; `repofinder.FleetRoots` adds the clone root to the roots every project and checkout lookup reads.
  - The dirs route's `clone` field comes from `launcher.CloneTarget`. Statuses are in `docs/api.md`.
- Launching as a crew member: `Launcher.resolveMember` (`internal/launcher/member.go`) is the one path a ship (`Launch`, `Request.Member`) and a crew boat (`LaunchCrew`, `CrewRequest.Member`) take: it resolves over `CrewLayers` plus the memory and run layers, applies the harness lock, the model rule and the notes block (`crew.NotesBlock`, repo slug from `originSlug` via `git remote get-url origin`), and returns the harness, model args and prompt. `CheckMember` refuses what needs no disk, before any clone.
  - Warnings go to `Launcher.Warn` (the CLI prints them, the server logs them).
  - The launch form's "Launch as" select (`LaunchDialog.tsx`, `memberRun` in `launchForm.ts`) shows only with Just launch.
- Ship cap (`internal/config/maxships.go`, ADR 0034).
  - Top-level `max_ships` (positive integer, default 3, `config.Config.MaxShips`) caps the ships underway or needing you that autopilot-mode launches may start; hand launches are never capped and count towards it, and so is an AdmiralBot launch on the engineer's instruction (`launcher.Request.OnInstruction`, set by `serveLaunch` from the actor token, never from the body).
  - There is no per-panel autopilot config: a `sources.<key>.autopilot` entry or a top-level `autopilot` object is removed by the startup migration.
  - `launcher.Request` carries `Autopilot` and `Resources` (JSON `autopilot` and `resources`, so `POST /api/ships` sets them), and `ExtraArgs` and `Panel` (`json:"-"`). Autopilot mode is a launch mode (ADR 0034).
  - `serveLaunch` refuses a resource not in the config (400), an `autopilot` request on a harness whose guard probe has not passed in the launch's fleet (400, `autopilotgate.Check`), an autopilot launch when `max_ships` ships are already underway or need you, launches in flight and ships the host has not listed yet included, unless AdmiralBot made it on the engineer's instruction (409; `admitMu` is held from the count to `LaunchOrder`'s return for autopilot launches only, so two launches cannot both take the last slot) and a named resource that is busy, missing or pending (409, nothing queued); it holds the reservation until `LaunchOrder` returns, through `ships.Service.Reserve`.
- Locked resources.
  - Config: top-level `resources` (`config.Resource{Capacity, Check}`, `capacity` an integer >= 1 defaulting to 1, `check` a non-empty argv of non-empty strings, names `^[A-Za-z0-9_.-]{1,64}$`) and `autopilot` launches name them.
  - `internal/resources.Set` answers which units are held and by whom: a ship holds one unit of each name in its `@admiral-resources` option (`Ship.Resources`, `json:"-"`; set from `launcher.Request.Resources`) while `underway` or `needs_you`, as do locks (`Set.Lock`, non-blocking, no check needed, for `admiral lock` to call) and reservations. A name no longer in the config holds nothing.
  - `Set.Ships` is `allShips` in `main.go` (List + Pending), so a just-launched ship counts before the host lists it (`ships.Pending` carries the request's resources).
  - `Set.Reserve` checks and reserves all-or-nothing under the Set's mutex and answers `Wait{Name, Why}` with `busy`, `missing` or `pending`.
  - `serveLaunch` reserves through `ships.Service.Reserve` and drops the reservation as soon as `LaunchOrder` returns, on every outcome.
  - Checks run as an argv with no shell, in their own process group, killed as a group at 10 s (`missing`); `Set.Run` runs them all at once, on `Refresh` (a config change) and every 15 s, never two at once for one resource, and a resource is `pending` until its first check ends (`none` when it has no check).
  - A changed check state or a released lock calls `Options.OnChange` (`main.go` pushes the `resources` message). A dropped reservation calls it too.
  - All three close the channel `Set.Changed` returns, and so does `Set.Wake`, which `main.go` calls on every ship change and config change (a ship leaving `underway` frees a unit with no event of the Set's own).
  - `GET /api/resources` and the WebSocket `resources` message (`resources.Service`, sent on connect and on change through `BroadcastOnce`) carry `{"resources": [{name, capacity, in_use, holders: [{kind: "ship", session} | {kind: "lock", label}], check}]}` sorted by name, with no timestamps.
  - `POST /api/resources/<name>/lock` (`internal/lockroute`, for `admiral lock`) holds a unit as an open request: no body, query `label` (cleaned to printable, at most 64 characters) and `wait=1`; it answers `200` with one flushed line `{"held":true}`, then stays open and releases the unit when the request context ends or the server shuts down (`srv.RegisterOnShutdown` closes `Route.Stopping`; the background context is cancelled only after the drain, which waits on this handler).
  - Without `wait` a busy resource answers `409`, an unknown one `404`; with `wait` the handler waits on `Set.Changed()` (fetched before each `Lock` try) and a 15 s timer (a pending ship that expires frees a unit with no wake) and a client that leaves while waiting holds nothing.
  - A request that is not local gets `403`, paired device or not (`auth.IsLocal`: a proxied loopback request is remote; a LAN peer with no token gets the middleware's `401` before it reaches the route); the handler reads the body first, because Go cancels the context on a hang-up only once it has.
  - `OnTake` pushes the `resources` message, since `Set.Lock` doesn't announce a take.
  - `admiral lock` (`internal/cli/lock.go`) splits its arguments at the first `--` before parsing flags, probes the server as `ships` does, sends `admiral lock (pid <its own>): <argv[0] base>` and runs the command after the `held` line; it returns a `cli.ExitError` (code, optional message) for 75, 127 and the command's status, which `main.go` maps; after `held` it keeps reading the response and, if that ends while the command runs, prints `lost the lock` to stderr and leaves the command running; it forwards only SIGTERM (it catches and ignores SIGINT, SIGHUP and SIGQUIT, which the terminal sends to the command). The `-h` scan in `main.go` stops at `--`.
- A no-skill or drafting ship's worktree (`internal/launcher/worktree.go`, ADR 0043): `Launch` gives every `Kind: "none"` launch, and every drafting launch (`Request.Drafting`, which needs a git checkout and an installed skill, runs With you and names `ships/<session>/campaign-ref` in its text), that is not restricted, event, promoted or a scout a worktree of the picked checkout through the `Launcher.Worktrees` seam (`GitWorktrees` in `cmd/admiral`; nil runs in place, as the `internal/ships` unit rigs do).
  - `Fetch` asks `git ls-remote --symref origin HEAD` for the default branch and fetches it, before the launch lock is taken (a checkout with no `origin` configured fetches nothing: it returns `refs/heads/<b>` for the first local branch among `init.defaultBranch`, `main` and `master`, and none of them refuses the launch with a 400 naming them), and `Add` runs `git worktree add --no-track -b admiral/<session> $ADMIRAL_HOME/worktrees/<session>` from the fetched ref.
  - Every git call the worktree makes (fetch, add, remove, the branch listing) has a 30s deadline and cannot prompt (`GIT_TERMINAL_PROMPT=0`, SSH `BatchMode=yes` unless the engineer set their own); a failed or timed-out fetch of a configured `origin` refuses the launch (400), and a search root that is not a git checkout runs in place.
  - The `dir` option stays the engineer's checkout (last dir, `Ship.Dir`, the moored record, Hand to Commodore); the worktree is only the harness's cwd and what `req.Before` gets, so a round's feedback lands in it.
  - A relaunch (`req.Session` set) never makes a worktree: it reuses the one its session has whatever its skill kind, which covers a feedback round and Hand to Commodore (a scout always runs in its checkout), and runs in the checkout when it has none. A failed launch removes only a worktree it made.
  - `pickName` treats a kept worktree as taking the name, and a surviving `admiral/<session>` branch too when the launch will make a worktree (one `for-each-ref`).
  - Only Return to port removes it: `advanceReturns` calls `launcher.RemoveWorktree(home, name, checkout)` after `stopShip` succeeds (it takes the repo from the ship's `dir` option and drops only this worktree's registration), for both `serveReturn` and `returnMerged`, and the branch stays.
  - Dismiss, Stop ship, sail-off, finishing (below) and a PR closed unmerged leave it.
  - **Local-only checkouts.** `launcher.LocalOnly(dir)` is true for a directory inside a working git checkout (`git rev-parse` succeeds, so a subfolder of a no-origin repo counts) whose configured `remote.origin.url` (read with `git config --get`, never `git remote get-url`, which applies `insteadOf`; only exit status 1 means no origin, any other failure refuses the worktree launch like a failed fetch) is empty or not a GitHub URL by `crew.OriginSlug`; a non-git folder is not local-only.
    - `local-only` and `branch` are in `sessionhost`'s `optionNames` and tmux format, which must list the same names in the same order.
    - `Launch` decides it once and records the `local-only` tmux option (`1`) next to `scout` and `drafting`, plus `branch` only for a local-only ship that has a worktree (a GitHub launch sets neither); `ships.Ship` carries `local_only` and a `branch` that Admiral derives as `admiral/<session>` when the option is set, never reading the option's text.
    - A local-only quick ship that gets closing steps (`withClosingSteps`: chat-launched, skill none) is told to commit, not push or open a PR, and report `prs: []`; a GitHub origin keeps today's text.
    - A drafting launch from a local-only checkout is refused (400: campaigns need a GitHub repo).
    - A non-GitHub origin still fetches and cuts from its default branch.
  - **Finishing.** `finishLocal` (after `autoMoor` in the run loop) ends a live local-only quick ship at needs you (reason `stop`) whose report says `done` with no PRs: a `finished` outcome record, then `recordKilled` (its `ended` keeps findings and usage and cleans files; `finished` comes first in `settle`, so it adds no card), then the session ends (a failed kill is tried again), with the worktree and branch kept and no moored record. A clean exit after such a report goes through `settle` and its `ended` record carries the report result. The card detector reads either as a `done` card.
- A restricted ship's temp dir (`internal/launcher/restricted_temp.go`): a real dir `$ADMIRAL_HOME/restricted/<session>-tmp` (0700) behind a short link `/private/tmp/adm-<8 hex>` (at most 28 characters, because the sandbox's `$TMPDIR` follows `CLAUDE_CODE_TMPDIR` only for short paths).
  - `CLAUDE_CODE_TMPDIR` and `TMPDIR` are the link, the profile's `sandbox.filesystem.allowRead` holds the resolved dir (it sits under the denied home) and `denyWrite` closes the whole of `/tmp/claude-<uid>` and `/private/tmp/claude-<uid>`.
  - `RemoveRestrictedFiles` removes the link only while it still points at the ship's dir, then the dir; `serve` calls `SweepRestrictedLinks` at start to remove dangling `adm-*` links that point under this home's `restricted/` and no others.
  - `RestrictedProfile(level, checkout, dir, home, tempLink)` takes the link.
  - The restricted sandbox probe (`internal/probes/restricted.go`) checks all of it on real Claude Code: the ship's `$TMPDIR` is under its link and writable, writes into the shared Claude temp dir are refused, Write to `.git` is refused through a symlink, a case variant and a hard link, a `.GITMODULES` touch and a rename of `.git` are refused, no `.git` appears below the clone's root after a nested `git init` or a repo moved in from the temp dir (the profile's `<checkout>/*/**/.git`, `<tempDir>/**/.git` and `<default root>/**/.git` denies, for each of Claude Code's default write roots `/tmp/claude`, `/private/tmp/claude` and `~/.npm/_logs`, as `denyWrite` and `Edit(//…)` rules; the profile holds no `Write(...)` rules, which Claude Code ignores), and a commit in the clone gates the probe (the `.git` deny is per path, so git can write its index and objects).
- The clone scan (`internal/promote/clonescan.go`, ADR 0038): unsandboxed git must never run over a tree a restricted ship planted a repository in.
  - `promote.ScanTree` walks the clone's work tree in Go with no links followed and refuses a `.git` (file, folder or link) or `.gitmodules` below the root and a root `.git` that is not a real folder, matched case-insensitively, and `promote.CheckModes` refuses a gitlink in an index or tree listing (`-z`, so odd paths arrive unquoted).
  - A refusal is `promote.ErrGitCarrier` with a fixed reason and the path, relative, cut to 200 raw bytes and then `%q`-quoted.
  - A relaunch over a kept clone (`shipCheckout`, a `Session` that names an existing clone, through `checkClonedSubmodules`, which also compares the root `.gitmodules` with the routine repo's) and `promote.Read` (the Promote route answers `400` with the path) both run it first.
  - `startFromSetup` reads again after the stop, so a clone that gained a carrier meanwhile answers the fixed `500` and logs the path.
  - `safeGit` blanks no filter driver: it is safe because `ls-tree`, `ls-files -s` and `hash-object --no-filters` run none, and `neutralgit` blanks them for every other call.
  - `nameFor` refuses a relaunch while the ship's tmux session is listed, and the scan runs only after; a process that left the session can still outlive it, and reuse has no production caller today (only `ships/wake.go` passes a `Session`, and it never sets `Restricted`).
  - Don't open a restricted clone, or any folder under it, in a shell or editor.
