# Devices and pairing

Access control, per-device tokens, pairing codes and the device API. Read it before changing `internal/auth`.

- `internal/auth` classifies each request by path.
  - Local: loopback peer, no `X-Forwarded-For`, `Forwarded` or `Tailscale-User-*` header, and an allowed Host; it needs no token. LAN: non-loopback peer, no proxy header.
  - Tailnet: loopback peer with `Tailscale-User-Login` (RFC 2047-decoded, as tailscale serve encodes a non-ASCII login, and trimmed once in `classify`, then compared exactly), and only while `remote.tailscale` is true and the login is on `remote.allowedLogins`; auth reads both from the live config on every request (`auth.WithRemote`), so removing a login disables its devices at once. Anything else gets 401 (403 for pairing).
  - The `remote` config key is `{tailscale, allowedLogins}` (`config.Remote`, `Manager.SetRemote`); with `tailscale` true `--listen` defaults to `127.0.0.1:<port>`, else `0.0.0.0:<port>` (the port is 7420, or `ADMIRAL_PORT` for a test), and an explicit `--listen` wins.
  - The listener follows the mode live (`cmd/admiral/rebind.go`): the config subscriber (`moveListener` in `main.go`) sends the move message to the browsers the move leaves behind (`Hub.SendPaths`, by the path `auth.PathName` gave each ships socket; at most 2 s), then `EnforceRemote`, then `listener.Move` binds the new address and retires the old one (retrying once with the old one closed, since a wider address can overlap it on some systems).
  - A bind that fails restores the old address, logs, and shows as the `listen` check of `GET /api/remote`; with mode on, once the move succeeded, the LAN connections already accepted are closed (`DropOffLoopback`) and every open LAN socket is cut through auth's socket registry (`Auth.CutLAN`; a WebSocket is hijacked, so only the registry sees it).
  - An explicit `--listen`, or a config that can't be read, never moves it.
  - `main` calls `Manager.Reload` after `OfferSetup`, so the start that follows setup reads the mode setup wrote.
- A device holds its own token, stored only as a sha256 hash in `$ADMIRAL_HOME/devices.json` (mode 0600, written through a temp file and rename). Compare with `subtle.ConstantTimeCompare`. A tailnet device is bound to the login it paired with and works only on the tailnet path; a LAN device works only on the LAN path. A device unseen for 90 days is dropped.
- A request carries the token as `Authorization: Bearer` or the cookie `admiral_token_<port>` (HttpOnly, SameSite=Strict, 400 days; re-issued at most daily; last-seen written at most hourly). The Origin rule applies to cookie and local requests, not Bearer. `?token=` is not read anywhere.
- Pairing: `POST /api/v1/pairing-codes` (behind the normal auth) returns `{code,url,expires}`; the code is 8 Crockford base32 characters shown `XXXX-XXXX`, lives 5 minutes, one at a time, and works once. `GET /pair?code=` and the `POST /pair` form redeem a code for a browser (cookie set, redirect to `/`); `GET /pair` serves the entry form; `POST /api/v1/pair` returns `{token,device:{id,name}}` and sets no cookie. Ten failed redemptions in 5 minutes give 429. The pair routes and nothing else skip the token check, and a request from the local path is refused with 403.
- Device API (`internal/auth/api.go`): `GET /api/v1/devices`, `PATCH /api/v1/devices/<id>` (rename), `DELETE /api/v1/devices/<id>`, `DELETE /api/v1/devices` (all). Revoking closes that device's WebSockets; `track` re-checks under the mutex that the device still exists before it registers a socket, so a revoke can't miss a socket opening beside it.
- Web Push subscriptions live on the device record in `devices.json` (`internal/auth/push.go`: `Subscriptions`, `DropSubscription`, the `/api/v1/push/` routes).
  - A loopback (Local route) subscribe makes or reuses the device `This Mac` (`thisMac: true`, no token, never matches `authenticate`); a Local request refreshes its `lastSeen` at most hourly so the 90-day prune leaves a Mac in daily use.
  - `internal/push` holds the rest: `vapid.go` (the one P-256 key in `$ADMIRAL_HOME/vapid.json`, made once, an unreadable or corrupt file is an error, never replaced), `encrypt.go` (RFC 8291), `endpoint.go` (`CheckEndpoint`, and `DialControl`/`SafeClient`, which refuse local destinations at dial) and `sender.go` (the `Sink` for the Push outcome: a bounded queue and one goroutine, `Deliver` never blocks, 404 and 410 drop the subscription). `cmd/admiral` joins the two with `pushDevices`.
  - Forwarding lives on the device record too (`forwarding`, `lastFollowed`): `push.Followers` reports follow, unfollow and the last follower socket's close through `FollowRecorder`, `*auth.Auth` writes them, and `forwardingState` reads `on` or `stopped` when listed from the injected clock, Admiral's start and `Followers.Connected`.
  - `cmd/admiral/push_e2e.go` (tag `e2e`, which `make build` passes and `make release` does not) reads `ADMIRAL_PUSH_TEST_ROOTS` so the e2e binary can reach a fake push service.
- Startup prints three lines: the local URL, `On other devices: http://<ip>:<port>/` (no token) and `To pair a device, run: admiral pair`.
  - `e2e/harness_test.go` reads the first two and mints a device through the loopback API.
  - With `remote.tailscale` on, `internal/tailscale` runs the `tailscale` CLI (`status --json`, `serve status --json`, 4 s each) once at startup: Funnel on for Admiral's port (a `Web` handler or a `TCPForward`, in serve or a `Foreground` serve) refuses to start with one line on stderr naming the off command; a raw TCP forward without Funnel only fails the `serve` check; any other failed check starts Admiral, and the `On other devices:` line is `https://<MagicDNS name>[:<port>]/` when serve proxies to Admiral's port, else `Tailscale mode is on, but <first failed check>`.
  - The pairing base is that URL, computed per mint; `admiral service install` prints the same.
  - With the mode off Admiral never runs `tailscale`, apart from Settings' Set up.
  - `internal/tailscale`'s `Route` also serves `POST /api/remote/logins` (one edit under a lock, through `Manager.SetRemote`) and `POST /api/remote/setup` (local requests only; `Prepare`, `EnableServe` on Admiral's live port, then `config.Remote.Allowing`, which `admiral setup` shares); see `docs/api.md`.
  - The new shell's Remote access page shows the checks, the URL with Copy, the logins and Set up, and a 401 on any request or a ships link that finds the token gone shows the signed-out line at `/pair` without a reload (`web/src/app/session.ts`).
