# Hooks and the autopilot guard

How `admiral hook` decides needs you, how `admiral guard pretooluse` refuses a merge or review, and the environment every ship gets. Read it before changing `internal/cli/hook.go`, `internal/cli/guard*.go` or the launcher bundle.

- With `needs_you` it also sets `@admiral-reason` in the same tmux call, a code and never payload text: `permission:<tool>`, `question`, `notification:<type>`, `stop`, or `bell` from a Codex bell; `working` unsets it, and `sessionhost` polls it into `Session.Reason`.
- A tool name or type is kept only if it matches `^[A-Za-z0-9_.:-]{1,64}$`, and a notification's reason is written only if none is set, so `permission:Bash` survives either order of Claude's two events.
- `internal/cli/hook.go` holds the event→state and event→reason rules, and Claude's `Stop` writes nothing while `background_tasks` has a running `subagent` or `teammate`, so a running `shell` task doesn't hold a ship back.
- A Monitor is the exception: it also reports as a `shell` task, so a Monitor's `PostToolUse` keeps its `tool_response.taskId` in the pane option `@admiral-monitors`, and a `Stop` writes nothing while one of those ids is running (each `Stop` drops the ids no longer running).
- A persistent Monitor is not kept, since it has no timeout to wake the session.
- A crew pane's plain `Stop` writes `idle`, not `needs_you`: it holds no lead's `Stop` and doesn't raise the ship.
- A lead's `Stop` held only by working crew sets `@admiral-crew-held`, which its next state write clears, and the last boat to go idle flags that lead with reason `stop`.
- `admiral guard pretooluse` (`internal/cli/guard.go`, also unlisted in the usage text) is Claude's other PreToolUse hook, in the settings for `Bash`, for `^mcp__.*pull_request_review.*$` and for `launcher.MergeToolMatcher`.
- All handlers have `"timeout": 10` and `"onFailure": "block"`, because Claude Code lets a call through when a PreToolUse command hook times out or fails (`onFailure` needs Claude Code 2.1.295 or later).
- It does nothing unless `ADMIRAL_AUTOPILOT` is exactly `1`; then it parses a Bash command with `mvdan.cc/sh/v3/syntax` (`guard_shell.go`, which also looks through wrappers, `sh -c`, `eval` and heredocs fed to a shell).
- When the command doesn't parse as bash, it walks the statements parsed before the error, then parses the whole text as zsh, then applies a text rule (a line that mentions a review and an approve or request-changes spelling) to the whole line.
- A program word with an expansion that is followed by `pr … review`, `pr … merge`, `pr … edit` or `api` is checked as `gh`; any other unknown program, or a shell reading a pipe, gets the text rule on its own call or statement, computed once per span.
- Where it has no text for what it judges (a program word that is only an expansion, a `-c`, `eval` or heredoc script that is only an expansion, a shell reading a pipe or a file, a GraphQL `query` that is only an expansion), it also reads the whole line, once, for long spellings only (`review` with `approve`, `request_changes` or `request-changes`); short flags are not matched there.
- A program word that is only an expansion (`$C`, `${=C}`, `"${C[@]}"`) that no rule names is refused as `shell_script`, because the command in it can't be seen, which is also how a long spelling split by quotes (`C="gh pr me""rge 5"; $C`) is caught.
- Other `gh` calls are allowed, `gh pr ready` among them, unless a rule below names them.
- It refuses, with exit 2 and the one reason line on stderr, a command or MCP call that would submit a review as APPROVE or REQUEST_CHANGES (`gh pr review`, `gh api` reviews calls and GraphQL), or a payload it can't read; those get the review reason.
- The merge rules (`guard_merge.go`) refuse with a merge reason: every `gh pr merge` that can merge, `--auto` and `--admin` included (`gh_pr_merge`; autopilot never merges); `gh api` writes to `pulls/<n>/merge` and `merges` (`gh_api_merge`); the GraphQL mutations `mergePullRequest`, `enablePullRequestAutoMerge`, `mergeBranch`, `enqueuePullRequest` and `dequeuePullRequest` (`graphql_merge`); writes to rulesets (repository and organization) and branch protection, through REST or GraphQL, which would lower the gate on a merge (`gh_api_gate_write`, `graphql_gate_write`); and any change of a pull request's base (`pr_base_change`: `gh pr edit -B` or `--base`, a REST write to `pulls/<n>` with a `base` field or an `--input` it can't read or that has one, GraphQL `updatePullRequest` with `baseRefName`, its input in a variable, or an expansion).
- A write is any `gh api` method but GET and HEAD, a method held in a variable, or gh's implicit POST (`-f`, `-F` or `--input` with no `-X`).
- API paths are percent-decoded and have empty and `.` segments dropped and `..` resolved before they are matched; one that climbs above its root is one expansion.
- An expansion in a path counts as any words there: a write is refused when the expansion ends the path after a prefix a merge or gate route extends (`repos/<o>/<r>`, `pulls/<n>`, anything under `branches`, `orgs/<o>`), or when the literal words after it end in `merge` or `merges` or hold `protection` or `rulesets`, so `gh api -X PATCH repos/o/r/issues/$N -f state=closed` and `-X PATCH repos/o/r/pulls/$N -f body=x` are allowed (only a PATCH may end a path in an expansion right after `pulls`, because the merge route is a PUT; a `base` field is refused as `pr_base_change`).
- MCP tools are matched by `launcher.MergeToolMatcher` (any `mcp__` tool with `merge` or `enqueue` in its name, in any case, spelled with character classes because Claude Code matchers are JavaScript regular expressions with no `(?i)`), and the guard refuses every tool the matcher selects except those whose last name segment starts with `list_`, `get_` or `search_` (`mcp_merge`); the guard compiles the same constant, so the two agree.
- Where the guard can't parse a command and falls back to text, the text rule also refuses text that mentions `pr … merge`, a `pulls/…merge` or `/merges` route, `rulesets`, `/protection`, or those mutation names (a merge in `eval "$C"`, `echo '…' | bash`; `pr` and `merge` count anywhere in the text, so `A='gh pr '; B='merge 1'; eval "$A$B"` is refused).
- A GraphQL `query` the guard can't read is refused (`graphql_merge`): a file or stdin that isn't shown on the line, a query that is only an expansion or has an expansion beside the word `mutation` or outside a value position, and an `operationName` beside an expanded query; pass values as GraphQL variables (`-f id="$ID"` with a literal query) instead.
- A script given as an expansion alone (`eval "$(cat m.sh)"`, `bash <<< "$X"`) is refused as `shell_script` unless the line itself shows a merge, which gets the merge rule.
- Rules that keep the guard from being routed around, with their own reason (`opaqueReason`): `gh alias` and `gh extension` (`gh_alias`, `gh_extension`); a first `gh` word that is not one of gh's built-in commands (`ghCommands`, including help topics; `gh co` is an alias and stays refused; `gh_unknown`); an expansion in the word after `gh pr` or `gh auth` (the first is refused with the merge rule, the second as `token_read`); the shell builtins `alias`, `unalias` and `hash name=path` / `hash -p`, and assignments to `aliases`, `functions`, `commands`, `BASH_ALIASES` and `BASH_CMDS` (`shell_alias`); and scripts the guard isn't shown.
- For `bash|sh|zsh FILE`, `source FILE` and `. FILE` the guard reads the file with the limits of any file it reads (a regular file of at most 1 MiB, from the call's cwd), checks it as a command line of its own, and uses that result; it refuses with `shell_script` only a file it can't read or parse, a script given by an expansion, a shell fed from a pipe, `-s` or `sh < f`, and the arguments of an `xargs` that runs `gh` or a shell.
- Stdin counts as shown only when the statement has exactly one input source and its text is literal: one heredoc or here-string with no expansion, or one `<` from a literal file, or no stdin redirect and a literal `echo`, `printf` or `cat` of a literal heredoc before the pipe (words with no escapes).
- A `<&`, a `<>` or a second redirect of fd 0 means stdin is not shown, because zsh reads several and bash the last.
- A GraphQL `query` on stdin, a write's `--input -` body and a `pulls/<n>` PATCH are refused otherwise.
- An `--input` body, from stdin or a file, is decoded as a JSON object before it is read, so a `\u` escape can't hide a name, an event or a key (this covers the review rules too); keys are read by their exact names, and a body with two keys that differ only in case, or that isn't a JSON object, is refused.
- Boolean flags are read as gh reads them, with `strconv.ParseBool` (`--disable-auto=0` is false), and a value that isn't a boolean is refused.
- The token is refused when it is read, not when it is named: an expansion of `GH_TOKEN`, `GITHUB_TOKEN` or the enterprise names in any form, `printenv` or a bare `env`, `gh auth token` or `status -t`, `git credential`, and `security find-generic-password` or `find-internet-password` with `-w` or `-g` (`token_read`); `grep -rn GITHUB_TOKEN .github` or a quoted heredoc that writes `${{ secrets.GITHUB_TOKEN }}` is allowed.
- `gh pr merge --disable-auto` without `--admin` is allowed: it merges nothing.
- Programs that run their arguments are looked through when they are `find` (`-exec`, `-execdir`, `-ok`, `-okdir`), `arch`, `script`, `flock`, `watch`, `unbuffer`, `doas`, `gtimeout`, `npx`, `xargs` and the usual wrappers; `git -c alias.x=!…` and `git config alias.x '!…'` are refused as `git_shell_alias`.
- A relative file is not read once the line has a `cd`, `pushd` or `popd` (the guard would read a different file from the one the call reads), `~/` is the home directory, and a shell is refused when `BASH_ENV`, `ENV` or `ZDOTDIR` is set on the line or when `--rcfile`, `--init-file` or `-i` comes beside a script.
- `gh auth status --show-token` is read as a boolean, and `git credential-*` helpers count as `git credential`.
- Known gaps:
  - The guard is best effort, and the GitHub rules of the base branch are the gate: it narrows what a ship can do by accident or by habit, and it can't contain an agent that runs arbitrary programs with a token that can merge.
  - The Merge route's token (`X-Admiral-Merge-Token`, injected into the `/app/` page's `<meta name="admiral-merge-token">` by `internal/server`) keeps a local curl from merging by accident; a process that fetches `/app/` and reads the meta, or impersonates a browser, still can.
  - A script run as `./FILE` runs unread (`bash FILE` is read, but the same file as a command is not).
  - A program word built from a literal and an expansion (`g$Y`, `$D/gh $S`), zsh glob qualifiers that run code (`*(e:'…':)`), the `(e)` parameter flag and arithmetic that evaluates a subscript (`$((X))` with `X='a[$(…)]'`) run a command the guard reads as data.
  - Sourcing nvm (`. ~/.nvm/nvm.sh`) is refused, because nvm defines aliases (`shell_alias`); set Node up outside the ship.
  - The guard is best effort and reads only the text of a Bash call: a merge through anything that is not a literal shell `gh` call is invisible to it, such as an interpreter (`python3 -c`), `make`, `curl` with a token from somewhere else, a nested agent, a `gh` shim earlier on `PATH`, or a replaced `$ADMIRAL_HOME/bin/admiral`.
  - Files the guard reads (`--input`, `-F @file`) can change before gh reads them.
  - Direct writes to the base, `git push`, REST `PUT contents`, `PATCH git/refs`, GraphQL `createCommitOnBranch` and `updateRef`, and the GitHub MCP file tools, are not hooked, and neither are writes to repository settings that raise access (`collaborators`, `PATCH repos/<o>/<r>`); the branch rules on GitHub are what stop them.
  - The GitHub MCP `update_pull_request` tool with a `base` argument changes a base and is not hooked.
- Codex and Copilot ships have no guard, and autopilot refuses any harness but Claude for that reason; so does `admiral crew launch` for a caller with `ADMIRAL_AUTOPILOT=1`, whose `--arg` values must also fit the autopilot args allowlist (`launcher.AutopilotArgs`, `internal/launcher/autopilotargs.go`, a per-harness table of flags with their arity; codex's and copilot's tables are ready but unreachable until a guard probe is registered for them in `probes`), checked in `LaunchCrew` after the hook refusal and before the window is made.
- A refusal writes one `guard_denied` line (`tool`, `rule`, no command text) under the home of `ADMIRAL_REPORT`, or else `ADMIRAL_HOME`; with no ship or home, or a failed write, it still refuses.
- Every ship also gets these variables:
  - `ADMIRAL_SHIP` (its session name).
  - `ADMIRAL_REPORT` (`$ADMIRAL_HOME/reports/<session>.json`).
  - `ADMIRAL_FINDINGS` (`$ADMIRAL_HOME/reports/<session>.md`, cleared at launch, markdown a scout or quick ship leaves for later; `internal/findings` copies it to `$ADMIRAL_HOME/findings/<hex ship>/<hex first launch>.json` when `ended` is written, before the ship's files go, and keeps it indefinitely, 0700/0600).
  - `ADMIRAL_INBOX` (`$ADMIRAL_HOME/inbox/<session>/`).
  - `ADMIRAL_CREW_DIR` (`$ADMIRAL_HOME/fleets/<fleet key>/crew/`, made 0700 when missing, kept across ships, and refused with a 500 when `fleets`, the key or `crew` is a link or not a directory).
  - `ADMIRAL_MISSIONS_DIR` (the fleet's missions directory, `$ADMIRAL_HOME/fleets/<fleet key>/missions/`, made and refused the same way, before the inbox is created; Commodore owns the files in it), which win over a fleet's env.
  - A launch with `crew` pins (Commodore only) also gets `ADMIRAL_RUN_CREW`, the per-ship run layer `$ADMIRAL_HOME/run-crew/<session>/` (0700) that Admiral fills with the pinned members' files, and a launch without pins has it unset even when a fleet's env sets it (`launcher/crewpins.go`; `RemoveShipFiles` removes it with the report and inbox).
  - Commodore ships on Claude also get `CLAUDE_CODE_AUTO_COMPACT_WINDOW=200000`, a fleet's `env` overrides it, and `1000000` turns it off.
  - An autopilot-mode launch also gets `ADMIRAL_AUTOPILOT=1` and `ADMIRAL_LOW_STAKES=advisor`, and a launch by hand has neither (nothing sets `ADMIRAL_AUTO_MERGE`, and it is still dropped from inherited env): Admiral owns these names, so it drops them from the fleet's env and runs `set-environment -r` for each on the session (`-r`, because the tmux server inherits Admiral's own environment, which may hold them; `-u` would fall back to it).
- A panel's autopilot args go after the fleet's dock args; Admiral removes any report and inbox a reused name left, then creates `reports/` and the inbox before the harness starts.
- Every start links `$ADMIRAL_HOME/bin/admiral` to the running binary and puts that directory first on a ship's `PATH`.
- `HiddenOrders` lists the orders that have a ship, which refuses a second launch from one unless the engineer sends `anyway`.
