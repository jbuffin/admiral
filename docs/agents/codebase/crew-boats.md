# Crew boats and subagents

Crew boats (teammates): the CLI, tmux options, the lead rule, subagent marks, option text as untrusted input and the wire shape. Read it before changing crew launch, `sessionhost` crew reads or the crew bridge.

- Crew boats (teammates, ADR 0014): `admiral crew` (`internal/cli/crew.go`) reaches tmux on `$ADMIRAL_HOME/tmux.sock` through `internal/sessionhost` and still needs no server; it finds the home from `ADMIRAL_HOME`, else from `ADMIRAL_REPORT`.
  - `launcher.LaunchCrew` (`internal/launcher/crew.go`) makes a `new-window -d` in the ship's session on a placeholder, sets the window options (`@admiral-crew-name`, `-harness`, `-dir`, `-launched`, `-role` when `--role` was given, `remain-on-exit`, `monitor-bell`), then respawns it as the harness with the chosen dock's env (argv: `exe`, the dock's `args`, the hook flags, the `--arg` values, the prompt; `launcher.RefuseHookArgs` in `hookargs.go` refuses a value that overrides or disables the hooks, before `new-window`), with `env -u` clearing the ship's `ADMIRAL_SHIP`, `ADMIRAL_REPORT`, `ADMIRAL_FINDINGS` and `ADMIRAL_INBOX` and every key the ship's dock `env` sets that the chosen dock's doesn't, except `ADMIRAL_CREW_DIR`, `ADMIRAL_MISSIONS_DIR` and `ADMIRAL_RUN_CREW`, which a boat keeps from the ship's session; `-e` carries only the chosen dock's `env`, never the caller's environment.
  - It never calls `Launch`/`shipContract`.
  - `sessionhost.ReadCrew` (`internal/sessionhost/crew.go`) is the one reader of crew from tmux (window rows with `@admiral-crew-name`), with `CrewState`, so `crew list` and the server compute the same `state`.
  - `parseRows` skips crew rows in its ship loop and folds them into `Session.Crew` through `parseCrew` (the one crew rule, shared with `ReadCrew`), but a crew row never sets a ship field (`PaneDead`, `ExitStatus`, `State`, `Options`, `PaneID` and the rest come only from the ship's own row, wherever it sits in the list), a session with only crew rows is no session, and crew fields stay out of `set()`'s event diff, because a window option shadows the session's of the same name; `Session.PaneID` is the ship's own pane, which `Host.SetNeedsYou`/`SetWorking` target instead of `=session:` (the current window's active pane).
  - `admiral hook` stamps `@admiral-activity` (RFC 3339) on `$TMUX_PANE` on every event: a crew boat's `last_activity`. **Lead rule** (`leadDecision`, `internal/cli/hook.go`): a lead's `Stop` (Claude Code, Codex) or Copilot lead `agentStop` leaves `@admiral-state` alone while a crew window of its session has a live pane (`pane_dead` 0) that is working, so the lead stays `underway`; otherwise `needs_you` `stop`.
  - A lead is a `$TMUX_PANE` whose window has no `@admiral-crew-name`; a crew boat's own `Stop` keeps `needs_you`, and no crew hook re-evaluates its lead.
  - A pane is working when its own `@admiral-state` is `working` (`show-options -pqv`, per live crew pane after one `list-panes -s`), or when it has no state and no `@admiral-activity` yet and its window's `@admiral-launched` is under 10 s old (ADR 0007's no-hook window; `crew launch` writes no state).
  - So a crew boat with no hook yet, such as one stuck on Codex's hook review dialog, holds a lead `Stop` that arrives within its first 10 s.
  - A held `Stop` is never re-evaluated: that lead shows underway until its own next hook. A dead pane keeps its state and never counts.
  - Each tmux read the hook makes has a 2 s deadline; a crew pane whose state read fails counts as having no state, so it falls to the launch-window check.
  - Claude's `background_tasks` rule runs first and the crew is read only when `Stop` would otherwise write `needs_you`; a failed crew read writes `needs_you` `stop`.
  - `@admiral-role` is a crew tail field of the row (before the subagents, which stay last), and `parseCrew` reads it only if it matches `launcher.CrewName`.
  - `@admiral-crew-transcript` (ADR 0021) is the next tail field, a **pane** option (the other crew record fields are window options): `crewTranscriptCall` (`internal/cli/hook.go`) appends `if -F -t <pane> '#{!=:#{@admiral-crew-name},}' "set -p …"` last (`sessionhost.CrewGateFormat`: a bare name format would read a boat named `0` as false; the call is skipped unless the pane matches `^%[0-9]+$`) in the event's one tmux call, Claude Code and Codex from `transcript_path` on any event, Copilot from `transcriptPath` on a lead `agentStop`.
  - `parseCrew` re-checks it with `sessionhost.ValidCrewTranscriptPath` (`ValidTranscriptPath` plus valid UTF-8, no control (C0/C1), bidi or line/paragraph separator character, and none of `'`, `"`, `\`, `` ` ``, `$`, `#`, `;`, `{`, `}`) and `Crew.Transcript` feeds `crew list --json`'s `transcript`.
    - Admiral never reads the file.
    - `tailFields` is 7; the subagents are at `+6`.
    - `ReadCrew` reads the state through the `#{@admiral-state}` format, which falls back to the window's and session's value; the two agree because nothing sets `@admiral-state` above pane level.
    - **`@admiral-subagents`** (`sessionhost.EncodeSubagents`/`DecodeSubagents`, `internal/sessionhost/subagents.go`; the server reads it with the same code) is kept by `admiral hook` on `$TMUX_PANE` as a JSON array of `{"id","type","start"}` (`start` RFC 3339, at most 64 entries; an empty list unsets the option).
    - Ids and types come from the payload and are kept only as safe tokens (a bad id drops the entry, a bad type is stored as `""`).
    - Adds: `SubagentStart` (Claude Code, Codex: `agent_id`, `agent_type`) and Copilot `subagentStart` (`agentId`, `agentType`); a listed id keeps its start.
    - Clears: a Claude Code `Stop` replaces the list from `background_tasks` entries of type `subagent` or `teammate` that are running; `SubagentStop`/`subagentStop` removes a listed id; Codex clears only on `SubagentStop` (its `Stop` has no `background_tasks`); a Copilot lead's `agentStop` or `userPromptSubmitted` clears all.
    - A stop for an unlisted id is ignored.
    - The harness for a `Stop` comes from `display -p -t "$TMUX_PANE" '#{@admiral-harness}'`, falling back to the payload's `background_tasks` (present, even `[]`, is Claude Code).
    - Subagent events never change `@admiral-state`.
    - A reader treats the list of a dead pane as empty (`parseRows` does, on `PaneDead`).
    - `DecodeSubagents` re-checks every entry on read with `sessionhost.SafeToken` (the hook uses it too): an id that is not a safe token, a `start` that is not RFC 3339 or a repeated id (the first wins) drops the entry, a type that is not a safe token reads as `""`, and the list is capped at 64.
    - A raw `\x1f` in an option makes its row the wrong length (the ship is unreadable); a raw newline in the last field leaves a fragment that is read as a row if it is well formed.
    - Only raw tmux on the socket can plant either; `admiral hook` writes JSON, which escapes both.
    - The read-modify-write takes no lock, so two hooks at once on one pane can lose an update.
    - The bundle registers `SubagentStart`/`SubagentStop` (Claude Code, Codex) and `subagentStart`/`subagentStop` (Copilot); the new Codex events bring back its hook review dialog once.
    - The `alert-bell` hook script stamps `@admiral-bell` on the ringing window's pane, and for a Codex crew boat also sets that pane `needs_you` (reason `bell`).
    - `sessionhost.Crew` also carries the pane's exit (`ExitStatus`, `Signal`, read in `parseCrew` for an anchored boat), which `ships.CrewExit` turns into `exit_code`/`exit_signal` on a `CrewBoat` (omitted while it lives).
    - **The bridge on a crew boat**: `GET /ws/bridge/{session}/crew/{name}` (`serveCrew`, `internal/bridge/browser.go`) finds the boat by name through `Ships.Crew` (a `find`, so `_setup`, `_admiral` and a non-ship 404), then holds its pane and window ids.
    - `internal/bridge/bridge.go` has one `conn` per watched session, the shared control client, with a `watch` per pane (key `""` for the ship, the window id for a boat); the same `watch` code serves both, with `state` (the ship's wire status, or the boat's own), the input clear (`InputSeen`, or `Ships.CrewInputSeen`, which writes `working` on the boat's pane by id through `Host.SetPaneWorking`) and the live gate differing.
    - `conn.start` reads each window's size before attaching and pins them all with `refresh-client -C @id:WxH` (attaching sets unpinned windows to 80x24); every later size is per window.
    - The ship's watch resolves `=<session>:^`, never `=<session>:`, which is the current window.
    - A boat's watch ends in `shipChanged` (reached by `ShipsChanged`) when its window id is no longer in `Ships.Crew`; the client detaches `ADMIRAL_BRIDGE_IDLE` after the last watch is gone.
    - **Option text is untrusted.** A crew boat writes its own window's `@admiral-crew-name`, and tmux prints option values raw, so the `list-panes` reader (`Host.poll`, `ReadOnce`, `ReadCrew`) does three things.
    - (1) Every row starts with a per-read random nonce (`rowFormat`, built for each command, 16 hex characters from `crypto/rand`), and `ownRows` drops any row that doesn't start with it before fields are counted: option text is written before the read and can't know it, so the lines a raw newline leaves, or a row an agent forged in its option, are dropped.
    - (2) As a second layer `format` wraps `#{session_name}` and every `#{@admiral-*}` in `#{s/[\x01-\x1f\x7f]/ /:...}` (`unprintable`), so a control character reads as a space. tmux copies a value that is not valid UTF-8 through raw, whatever the substitution says, so this alone doesn't hold.
    - (The class is a range of literal bytes: the colon in `[[:cntrl:]]` ends a format modifier.) (3) `parseCrew` reads a name only if it matches `launcher.CrewName`, and when two windows of one session claim a name it reads neither and `Host.poll` logs `admiral: crew boat <session>/<name>: two windows claim this name, so neither is listed` once.
    - What the reader doesn't do: a row that a value still breaks (an invalid UTF-8 byte next to a control character) keeps its nonce and loses its field count, and `parseRows` then holds that session unreadable at its last state, so a boat can freeze its own ship's reads.
    - `hook.go`'s crew read and the launcher's name checks read raw options of their own.
    - A boat dropped by (3) leaves `crew[]`: its bridge closes, its needs-you leaves the ship's wire status, and no inbox item or closed push is made for it.
    - A crew bridge also ends on tmux's `%window-close` / `%unlinked-window-close` for its window.
    - `admiral attach` reads `sessionhost.ReadOnce` and targets `=<session>:^` or `=<session>:<window id>`.
- Crew boats and subagents on the wire.
  - Words: `crew` is the crew boats that are teammates (crew windows), `subagents` the subagent marks; GLOSSARY.md's "crew boat" covers both.
  - Every ship in `GET /api/ships` and the `ships` WebSocket message carries three fields, always present (`[]`, never `null`): `crew`, sorted by name, each `{"name","harness","dir","status","reason","role","launched","last_activity","conversation"}` (`role` is left out when none; `conversation` is always present and true for a Claude boat with a recorded transcript, whose path never leaves the server); `subagents`, each `{"id","type","start"}`, from the ship's own pane (a crew boat's own subagents stay off the wire); and `crew_live`.
  - A crew boat's `status` is the value `admiral crew list --json` calls `state`: `underway`, `needs_you` or `anchored`.
  - `reason` only while `needs_you` (the crew pane's `@admiral-reason` if it is a safe token, else `unknown`); `last_activity` is the pane's `@admiral-activity`, omitted before its first hook.
  - `crew_live` counts crew boats with a live pane (`underway` or `needs_you`), so the UI can warn before Dismiss; it is not the hook's "working", which means only `@admiral-state` `working`.
  - The data comes from the rows `Host.poll` already reads (`#{@admiral-subagents}` is the last tail field, outside `optionNames`), so there is no extra tmux call per ship and a restart needs nothing beyond the next poll. **The wire status counts crew** (`wireStatus`, `internal/ships/crew.go`, applied in `Service.ship()` only): while a ship's own status is `underway` and a crew boat is `needs_you`, the ship's `status` is `needs_you`, `reason` `crew` and `stop_since` the earliest, over the needing boats, of the boat's `last_activity` or else its `launched`.
  - This reaches the API, the WebSocket, `Get()` (so the bridge's `ship` message) and `InputSeen`'s response.
  - The inbox builds a stop for the ship only while it needs you itself (`status` `needs_you` and `reason` not `crew`) and one stop per `needs_you` entry of `crew`, keyed `stop:<session>/<crew>`, whatever the ship's status except `sailing_off`.
  - The ship's own status stays in `FromSession`, `status()` and `sess.State`, which `InputSeen`'s decision, Dismiss, sail-off, the bell, the startup exit-0 kill and the outcome log use, and `@admiral-state` is never written for a crew boat.
  - The ships push signature covers crew membership, each boat's status and reason and the subagent ids, not `last_activity`.
  - Sail-off and Dismiss kill the whole session (`kill-session`), which ends crew windows and their harness processes; an anchored ship's live crew keep running until Dismiss.
  - `launcher.CloseCrew(ctx, windowID)` is the one kill both `admiral crew close` and the close route use.
