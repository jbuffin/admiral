# The new shell at `/app/`

The new web shell: modules, pages, moored ships, inbox, routines, alerts and push. Read it before changing `web/src/app/`.

The redesigned UI is a second Vite entry: `web/app/index.html` builds to `dist/app/index.html`, with hashed assets in the shared `dist/assets/`, and its source is `web/src/app/`. `serveUI` serves `app/index.html` for `/app` and any extensionless path under `/app/`; exact `/` answers 302 to `/app/` with its query string, and the frozen old UI is the root `index.html` served at `/classic/` (its assets stay at `/assets/` and it keeps the unversioned `/api`); any other extensionless path outside `/app` and `/classic` is a 404, and `/classic/…` serves the old index. Auth lets an unpaired device reach `GET` and `HEAD /`. `vite dev` does the same through the `app-shell-fallback` middleware in `web/vite.config.ts`. `web/scripts/gen-shell-tokens.mjs` writes the gitignored `web/src/app/shell-tokens.css` from `designs/redesign/tokens.json` (`gen-tokens.mjs` and `src/tokens.css` for the old UI are unchanged). `npm run build` and `typecheck` run both.

The new shell's Chat surface is `ChatPanel.tsx`: the shown fleet's AdmiralBot conversation (`useChat.ts` reads `GET /api/chat/<fleet>/session`, calls `start` on open, and takes live snapshots from the per-fleet `chat` WebSocket message that `shipsLink.ts` keeps in `chats`), with the Inbox as a rail beside it above the stacked width (it reuses `InboxPanel.tsx`'s `Row`, `useInboxQueue` and `usePeekEntry`).

- A rail row for an item opens Peek in place of the rail at `/app/chat/<fleet>/item/<session>/<id>` (`chatPeekOf` in `router.ts`), so the chat stays; Back and a finished answer return to `/app/chat`.
- Open terminal (the header, and beside the not-started note) opens `/app/chat/<fleet>/terminal` (`chatTerminalPath`/`chatTerminalOf`): the fleet's `_chat-<fleet>` session through the bridge, in place of the conversation, with the touch keys and Back to chat.
- It returns to the conversation when the session ends (its reconnect probe reads `running` from the session route) or another fleet is chosen, and the not-started note clears when the first SessionStart arrives.
- A waiting chat question is also an Inbox item: `inbox.Service` lists `chat.Service.WaitingQuestions` (named "AdmiralBot", fleet from the directory) and hands an answer for a `_chat-<fleet>` session to `chat.Service.AnswerQuestion`, the one code path the chat's own answer route also uses; `chat.Service.OnQuestions` (wired to `inbox.Service.Changed`) pushes the Inbox when a chat's questions may have changed.
- `chat.ts` (pure) turns a snapshot into the thread: a question card is open, answered ("You answered: …") or Withdrawn when the snapshot's `questions` no longer holds it, which is every card from before a New chat.
- A fleet's AdmiralBot Preferences page is `ChatSettingsPage.tsx` (`chatSettings.ts` builds the changed-keys `{chat}` body for `PUT /api/fleets/<key>`).

The shell's modules are in `web/src/app/`: `api.ts` (the only place that builds `/api/v1` URLs), `router.ts` (History API routing), `fleets.ts` (the active fleet), `Flag.tsx` (harness flag), `FleetSwitcher.tsx` and `Shell.tsx` (layout), and for Preferences `Preferences.tsx` (nav and frame), `FleetPage.tsx` (a fleet's search roots, owners, wake reviewers, clone root and colour, and its docks read-only), `fleetSettings.ts` (what a save sends and where a 400 shows), `OrderSources.tsx` (a fleet's plugin sources only: add, restart, move, remove), `SettingsForm.tsx` (a plugin source's settings form), `GitHubPage.tsx` with `githubViews.ts` (a fleet's GitHub page: connection, repos, the views list, priority labels and refresh). Also:

- `githubViews.ts` holds the pure view-list rules.
- `NewViewCard.tsx` with `newView.ts` is the + New view card under the views list: presets, the builder and its live count; `newView.ts` holds the query builder, the presets as data and the hand-edit rule.
- `gripReorder.ts` is the drag and arrow-key reorder the views list uses.
- `sourceSettings.ts` holds the pure rules for which fields are JSON fields and what a save sends for a kept secret.
- `UsagePage.tsx` with `fleetUsage.ts` is a fleet's Usage and the cross-fleet Usage page: per-harness figures split by spender, quota bars; money never summed.
- `HarnessCapabilities.tsx` with `capabilities.ts` shows a fleet's harnesses and what each was probed to do.
- `MissingCapability.tsx` is the one-line note that names a capability a harness lacks, with Check again, for any feature greyed out for it.
- The Crew page is `CrewPage.tsx` (the member list by layer, the member detail at `/app/crew/<name>`, the edit form, rename sheet and notes) with `crew.ts` (the pure part: grouping, the PUT body, which input a 400 belongs beside, note scopes).
- Member text and notes are untrusted and render as text.
- The generator also writes the gitignored `shell-tokens.ts` (the fleet sequence length and the harness placeholder letters), and `npm run dev` runs both generators first.

The Ships page groups the active fleet's ships as Needs you, Underway, Moored, then Anchored (`shipList.ts`).

- A moored row (`Shell.tsx`, chips and labels in `moored.ts`) shows each PR's link and chips from `prs`, how long the ship has waited from `moored_at`, a quiet "last checked" when the poll is stale, and Wake, Dismiss and Don't follow reviews buttons (Wake posts the wake route with no text and is off with a reason when `no_resume` is true; the row's name links to the ship view, the buttons sit outside the link).
- The ship view of a moored ship says it is moored, offers Wake, and shows calm moored states in the Conversation and Terminal tabs (no bridge); its message box is on (`boxState`'s moored case) and sending posts the wake route with the text instead of `/send`, with no pending bubble, the draft kept on an error.
- Opening Ships posts `/api/moored/refresh` once; the poller's `ships` push brings the new chips.
- The old UI hides moored ships: `web/src/ships.ts` drops them from its feed.

- `stack_ready` also needs the stack to merge cleanly into its base, which GitHub does not say per layer.
  - For a ship of stacked or chained PRs, at least two of them open and every open one `MERGEABLE` (merged and closed layers are left out, the top is the last open layer and the base the lowest open layer's base; a lone open PR is left to GitHub's own answer; a ship that reviews a PR is never checked), `checkStackBase` (`internal/ships/stackbase.go`, called by the poll before `storePoll`) reads the shape (cached per ship by the open PRs' head SHAs), then asks `Service.StackChecker` (`internal/stackmerge`: an Admiral-owned bare clone per repository under `$ADMIRAL_HOME/stackcheck/`, a clean git environment, the fleet's own `gh auth token` as the fetch credential, no redirects followed, `git merge-tree --write-tree`) whether the top PR's head merges into the base branch, and sets `Status.ConflictsWithBase` on the top PR's stored answer.
  - The poll serves it as `prs[].conflicts_with_base` on the top PR, so a ship with no Fix offer still shows why it is not ready.
  - That makes `ProblemsOf` report `conflicts_with_base`, so the offer, the Fix route and the hook all see it, and `moor.StackReady` (which reads it from the PR) makes `mooredShips` serve `stack_ready` false.
  - Each poll reads the base branch's SHA with `git ls-remote` and answers from the (base SHA, top SHA) cache; it fetches (a full fetch of the base branch and the PR head, so a first check of a large repository costs the poll as long as that fetch, up to 90 s) only when one of the two commits is not in the clone yet, and prunes unreachable objects after each fetch.
  - A failed network call backs the repository off for 30 s, doubling to 4 min, and answers "cannot run" meanwhile. A check that cannot run changes nothing.
  - A moored ship whose stack is ready (`stack_ready`) shows Ready to merge on its Ships row and in its ship view, and stays in the Moored group.
  - `createInboxQueue` derives a `merge:<session>` entry from it, which opens a Peek with the PRs and a Merge button.
  - Every ship view has a PR tab (`PRTab` in `ShipPRs.tsx`, pure parts in `prTab.ts`): a count on the tab, a summary line in the view's head that opens it, `#n` sub-tabs in stack order for two or more PRs, and the selected PR's header and chips, read from each PR's detail every 30s while it is open.
  - A moored ship's tab also has Merge, for a ready ship, and Don't follow reviews; Wake stays in the view's head, and the tab has no Dismiss.
  - Peek and the tab share `MergeControl` (`PeekMerge.tsx`) and `MooredActions` (`MooredActions.tsx`).
  - Under the selected PR's chips the tab shows its Checks, Description (Markdown through `renderMarkdown`, HTML comments removed), Reviewers (one row per person) and Conversation (threads and comments, oldest first), read-only, from `PRDetailSections.tsx` over the pure `prSections.ts`; they show only once the PR's detail has loaded, and GitHub's text renders as text.
  - The `.pr-detail` container query (640px) folds Reviewers to a one-line summary above Checks at iPad portrait and phone widths.
  - The tab, for a ship of two or more PRs, reads the PR shape from `GET /api/ships/<session>/stack` (when it opens, every 30s and after a merge) and takes the sub-tab order, the bar and Merge from it; the client never classifies PRs, and until the shape is read, or when the read fails, there is no bar and no Merge.
  - The stack bar (`stackBarLine`, `stackBarAction`): `stacked` shows `Stacked on GitHub · stack #n` and Merge takes the whole stack; `chained` shows `Not a GitHub stack.` with a Stack on GitHub button on a moored ship (a `Sheet` listing the PRs bottom first, one `POST /stack` on confirm) or `Stack after the ship moors` on a ship still out, and no Merge, only the hint `Stack them on GitHub to merge together` once every open PR is ready; `mixed` shows a bar with nothing to press and no Merge; `independent` and `none` show no bar.
  - Each independent PR gets its own Merge on its sub-tab (`mergeFor`; it sends `{pr: <url>}`, and the hint is the method alone) and the ship stays moored until the last one merges or closes.
  - Outside the tab (Peek's `MergeBody`, the My PRs row) `ShipMerge` reads the shape once, only for a ship of two or more PRs that shows `stack_ready`: a stacked ship merges whole there, any other points to `?tab=pr` on the ship view.
- A ship that reviews a PR (`reviews(ship)` in `moored.ts`: any `prs[].reviewing`) never offers Merge, Ready to merge or Don't follow reviews on any surface (the tab, the moored row, the ship view, the Orders row, the Inbox), though the server still serves `stack_ready` for it.
  - Its PR header leads with a `Reviewing · by @<author>` mark, its summary reads `Reviewing <n> PR(s) by @<author> · author responded` or `· waiting on the author`, and a stack-URL ship with two or more PRs and at least one reviewed layer shows `Reviewing a GitHub stack by @<author> · <n> PRs, bottom to top.` as its stack bar (`n` counts the reviewed layers).
  - `reReviewPlace` (`moored.ts`) says where Re-review is offered and with which URL: the stack bar, the responded PR, or nowhere.
  - When a reviewed PR's `responded` is true on a moored ship, the tab shows a feedback bar with Re-review (a stack ship with the bar puts Re-review stack on the bar), and `createInboxQueue` derives a `rereview:<session>` entry ("@author responded on #n") whose Peek (`/app/inbox/<session>/rereview`) holds the one-tap Re-review.
  - Both post `POST /api/ships/<session>/rereview` with the PR's or the stack's `url` as served (`ReReview.tsx`).
  - A new Inbox entry type also goes in `RANK`, `targetOf`, `peekOf`, `peekPath`, `peekKey`, `rowVerb`, `keyHint` and `keyAction`.
- Alerts: `push.AlertSink` (a sink of the push watcher, queued through `push.Async` so a slow window never holds up the feed) sends the decided payload as an `alert` message through `Hub.SendWatching`, to the windows `Hub.Watching` counts and no other.
  - `ToastRegion.tsx` (started by `Shell`, a polite `role="status"` region) hears it through `onShipsMessage`: `createAlertHandler` (`alerts.ts`) chimes unless `admiral.muted` is set (the old UI's key; the new shell has no mute control yet) and pushes a toast onto the pure queue in `toasts.ts` (two at most, the same tag replaces, `TOAST_MS` expiry).
  - A tap opens `alertDestination`'s path: Peek while the item, stop or merge entry is still there, otherwise `/app/inbox`, and an anchored ship's view for `target: "ship"`. A panicking sink is recovered in the watcher and logged.
- The attention count is the number of entries in the one shared Inbox queue (`sharedInboxQueue` in `inbox.ts`, read by the Inbox panel, the Chat rail, Peek and the count) that aren't folded and aren't `notice` items, across every fleet. `attention.ts`'s `watchAttention`, started by `Shell`, syncs that queue from the `shipsLink.ts` signals and ticks its folds, then `applyAttention` puts the count in the document title (`(n) Admiral`), a dot on the favicon and the Badging API's app badge (skipped where the browser lacks it).
- Push on this device and in the worker.
  - `/app/preferences/admiral/notifications` (`NotificationsPage.tsx`) holds the switch `Notifications on this device` and a Devices list with each device's push on or off.
  - What the switch shows is `pushSwitchState` (`pushSwitch.ts`, a pure function; overlapping states take plain HTTP, then Home Screen, then blocked, then Mac off); `pushDevice.ts` reads its inputs (`GET /api/v1/push/key`, the browser's subscription, `GET /api/v1/push/subscription?endpoint=`) and turns it on (`Notification.requestPermission()` first, from the tap) or off.
  - `sw.ts` handles `push` (always shows a notification: `swPush.ts` `notice`, a generic line for a body that doesn't parse, every field text only) and `notificationclick` (focuses an open `/app/` window and posts it the payload, else opens `/app/?push=<payload>`; `clickUrl` never leaves `/app/`).
  - `pushLink.ts`, started by `Shell`, holds the click message (from an open window) or the address's payload until `canResolve` (`pushResolve.ts`) says the link is open and a ships and an inbox snapshot have arrived on this connection (`shipsFresh`, `inboxFresh` in `shipsLink.ts` reset on each connect and close, unlike `shipsLoaded`), because a window resumed from the background holds old lists; then it goes to `alertDestination`.
  - The same freshness gates closing each shown notification whose payload resolves to the Inbox (`staleNotices.ts`, matched on `data` because item and crew tags share a shape), which runs whenever fresh ships or Inbox change.
  - The worker is one classic file: `sw.ts` must not import a module the app also imports (the build would split a chunk and put an `import` in `sw.js`), so worker-only logic lives in `swRules.ts` and `swPush.ts`, which only `sw.ts` imports; `swBuild.test.ts` builds the real config and checks `sw.js` has no `import`. The page, not the worker, sets the badge.
- Routes: `/app/inbox`, its Peek paths `/app/inbox/<session>`.
  - `/app/inbox/<session>/crew/<name>` and `/app/inbox/<session>/item/<id>` and `/app/inbox/<session>/merge` (a session or crew name holding `/` is no Peek).
  - `/app/ships` (a ship opens on Terminal with `?tab=terminal` or on its PR tab with `?tab=pr`; the ship view drops the query from the URL once read, and any other value opens Conversation).
  - `/app/chat`, `/app/campaigns`, `/app/routines`.
  - `/app/crew`, `/app/<source key>` and `/app/<source key>/<row id>` (a module's page, `ModulePage.tsx`; kept until the first `sources` message, then the inbox if no module of that key exists).
  - `/app/preferences/<fleet key>/github` (`GitHubPage.tsx` over the pure `githubViews.ts`: each change saves the whole settings through `PUT /api/sources/<key>`; the nav item shows a dot while gh is signed out).
  - `/sources` (Plugin sources, no GitHub card).
  - `/fleet`, `/capabilities` and `/usage`, plus `/app/preferences/admiral/all-usage` for all fleets.
  - `/app/preferences/admiral/notifications` and `/app/preferences/admiral/remote` (bare `/app/preferences` redirects to the active fleet's, without changing `?fleet=`).
  - `/app`, `/app/` and unknown paths redirect to `/app/inbox` with `replaceState`, keeping the query.
- The Routines screen (`RoutinesPage.tsx`, over the pure helpers in `routines.ts` and `cron.ts`) lists the active fleet's routines from `GET /api/v1/fleets/<key>/routines` with a plain-words When, its last run (from `last_run` on the list) and a switch that turns it on or off, and opens a routine at `/app/routines/<id>` (a new one at `/app/routines/new`, which opens a kept AdmiralBot draft from `?draft=<id>` into the unsaved form, or the empty form with a note when it has expired; the phone shows list or detail, as Crew does).
  - The form edits only the fields `routines.Launch` holds, offers only docks that passed `autopilot.guard_hook` with a judge set (`autopilotDocks`) and says why when none qualify, and keeps showing the stored Before acting.
  - Recent runs polls the open routine's trigger log about every 10 s; a breaker record reloads the list and then reopens the form, so it shows the stored Ask first; a Save reopens it from the server's answer. Delete asks a second tap on the button.
  - The header holds the fleet's Hold fire switch and the all-fleets one, each with a Stop all worker-launched button beside it (counts from `worker_ships` and `all_worker_ships`, disabled at 0, behind a confirm); the UI is the only way off Hold fire.
  - The event picker never offers `new_in_view` (`triggerRemoved` in `routines.ts`): a stored routine that names it shows as Broken with a note, the server refuses to save one and the scheduler never fires one.
  - A migration notice's `notice.entries` stay on disk, but the Inbox shows its body as plain text.
- The Routines screen has two tabs (`RoutineTabs.tsx`): Routines and Standing orders at `/app/routines/standing-orders` (`standingOrdersTab` in `router.ts`; `routineOf` and `routineCreating` skip it).
  - `StandingOrdersPage.tsx` shows the active fleet's `GET /api/v1/fleets/<key>/standing-orders`: the Limits as the server's sentences, each linking to `/app/preferences/<key>/limits?field=<field>`, the Checks (20, 300 characters each) and the Guidance (2000), counted in runes, plus Copy to another fleet and the judge line from `JudgeLine`.
  - With no judge it lists the features that need one and a `MissingCapability` row per dock.
  - The pure part is `standingOrders.ts` (counters, the changed-key body, where a 400 shows).
  - The Limits page, `LimitsPage.tsx` at `/app/preferences/<key>/limits` and last in each fleet's Preferences nav, edits the preset and every Limit with one control per sentence field (the control's `id` is the field, and `?field=` scrolls to it and focuses it).
  - `limitsForm.ts` builds the changed-leaves `{limits}` body, with `null` for a reset and `threshold: null` when a raised T4 ceiling reaches the threshold in effect, stored or preset; `fleetSettings.ts` `errorTarget` maps a `limits.<path>` 400 to its field.
  - Filing (`FilingForms.tsx` over the pure `filing.ts`): `NewStandingOrder` sits under the Standing orders intro.
  - With a judge, Draft posts the prose to `…/standing-orders/draft` and the review shows the drafted Limit changes (each removable, values edited on the Limits page), Checks and Guidance (editable), the drafter's `problems` by part and a loosening warning; a loosening needs a second tap on Confirm.
  - Confirm saves the Limits first (`saveFleet`, then `fleets.value` is set from its answer), then the orders from the tab's stored values plus the kept draft, through the existing PUT routes; a 409 from the Limits PUT shows Reload, and a part-saved failure says which part was saved.
  - A 409 from the drafter, or a fleet with no judge, turns the input into the plain form that saves the text as a Check or Guidance ("It's a Limit" links to the Limits page).
  - `DescribeRoutine` at the top of the Routines tab list posts to `…/routines/draft` and opens the new-routine editor filled from the draft with its one problem shown by field; nothing is stored until Save.
  - The Routines tab reads the judge from the shared `capabilities` signal (the same one Check again updates); when the judge is off it hides the Describe input and shows the judge line and a `MissingCapability` row per dock.
- The Hold fire banner: `holdFireLink.ts`, started in `main.tsx`, reads `GET /api/v1/fleets/<key>/hold-fire` for the active fleet on a fleet change, every 15 s and when the window regains focus (AdmiralBot can turn it on and no socket message says so). `Shell.tsx` renders it as a `role="status"` bar above the panel in both shells while the fleet's or the all-fleets switch is on, naming who and when, with a link to Routines.
- Active fleet: `?fleet=<key>`, kept across navigation. Without it, the last choice (`localStorage` key `admiral.app.fleet`), then the first fleet; an unknown key falls back the same way. Inbox and Preferences name no fleet.
- Phone (up to 640px wide): a header with the fleet switcher (a sheet) and the surface title, and a bottom tab bar of Inbox, Chat, Ships and More. More opens a sheet with Campaigns, Routines, Crew and Preferences. Wider screens, iPad portrait included, show the 248px sidebar.
- The fleet list comes from `GET /api/v1/config`; the shell makes no unversioned `/api` or `/ws` request.
- A fleet's Harness capabilities page lists its harnesses from `GET /api/v1/harness-capabilities` and re-runs one harness with `POST /api/v1/harness-capabilities/check`, shown as checking while it waits and as an alert when the check cannot run.
- Harness flags load `/api/v1/logos/<harness>` as an `<img>` and show the placeholder letters when it 404s. Logos are never inlined.

## Lint and the effect budget

`make lint` runs ESLint over `web/src` (`web/eslint.config.js`, untyped rules, Babel as the parser because TypeScript 7 has no JS compiler API for `@typescript-eslint`) with `--max-warnings 0`. It enforces `react-hooks/rules-of-hooks` and `exhaustive-deps`, and two local rules in `web/eslint-rules.js`: `admiral/no-raw-effect` bans a raw `useEffect` or `useLayoutEffect` in component files (`*.tsx`), and `admiral/no-deferral` bans `setTimeout` with no delay or a `0` delay, `requestAnimationFrame` and sleep promises in any non-test file. Inline `eslint-disable` comments don't work.

Effects and focus or settle deferrals go through the Preact hooks in `web/src/app/hooks/` (not the harness hooks): `useFocusOnOpen` and `useFocusOnClose` focus after render, `usePollUntil` waits for a condition, `useSubscribe` listens to an event target. `web/eslint-suppressions.json` lists today's exceptions and only shrinks: after removing a case, run `node_modules/.bin/eslint --prune-suppressions src` from `web/`, and never add to the file to pass lint.
