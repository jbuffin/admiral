# Ships, routes and mooring

The ship API routes, ship statuses, mooring, the moored poll, and the PR actions (merge, update branch, ready for review, chained PRs). Read it before changing `internal/ships`, `internal/moor` or a ship route.

- `internal/state` is `$ADMIRAL_HOME/state.json` (ship positions, each dock's last directory, the kept inbox records, the resume text), `internal/ships` serves `GET`/`POST /api/ships`, `PUT /api/ships/<session>/position`, `POST /api/ships/<session>/input-seen` (a browser sent input: clears needs you), `POST /api/ships/<session>/answer` and `.../crew/<name>/answer` (send `internal/keymap`'s keys for Allow once, Deny or a question's option, only while the pane's `@admiral-reason` matches the body's;
  - Claude and Copilot panes are answered in place, Copilot's on `notification:permission_prompt`, `question` and `notification:elicitation_dialog` (its question form takes Down then Enter, not digits); `Service.Questions`, `shipconv.PendingQuestions`, gives the pending questions for the gate), `POST /api/ships/<session>/dismiss` (ends an anchored or a moored ship), `POST /api/ships/<session>/unfollow` (Don't follow reviews: ends a moored ship;
  - any other ship is refused as Dismiss refuses it), `POST /api/ships/<session>/merge` (the engineer's Merge act on a moored ship's ready PR: `serveMerge` in `internal/ships/merge.go` re-reads the PRs from GitHub, runs `gh pr merge` through `moor.GitHub.MergePR` with the repository's default method, answers 202 and asks for a poll, and it needs the page's merge token or answers 403;
  - a ship with several PRs reads their shape from GitHub: a GitHub stack merges whole with `gh stack merge <number>`, independent PRs merge one at a time by `pr`, and chained or mixed PRs are refused with 409; the poller, orders and agents never merge; the guard in `internal/cli/guard_merge.go` still refuses an agent's merge), `POST /api/ships/<session>/wake` (wakes a moored ship by hand: 201 with the ship, `ships.Service.Wake`, whose prompt ends with a section naming the ship's own open PRs, from `wakeprs.go`;
  - see [the wake decision](wake.md)), `POST /api/ships/<session>/answer-review` (a hand feedback round on one PR, body `{"pr"}`, `ships.Service.answerReview`, or Answer all reviews on the ship's stack, body `{"stack"}`, `serveAnswerAll`; 201 with the ship; see "A hand round" in [the wake decision](wake.md)), `POST /api/ships/<session>/fix` (Fix PR and Fix stack: one hand round on the whole moored ship, no body, `ships.Service.fixWake`;
  - 201 with the ship; see "A hand round" in [the wake decision](wake.md)), `POST /api/moored/refresh` (kicks the moored poll, 202), `POST /api/ships/<session>/crew/<name>/close` (kills one crew boat's window, live or anchored, like `admiral crew close`; 404 `ship <session> not found` or `crew boat <name> not found`, the latter too when the window closed between the poll and the kill) and the WebSocket `ships` message.
- Each ship carries a `tail`, a line from its conversation: `internal/shipconv`'s `Tails` follows Claude ships' transcripts (re-reading one only when it changed) and `conversation.Tail` picks the line.
- `internal/shipconv` serves `GET /api/ships/<session>/conversation[?before=<id>]` and the WebSocket `conversation_open`, `conversation_close` and `conversation` messages (a Claude Code ship's conversation, `docs/api.md`); it finds the file from the ship's `@admiral-transcript` pane option, which the launcher sets at launch beside `--session-id` (a launch that resumes a Claude conversation carries `--resume <id>` instead, and `transcriptfs.StartedSession` reads it for Claude only), and `internal/transcriptfs` holds the ADR 0019 path checks and the open it reads through.
- A ship carries `reason` (the validated code, `idle` for a ship no hook has spoken for) and `stop_since` (RFC 3339; the open stop's start from the log's track) only while its `status` is `needs_you`.
- A ship's `status` is `underway`, `needs_you`, `anchored` (with `exit_code` or `exit_signal`), `sailing_off` (exit 0, session killed after 3 s) or `moored` (a ship that exited 0 while its report listed a PR that GitHub confirms open on the fleet's built-in GitHub source's host and that routes to the ship's fleet: `internal/moor` reads the report (versions 1 and 2) and writes `$ADMIRAL_HOME/moored/<name>.json`, `internal/ships` ends the session, writes a `moored` outcome and lists the record, `internal/launcher` keeps the name reserved; `gh` is retried for `ADMIRAL_MOOR_RETRY`, 8 s by default, and a PR GitHub cannot confirm sails the ship off; the check runs for exit-0 ships found at startup too).
- `ships.Service.RunMoored` polls every moored ship's PRs (`moorpoll.go`): one batched `gh api graphql` per fleet client (`github.Client.PullRequests`, one aliased `repository{pullRequest}` per PR, parsed from `data` even when gh exits 1 for a `NOT_FOUND`) every `ADMIRAL_MOOR_POLL` (2 min) and on each kick; a kick during a poll coalesces.
- A PR GitHub answers `NOT_FOUND` for counts as closed; a failed call keeps the last chips, marks the ship `stale` and never ends mooring.
- The ship sails off (`endMoored`: the record is removed with `moor.Remove`, the cache and name are freed, one `unmoored` written; the first ending wins a race) when every PR is merged or closed, or on Dismiss or Don't follow reviews; there is no idle timeout and a merge wakes nothing.
- A wake (`internal/ships/wake.go`) recreates the moored ship's session under its own name and session: `Launcher.Launch` takes `Request.Name` and `Request.Session` (refusing 409 while that session is live, under `l.mu`, so no launch takes the name between) and `Request.Prompt` (the harness prompt verbatim, so the report's `resume` text is not prefixed with a skill again), and sets the session option `@admiral-round` from `Request.Round`.
- The wake goes through `admit` and `LaunchOrder` with the record's `source`, `order`, `url`, `panel`, `title` and `resources`, so the order key and the claim hold, but `LaunchOrder` skips the order read and its own-ship refusal when `Round` is set.
- The round count is `Record.Round + 1`; `moor()` writes the live `round` option and `resources` back into the record, so a ship that moors again keeps both.
- The report's `resume` text is kept only when it is `/skill resume <run>` or `$skill resume <run>` (`moor.ValidResume`), since it is the prompt.
- `Request.Before` runs under the launcher's lock just before the session is made: it re-checks that the record is still the one the wake read (a Dismiss, Don't follow reviews or merged PR that ended the mooring first wins and the wake answers 409) and writes the feedback file into the validated checkout; from then on `endMoored` loses to the wake (`Service.committed`). `woken` is written by `launched` for a round. The record is removed once the woken session exists.
- `Service.Wake` (by hand: no autopilot, counted toward the cap, never blocked by it, the engineer's text after the `resume` text) and `Service.FeedbackRound` (autopilot, refused at the cap or on an unguarded harness; the feedback text goes to `<checkout>/.admiral/untrusted/feedback-<N>.md` through `moor.WriteFeedback`, never into the prompt, argv, options or environment) are the two entries; neither carries crew pins.
- A wake writes `woken` (`round`, `by` `hand` or `feedback`, `pr` for a round) instead of `launched`, and the round's end writes `round` (`round`, `end`: `moored` beside `moored`, `sailed`, or `anchored`).
- `unmoored` carries `reason` (`merged`, `closed`, `prs_done`, `dismissed`, `unfollowed`) and `prs`, each `{url, state}` as last polled; hooks, a Codex bell and the 10 s no-hook rule decide needs you (every hook runs `admiral hook <event>`, internal and unlisted in the usage text, which reads the harness's JSON on stdin and sets `@admiral-state` on `$TMUX_PANE`; it always exits 0.
- Update branch: `POST /api/ships/{session}/update-branch` (`serveUpdateBranch`, `internal/ships/merge.go`) is the engineer's act on a behind PR, behind `mergeGuarded` like Merge and off AdmiralBot's list. It runs `gh pr update-branch` through `moor.GitHub.UpdateBranch`, so it needs no resumable ship. The PR tab shows it beside the `merge_reasons` the poll serves (`Status.MergeReasons` in `internal/moor/poll.go`), which say why GitHub won't merge an open PR.
- Mark ready for review: `POST /api/ships/{session}/ready-for-review` (`serveReadyForReview`, `internal/ships/readyforreview.go`) takes the named draft PRs, bottom to top, out of draft with `gh pr ready` through `moor.GitHub.MarkReadyForReview`, behind `mergeGuarded` like update-branch.
  - It checks every PR fresh before any write, works on a moored or a live ship (`carriedBy`, as the PR detail route does, so an anchored or sailing-off ship carries nothing), skips a PR that is already out of draft, and answers one result per PR so one failing does not hide the rest.
  - The PR tab reads Draft or Ready for review from each PR's detail (`PRDetail.draft`), not from the ships API; an order's `pr.draft` comes from the search's `isDraft` and only colours the orders list's PR icon.
- Chained PRs on orders: `moor.Chains` finds them among one view's open PRs, following the longest run past a fork since a view can hold a stranger's PR built on the chain.
  - `ReadShape` keeps the strict `lineUp`, so a ship whose own PRs fork reads `mixed`.
  - The GitHub source sets each order's `chain` in `refresh()` (`addChains`; `mine` compares authors with the login of the view's own search, since `g.viewer` is empty on the first refresh) and `validate.go` must parse it or it is dropped.
  - `POST /api/sources/<key>/stack` (`internal/sources/stack.go`) re-reads the PRs, links only the viewer's own chain and takes the merge guard through `Service.MergeGuard`, which `cmd/admiral/main.go` wires and nil refuses.
  - The same `StackChecker` (`Supervisor.StackChecker`, wired in `main.go`; the e2e build's `stackRemote` points it at `$ADMIRAL_HOME/e2e-remotes/<host>/<repo>.git`) marks chain and stack orders with `conflicts_with_base` (`markStackConflicts`, `internal/sources/stackconflict.go`): `refresh()` serves the last answer and starts a background check per group with none in flight, keyed by repo, top PR number, top head SHA and base, and a changed answer queues one more refresh; it is display only and changes neither `stack_ready` nor Merge.
  - A failed merge's message is everything `gh` printed (`mutationMessage` in `internal/github/merge.go`) and `serveMerge` logs it.
  - Web: `viewGroups` makes a `chainRow` group (not a ship carrier, not launchable) and `StackSheet.tsx` is shared with the ship PR tab.
