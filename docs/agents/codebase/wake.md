# The wake decision

How the moored poll decides to wake a ship, hand rounds, tiers and the wake state. Read it before changing `internal/ships/wake*.go` or `internal/moor`.

`moor.DecideWake` (`internal/moor/wake.go`) is pure: a moored ship's PR answers, its wake state, the fleet's `wake_reviewers`, whether it is live and `now` give a `Decision` (wake or not, the one PR, its events, the feedback text, the T3 events and the `Next` state). `PollMoored` calls it for each answered, not-live record whose mooring did not end this poll and that has a valid resume text (a record with none is not decided: its no-resume note stands). It passes `Live=false`, the fleet's `wake_reviewers` and `now`.

- **Saving `Next`.** A decision that does not wake saves `Next` when it differs from the stored state, so a condition keeps its first-seen time. The write skips a ship whose wake is `committed`, whose record is no longer the one polled, or whose stored state changed since the poll read it.
- **A live ship's open PRs and moor on done** (`internal/ships/openprs.go`).
  - `refreshOpenPRs` runs each pass: it stats the ship's report file and, only when the stamp (mtime, size) changed, reads it through `loadReport` (`readReport`'s guards without its log line), takes `Report.Result` and asks `moor.CountedAnswered` in a goroutine; `openPRsOf` serves the cached answer, which `ship()` joins with `carriedOpen` (the running-ships poll's OPEN PRs, via `withCarried`) into `Ship.OpenPRs`, so the request path never asks GitHub.
  - `countedPRs` (clean exit) and `serveMoor` check the same union.
  - `autoMoor` moors a live ship at needs you (reason `stop`), not returning, whose report says `done` with open PRs, once per report stamp.
  - `serveMoor` handles `{"moor": true}` on `/stop` and `/return` with a fresh check.
  - All three end in `moorShip`, under the ship's `lockShip` (shared with `stopShip`, so a Stop that came first leaves nothing to moor): `moor()` (record, `moored`, `endRound("moored")`), then `recordKilled` and `endSession`, so a woken ship's round logs `moored`, not `anchored`.
  - A check GitHub does not answer (gh down past `RetryWindow`) is not cached under the stamp: it is retried with a wait that doubles from 30 s to 4 min.
  - `serveMoor` answers 409 for it, and 500 when the session will not end after the record is written.
- **A hand round** (`POST /api/ships/{session}/answer-review`, `Service.answerReview` in `internal/ships/wake.go`).
  - `moor.DecideHandRound` is `DecideWake`'s work for one PR with the debounce passed: both call `scan` (every answered PR's events and resolved state) and `openRound` (the chosen PR's events oldest first, every answered PR's window opened, the chosen cursor advanced), so the two rounds cannot drift.
  - `moor.DecideFixRound` is the third caller of that step: `openWindow` (the cursor default, `RoundStart`, `Dropped`, and for a handled PR the advanced cursor and the `{Head, failed, Conflicting, Behind}` snapshot) and `isCondition` (the condition-event kinds), with the same condition event bodies.
  - `decide` stores each PR's count in `polled.feedback` before any early return; `prsOf` reads only that and serves `feedback` and `answer` on a moored ship's `OPEN` PR, so the list never reads wake state.
  - The route checks the ship (`wakeable`), then that `pr` is exactly one of the record's `PRs`, then, in the launch hook under `saveWake`'s `wakeMu`, recomputes the round from the stored poll answers and a fresh `ReadWake` (409 when the PR has none); both rounds share `roundHook` (save the state, write the feedback file, undo the state if the write fails); the hook also refuses a `pr` that is not in the record it was given (400), and a launch that fails afterwards puts the wake state back and leaves the file.
  - It launches as `By: "hand"` with `PR` set, so it is attended and counts toward the cap without being blocked by it. AdmiralBot is not on its allow list.
- **The fix round** (`POST /api/ships/{session}/fix`, `Service.fixWake` in `internal/ships/fix.go`).
  - Fix PR and Fix stack wake a moored ship once for every answered `OPEN` PR it authored (`Record.Reviewing` PRs are taken out before `scan`).
  - `moor.DecideFixRound` takes the lowest such PR with a merge problem (`ProblemsOf`: a conflict, a branch behind a strict base, an own failing check, a stack that conflicts with its base, read from the stored answer, not from edge events) as the round's PR, writes every covered PR's problems and waiting feedback into one `feedback-<round>.md`, opens the window on every covered PR, and sets `FixRound.Stack` when it covers more than one.
  - `decide` in `moorpoll.go` stores the offer on `polled.fix`, `mooredShips` serves it as `ship.fix`, and the web shows Fix instead of Answer review and Answer all reviews while it is set.
  - The prompt is still `<resume> feedback round N on <PR>`; PR titles and check names reach the ship only through the untrusted feedback file.
  - The route runs `wakeable`, decides, then wakes through `roundHook` (`fixHook`) with `By: "hand"`, and the hook decides again, so a stale page gets a 409.
- **The ship context** (`wakeContextText` in `internal/ships/wakecontext.go`, built by `wakeContext` in `wakeWith`).
  - Every wake builds a document in Admiral's fixed vocabulary: the ship's name and round, that this is a fresh session that does not hold the earlier conversation, its order and issue URLs (strict GitHub URL shapes only), the path of its order text, repo (`repokey.OriginSlug`), checkout and branch (`repokey.Branch`, read at wake time, "unknown" when git cannot say), every PR in its PR tab with its state and whether it opened or reviews it, the one PR the engineer's message means when it has exactly one open PR it opened, each earlier round's transcript path, and the last report's result as `done`, `partial`, `failed` or `unknown`.
  - It never holds the title or any order, launch or GitHub text.
  - The order's text is written, by `moor.WriteOrder` inside `req.Before` after the wake's own hook (so every wake kind gets it, Return to port too), to `<checkout>/.admiral/untrusted/order.md`, as data; a link planted there refuses the wake, and an order its source no longer lists gets no file and a line that says so.
  - It reaches the ship two ways. The hand Wake's prompt ends with it (after the resume text, the engineer's text and the PR section), and a hand Wake with no resume text and no message is the document plus `wakeWaitLine`. Every wake also sets `launcher.Request.Context`: the launcher writes it to `<home>/reports/<session>.context.md` after `shipContract` clears the ship's files and sets `ADMIRAL_CONTEXT` to it; a first launch has neither.
  - `admiral ship-note`, a Claude ship's SessionStart hook, adds that file after its campaigns note in `additionalContext`. It reads only a regular file beside `ADMIRAL_REPORT`, never a link or one over 16 KiB, so a file in a repo cannot pose as Admiral's. That is how a Claude wake whose prompt a skill parses gets the context. Codex and Copilot ships have no hook: they get the hand Wake prompt section and the file, and read the file only if they are told to.
  - The launch clears the ship's report and inbox, so `req.Before` also runs `moor.WriteShipCopy`: the report goes to `<checkout>/.admiral/untrusted/last-report.json` and each regular `.json` file in the inbox (items and `.answer.json` answers, 1 MiB at most, links skipped) to `.admiral/untrusted/inbox/`, through the guarded root of `WriteOrder`, replacing the earlier round's copies. The document names those paths as data to read, not instructions, only when `moor.PlanShipCopy` found something to copy, and holds none of their text.
  - The prompts a skill parses stay byte-identical: Commodore treats `<resume> feedback round <N> on <PR>` as a feedback round only when nothing follows the PR, and Answer all's `/commodore <stack>` and a re-review's `/commodore <url>` are built from fixed shapes.
- **The Answer all reviews wake** (the `{"stack"}` body of the same route, `serveAnswerAll` and `Service.answerAll`).
  - It is a hand wake with a new Commodore prompt, `<resume's skill token> <stack URL>`, not a feedback round: the run is a different one, whose report sets the next mooring's resume.
  - The stack is read fresh (`stackFor`: `PullRequestDetail` on the ship's PRs until one has a stack, 502 on the first error) and must hold exactly the record's PRs; `stack` must equal its URL.
  - The hook is `roundHook` again, saving `moor.DecideStackRound` (one `scan`, then `openRound` for every OPEN PR) and returning no feedback text, which `roundHook` takes to mean write nothing.
  - `servePRDetail` sets `answer_all` from `answerAllPrompt`, which reads only the poll's stored answers under `mooredMu` (`stackOpen`: more than one OPEN, each with `feedback`), so the detail and the route agree.
  - A `feedback-<N>.md` left by an earlier failed PR launch stays in the checkout; nothing names it.
- **Scouts** (`internal/ships/claim.go` `checkScout`, `return.go` `advanceScouts`, `launcher.Request.Scout`): a scout is an autopilot ship with the session option `scout`=`1` (`Ship.Scout`), gated by `autopilotgate.CheckScout` in `admit` and, for a crew boat, in `LaunchCrew` (`Launcher.ScoutGate`, nil refuses).
  - `ADMIRAL_SCOUT` holds its resolved checkout and is cleared for every other launch, the chat and a boat's dock env; a scout's boats inherit it.
  - The run loop calls `advanceScouts` after `advanceReturns` and before `autoMoor`: a scout at its own `stop` is stopped with `stopped` `scout: true` (`commitments/shiplog.go` reads that as sailed), and `autoMoor`, `countedPRs` and Hand skip it.
  - A scout gets no worktree, even with no skill: it runs in the checkout it was launched in, so `ADMIRAL_SCOUT` names that checkout.
- **Hand to Commodore** (`internal/ships/hand.go`, `POST /api/ships/{session}/commodore`; the route doc is in `docs/api.md`).
  - It has the shape of Return to port: the pane option `handing` goes `queued` to `sent`, `advanceHands` runs beside `advanceReturns` each pass, and `s.handing` keeps one goroutine per ship.
  - A ship can rewrite its own pane options, so the hand lives in memory only: `serveHand` keeps a `handEntry` in `s.hands` (fleet, harness, checkout, origin slug, conversation id, the ask and the relaunch request), and only a ship with an entry advances; `handDrift` fails the hand when the live options or conversation differ from it.
  - A mark with no entry (Admiral restarted, or the ship set it) is cleared with a `handing_failed`.
  - The ship writes its ref to `$ADMIRAL_HOME/ships/<session>/ref`.
  - `conversationOf` binds the conversation through `transcriptfs.BindFor` from the `transcript` option and the pane's start command, never the option alone.
  - `finishHand` reads the ref (`readRef`), stops the ship with `stopShip` (`stopped` with `handed`, `ref`, `conversation`), then `admit` and `LaunchOrder` relaunch it as `wakeWith` does, with `ResumeConversation` and `Round` plus one.
  - `stopShip`, an exit or an anchor on a ship being handed ends the hand with `handing_failed`; `autoMoor` and `serveReturn` yield to it.
  - Restricted and event-launched ships are known only from the trigger log, so `Service.EventShip` is wired in `cmd/admiral/routines_wire.go` and a log it cannot read refuses the hand. Outcome events: `handing`, `handed`, `handing_failed`.
- **A round.** A decision that wakes calls `Service.FeedbackRound(…, next)` outside `mooredMu`, under `pollMu` (one poll waits for the launch; kicks coalesce).
  - Its launch hook writes the feedback file, then `next` (the cursor advanced, `RoundStart` set), after `commitWake`; if the launch then fails, the previous wake state is put back (its file is removed when there was none) and the feedback file stays in the checkout, so the next poll hands the same events again. A refused launch never ran the hook, so it changes nothing.
  - A state write that fails refuses the launch with its own 500.
  - A crash between the state write and the session's start leaves the cursor advanced: those events are not handed again. One launch is tried per ship per poll.
- **The lock.** `Service.wakeMu` serializes every read-modify-write of a ship's wake state: the poll's `Next` write, the round-start write and the hand wake's write. It is taken after `mooredMu` is released, never inside it.
- **Waiting.** `launcher.Error.Wait` is the typed reason, set where a refusal can clear later: at the cap (`Waiting for room under the cap`), for a resource that is `busy`, `missing` or `pending` (`Waiting for <resource> (<why>)`), for a wake already in progress (`Waiting for the current wake to finish`) and for a host not known (503, `Waiting for Admiral's terminal host`) and for the quota hold (`Held for quota: <harness>'s <window> is at N% (line M%), resets <time>`, set in `admit` only for a `launcher.Request.Unattended` launch: a routine run, a commitment or a feedback round, never a hand launch, AdmiralBot's or an accepted proposal; routines check `Scheduler.QuotaHold` first so a held run becomes a proposal instead of waiting). Nothing parses message text.
  - Any other refusal (fleet or dock not found, no guard, an unknown resource, a write failure, a launcher refusal after admit) is permanent and reads `Can't wake: <message>`.
  - The text is kept on the ship's `polled` entry as `waiting`, which a new poll answer replaces (so it clears when a poll answers and does not decide to wake), and `dropMoored` (a successful wake) and `endMoored` (the mooring ends) remove. `markStale`, a poll that failed to reach GitHub, keeps it.
  - Only a typed `Wait` reads as waiting: the 503 carries `WaitHost`, and no status code is read as a wait.
  - The decision's wake state is passed to `feedbackRound`, which refuses with `Waiting for the current wake to finish` when the stored state no longer matches it (the next poll decides again).
  - Every `RemoveWake` goes through `removeWake` under `wakeMu`; the hand wake's hook logs a wake state it cannot read or save and wakes without a round window. The row shows it as its note; Wake by hand stays on.
- **Running ships.** The same poll also asks about live ships (`internal/ships/runprs.go`): `Service.Candidates` (wired to `shipconv.Service.PRCandidates`) gives the PR URLs in the ship's and its crew boats' tool results, and a candidate is carried when `Status.Author` is the fleet's `Status.Viewer` and `CreatedAt` is not before the ship's `launched`.
  - Candidates are filtered to the client's host and the fleet's route, rebuilt canonically, capped at 20 per ship per poll and asked in a query of their own (`PollMoored` makes at most two per fleet), so a bad one stales nothing; one GitHub cannot answer is retried up to `maxCandidateTries` and a gone one rejected.
  - Each confirmed PR is appended to the session's `@admiral-prs` option (which a wake also fills from the record), so a restart keeps it, and `running.found` only caches it.
  - At a clean exit `countedPRs` passes the carried open PRs and the report's through `moor.CountedOK`, and falls back to the last poll's open PRs only when GitHub cannot be reached.
  - `GET /api/ships/<session>/pr` (`prdetail.go`) reads one carried PR fresh.
- **Reviewing ships.** A ship whose `url` option is a PR or stack URL, or whose `launch-prs` option (the PR URLs a sourceless round-0 launch's note and text name, found by `conversation.PRURLsInText` in `LaunchOrder`) is set, carries those PRs from launch (`internal/ships/revieworder.go`): another author's as *reviewing*, the fleet user's own as a plain PR.
  - `running.order` is the launch's one check of the order URL and launch PRs, kept apart from the printed candidates', which reject any PR the viewer did not open.
  - A stack resolves through `GitHub.StackOpenPRs` (REST `repos/<o>/<r>/stacks/<N>`, strict parse in `moor.ParseStack`).
  - The reviewed PRs are in the `prs` session option and listed in the `reviewing` option (a subset), written by `persistCarried`, and in `moor.Record.Reviewing`.
  - `decide` hides them from `DecideWake`, `autoMoor` moors a done report that has an open reviewed PR, and `serveMerge` and `serveUnfollow` answer 409 for them.
  - `LaunchOrder` kicks a poll for an order URL that is a PR or stack URL, or when the launch names a PR, so the check does not wait for the poll interval, and `setMoored` hands a ship's live poll to its new record when it is not stale and covers every PR.
  - The check stays pending until every target answers (a failed ask counts toward `maxCandidateTries`) and reruns once per process, since the option alone does not say every layer answered; `dropMoored` seeds a woken ship's `running.reviewing` and its `reviewing` option from the record, so a round GitHub never answers re-moors with the role.
- **One round at a time.** A live ship is not decided on by the poll. When the round's ship moors again, the next poll decides from the advanced cursor, and what came in during the round is the queue.
- **A hand wake** (the row, the ship view and the bridge prompt all go through `Service.Wake`) runs a hook after `commitWake` that sets every PR's `RoundStart` and gives a PR with no cursor the old `moored_at` as its cursor, the way a decision does; cursors, snapshots and first-seen times stay. It is put back if the launch fails.
- **`ADMIRAL_WAKE_DEBOUNCE`** (10 min) is the debounce, for tests.
- **A stranger's feedback** (T3) becomes an Inbox item of kind `wake_proposal` (`internal/inbox/proposal.go`), written by the server under `_admiral` like a notice and read with the same rules (only `_admiral` may hold one; the `wake_proposal` object, `{ship, session, pr, login, events: [{id, kind, url, at, body}]}`, is required).
  - `decide` calls `moor.ProposeT3` on `Decision.T3` for a record with a valid resume text (a ship with none gets no proposal): one batch per PR and author, the not-yet-proposed events, held until the author's newest event is older than `ADMIRAL_WAKE_DEBOUNCE` unless this decision wakes the ship on that PR, an empty or invalid login grouped as `ghost`.
  - The id is `wake-` and 20 hex characters of a SHA-256 over ship, PR, login and the sorted event IDs, so a repeated batch is a no-op: `WriteWakeProposal` never rewrites an item and leaves an answered one answered.
  - The event IDs go into the PR's `proposed` (`{id, at}`) in `Next`, folded in before the single state write, and an entry goes once the cursor is past its `at`. Proposal files are written before the state write.
  - They are written under `wakeMu` with the mooring and the stored state re-checked, and a proposal that cannot be written stops the poll's decision there: no wake and no save, so the next poll retries.
  - A round that is refused saves the state it read plus only the new `proposed` entries, never the advanced cursor.
  - A proposal never expires; Remove from inbox acts as Dismiss.
- **Launch and Dismiss** are `POST /api/inbox/_admiral/<id>/launch` and `/dismiss` on `inbox.Service`, which reaches `ships.Service.LaunchProposal` through its `LaunchProposal` hook (set in `cmd/admiral/main.go`; `internal/ships` imports `internal/inbox`).
  - Launch first checks the item against the moored record (the ship's name, a valid login or `ghost`, every event proposed: recorded, or behind the cursor and pruned) and answers `404` otherwise, then runs `wake()` with `by="proposal"`: autopilot with `autopilotgate.Check`, no cap check, the hand wake's round-start hook plus `feedback-<N>.md` holding only the proposal's events, and the cursor unmoved.
  - Both answer through `answerMu`, so a second press is `409`; outcome events `proposal_launched` and `proposal_dismissed` name the woken ship's session.
  - `removeWake` also deletes the ship's proposals and their answers, under `wakeMu`.

- **The round history** (`internal/moor/rounds.go`) is `$ADMIRAL_HOME/moored/rounds/<name>.json`: one `{round, session_id, fleet, transcript, started, ended}` per round, the latest `moor.MaxRounds` (50), never any transcript content.
  - `moor()` appends the round under `wakeMu` before it writes the record, keyed by round number so a retry adds nothing; the record is deleted on every wake and the history is not. `removeWake` removes it, so every end of a mooring does.
  - The path goes in only through `transcriptfs.Bind` (`internal/transcriptfs/bind.go`), the one rule `shipconv` uses too: the option's `<ns> launch <path>` form, `ValidTranscriptPath`, and the start command's `--session-id` (or a Claude ship's `--resume`) equal to the path's id, read by `transcriptfs.StartedSession` before the first `--` and outside an order's text; `started` is the pane's launch time (the `launched` option, RFC 3339) for every harness.
  - A failed history write is logged and `moor()` still writes the record, so the ship keeps following its PR and loses only the dividers.
  - Recording round N drops a held round N of another session and everything after it, so an orphaned history is not inherited.
  - The conversation route looks up the moored record before it syncs tmux.
  - `internal/shipconv/rounds.go` stitches the rounds (`docs/api.md`, "A ship's rounds"), opening each recorded file through `transcriptfs` under its fleet's `projects/`.
- **Poll bounds.** `github.Client.PullRequests` (`internal/github/pr.go`) reads, per PR, the last 20 reviews, the last 20 review threads with their last 10 comments, the last 20 PR comments, up to 20 pending review requests and 20 review-requested timeline events, and up to 50 check contexts on the head commit; each body is cut to 4096 bytes. GitHub returns bodies whole and the client cuts them, so a poll of a busy PR can still be large. `viewer { login }` comes once per query.
- **Events.** A review is an event when it is `CHANGES_REQUESTED`, or `COMMENTED` with a body (its inline comments count through the threads); `APPROVED` alone, `PENDING` and `DISMISSED` are not. A thread comment or PR comment is keyed by `createdAt` and id, so an edit never wakes. A condition (a failing check, a conflict, behind base) takes the time of the first poll that saw it.
- **The repo's own CI** is a GitHub Actions check run with a workflow run, plus any check run or status the base requires for the PR (`isRequired`). Failing is `FAILURE`, `TIMED_OUT`, `STARTUP_FAILURE` or `ACTION_REQUIRED` for a check run, `ERROR` or `FAILURE` for a status; `CANCELLED` is not. Every other check is ignored.
- **Behind base** wakes only when the base readably requires up-to-date branches: a ruleset's `strictRequiredStatusChecksPolicy` or a non-null `branchProtectionRule.requiresStrictStatusChecks`. Classic branch protection is invisible to a non-admin token, so a null or unreadable rule means not required.
- **Tiers.** T1 is the fleet client's gh viewer. T2 is a `wake_reviewers` login, a Bot authoring a review or a review-thread comment, and a requested reviewer (from pending requests and the timeline; a team makes nobody T2). Everyone else is T3: returned beside the decision for the Inbox, never waking. A Bot's plain PR comment is ignored. Logins compare case-insensitively. GraphQL gives a Bot's login without `[bot]`, so a `wake_reviewers` entry `foo[bot]` matches the Bot `foo`; a bare `foo` matches only a User `foo`, never a Bot.
- **The ship's own replies** share the viewer's login, so a viewer event created between a round's start and the ship's re-mooring is dropped. A dropped event that is still newer than the cursor is recorded in the PR's `dropped` ids at a wake, so a later round's window never hands it.
- **Debounce and queueing.** A ship wakes when the newest waking event is at least 10 minutes old. One PR per round: the lowest layer of the record's `prs` with waking events; the others stay queued behind their cursors. A PR with no cursor (the first mooring) treats events before `moored_at` as history. `T3` holds every T3 event newer than the cursor, so it repeats from poll to poll until a later waking event passes it; its consumer dedupes by id.
- **The wake state** is `<home>/moored/wake/<name>.json` (`moor.ReadWake`, `WriteWake`, `RemoveWake`): per PR URL, a cursor, the last round's start, a snapshot of the conditions at that start, the first-seen times of conditions and the dropped ids. A poll that sees a conflict, behind base or failing check gone clears it from the snapshot, so its return is new and wakes after the debounce. It sits in a subdirectory so `moor.List` skips it, survives a wake's `dropMoored`, and is removed with the record when the mooring ends for good (Dismiss, merged or closed PRs seen by the poll, and a woken ship whose round ends with no open PR).
