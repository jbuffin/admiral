# AdmiralBot on each harness

The MCP fence and AdmiralBot on Claude, Codex and Copilot. Read it before changing the fence, `internal/launcher/chat_codex.go` or `chat_copilot.go`.

- **The fence** (ADR 0023).
  - The chat has no built-in tool (`--tools ""`) and reaches Admiral only through the stdio MCP server `admiral` (`admiral mcp`, `internal/cli/mcp.go`) that `mcp.json` names; `--strict-mcp-config` keeps every other server out.
  - `chat-claude-settings.json` holds `permissions.allow` of exactly `mcp__admiral__*` (`launcher.FencePermissions`), `permissions.deny` of `Edit`, `Write` and `NotebookEdit` as a backstop, and `blockReadsOutsideWorkingDirectories`. Ships' bundles and command lines are unchanged.
  - The server reads its identity from the `env` of `mcp.json`: `ADMIRAL_ACTOR_TOKEN` (the minter's token for the chat's nonce), `ADMIRAL_PORT`, `ADMIRAL_HOME` and `ADMIRAL_CHAT_FLEET`.
  - The token goes only there, never into argv, a tmux option or the settings.
  - Ships can read `$ADMIRAL_HOME`, so the token is not a secret from ships; the fence is against the chat model, which has no file or shell tool.
- **The fence probe** (`internal/probes/claude_mcp_fence.go`, capability `bot.mcp_fence`). It runs Claude Code headless with `launcher.FenceArgs`, `--output-format stream-json --verbose` and a config naming one server, `admiral mcp-probe` (hidden, serves one tool `ping`), and asks for a shell command and for the tool. It passes on what Admiral observes: no `ran-<nonce>` file, the server's `called-<nonce>` file, and a `system`/`init` record that lists no built-in tool and no other MCP server. The init shape is assumed from Claude Code's stream-json output. The harness picker offers a harness once its fence probes have passed.
- **AdmiralBot on Codex** (`internal/launcher/chat_codex.go`, `internal/probes/codex_probes.go`).
  - `StartChat` runs Codex with its own `CODEX_HOME`, `$ADMIRAL_HOME/chat/<fleet>/codex-home/`, which holds only a link `auth.json` to the engineer's login (`LinkCodexLogin`, the one place that decides link or copy: a token refresh resolves the link and renames a temp file over the engineer's `auth.json`, per Codex's `FileAuthStorage` on its main branch, so the engineer's login stays the one current file and the link stays); the engineer's `config.toml`, plugins, skills and MCP servers never enter it, and the dock's `args` are dropped.
  - `Codex` has no profile for the fence, so argv carries it as `-c` and `--disable` flags from one table, `codexFenceFeatures` and `CodexFenceArgs`, which the probes share: `--strict-config` (an unknown `-c` key is refused), `features.shell_tool=false`, `web_search="disabled"`, a read-only sandbox, `approval_policy="never"`, each feature in the table disabled, and `default_tools_approval_mode="approve"` on the `admiral` server.
  - `features.code_mode_host` stays on, since Codex reaches MCP tools through it.
  - `prepareCodexChat` refuses to start a chat whose `codex-home/config.toml` sets `mcp_servers`, `notify`, `model_providers` or `profile`/`profiles`, which the flags do not cover.
  - The TUI gets `--no-daemon` only when it accepts it (`codexpane.HasNoDaemon`).
  - The fence is not airtight: Codex still lists `exec`, `wait`, `sleep`, its `collaboration` tools, `request_user_input` and the MCP resource tools, and its read-only sandbox does not stop reads outside the chat's directory.
  - The actor token never goes on argv: the launcher writes it to the 0600 file `chat/<fleet>/admiral-mcp-token` and the `admiral` server's `env` names it in `ADMIRAL_ACTOR_TOKEN_FILE`, which `admiral mcp` reads when `ADMIRAL_ACTOR_TOKEN` is empty. The instructions go in `-c developer_instructions=…`.
  - `chat.Service.Login` stays the engineer's identity dir, while the reader and `recordReset` use `launcher.ChatCodexHome` (rollouts under its `sessions/` only, `transcriptfs.OpenFor("codex", …)`, usage from `usage.ParseCodex`). New chat types `/new`.
  - Codex's `SessionStart` hook fires with the first turn, not at TUI start, so a fresh Codex chat has no transcript option.
  - `chat.Service` reads the pane instead: with no trust dialog, update dialog or startup on screen and the composer showing, a trusted chat is ready, Send pastes the message, and the first turn's hook binds the rollout, which the reader reads from its start.
  - While the "Hooks need review" dialog is up the panel says to trust them in the terminal (`CodexTrustHooks`); while its update dialog is up (matched by its "Update now" and "Skip until next version" options, not the start-screen banner, which leaves a ready composer ready) the panel says to choose Skip in the terminal (`CodexUpdate`), since Enter would run a brew upgrade; after "Continue without trusting" it says the hooks aren't trusted and how to recover (`CodexUntrusted`). Claude's `NotStarted` is unchanged.
  - Two probes gate the chat: `bot.mcp_fence` runs a fenced `codex exec --json` that is asked for a shell command, a web search, a browser, a sub-agent that creates the same sentinel, and the `ping` tool of a probe server, and passes on no sentinel file, only `agent_message`, `reasoning`, `error` and `mcp_tool_call` items for the probe server, and the server's `called-<nonce>` file; `bot.config_home` runs `codex exec --json` with the base fence flags and no server in a throwaway home holding only the login link, and fails on a plugin in `plugins/cache` or no reply.
  - `exec --json` prints `thread.started`, `turn.started`, `item.started` and `item.completed` (`agent_message` with `text`, `mcp_tool_call` with `server`, `tool`, `arguments`, `result` and `status`, `error` with `message`), `turn.completed` with usage and `turn.failed`.
  - The fake `codex` answers a `codex exec --json` run in that shape (see `docs/agents/testing.md`).
- **AdmiralBot on Copilot** (`internal/launcher/chat_copilot.go`, `internal/probes/copilot_probes.go`).
  - `StartChat` runs Copilot 1.0.109 with its own `COPILOT_HOME`, `$ADMIRAL_HOME/chat/<fleet>/copilot-home/` (0700), and `COPILOT_PLUGIN_DIR_ONLY=true`, so only the `--plugin-dir` bundle (the hooks) loads as a plugin.
  - The login is the engineer's, in the macOS Keychain, and works from an empty home; Admiral never writes `~/.copilot`, and the dock's `args` are dropped.
  - The fence is one table the chat and the probes share: `CopilotBaseFenceArgs` (`--disable-builtin-mcps`, `--no-ask-user`, `--no-auto-update`, `--disallow-temp-dir`, `--sync-session=off`, `--excluded-tools=<built-ins>`), `CopilotFenceArgs(server)` (adds `--allow-tool=<server>`, which approves the server's tools even in the TUI) and `CopilotToolArgs` (one `--available-tools=<server>-<tool>` per tool; Copilot names an MCP tool `<server>-<tool>`, takes exact names only, and drops an unknown name with a notice, so no glob or bare server name works).
  - `ChatTools` lists the tools and a test in `internal/cli` checks it against the server's own.
  - `CopilotEnvKept` drops `GH_TOKEN`, `GITHUB_TOKEN`, their enterprise forms, `GH_HOST`, every `COPILOT_*` and every `OTEL_*` variable from the dock's env, Admiral's and the tmux server's global env.
  - At start `prepareCopilotChat` removes what Copilot loads from a trusted working directory (`.mcp.json`, `.github`, `.vscode`, `.copilot`, `.agents`, `.claude`, `CLAUDE.md`, `AGENTS.md`, `GEMINI.md` and the like) and refuses with 409, naming the entry, when the chat dir sits inside a git work tree or the chat home holds anything but an allowlist (what Admiral writes, and what Copilot creates: `config.json`, `settings.json`, `installed-plugins/` empty, `logs/`, `plugin-data/`, `session-state/`, `session-store.db*`, `settings.json.lock`, `ide/`, `servers/`, `open-sessions-state.json`, `sidebar-sessions-state*`), a key of `config.json` or `settings.json` that Copilot does not write itself, a symlink or an entry it cannot read.
  - The instructions are `copilot-instructions.md` in the home, which Copilot loads.
  - The token never goes on argv: it is in the 0600 file `chat/<fleet>/admiral-mcp-token`, and the `admiral` server's `env` in the inline `--additional-mcp-config` JSON names it in `ADMIRAL_ACTOR_TOKEN_FILE` (Copilot passes a local server's `env` through).
  - `--session-id` is a new UUID at each start, so the transcript is `session-state/<id>/events.jsonl` in the chat's home.
  - `chat.Service.Login` stays the engineer's identity dir; the reader and `recordReset` use `launcher.ChatCopilotHome` (`usage.ParseCopilot`).
  - `sessionStart` fires from the plugin's hooks at the first prompt of a session, not at launch, with `source: "new"` and no transcript path, so `internal/cli/hook.go` derives `$COPILOT_HOME/session-state/<sessionId>/events.jsonl` for a chat.
  - `/clear` ends the session (`sessionEnd`) and makes a new `session-state/<uuid>/`; its `sessionStart` fires at the next prompt, which re-binds the reader to the new file. New chat types `/clear`.
  - In a fresh home Copilot asks "Confirm folder trust"; the panel says to choose Yes in the terminal (`CopilotTrustFolder`). 1.0.109 offers only "1.
  - Yes" and writes no `trustedFolders`, so a fresh Copilot process in the chat dir asks again; `/clear` does not.
  - A trusted chat is ready when the composer footer (`/ commands`) shows; the trust dialog's `❯` is not the test.
  - Two probes gate the chat: `bot.mcp_fence` runs `copilot -p … --output-format json --log-level all` in the chat's configuration (shared fence, `--plugin-dir`, the instructions file) with only the probe server's tool, asked for a shell command, a web fetch, a sub-agent and the probe's `ping`, and passes on no sentinel file, a logged tool set (`copilotToolsFingerprint`) that is only `probe-ping`, only `tool.execution_start` events of the probe's server, no `permission.*` event, no hook outside Admiral's plugin's and the server's `called-<nonce>` file; `bot.config_home` runs the base fence with no server in an empty throwaway home and fails on a plugin in `installed-plugins`, another server's tool call or no reply.
  - Both cap a run with `--max-ai-credits 30`, the least Copilot accepts.
  - Copilot writes in the home `config.json`, `logs/`, `session-state/`, `session-store.db`, `plugin-data/` and an empty `installed-plugins/`; the TUI adds `ide/`, `servers/` and two state files.
  - The fake `copilot` answers a `copilot -p --output-format json` run in that shape (see `docs/agents/testing.md`).
