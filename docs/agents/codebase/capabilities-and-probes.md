# Capabilities, probes and the autopilot gate

What each harness claims, the probes that prove it, the autopilot gate, model lists and the harness capabilities routes. Read it before changing `internal/capabilities`, `internal/probes` or `internal/autopilotgate`.

- `internal/capabilities` is what each harness claims and what a probe proved (ADR 0035).
  - `Table()` lists the capabilities by feature (judge, bot, restricted, autopilot), and `Claims` and `ClaimedBy` say which harness versions claim each one (every version, except Claude's guard hook from 2.1.295).
  - Results live in `$ADMIRAL_HOME/capabilities.json`, keyed by the fleet's `Key`, then harness, then the harness version probed, beside the last detected version.
  - `admiral setup` and the server write it, and `admiral crew launch` reads it from inside a ship, so every write re-reads the file and merges under `capabilities.json.lock`, and every query reads the current file.
  - A corrupt or unreadable file reads as all `not_checked` with the error returned, and the next write moves it to `capabilities.json.bad`.
  - A capability is `passed` only with a passing result for the last detected version (`Store.Proven`), whatever the table claims.
  - `DetectVersion` runs the harness's `--version` under the fleet's env.
- `internal/probes` runs the probes that fill that store.
  - A `Probe` is registered for one (harness, capability) pair, so a new probe is a registration in `defaultProbes`.
  - A probe that could not run every command and showed no leak or confinement failure returns `Outcome.Inconclusive`: `Runner.run` stores nothing (a stored pass stays, a version never proven stays not checked) and the report line says `inconclusive: …`; the restricted sandbox run is retried up to twice first, and a run that showed a leak or a confinement failure is never rerun, and it and a time limit still fail; a model that made no tool call is inconclusive too.
  - `harnesscaps` puts an inconclusive line's detail on the check response only; a later plain GET shows the stored detail again.
  - `Runner.Run(ctx, fleet, harness)` is the one entry point for "probe this now": it detects the version, records it, runs the harness's probes for the capabilities the version claims, stores each result under that version and returns a `Report` with a line per table capability (a capability with no probe, or older than its claim, is `not_checked`).
  - It is synchronous, bounded by `Runner.Timeout`, and two concurrent runs for one fleet and harness share one.
  - A failed `--version` clears the recorded version, so the old version's passes stop counting, and keeps why (`Snapshot.VersionError`, cleared by the next good detection).
  - A run does not end with its caller's context, so one client going away cancels nothing for the others; only `Runner.Close` (the server calls it at shutdown) or the run's own time limit ends it.
  - A cancelled run stores no result and leaves the recorded version alone, while a timeout counts as a failure.
  - `admiral setup` calls `Run` for every fleet harness after it saves; the server calls `Refresh` at start, which detects each fleet harness's version in the background, records it and re-runs the probes of a harness whose version differs from the one its results were stored under (a harness never probed only gets its version recorded). A config reload doesn't re-detect.
  - `Judge(harness, id)` is the probe of one judge capability (no tools, no network, JSON schema, per-call cap): it calls `judge.For` and makes its call on the Lookout model through `internal/judge`, and passes on what Admiral sees (a sentinel file, a nonce read back, a request to a loopback listener, claude's `structured_output`, `error_max_budget_usd`), never on what the model says.
  - A harness with no mechanism (codex call cap, copilot schema and cap) records its fixed reason with no call.
  - `ClaudeGuard` runs the fleet's `claude` headless on `haiku` with `Bash` allowed, in an empty temporary directory with its own copy of the hook bundle and `admiral` link (so it works before any server has started), asking it to run `touch <dir>/ran-<nonce>`.
  - `admiral guard pretooluse` notes every Bash call it is asked about in `seen-<nonce>` while `ADMIRAL_PROBE_NONCE` (16 lowercase hex) and `ADMIRAL_PROBE_DIR` (absolute) are set, denies exactly that command, and writes `denied-<nonce>` in `ADMIRAL_PROBE_DIR`, never an outcome.
  - It passes only when the denial file exists and the sentinel doesn't; with no denial, `seen` and the sentinel tell a hook that never ran from a model that ran another command or never called the tool.
  - The probe fails, naming the arg, when the fleet's `claude` args would override the hooks (`launcher.RefuseHookArgs`).
  - The launcher removes both probe variables from a ship's env.
  - The harness's env is the fleet's with the ship and pane variables removed and `ADMIRAL_AUTOPILOT=1`.
  - `ClaudeScoutGuard` (capability `scout.guard_hook`, same claude minimum) is the same run with `ADMIRAL_SCOUT=<checkout>` added (autopilot stays on, so the two stack as on a real scout), asking `Write` (allowed) for `<checkout>/scout-<nonce>`; the guard notes every `Write` it is asked about in `scout-seen-<nonce>` and a refusal of that file in `scout-denied-<nonce>` (`probes.ScoutSeenPath`, `ScoutDeniedPath`, `ScoutFilePath`); it passes only when the denial exists and the file doesn't.
  - The scout guard itself is `internal/cli/guard_scout.go`; the bundle's guard group matches Bash and Monitor (both parsed as shell), and it adds Edit/Write and scout MCP matchers (`launcher.ScoutEditMatcher`; `launcher.ScoutMCPMatcher`, which takes every GitHub MCP tool without a read-verb prefix) that run the same `admiral guard pretooluse`, which returns at once unless `ADMIRAL_SCOUT` or autopilot is set.
  - `ADMIRAL_SCOUT` is scrubbed from probe and judge envs (`capabilities.ScrubbedEnv`).
- `internal/autopilotgate` decides which harness may carry autopilot mode in a fleet: only when the code registers a guard probe for the harness (`probes.GuardHarnesses`, so a stored pass for any other harness proves nothing) and that probe passed there for the last detected version (`Proven`, which reads the store fresh on every call, with no cache; a corrupt or unreadable store is not proven).
  - `Check` returns a `*Refusal` and posts one dismiss-only Inbox notice, "Couldn't launch unattended on the harness: guard not proven", unless an open notice with the same title and body (the body names the fleet by name and key) exists.
  - `CheckQuiet(home, fleet, harness)` returns the same typed errors with no Inbox notice. Its only callers are `ships.Service` (`gate` when the request sets `QuietGate`, which commitments do, and `scoutGate`). A routine save (`validateLaunch` in `internal/routines/routines.go`) and a commitment record (`checkLaunch` in `internal/chat/commitments.go`, with its campaign twin in `internal/chat/campaigncommit.go`) call `Proven` and `Advisor(f, capabilities.Open(home))` themselves, for their own messages. See [routines](routines-and-events.md) and [commitments](commitments-and-campaigns.md).
  - A fleet or dock `POST /api/ships` doesn't know is a 404 before the gate, with no notice.
  - `ships.Service.admit` calls it before the cap check, and `launcher.Launcher.AutopilotGate` (set in `main.go` and `internal/cli/crew.go`; nil refuses) does for `crew launch`, so neither runs `--version`.
  - After the guard, `Check` asks `Advisor`: the fleet needs a judge harness (`judge.Choose` on the store, nothing stored), else it returns an `*AdvisorRefusal` and posts the notice "Couldn't launch unattended on the harness: advisor not proven", whose body names the fleet by name and key and gives the reason.
  - `Check` and `Launcher.AutopilotGate` take the `config.Fleet`. The args allowlist is not gated.
  - `ScoutProven(home, fleetKey, harness)` and `CheckScout` are the scout gate: the harness needs a registered scout probe (`probes.ScoutGuardHarnesses`), a pass of `scout.guard_hook` and a pass of the autopilot guard; `CheckScout` returns a `*ScoutRefusal` naming the first missing one and posts no Inbox notice.
  - `GET /api/harness-capabilities` computes `autopilot.advisor` the same way for every harness (`autopilotgate.AdvisorStatus`: `not_checked` until a judge result exists in the fleet, then passed or failed), so it is never a stored row.
  - `admiral advise` (`internal/cli/advise.go`) is the advisor: one judge call (`judge.Strong`) on the ship's fleet, whose fleet comes from the session option `@admiral-fleet` through the `shipFleet` seam; it logs one `advised` outcomes line.
- `internal/harnessmodels` lists each dock's models from its harness (`List` runs the dock's resolved executable alone, speaking claude's `stream-json` `initialize`, codex's `app-server` `model/list` or copilot's `--acp` `session/new`, in its own process group, bounded in time, per-line size and total bytes).
  - `clean` drops names that fail `config.ValidModelName`, repeats and anything past 500.
  - `Store` keeps each dock's last list in `$ADMIRAL_HOME/harness_models.json` (`Entry{Models, ListedAt, Error}`), and `Service` is the one lister: one lock per dock, a failure or an empty result keeps the last good list and records the error, and `onChange` fires only when the served list changes.
  - `main.go` wires it with `config.Manager.SetHarnessModels` (so `Config.HarnessModels` survives reloads, like `ChatProbe`) and `probes.Runner.SetModelLister`; `Runner.Run` (Check again) and `refresh` (startup) start a listing in a background goroutine before version detection, so neither a config read nor startup waits for it.
  - `Config.ModelsFor(fleet, harness)` is the one place that picks the listed list or the built-in `ChatModelsFor`; the chat settings and `DockView.Models` use it (a launch checks only `config.ValidModelName`).
  - Saving a chat model is checked against it in `mergeChat`; loading only checks the name pattern. The judge's `ModelPair` is separate and unchanged. It is not a capability probe.
- `internal/editors` serves `GET /api/editors` (shape in `docs/api.md`): whether the request is local (`auth.IsLocal`, injected) and whether VS Code is installed (`vscodeInstalled` in `cmd/admiral`, which an e2e build answers from `ADMIRAL_VSCODE_TEST=installed` alone and never from the machine). `ships.Ship.Worktree` (`worktree`) is `launcher.WorktreeOf`, the ship's own worktree while it exists; the shell's `OpenInVSCode` opens it, else `dir`, with a `vscode://file/` link.
- `internal/harnesscaps` serves `GET /api/harness-capabilities` and `POST /api/harness-capabilities/check` (shapes in `docs/api.md`). The check calls the server's one `probes.Runner`, so concurrent checks of a harness share a run.
